# 05｜数据闭环：从失败挖掘到模型飞轮

## 本模块解决的问题

机器人规模化部署后，真正的护城河不是"初始模型有多好"，而是**数据闭环能不能让模型越用越好**。本章回答：

```text
数据闭环的完整链路是什么？
机器人运行数据包含哪些类型？
失败挖掘（Failure Mining）为什么是核心价值？
数据飞轮怎么让失败率持续下降？
```

配套代码：`src/robotics/data_loop/`（采集/存储/挖掘/训练/部署的飞轮模拟）。

---

## 1. 数据闭环的完整链路

```text
Robot
  ↓ 产生运行数据（sensor/camera/state/action/model output/metrics/error/task result）
Runtime Data
  ↓ 上传
Storage
  ↓ 分析
Failure Mining（失败挖掘）
  ↓ 失败案例
Dataset（训练数据集）
  ↓ 训练
Model（改进的模型）
  ↓ 部署（OTA）
Robot（跑得更好）
```

**闭环的本质：失败的案例 → 训练数据 → 更聪明的模型**。数据从机器人来，又回到机器人去，形成飞轮。

---

## 2. 运行数据的类型（master prompt 要求）

| 数据类型 | 内容 | 用途 |
|---|---|---|
| sensor / camera | 传感器读数、图像 | 训练输入 |
| robot state | 关节角、位姿 | 状态标签 |
| action | 模型输出的动作 | 行为数据 |
| model output | 模型中间输出 | 调试、蒸馏 |
| runtime metrics | latency、CPU/GPU、温度 | 系统优化（Stage 15） |
| error | 错误信息、堆栈 | 故障分析（Stage 29） |
| task result | 成功/失败 | **失败挖掘的核心输入** |

**task result 是最关键的**——它是"这个案例要不要进训练集"的判决依据。

---

## 3. 失败挖掘（Failure Mining）

从海量运行数据中筛选失败案例，并分析失败原因：

```text
运行数据（大量成功 + 少量失败）
   ↓ 筛选 task result == failed
失败案例（珍贵的"负面样本"）
   ↓ 按失败原因分类（low_light / occlusion / novel_object ...）
针对性训练（模型学到"这种情况我错了，下次注意"）
```

**失败案例比成功案例更值钱**：成功案例只是"重复已知"，失败案例是"暴露盲区"。一个低光照下抓取失败的案例，比 1000 个正常光照的成功案例更能提升模型。

---

## 4. 实测：飞轮让失败率持续下降

模拟：初始模型对所有失败类型（低光照/遮挡/新物体）成功率都只有 50%。每轮采集 300 个任务 → 挖掘失败 → 训练 → 部署，跑 4 轮：

```text
round   failure_rate
1       51.7%
2       37.0%
3       17.0%
4        5.0%
```

**4 轮飞轮，失败率从 51.7% 降到 5.0%（下降 10 倍）**。这就是数据闭环的价值：

```text
第 1 轮：模型盲区多，失败率 51.7%
   ↓ 挖掘 155 个失败案例（按原因分类）
第 2 轮：模型学到"低光照/遮挡/新物体"的情况，失败率 37%
   ↓ 继续挖掘 + 训练
第 4 轮：模型已覆盖大部分盲区，失败率 5%
```

**数据飞轮 = 规模化的核心护城河**：部署的机器人越多，数据越多，模型越好，产品越强——竞争对手追不上。

---

## 5. 数据闭环的工程难点（理论）

| 难点 | 说明 |
|---|---|
| 数据量大 | 数千台机器人每天 TB 级数据，需要存储/压缩/采样策略 |
| 标注成本 | 失败案例需要人工/自动标注（错误原因） |
| 数据质量 | 噪声、异常、隐私（相机数据） |
| 闭环延迟 | 从失败到新模型部署要多久（越快飞轮越快） |
| 回滚风险 | 新模型可能引入新问题（呼应 Stage 20 灰度） |

工业上常用"异常检测 → 自动上传"（只上传失败/异常案例，省带宽）——这也是 Stage 23 云边架构里"数据上传"的优化点。
