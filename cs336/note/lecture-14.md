# Lecture 14: 数据 Data II - 数据处理

## 1. 本讲核心问题

原始数据（raw data）不能直接用于训练 LLM。从互联网抓取的原始 HTML 到最终喂给模型的 token 序列，中间需要经过一整套复杂的数据处理 pipeline。**本讲的核心问题是：如何把一个混乱的原始文本集合变成一个高质量的训练数据集？** 包括清洗、过滤、去重、混合等关键步骤。更深层的问题是：数据为什么是一个 **long-tail problem**？

---

## 2. 通俗解释

### 数据清洗 ≈ 做菜前的备菜流程

想象你要给 1000 个学生做一顿大餐：

1. **Transformation（格式转换）** ≈ 把菜从包装袋里拆出来
   - HTML → 纯文本：好比剥掉塑料包装，只要里面的食材
   - PDF → 文本：好比把冻肉解冻

2. **Filtering（过滤）** ≈ 挑菜、去烂叶子
   - 语言识别：确保你拿到的都是"菜"而不是"塑料模型"
   - 质量过滤：去掉老叶子、发黄的、有虫眼的
   - 毒性过滤：去掉发霉变质的（有毒内容）

3. **Deduplication（去重）** ≈ 去掉重复的菜
   - 同一个句子出现了 100 次 → 只保留 1 次
   - 99% 相似的两段文字 → 只保留 1 段

4. **Mixing（混合）** ≈ 按比例搭配不同类型的菜
   - 不能全是肉（代码），也不能全是蔬菜（百科）
   - 需要合理的营养搭配比例

**核心类比：** 做菜前不洗菜、不去烂叶子、不按比例搭配——做出来的食物再好的厨艺也难以下咽。同样的，不经过数据处理的原始数据直接训练 LLM，模型会学到大量噪音、重复内容和有害信息。

## 3. 数学公式 + 工程意义

### 3.1 语言识别：fastText 的工程原理

fastText 是一个基于 n-gram + 线性分类器的语言识别工具：

$$
P(\text{lang} = l \mid \text{text}) = \text{softmax}\left( \mathbf{W} \cdot \frac{1}{|T|} \sum_{t \in T} \mathbf{e}_t + \mathbf{b} \right)
$$

其中 $\mathbf{e}_t$ 是每个 n-gram 的嵌入向量，$\mathbf{W}$ 是分类矩阵。

**工程参数：** fastText 语言识别通常在 2-gram 到 5-gram 范围内工作，模型的分类器可以处理 176 种语言，单 CPU 可以处理 ~10,000 条/秒。

### 3.2 质量过滤：KenLM 的困惑度

KenLM 是一个 n-gram 语言模型，使用 Kneser-Ney 平滑。给定文本的困惑度（perplexity）：

$$
\text{PPL}(T) = \exp\left(-\frac{1}{N}\sum_{i=1}^N \log P(w_i \mid w_{i-1}, \ldots, w_{i-n+1})\right)
$$

**工程意义：** PPL > 某个阈值（如 1000）的文档被认为是低质量的。这个阈值需要在验证集上仔细调优——太低会过滤掉太多数据，太高会保留太多噪音。

### 3.3 MinHash 去重

MinHash 是近似去重算法，用于估计两个集合的 Jaccard 相似度：

$$
J(A, B) = \frac{|A \cap B|}{|A \cup B|} \approx \frac{1}{k}\sum_{i=1}^k \mathbf{1}[h_i^{\min}(A) = h_i^{\min}(B)]
$$

**工程参数（Dolma 为例）：**
- n-gram 大小: 13-gram
- Hash 函数数量: 20（减少误判）
- Jaccard 阈值: 0.8（超过 80% 相似的文档视为重复）
- 内存需求: 对于 15T tokens，约需要 100-500 GB RAM

### 3.4 Suffix Array 精确去重

对于精确重复，可以使用后缀数组（suffix array）：

构建后缀数组的时间复杂度 $O(N \log N)$，空间复杂度 $O(N)$。对于一个 15T tokens 的数据集，这需要 **数百 TB 的存储和数千 CPU 小时**。

### 3.5 数据混合的 Scaling 外推

在 小规模实验 （如 1B 参数）上测试不同的数据混合比例：

$$
\text{Loss}(N, D, \text{mix}) \approx \text{Loss}_{\text{base}}(N, D) + \text{MixEffect}(\text{mix})
$$

**工程方法（DeepMind Chinchilla 论文）：**
1. 在 70M-16B 参数之间运行多个实验
2. 拟合数据混合比例与 loss 的关系
3. 外推到目标规模（如 70B）

**关键风险：** 数据混合的最优比例可能不是 scale-invariant 的——小规模的结论不能保证在大规模上成立。这就是为什么需要 multi-scale 实验。

## 4. 工业界真实实现

### 4.1 DCLM 数据处理 Pipeline

DCLM（DataComp for Language Models）是 2024 年最重要的大规模数据实验项目之一。其完整 pipeline：

```
Raw Common Crawl (200TB+)
    │
    ▼
[1] HTML Extraction ( resiliparse / trafilatura )
    │  ~80% 数据在此被丢弃（导航栏、广告、模板等）
    ▼
[2] Language Identification (fastText)
    │  保留英文（lang=en，confidence > 0.65）
    ▼
[3] Quality Filtering (fastText classifier + KenLM PPL)
    │  用高质量数据（如 Wikipedia）训练二分类器
    │  过滤 PPL > 阈值的文档
    ▼
[4] Deduplication
    │  Exact dedup + MinHash (Jaccard > 0.8)
    ▼
[5] Personal Information (PII) Redaction
    │  正则表达式 + 实体识别
    ▼
[6] Final Corpus: ~2T tokens (干净数据)
```

**DCLM 核心发现：** 优秀的数据过滤 + 更少的数据 优于 差的过滤 + 更多的数据。DCLM-Baseline 用约 2T tokens 就达到了与更大数据集相当的效果。

### 4.2 Dolma 的完整处理链

Dolma（AI2 发布）的处理步骤更细致：

| 步骤 | 工具 | 说明 |
|------|------|------|
| HTML 提取 | trafilatura, resiliparse | 支持多种 HTML 解析策略 |
| 语言检测 | fastText (157 种语言) | 多语言支持 |
| 质量过滤 | 多级过滤 | 包括长度、PPL、重复度等 |
| 去重 | 多级去重 | 段落级 + 文档级 |
| PII 移除 | Presidio + 正则 | 邮箱、电话、IP 等 |
| 格式清理 | 自定义脚本 | 统一 Unicode、空白符等 |

### 4.3 Llama 3 的数据处理（Meta 公开的部分）

- **URL 级去重**：先在整个 Common Crawl dump 级别去重
- **文档级去重**：MinHash 去重（可能是 20 个 hash 函数）
- **行级去重**：训练数据中每条文档内去重
- **启发式过滤**：
  - 去除过短文档（< 200 chars）
  - 去除 LLM 生成的合成数据
  - 去除 HTML 残留（如未闭合标签）

### 4.4 DeepSeek 的数据创新

DeepSeek V3/V4 使用了更激进的数据策略：

- **"Data Curriculum"** — 训练后期提高高质量数据的采样比例
- **知识密度过滤** — 不仅过滤低质量，还识别"信息密度"低的文档
- **领域专业数据** — 针对数学、代码等特定能力收集专项数据

## 5. CUDA/GPU 视角

### 5.1 为什么数据预处理不在 GPU 上做？

数据预处理是 CPU-intensive，不是 GPU-intensive 的：

| 操作 | CPU/GPU | 原因 |
|------|---------|------|
| HTML 解析 | CPU | 无并行性，字符串处理 |
| KenLM 推理 | CPU | 内存密集型，n-gram 查找 |
| fastText 分类 | CPU | 矩阵太小，GPU 优势不足 |
| MinHash | CPU | 基于 hash，无矩阵运算 |
| Tokenization | CPU | 顺序处理，内存限制 |

### 5.2 预处理的计算需求

对于 15T tokens 的数据集预估：

| 步骤 | CPU 核心·小时 | 内存需求 |
|------|-------------|---------|
| HTML 提取 | 50,000-200,000 | 16 GB |
| 语言识别 | 5,000-10,000 | 8 GB |
| 质量过滤 | 10,000-30,000 | 16 GB |
| 去重 | 100,000-500,000 | 500 GB+ |
| **总计** | **~165,000 - 740,000** | **~500 GB+** |

**工业实践：** 在 1000 核的集群上，完整处理 15T tokens 的数据需要 **1-4 周**。

### 5.3 GPU 训练时的数据加载

训练时数据已经预处理完成（tokenized + shuffled），每个 epoch 的数据在离线阶段已经处理好。这是因为：

```python
# 离线预处理（CPU/磁盘）→ 在线训练（GPU）
# 不好的做法：每次读取原始文本并 tokenize（浪费 GPU 等待）
# 好的做法：预处理为 .bin 文件，GPU 直接读取
data = np.memmap('data/train.bin', dtype=np.uint16, mode='r')
```

**Megatron-LM 的数据策略：**
- 数据被预先分为多个 `.bin` 文件
- 每个文件 ~1-10 GB
- 训练时按 index 随机读取
- 数据在多个 worker 进程中并行加载

## 6. 本讲与整个 LLM 系统的关系

```
┌──────────────────────────────────────────────────────┐
│        数据 pipeline 在 LLM 系统中的位置               │
├──────────────────────────────────────────────────────┤
│                                                       │
│  原始数据 ──▶ 处理 ──▶ Tokenized ──▶ 训练 ──▶ 模型    │
│   (混乱)      (清洗)    (标准化)     (学习)     (产物)  │
│                                                       │
│  数据处理的每个环节都会影响最终的模型质量：              │
│  - 去重不够 → 模型 memorization，浪费容量              │
│  - 过滤太严 → 数据多样性降低，泛化能力下降             │
│  - 混合比例不对 → 某些领域能力过强/过弱                 │
│  - PII 没处理 → 隐私泄露风险                          │
└──────────────────────────────────────────────────────┘
```

### 为什么数据是 Long-Tail Problem

数据质量遵循 **帕累托分布**（Pareto distribution）：

- **头部（~20% 数据）：** 高质量、干净、信息丰富 → 贡献 ~80% 的模型性能
- **尾部（~80% 数据）：** 噪音、低质量、重复、有害 → 拖累训练，但包含稀有但重要的知识

**长尾挑战：**
1. 需要过滤掉 80% 的垃圾，但不能丢失尾部的珍贵信息
2. 尾部包含稀有语言、专业领域术语、低频事件——这些对泛化很重要
3. 过滤算法的阈值设置本身就是一个 trade-off

## 7. 面试问题

1. **解释 DCLM 数据处理 pipeline 的每个步骤及其目的。如果让你简化这个 pipeline，你会去掉哪些步骤？为什么？**

   *参考答案：核心不可省略的步骤是去重（减少 memorization）和质量过滤（减少噪音）。简化可以考虑去掉 PII 移除（如果部署时有后处理），或简化语言识别（如果只需要英文数据）。但每简化一步都会带来特定风险。*

2. **什么是 MinHash？为什么在大规模去重中用它而不是直接比较？**

   *参考答案：MinHash 是一种估计 Jaccard 相似度的算法，可以将 $O(N^2)$ 的暴力比较降低到 $O(N)$ 复杂度。通过 LSH（Locality-Sensitive Hashing），可以将相同 hash 值的文档分桶，只在桶内比较。对于 10B+ 文档的数据集，这是唯一可行的方法。*

3. **KenLM 和 fastText 都是用于质量过滤的分类器，它们的本质区别是什么？适用场景有什么不同？**

   *参考答案：KenLM 是生成式模型（n-gram + Kneser-Ney 平滑），衡量"这段文字有多像高质量文本"；fastText 是判别式模型（线性分类器 + n-gram 特征），直接判断"这段文字是高质量还是低质量"。KenLM 不需要负样本，但计算慢；fastText 需要标注数据，但训练和推理都快。*

4. **数据混合（data mixing）为什么不能只在小规模实验，而需要外推到大规模？外推的风险是什么？**

   *参考答案：数据混合的最优比例可能不是 scale-invariant 的——小模型和大模型对不同数据类型的学习效率不同（例如小模型更需要简单数据，大模型更需要多样数据）。外推风险包括：比例偏移导致某些能力退化，或大模型学到不同的 bias。Multi-scale 实验（从小到大多个规模）可以减轻风险。*

5. **如果训练数据中 30% 是 GitHub 代码，模型会产生什么问题？如何应对？**

   *参考答案：模型可能过度倾向于生成代码风格的回答，甚至在非编程场景中也使用代码格式。还可能学到代码中的特定偏见（如变量命名偏好）。应对方法：（1）合理降低代码比例（通常 5-15% 足够）；（2）在 post-training 阶段用对话数据纠正；（3）使用 data curriculum 策略，在训练早期多采样代码，后期减少。*

> **关键 Takeaways:**
> 1. 数据处理是训练前最耗时、最关键的步骤之一
> 2. "垃圾进，垃圾出"——数据质量直接决定模型能力
> 3. 去重不加 → 模型浪费容量在重复内容上
> 4. 过滤阈值是核心 hyperparameter —— 太松太严都有问题
> 5. 数据混合比例需要 multi-scale 实验验证
> 6. 长尾效应：大数据并不意味着自动高质量
