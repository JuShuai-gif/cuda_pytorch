# Liger Kernel 重实现 + Triton/TileLang 横向对比项目

> 不建议把 Liger Kernel 逐行照抄一遍，建议做成一个 **Liger Kernel 重实现 + Triton/TileLang 横向对比项目**。
>
> 这样既能学到训练算子工程化，也能形成一个有说服力的简历项目。
>
> Liger 官方本身就是按照"底层 Triton 算子、PyTorch 封装、正确性测试、收敛测试、benchmark"组织的，所以很适合作为参考架构。

---

## 一、可以做，但不要一开始重写整个仓库

Liger 中不同算子的难度差别非常大。

建议先完成 6～8 个有代表性的算子，而不是追求"文件数量全部复制"。

### 第一阶段：基础算子

按这个顺序：

1. RMSNorm
2. LayerNorm
3. SwiGLU
4. GEGLU
5. RoPE
6. CrossEntropy

这些算子可以覆盖：

- pointwise 操作
- reduction
- masking
- broadcasting
- 数值稳定性
- forward/backward
- kernel fusion
- 多维索引

### 第二阶段：复杂融合算子

再做：

1. Fused Linear Cross Entropy
2. KL Divergence / JSD 等 loss
3. Chunked Loss
4. 量化或 fused activation

其中最值得深入研究的是：

```text
hidden_states
    ↓
linear projection
    ↓
logits
    ↓
cross entropy
```

普通 PyTorch 会显式生成一个很大的：

```text
[batch_size × sequence_length, vocab_size]
```

logits 张量。

Fused Linear Cross Entropy 的核心价值，是通过分块和融合降低这个中间张量带来的显存压力。

## 二、"抄一遍"应该怎样抄

最有效的方式不是：

```text
打开 liger 源代码
→ 一行一行复制
→ 修改变量名
```

这样只能熟悉语法，很难理解为什么这么设计。

建议采用下面的重实现流程。

### 每个算子的学习流程

#### 第一步：只看数学定义

例如 RMSNorm：

```math
y_i = \frac{x_i}{\sqrt{\frac{1}{N}\sum_j x_j^2+\epsilon}}w_i
```

先不要看 Liger 的 Triton 实现。

#### 第二步：自己写 PyTorch Reference

```python
def rms_norm_reference(
    x: torch.Tensor,
    weight: torch.Tensor,
    eps: float,
) -> torch.Tensor:
    x_float = x.float()
    variance = x_float.pow(2).mean(dim=-1, keepdim=True)
    normalized = x_float * torch.rsqrt(variance + eps)
    return (normalized * weight.float()).to(x.dtype)
```

先确认数学逻辑和数据类型处理。

#### 第三步：独立写 Triton 版本

只根据数学公式设计：

- 一个 program 处理什么数据？
- 是一行一个 program，还是一个 block 多行？
- reduction 怎么处理？
- `BLOCK_SIZE` 应该怎么选？
- mask 怎么生成？
- 哪些计算要升为 FP32？
- 是否需要保存中间结果供 backward 使用？

#### 第四步：写正确性测试

先证明它算得对。

#### 第五步：再阅读 Liger 实现

比较：

- Liger 的 program mapping
- reduction 方式
- dtype 转换
- backward 推导
- block size
- num_warps
- 特殊 shape 分支
- 为什么比你的实现快

#### 第六步：重新优化自己的实现

不是直接替换成 Liger 代码，而是记录：

```text
我的第一版
→ 性能瓶颈
→ Liger 的设计
→ 我的第二版
→ 性能变化
```

#### 第七步：用 TileLang 再实现一次

这时你已经理解算法，再对比两个 DSL：

```text
Triton：
更接近线程块和标量/向量索引表达

TileLang：
更强调 tile、shared memory、pipeline 和算子级描述
```

这个过程的学习价值远高于单纯复制。

## 四、七项任务应该怎么具体落实

你列出的七项非常合理，但需要把标准定义清楚。

### 1. PyTorch Reference

PyTorch Reference 的目标不是最快，而是：

- 数学意义清楚
- 代码容易验证
- 作为正确性基准
- 支持 autograd
- 尽量避免复杂 fusion

建议提供两个 reference：

```text
naive_reference
torch_compiled_reference
```

例如 benchmark 时比较：

```text
PyTorch Eager
torch.compile
Liger Triton
Your Triton
Your TileLang
```

这样比较才比较完整。

### 2. Triton 实现

每个训练算子至少包含：

```text
forward kernel
backward kernel
torch.autograd.Function
nn.Module wrapper
```

例如：

```python
class TritonRMSNormFunction(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x, weight, eps):
        output, rstd = triton_rms_norm_forward(x, weight, eps)
        ctx.save_for_backward(x, weight, rstd)
        ctx.eps = eps
        return output

    @staticmethod
    def backward(ctx, grad_output):
        x, weight, rstd = ctx.saved_tensors
        grad_x, grad_weight = triton_rms_norm_backward(
            grad_output,
            x,
            weight,
            rstd,
        )
        return grad_x, grad_weight, None
```

只写 forward 不足以完整复现 Liger，因为 Liger 的主要应用场景是训练，其工程结构包含核心 Triton 操作、PyTorch/Transformers 封装、正确性测试和训练收敛测试。

### 3. TileLang 实现

TileLang 版本不要强求与 Triton 使用完全相同的算法。

应该允许：

```text
相同数学功能
不同 kernel mapping
不同 shared-memory 方案
不同 pipeline
不同 block/tile 配置
```

这正是横向对比的价值。

例如 GEMM 类算子，TileLang 可能更适合显式表达：

```text
Global Memory
→ Shared Memory
→ Register Fragment
→ GEMM
→ Global Memory
```

而 RMSNorm 等 reduction 算子，Triton 可能更直接。

TileLang 官方仓库本身也提供 kernel 示例和完整 benchmark 配置，可以参考它的测试及调优组织方式。

#### 一个重要现实问题

不是每个 Liger 算子都值得写 TileLang 版本。

建议分类：

| 算子              | Triton | TileLang | 原因               |
| ----------------- | -----: | -------: | ------------------ |
| RMSNorm           |   必做 |     必做 | reduction 入门      |
| SwiGLU            |   必做 |     必做 | pointwise fusion   |
| RoPE              |   必做 |     可做 | 索引操作较多           |
| CrossEntropy      |   必做 |     必做 | reduction + 数值稳定 |
| Fused Linear CE   |   必做 |     必做 | GEMM + loss 融合    |
| DPO/KTO Loss      |   可做 |    可跳过 | 更偏训练业务逻辑         |
| FlashAttention    |  可扩展 |   强烈推荐 | TileLang 更有发挥空间   |

### 4. Correctness Test

正确性测试不能只测试一个 `[1024, 4096]`。

至少覆盖以下维度。

#### Shape

```python
SHAPES = [
    (1, 128),
    (7, 768),
    (32, 1024),
    (127, 4096),
    (1024, 4096),
    (4096, 8192),
]
```

故意加入非 2 的整数次幂：

```text
7
127
513
1000
4097
```

这样能验证 mask 和边界处理。

#### Dtype

```text
float32
float16
bfloat16
```

#### 内存布局

```text
contiguous
non-contiguous
不同 stride
```

不过第一版可以先只支持 contiguous，然后在接口中明确检查：

```python
if not x.is_contiguous():
    raise ValueError("x must be contiguous")
```

#### Forward 测试

```python
torch.testing.assert_close(
    actual,
    expected,
    rtol=...,
    atol=...,
)
```

#### Backward 测试

必须分别比较：

```text
output
grad_input
grad_weight
grad_bias
```

#### 数值稳定性

测试：

```text
非常大的输入
非常小的输入
全零输入
正负混合
长序列

```

```text
large logits
ignore_index
label smoothing
不同 reduction
```

### 5. 不同 Shape Benchmark

Benchmark 需要避免常见错误。

#### 至少预热

```python
for _ in range(25):
    fn()
```

#### 使用 CUDA Event 或 `triton.testing.do_bench`

```python
latency_ms = triton.testing.do_bench(
    lambda: fn(x, weight),
    warmup=100,
    rep=500,
)
```

#### Benchmark 前后保证同步

不要直接使用：

```python
start = time.time()
fn()
end = time.time()
```

因为 CUDA 默认异步执行，这样测出来通常不是真实 kernel 时间。

#### 分开测模式

训练算子建议分成：

```text
forward
backward
forward + backward
```

不要只给一个总耗时。

#### 推荐 shape 维度

RMSNorm：

```text
M：token 数
N：hidden size
```

例如：

```python
M_VALUES = [1, 16, 128, 512, 2048, 8192]
N_VALUES = [768, 1024, 2048, 4096, 8192]
```

CrossEntropy：

```text
M：token 数
V：vocabulary size
```

例如：

```python
M_VALUES = [128, 512, 2048, 8192]
V_VALUES = [32000, 50000, 128256]
```

#### Benchmark 输出

不要只输出一句：

```text

```

应该保存完整 CSV：

```text

provider
mode
dtype
shape

gpu

torch_version
```

## 五、带宽和 FLOPS 怎么分析

这一项要注意：不是所有算子都适合用 FLOPS 衡量。

### 1. 内存密集型算子

例如：

- RMSNorm
- LayerNorm
- RoPE
- SwiGLU
- elementwise loss

主要看：

```text
GB/s
DRAM utilization
L2 hit rate
Arithmetic Intensity
```

### 2. 计算密集型算子

例如：

- GEMM
- Fused Linear Cross Entropy 中的 linear
- Attention
- Dequant GEMM

主要看：

```text
TFLOPS
Tensor Core utilization
SM utilization
Arithmetic Intensity
```

### Effective Bandwidth

通用公式：

```math
Effective Bandwidth = (Estimated Bytes Read + Estimated Bytes Written) / Execution Time
```

例如简单 FP16 pointwise：

```text
读取 x：N × 2 bytes
读取 weight：N × 2 bytes
写入 y：N × 2 bytes
```

理论流量约为：

```text
6N bytes
```

于是：

```math
GB/s = 6N / (t × 10^9)
```

但是必须在文档中说明：

> 这是基于算法语义计算的 effective bandwidth，不等同于 Nsight Compute 实际测量的 DRAM bytes。

因为：

- weight 可能命中 L2
- 一个输入可能被多次读取
- cache line 和 sector 会造成额外传输
- 编译器可能重算而不是保存
- 中间结果可能只存在寄存器中

### FLOPS

通用公式：

```math
FLOPS/s = Operation Count / Execution Time
```

例如 GEMM：

```math
C_{M×N} = A_{M×K} × B_{K×N}
```

通常按：

```text
2MNK
```

个浮点操作计算。

然后：

```math
TFLOPS = 2MNK / (t × 10^12)
```

对于 RMSNorm、Softmax、CrossEntropy，应当自己明确 FLOP 统计规则，因为：

- `exp`
- `log`
- `rsqrt`
- 除法

并不能简单等价为一个普通加法 FLOP。

因此这类算子更适合把：

```text
延迟
有效带宽
实际 DRAM 吞吐
```

作为主要指标，FLOPS 作为辅助指标。

### Arithmetic Intensity

```math
Arithmetic Intensity = FLOPs / Bytes Transferred
```

单位是：

```text
FLOPs / Byte
```

它可以帮助判断 kernel 是：

```text
Memory Bound
还是
Compute Bound
```

NVIDIA 的 Roofline 模型正是把算术强度、峰值计算能力和内存带宽结合起来，判断 kernel 离硬件上限有多远。

## 六、Nsight Compute 应该分析什么

不要打开 Nsight Compute 后把几百个指标全部截图。

每个 kernel 固定分析以下几组即可。

### 1. Launch Statistics

看：

```text
Grid Size
Block Size
Registers Per Thread
Shared Memory Per Block
Waves Per SM
```

重点问题：

- 一个 program/block 处理多少元素？
- grid 是否太小，GPU 吃不满？
- 寄存器是否太多？
- shared memory 是否限制 occupancy？

### 2. Occupancy

看：

```text
Theoretical Occupancy
Achieved Occupancy
Active Warps Per SM
Register limitation
Shared-memory limitation
```

但不要把 occupancy 当作越高越好。

有些 kernel：

- occupancy 不高
- 但是数据复用很好
- Tensor Core 吞吐很高
- 最终性能仍然很好

### 3. Memory Workload Analysis

看：

```text
DRAM Throughput
L2 Throughput
L1/TEX Throughput
L2 Hit Rate
Global Load Efficiency
Global Store Efficiency
Memory Sectors
```

Memory Workload Analysis 可以展示数据传输、缓存命中以及内存请求情况。

### 4. Compute Workload Analysis

看：

```text
SM Throughput
Tensor Core utilization
FP32 pipeline utilization
FP16 pipeline utilization
Instruction mix
```

例如 RMSNorm 通常不应该期待很高的 Tensor Core 利用率。

而 GEMM 如果 Tensor Core 利用率很低，就要检查：

- dtype 是否合适
- shape 是否对齐
- TileLang/Triton 是否生成了 MMA 指令
- tile size 是否合理

### 5. Scheduler Statistics

看：

```text
Eligible Warps Per Scheduler
Issued Warps Per Scheduler
Active Warps
No Eligible Warp
```

它可以帮助判断：

- warp 是否足够
- 是否存在长延迟
- 是否被依赖链卡住
- 是否存在严重 load-use latency

### 6. Warp Stall Reasons

重点看：

```text
Long Scoreboard
Short Scoreboard
Barrier
Wait
Not Selected
Math Pipe Throttle
MIO Throttle
```

典型解释：

| Stall              | 常见原因                    |
| ------------------ | ----------------------- |
| Long Scoreboard    | 等待 global/L2 memory     |
| Short Scoreboard   | 等待 shared memory 或特殊运算 |
| Barrier            | 同步过多                    |
| Math Pipe Throttle | 计算 pipeline 饱和          |
| MIO Throttle       | 内存指令发射压力                |
| Not Selected       | warp 足够多，调度器选择了其他 warp |

### 7. Roofline

推荐命令：

```bash
ncu \
  --set roofline \
  --target-processes all \
  -o profiles/rms_norm/triton_rms_norm \
  python benchmarks/profile_rms_norm.py \
  --provider triton \
  --m 4096 \
  --n 4096 \
  --dtype float16
```

或者使用更全面的分析：

```bash
ncu \
  --set full \
  --target-processes all \
  --kernel-name regex:rms_norm \
  -o profiles/rms_norm/triton_rms_norm_full \
  python benchmarks/profile_rms_norm.py
```

Nsight Compute 当前支持 Roofline 和层级 Roofline；后者可以进一步展示 L1、L2 和 DRAM 等不同层级的性能上限。

## 七、Nsight 分析时需要单独写 profile 脚本

不要直接 profile 完整 pytest 或完整 benchmark。

否则 Nsight 会捕获大量：

- PyTorch 初始化 kernel
- 内存清零 kernel
- random kernel
- reference kernel
- backward 的其他 kernel

建议单独写：

```python
# benchmarks/profile_rms_norm.py

import argparse
import torch

from kernel_lab.triton_ops.rms_norm import triton_rms_norm


def main() -> None:
    parser = argparse.ArgumentParser()
    parser.add_argument("--m", type=int, default=4096)
    parser.add_argument("--n", type=int, default=4096)
    parser.add_argument("--iterations", type=int, default=5)
    args = parser.parse_args()

    x = torch.randn(
        args.m,
        args.n,
        device="cuda",
        dtype=torch.float16,
    )
    weight = torch.ones(
        args.n,
        device="cuda",
        dtype=torch.float16,
    )

    # 在 profiler 捕获前完成编译和预热
    for _ in range(20):
        triton_rms_norm(x, weight, eps=1e-6)

    torch.cuda.synchronize()

    torch.cuda.cudart().cudaProfilerStart()
    for _ in range(args.iterations):
        triton_rms_norm(x, weight, eps=1e-6)
    torch.cuda.cudart().cudaProfilerStop()

    torch.cuda.synchronize()


if __name__ == "__main__":
    main()
```

然后：

```bash
ncu \
  --profile-from-start off \
  --set full \
  -o profiles/rms_norm/report \
  python benchmarks/profile_rms_norm.py
```

这样可以减少无关 kernel。

```text
GEMM + loss 融合
共享内存、分块、流水线
```

### 阶段四：接入真实模型

最后把自己的算子接进一个小型 Llama/Qwen 模型：

```text
原始 Hugging Face 模型
→ 替换 RMSNorm
→ 替换 RoPE
→ 替换 SwiGLU
→ 替换 CrossEntropy
→ 测训练 loss 是否一致
→ 测显存和吞吐
```

这一步才真正对应 Liger Kernel 的实际用途。

---

## 十一、最终项目的评价标准

不要以"抄了多少个文件"为完成标准，而要以以下指标判断：

```text
能否独立推导 forward/backward
能否解释 program 和 tile 如何划分
能否处理非规则 shape
能否证明数值正确
能否设计公平 benchmark
能否计算有效带宽或 TFLOPS
能否通过 Nsight 找到瓶颈
能否解释 Triton 和 TileLang 的性能差异
能否接入真实模型并保持训练收敛
```

因此，这个计划完全可行，命名为：

> **LLM Training Kernel Lab：Liger Kernel 算子重实现与 Triton/TileLang 性能对比**

第一阶段只做 **RMSNorm 一项的完整七步闭环**。跑通以后再扩展 SwiGLU、RoPE 和 CrossEntropy，不要同时铺开全部算子。
