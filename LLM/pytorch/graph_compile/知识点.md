## `00_overview.py` - 先看地图，知道谁是谁

**核心比喻**：
- **FX** = 图的格式（纯 Python 对象，可读可写）
- **Dynamo** = 抓图的人（拦截 Python 字节码，实时记录成 FX 图）
- **Inductor** = 吃图的人（把 FX 图编译成 Triton/C++ kernel）

**`torch.compile = Dynamo（前端抓图）-> AOTAutograd（中间处理梯度）-> Inductor（后端生成代码）`**

**四种"图"**：
1. **Computation Graph** - 数学层面的抽象图（matmul、relu 这些运算的关系）
2. **CUDA Graph** - GPU 驱动层面的图，减少 CPU 向 GPU 发指令的开销
3. **FX Graph** - PyTorch 算子级别的中间表示（`aten.linear`、`aten.relu`），编译器吃的 IR
4. **Inductor IR** - 编译器内部更底层的表示，做算子融合和代码生成

**演进史**：Eager（写一行跑一行）-> TorchScript（静态图，C++ 可部署）-> FX（图是 Python 对象，可读可改）-> `torch.compile`（Dynamo 自动抓图 + Inductor 编译）

**特别有价值的是**：文件里画出了 Dynamo 的源码级调用链——从 `torch.compile()` 到 PEP 523 帧拦截，到字节码逐条分发（`LOAD_FAST`、`CALL_FUNCTION`、`RETURN_VALUE`），再到最终生成 `torch.fx.Graph`。

**FX Graph 作为统一 IR 的价值**：`symbolic_trace`（通过 AST）和 Dynamo（通过字节码）虽然抓图手段不同，但输出都是 `torch.fx.GraphModule`。后续所有环节只认这个格式，前端可换，后端可插。

## `01_fx_graph.py` - 学会读图、造图、改图

### Part 1：`symbolic_trace` 怎么工作的

它给 `forward()` 喂一个"假输入"（Proxy），每执行一个操作就记录一个节点。最后得到一张有向无环图，图中的边就是 Python 的对象引用——relu 的 `args` 里存的就是 linear 节点的指针。

四种 op 类型：
- `placeholder` - 输入参数
- `call_module` - 调用 `nn.Module`（如 `self.linear`）
- `call_function` - 调用普通函数（如 `torch.relu`）
- `output` - 返回值

Python 代码和 FX Graph Node 的对应关系：

```
Python 代码                    FX Graph Node
──────────────────────────────────────────────
def forward(self, x):          -> x (placeholder)
y = self.linear(x)             -> linear (call_module)
y = torch.relu(y)             -> relu (call_function)
y = torch.abs(y)              -> abs_1 (call_function)
return y + 2.0                -> add (call_function) -> output
```

`args` 就是图的边——存的是 Python 对象引用：
- relu 的 args 是 `(linear,)` -> 数据从 linear 流向 relu
- add 的 args 是 `(abs_1, 2.0)` -> 数据从 abs_1 流向 add

### Part 2：从零手写 MiniGraph（~160 行）

让你理解 FX Graph 的底层数据结构：
- 核心是一个**双向循环链表**维护节点拓扑顺序
- 每个节点有 `users` 字典记录"谁依赖我"（反向索引）
- 自动命名去重：第一个叫 relu，第二个叫 `relu_1`
- 插入节点时自动维护上下游关系

关键数据结构：

```python
class MiniNode:
    name   # 节点名
    op     # placeholder / call_module / call_function / output
    target # 被调用的对象
    args   # 输入节点列表，即图的边
    users  # 下游节点集合：谁把本节点当输入
    _prev  # 双向链表前驱
    _next  # 双向链表后继
```

### Part 3：图改写

这是 FX Graph 最强大的特性——不改 Python 源码，直接改图的节点就能改变模型行为。例如把所有 `relu` 替换成 `gelu`：

```python
for n in gm.graph.nodes:
    if n.op == "call_function" and n.target == torch.relu:
        n.target = torch.nn.functional.gelu
gm.recompile()
```

### Part 4：改图的多个时机

可以在 Dynamo 之后（自定义 backend）、Inductor 内部（custom lowering）、导出后（ONNX）等阶段修改图，但 FX Graph 是**唯一面向用户、可读可写**的 IR。

自定义 backend 就是在 Dynamo 抓图后、Inductor 前拦截图：

```python
def my_backend(gm, inputs):
    for n in gm.graph.nodes:
        if n.target == torch.relu:
            n.target = torch.nn.functional.gelu
    gm.recompile()
    return gm.forward

torch.compile(model, backend=my_backend)
```

## `02_fx_internals.py` - 剥开 FX 的底层实现

逐层拆解 FX 的内存结构和实现方式，共 6 层：

### 第 1 层：Node —— 图中的单个节点

```python
class Node:
    name          # 唯一标识，如 'linear', 'relu'
    op            # placeholder | call_function | call_module | output | get_attr
    target        # 被调用的目标（函数、模块名、字符串）
    args          # 位置参数（Node 或值的 tuple）
    kwargs        # 关键字参数
    _input_nodes  # {node: uses} - 上游依赖（谁喂数据给我）
    users         # {node: uses} - 下游依赖（谁要吃我的输出）
    _prev         # 双向链表：前驱
    _next         # 双向链表：后继
```

关键点：`args` 里存的是真实的 Node 对象引用，不是字符串。而 `print_tabular()` 显示的是简化后的文本。

### 第 2 层：Graph —— 节点容器

Graph 本质上是一个：
- **双向链表**（`Node._prev` / `Node._next`）
- **字典索引**（按名字查 Node：`_nodes_by_name`）
- 每个 Node 维护自己的 `users` / `_input_nodes`

通过 `_root` 哨兵节点标记链表首尾，创建节点时自动插入链表、注册名称、更新上下游关系。

### 第 3 层：args 里存的是真的 Node 对象

`print_tabular()` 里显示的是字符串，但在内存里 args 存的是活生生的 Node 对象引用。图的边就是 Python 指针。

### 第 4 层：GraphModule —— 让图可执行

GraphModule 的核心魔法是 `recompile()`：
1. 把 Graph 节点列表翻译成 Python 源码（`graph.python_code()`）
2. 用 `exec()` 执行这段代码生成 `forward` 方法
3. 所以 `gm(x)` 和普通模型调用完全一样

翻译过程：
```
Graph:  x -> linear -> relu -> output
        |
        v 翻译成 Python 代码
def forward(self, x):
    linear = self.linear(x)     # call_module
    relu = torch.relu(linear)   # call_function
    return relu                 # output
```

### 第 5 层：Proxy —— 图的"木马"构建器

Proxy 是 `symbolic_trace` 用来"骗" forward 的假 tensor。它伪装成 Tensor，重载了所有运算符（`__add__`、`__matmul__` 等），但实际不做计算，而是在 Graph 上创建新 Node。

```python
class Proxy:
    def __add__(self, other):
        # 在 Graph 中创建一个 call_function(torch.add) 的 Node
        return self.tracer.create_proxy("call_function", torch.add, (self, other), {})
```

执行流程：
```
y = self.fc(x)     # x 是 Proxy -> fc 内部调用被拦截 -> 创建 call_module Node
z = y + 2.0        # y 是 Proxy -> Proxy.__add__ 被拦截 -> 创建 call_function(add) Node
return z           # z 是 Proxy -> 记录为 output Node
```

### 第 6 层：完整对象关系图

```
GraphModule (nn.Module 子类)
  ├── graph: Graph
  │    ├── _root: Node (哨兵，链表头尾)
  │    ├── _len: int
  │    ├── _nodes_by_name: {str -> Node}
  │    └── _owning_module -> 指回 GraphModule
  │
  │    双向链表: _root <-> x <-> linear <-> relu <-> output <-> _root
  │
  │    每个 Node:
  │      .name      = "relu"
  │      .op        = "call_function"
  │      .target    = <built-in function relu>
  │      .args      = (Node("linear"),)   <- 真的 Node 对象
  │      ._input_nodes = {Node("linear"): 1}
  │      .users        = {Node("abs_1"): 1}
  │
  ├── parameters (来自原始模型):
  │    fc1.weight: (8, 4)
  │    fc1.bias:   (8,)
  │
  └── code: str  <- graph.python_code() 生成的 Python 源码
       def forward(self, x):
           linear = self.linear(x)
           relu = torch.relu(linear)
           return relu
```

## 掌握优先级

分三层，越往上越需要实操。

### 必须动手会的

- 读图：`gm.graph.print_tabular()` 看节点、看懂 4 种 op
- 改图：遍历 `gm.graph.nodes`，改 `node.target` 然后 `gm.recompile()`
- 写一个自定义 backend：`def my_backend(gm, inputs): 改图; return gm.forward`，丢给 `torch.compile(model, backend=my_backend)`

### 理解原理就够的

- Dynamo 通过 PEP 523 字节码拦截抓图（知道它跟 `symbolic_trace` 的区别就行）
- Inductor 做 lowering + fusion + codegen 生成 Triton kernel（知道它能干什么，不必读源码）
- AOTAutograd 在训练时插入反向传播节点（推理时跳过）

### 面试/排查问题时翻出来看

- 源码级调用链（`00_overview.py` 里画的那条链）
- Graph 底层数据结构（双向链表 + users 索引）

**实际工作**：80% 的时间都在跟 FX Graph 打交道——读图、改图、自定义 backend。Dynamo 和 Inductor 是黑盒，会用就行。

## 实际工作中的具体例子

### 例子 1：调试「为什么我的模型编译后精度掉了」

怀疑某个算子在编译后数值异常，先看看它被编译成了什么：

```python
import torch

class MyModel(torch.nn.Module):
    def forward(self, x):
        return torch.silu(x) + x  # 怀疑 silu 编译后数值不对比

model = MyModel().cuda()

# 拦截图，看发生了什么
def debug_backend(gm, example_inputs):
    gm.graph.print_tabular()             # 看节点列表
    for n in gm.graph.nodes:
        print(f"{n.name}: {n.target}")   # 看每个节点对应什么操作
    return gm.forward                     # 不做任何编译，直接执行

opt = torch.compile(model, backend=debug_backend)
opt(torch.randn(4, 4).cuda())
```

输出会告诉你 `silu` 是否被 inductor 融合成了别的 kernel，从而定位问题。

### 例子 2：生产环境中用自定义算子替换标准算子

你的推理服务想用 `xformers.memory_efficient_attention`（更快）替换标准的 `torch.nn.functional.scaled_dot_product_attention`：

```python
from torch.fx import GraphModule
import xformers.ops as xops

def replace_attention(gm: GraphModule, example_inputs):
    for n in gm.graph.nodes:
        if n.op == "call_function" and n.target == torch.nn.functional.scaled_dot_product_attention:
            n.target = xops.memory_efficient_attention
    gm.recompile()
    return gm

# 一行 compile，全局生效
model = torch.compile(model, backend=replace_attention)
```

不改模型代码，不改训练脚本，只在 compile 层做一次替换。

### 例子 3：统计模型中每种算子的调题次数（性能分析）

想知道模型里 `matmul` 被调了多少次、哪些算子最慢：

```python
from collections import Counter

def count_ops(gm, example_inputs):
    counts = Counter()
    for n in gm.graph.nodes:
        if n.op == "call_function":
            counts[n.target.__name__] += 1
    print("算子调用统计:")
    for op, cnt in counts.most_common():
        print(f"  {op}: {cnt}")
    return gm.forward

torch.compile(model, backend=count_ops)(input_tensor)
```

### 例子 4：给模型加 profiling 插桩

在不改模型代码的情况下，给每个卷积层前后插入 GPU 计时：

```python
def profile_insert(gm, example_inputs):
    """在 conv2d 前后插入 cuda event 计时"""
    graph = gm.graph  # 这告诉你 gm.graph 就是一个可读可写的 Python 对象
    for n in graph.nodes:
        if n.op == "call_function" and n.target == torch.conv2d:
            with graph.inserting_before(n):
                start = graph.call_function(torch.cuda.Event, ())
                record_start = graph.call_method("record", (start, torch.cuda.default_stream()))
            with graph.inserting_after(n):
                end = graph.call_function(torch.cuda.Event, ())
                record_end = graph.call_method("record", (end, torch.cuda.default_stream()))
    graph.lint()
    gm.recompile()
    return gm.forward

torch.compile(model, backend=profile_insert)(input_tensor)
```

不改 `forward()` 一行代码，纯图操作完成插桩。

### 例子 5：强制某算子不参与融合（解决正确性 bug）

Inductor 有时候会把几个算子融合成一个 kernel 导致数值异常，你需要强制某个算子单独跑：

```python
def force_no_fuse(gm, example_inputs):
    for n in gm.graph.nodes:
        if n.op == "call_function" and n.target == torch.softmax:
            n.meta["no_fuse"] = True  # 标记不要融合
    return gm.forward

torch.compile(model, backend=force_no_fuse)(input_tensor)
```

### 总结

这些例子有个共同点：**你操作的只是一个 `torch.fx.GraphModule` 对象**。读它（`print_tabular`）、改它（替换 `node.target`、插入/删除节点）、交给 Inductor 编译。这是日常工作里最核心的技能。

## Graph Break 完全手册

### 什么是 Graph Break

Dynamo 在追踪 `forward()` 的字节码执行时，一旦遇到它「不认识」的 Python 操作，就会把当前图收尾、执行这段 eager 代码，然后重新开始追踪下一张图。

```
一张大图 → 拆成 子图1 + eager代码 + 子图2 + eager代码 + 子图3 ...
```

**本质**：Dynamo 只能追踪纯 PyTorch 张量计算。任何涉及 Python 动态行为（I/O、控制流依赖张量值、第三方库调用等）的操作都会导致断开。

### Graph Break 的真正影响

以 `print(f"sum={y.sum().item()}")` 导致断开为例：

```
子图 1: x -> linear -> y -> sum     (print 之前全被编译成一张图)
sum=4.96                            (print 在 eager 模式里执行，不在图里)
子图 2: y -> relu                   (print 之后重新开始追踪，生成另一张图)
```

影响体现在三个层面：

#### 影响 1：算子融合被打断（最直接、最大的损失）

Inductor 会把多个 PyTorch 算子合并成一个 Triton kernel，避免中间结果写回显存再读出来。但融合只能在同一张子图内部进行。子图 1 末尾的 `sum` 和子图 2 开头的 `relu` 本来可以合成一个 kernel：

```
融合前（两张子图）：
  kernel_1: load x -> linear -> sum -> store 到显存     ← 子图1 收尾写回
  [eager: print 消费 sum 的结果]
  kernel_2: load 显存 -> relu -> store 到显存            ← 子图2 重新从显存读

融合后（如果没断开）：
  kernel_1: load x -> linear -> sum -> relu -> store 到显存  ← 一次搞定
```

GPU 计算很快，瓶颈在**显存读写带宽**。多一次 store + load 就是多两趟显存往返，对于大张量这是实实在在的性能损失。

#### 影响 2：GPU <-> CPU 同步等待

`print()` 这类 eager 代码跑在 CPU 上，但它消费的输出（`sum` 的结果）来自 GPU。这意味着 GPU 必须**等当前 kernel 执行完，把数据拷回 CPU**，CPU 才能继续。这打断了 GPU 的流水线，相当于一个硬同步点。

```
正常编译图：kernel -> kernel -> kernel  （GPU 一气呵成，CPU 不参与）
有 graph break：kernel -> GPU 等 -> CPU 等 -> print -> CPU 把数据送回 -> kernel  （GPU 空转等 CPU）
```

#### 影响 3：CUDA Graph 的收益被稀释

`torch.compile` 加上 `mode="reduce-overhead"` 会用 CUDA Graph 包裹整个 forward，把多次 kernel launch 合并成一次。子图越多，CUDA Graph 的粒度越碎，减少 launch 开销的效果越差。

#### 总结

断一次，就多一次显存读写 + 一次 GPU 等 CPU 的同步。断在热点路径（transformer 的 attention 中间、大规模卷积中间）是灾难；断在初始化或数据预处理里就完全无所谓。判断标准永远是：**这个断点是否阻止了本可以融合的热点算子**。

### 常见 Graph Break 原因及示例

#### 1. 打印/logging（最常见）

```python
def forward(self, x):
    y = self.linear(x)
    print(f"shape={y.shape}")   # ← break: print 是 Python I/O
    return torch.relu(y)

# 解决：去掉 print，或改用 torch 内部 logging
```

#### 2. `.item()` 把张量变 Python 标量

```python
def forward(self, x):
    y = self.linear(x)
    loss = y.sum().item()        # ← break: 从 GPU → CPU → Python 数字
    if loss > 0.5:               # ← break: Python 值参与控制流
        return y * 2
    return y

# 解决：
# - 推理场景: 直接用张量比较 torch.where(y.sum() > 0.5, y, y * 2)
# - 训练场景: 不在 forward 里做条件分支，把 loss 判断移到训练循环
# - 可选: torch._dynamo.config.capture_scalar_outputs = True（只修 .item()，不修控制流）
```

#### 3. 依赖张量值的动态控制流（if/while 条件依赖 tensor）

```python
def forward(self, x):
    if x.shape[0] > 16:            # ← break: shape 是 Python int
        x = x[:16]
    y = self.net(x)

    n = x.sum()                    # ★ 不 break（sum 在图内）
    for i in range(n):             # ← break: n 是 Tensor，range 需要 Python int
        y = y + 1
    return y

# 解决：
# - 用 torch.where / torch.cond / torch.while_loop 替代 Python if/for
# - 或者 guard 写死（如果 shape 真的不会变）：省略 shape 检查
```

#### 4. 调用第三方 C/C++ 库（非 PyTorch）

```python
import cv2

def forward(self, x):
    img = x.cpu().numpy()          # ← break: .numpy() 出图了
    img = cv2.GaussianBlur(img)    # ← break: cv2 不是 PyTorch 算子
    return torch.from_numpy(img)   # ← break: 重新进图

# 解决：用 torch 算子实现，或在数据预处理阶段完成 cv2 操作
```

#### 5. `.numpy()` / `.tolist()` / `.data` / `.detach()` 的误用

```python
# .numpy()     - break: 从 Tensor 转为 NumPy，出了追踪范围
# .tolist()    - break: 从 Tensor 转为 Python list
# .data        - 不 break 但会绕过 autograd 图，编译后行为不一致，禁止使用
# .detach()    - 不 break，但会让梯度断开
```

#### 6. DataLoader / Dataset 内部逻辑

```python
class MyDataset(torch.utils.data.Dataset):
    def __getitem__(self, idx):
        img = load_image(idx)        # 不在 model.forward 里，不会触发 compile
        if random.random() > 0.5:    # 不触发 compile
            img = flip(img)
        return img
```

**注意**：Graph break 只发生在被 `torch.compile` 包裹的函数内部。DataLoader 不属于模型，不会影响编译。

#### 7. 不支持的 dunder 方法 / 未注册的算子

```python
def forward(self, x):
    # 未用 torch.library 注册的自定义 C++ 扩展
    return my_custom_kernel(x)  # ← break（如果能 trace 但无 lowering 则在 inductor 阶段报错）
```

#### 8. 动态 shape 变化导致 recompile（非 graph break，但表现类似）

```python
@torch.compile
def fn(x):
    return self.net(x)

for i in [16, 32, 64]:
    fn(torch.randn(i, 128))  # 每次 shape 变化可能触发一次重新编译
```

**区别**：
- **Graph break**：一张图被切成多块，同一次 forward 内发生
- **Recompile**：不同 shape/stride/dtype 的输入导致重新编译，跨多次 forward

#### 9. 生成器 / yield 语句

```python
def forward(self, x):
    for i in range(3):     # range 不 break（Python 常量循环是 Ok 的）
        x = self.linear(x)
        yield x            # ← break: Dynamo 不追踪生成器
    return x
```

### 如何诊断 Graph Break

#### 方法 1：看 warning 日志

```bash
# 运行时会自动打印：
W0730 07:31:31  Graph break from `Tensor.item()`...
```

#### 方法 2：用 TORCH_LOGS 开启详细诊断

```bash

# 输出每个 break 的位置和原因

TORCH_LOGS="recompiles" python your_script.py
# 输出每次重新编译的原因（shape 变化等）
```

#### 方法 3：用 torch._dynamo.explain() 分析

```python
# 返回 (未编译的结果, 编译分析报告)

print(explanation.break_reasons)              # 每次断的原因
print(explanation.compile_times)              # 编译耗时
```

### Graph Break 的影响评估

| 断的位置 | 影响 | 处理优先级 |
|----------|------|-----------|
| 初始化代码（模型构造、参数加载） | 无影响 | 忽略 |
| 训练循环外的预处理 | 极小 | 可忽略 |
| 训练循环内的 print/log | 中等 | 建议修复 |
| forward 中间的条件分支 | 严重 | 必须修复 |
| 热点算子中间的 `.item()` | 严重 | 必须修复 |

**关键判断**：graph break 的真正代价是**阻止跨断点的算子融合**。如果你的 forward 只有一个 linear 和一个 relu，中间断一下损失不大；但如果是一个 100 层的 transformer 中间断了，那前面 50 层和后面 50 层无法融合，性能打折扣。

### 修复策略（按推荐顺序）

1. **删掉**：去掉 forward 里的 `print`、`logging`、调试用的 `.item()`
2. **替换**：用纯 PyTorch 算子替代 Python 逻辑
   - `if x.sum() > 0` -> `torch.where(x.sum() > 0, ...)`
   - `for i in range(n)` -> `torch.while_loop` 或用向量化操作
3. **前置**：把不合规的代码移到 `forward` 外面（数据预处理、loss 计算等）
4. **允许**：`capture_scalar_outputs = True` 允许 `.item()` 进入图
5. **接受**：如果断点不在热点路径上，且 `TORCH_LOGS=graph_breaks` 确认断点数量可控，就不修

### 实际工作流程

```bash
# 1. 诊断
TORCH_LOGS="graph_breaks" python train.py 2>&1 | grep "Graph break"

# 2. 统计断点数量
python -c "
import torch
model = YourModel()
x = torch.randn(2, 3, 224, 224)
exp = torch._dynamo.explain(model)(x)
print(f'Graph breaks: {exp.graph_break_count}')
print(f'Break reasons: {exp.break_reasons}')
"

# 3. 逐个修断点：优先修热点路径上的

# 4. 修完后验证
TORCH_LOGS="graph_breaks" python train.py 2>&1 | grep -c "Graph break"
# 目标：0（或 1-2 个非热点位置的断开，可接受）
```

### 注意事项

- **不要为了消除所有 graph break 而魔改代码**。非热点路径上偶尔的断点（如 epoch 开始的统计打印）对性能影响微乎其微
- **`torch.compile` 和 `torch.jit.script` 的兼容性要求不同**。compile 的容忍度更高——它会自动 graph break 而不是直接报错
- **Graph break 不会导致计算错误**，只会影响性能。程序结果仍然是正确的
- **recompile（重新编译）比 graph break 更隐蔽**。如果每步 forward 的输入 shape 都在变，可能触发大量重编译，用 `TORCH_LOGS="recompiles"` 诊断
- **`dynamic=True` 参数**可以减少 shape 变化导致的 recompile，但会增加编译时间，按需使用
- **Guard 失败 ≠ graph break**。guard 是 Dynamo 的缓存机制：下次遇到相同 shape/dtype 直接复用之前编译的图。guard 失败意味着需要重新编译（recompile），不是 graph break

## Backend 与 Mode 选型手册

### 四种 backend（`torch.compile` 的 `backend` 参数）

| backend | 干的事情 | 适用场景 |
|---------|----------|----------|
| `inductor` | 全链路：Dynamo 抓图 -> AOTAutograd -> Inductor 算子融合 + 代码生成（Triton/C++） | **默认，99% 场景** |
| `eager` | Dynamo 只抓图，不做任何优化直接跑 | 怀疑问题出在图本身，验证图是否正确 |
| `aot_eager` | Dynamo 抓图 + AOTAutograd 处理，但**跳过 Inductor 融合** | 怀疑融合导致数值异常，排查用 |
| `cudagraphs` | 只做 CUDA Graph 包裹，**不做算子融合** | kernel 少但大，不需要融合只想减少 launch 开销 |

**排查选型口诀**：
```
正常用         -> inductor，99% 场景
怀疑编译导致问题 -> eager，看是不是图的问题
怀疑融合有问题   -> aot_eager，跳过 fusion 但保留 AOTAutograd 处理
kernel 大且少   -> cudagraphs，不需要融合
```

### 三种 Inductor mode（`backend="inductor"` 时的 `mode` 参数）

| mode | 干什么 | 适用场景 |
|------|--------|----------|
| `default` | 标准编译，编译快，效果已经很好 | **日常开发** |
| `reduce-overhead` | 额外用 CUDA Graph 包裹整个 forward，消除 CPU launch 开销 | **LLM decode**（每次推一个 token，很多小 kernel，launch 开销占比大） |
| `max-autotune` | 自动调优 kernel 参数（block 大小、tiling 策略等），编译最慢但跑最快 | **模型上线**、追求极致吞吐 |

**Mode 选型口诀**：
```
日常开发     -> default，编译快
LLM decode  -> reduce-overhead，消除大量小 kernel 的 launch 开销
模型上线     -> max-autotune，编译最慢但运行最快
```

**为什么 LLM decode 场景 `reduce-overhead` 特别有用**：LLM 推理时一次只生成一个 token，每步的计算量很小（一个 token 的 attention + FFN），但需要 launch 多个 kernel。大 batch 时 GPU 忙于计算，launch 开销被覆盖；小 batch（尤其 batch=1）时 launch 本身成了瓶颈。CUDA Graph 把多次 launch 合并成一次，效果显著。

### AOTAutograd 在哪一步

```
torch.compile 的完整链路：
  前向: Dynamo（抓图）-> AOTAutograd -> Inductor（融合 + 代码生成）
```

AOTAutograd 夹在 Dynamo 和 Inductor 之间。它做的事情是：

- **训练时**：拿到 Dynamo 抓出的 FX Graph，把它拆成前向图和反向图，插入梯度计算节点。这样 Inductor 拿到的图已经包含了完整的 forward + backward。
- **推理时**：虽然没有反向传播，AOTAutograd 依然会跑一遍（做图规范化、死代码消除等），但基本等于透传。

所以 `04_compile.py` 里保存的 `2_aotautograd.py` 就是「AOTAutograd 处理后、Inductor 编译前」的图。换言之：

```
Dynamo 输出: FX Graph（原始 Python 操作的记录）
    |
    v AOTAutograd 处理
规范化后的 FX Graph（forward+backward 已拆分，冗余节点已消除）
    |
    v Inductor 编译
Triton / C++ kernel（可执行的 GPU 代码）
```

## Graph Break 调试与修复速查（来自 `05_graph_break.py`）

### 程序化检测 Graph Break（数子图）

`05_graph_break.py` 里用了一个很巧妙的模式：用自定义 backend 来**数子图数量**，每个子图触发一次 backend 回调：

```python
def run_test(fn, x=None):
    """测试一个函数触发多少子图。n=1 表示无 break"""
    torch._dynamo.reset()
    gm_count = [0]

    def _check(gm, inputs):
        gm_count[0] += 1          # Dynamo 每生成一张子图就回调一次
        return gm.forward

    inp = x if x is not None else torch.randn(100)
    f = torch.compile(fn, backend=_check)
    f(inp)
    return gm_count[0]            # 1 = 无 break, >1 = 有 break

# 使用
print(run_test(my_func))  # 返回 2 → 断了 1 次（2 张子图）
```

这个模式比看 warning 日志更可靠：不依赖终端输出，可以写进测试用例自动检测。

### 五种 Debug 方法

| 方法 | 命令/代码 | 适用场景 |
|------|-----------|----------|
| ① 日志定位 | `TORCH_LOGS="graph_breaks" python script.py` | 最常用，直接打印 break 位置和精确行号 |
| ② 代码检查 | `torch._dynamo.explain(fn)(*args)` | 在 Python 代码中获取 `graph_break_count` 和 `break_reasons`，不需环境变量 |
| ③ 全量 dump | `TORCH_COMPILE_DEBUG=1 python script.py` | 把所有中间产物（FX Graph、Triton kernel）dump 到磁盘 |

### 12 种 Graph Break 场景完整分类

`05_graph_break.py` 对每种场景做了**实测**，统计了产生的子图数量：

| 编号 | 场景 | 触发条件 | 实测 |
|------|------|----------|------|
| [1] | 数据依赖 if | `if y.sum() > 0:` Dynamo 不知道条件真假 | ✗ BREAK |
| [2] | 数据依赖循环 | `for _ in range(int(tensor_val)):` 循环次数依赖 tensor 值 | ✗ BREAK |
| [3] | `.item()` 逃逸 | tensor -> Python 标量，Dynamo 失去对值的追踪 | ✗ BREAK |
| [4] | `.cpu()` / `.numpy()` | 数据逃逸出 PyTorch 进入 NumPy，无法继续符号追踪 | ✗ BREAK |
| [5] | `print` 副作用 | print 不是 PyTorch 操作 | ✗ BREAK |
| [6] | Python list 构造 | `lst = [y, y+1]` list 包含 tensor，Dynamo 部分追踪 | ✗ BREAK |
| [7] | 数据依赖索引 | `y[idx]` 中 idx 是 tensor 运算结果，索引值依赖运行时数据 | ✗ BREAK |
| [8] | try/except | 异常处理中带有数据依赖分支 | ✗ BREAK |
| [9] | 复杂控制流 | `return` 在循环内，控制流复杂 | ✗ BREAK |
| [10] | 输入 shape 变化 | 不同 shape 输入导致 guard 失效 | 重编译（非 break） |
| [11] | bool 参数分支 | `def fn(x, flag: bool): return a if flag else b` | ✓ OK（常量控制流可处理） |
| [12] | 自定义 autograd | `torch.autograd.Function.apply` | ✓ OK（通常可追踪） |

**关键区分**：[10] 是 recompile（重编译），不是 graph break。重编译发生在多次 forward 之间，每次 shape 变了就重新编译一次；graph break 发生在单次 forward 内部，把一张图拆成多张。

### 七种修复方案（带实测对比）

来自 `05_graph_break.py` Part 3，每种修复都用 `run_test` 验证了子图数量变化：

**修复 1：数据依赖 if/else -> `torch.where`**
```python
# 修复前（break）
def b1(x):
    return torch.cos(x) * 2 if torch.cos(x).sum() > 0 else torch.cos(x)

# 修复后（OK，1 张子图）
def g1(x):
    y = torch.cos(x)
    return torch.where(y.sum() > 0, y * 2, y)
```

**修复 2：`.item()` -> `capture_scalar_outputs=True`**
```python
# 一次性全局开启，.item() 不再导致 break
torch._dynamo.config.capture_scalar_outputs = True
```

**修复 3：print -> 移到 compile 外部或用 TORCH_LOGS**
```python
# 不要这样
def forward(self, x):
    print(f"shape={x.shape}")  # break
    return self.net(x)

# 改为：在训练循环里 print，forward 保持纯净
```

**修复 4：numpy -> torch 等价操作**
```python
# 修复前（break）
np.abs(y.cpu().numpy())

# 修复后（OK）
torch.abs(y)        # 直接 torch，不逃逸
torch.where(c, a, b)  # 替代 np.where
```

**修复 5：Python for/while -> 向量化 tensor 操作**
```python
# 修复前（break）
for i in range(n):
    y += x[i]

# 修复后（OK）
y = x.sum()         # 一步到位
```

**修复 6：动态 shape 重编译 -> `dynamic=True` 或 `mark_dynamic`**
```python
torch.compile(fn, dynamic=True)       # 标记所有维度动态
torch._dynamo.mark_dynamic(x, 0)      # 仅标记第 0 维（batch）动态
```

**修复 7：自定义函数 -> `torch.compiler.allow_in_graph`**
```python
@torch.compiler.allow_in_graph
def my_custom_op(x):
    return some_custom_kernel(x)       # Dynamo 现在能追踪了
```

**额外：自定义 C++ 扩展 -> `torch.library.register_fake`**
```python
# 让 Dynamo 知道自定义 C++ kernel 的 shape/dtype 签名
@torch.library.register_fake("mylib::my_op")
def _(x):
    return torch.empty_like(x)
```

## torch.compile 全链路源码级架构（来自 `06_architecture.py`）

以 `fn(x) = sigmoid(relu(linear(x))) + 1` 为例，走通 5 个阶段。

### 整体链路概览

```
compiled_fn(x)
  |
  ├─ ① Dynamo（抓图）
  |     字节码 → VariableTracker 符号执行 → FX Graph
  |
  ├─ ② AOTAutograd（autograd 提前追踪）
  |     functionalization → joint graph → min-cut 切分前向/反向
  |
  ├─ ③ Inductor（编译）
  |     lowering → scheduler + fusion → codegen (Triton/C++)
  |
  ├─ ④ Triton 编译
  |     Python → TTIR → TTGIR → LLVM IR → PTX → .cubin
  |
  └─ ⑤ 执行
        guard check → kernel.launch()
```

---

### 阶段 ① Dynamo：字节码拦截 -> FX Graph

**Dynamo 看到的第一手材料是 CPython 字节码，不是 Python 源码。**

原理：PEP 523（Python 3.6+）允许替换帧评估函数，Dynamo 通过 `_PyInterpreterState_SetEvalFrameFunc` 替换掉 CPython 默认的 `ceval.c` 主循环。此后每次调用被编译函数时，CPython 进入 Dynamo 的 `eval_frame`：
- 创建 `InstructionTranslator`
- 逐条读取字节码：`dispatch_table[opcode](self, inst)`
- 符号执行 -> 构建 FX Graph

#### VariableTracker（符号世界的变量）

Dynamo 不能真正执行计算（没有真实数值），所以它用 `VariableTracker` 记录符号信息：

| Python 值 | VariableTracker | 存什么（符号信息，无真实值） |
|-----------|-----------------|----------------------------|
| `torch.Tensor` | `TensorVariable` | `.shape=(4,8)`, `.dtype=float32`, `.device=cuda:0`，**无 `.data`** |
| `torch.relu` | `UserFunctionVariable` | `.target=torch.relu` |
| `42, 3.14, "hello"` | `ConstantVariable` | 真实值（常量不需要符号） |
| `nn.Linear(8,16)` | `UnspecializedNNModuleVariable` | parameters: `{weight:(16,8), bias:(16,)}` |

**关键代码路径**（`TensorVariable` 调用 `torch.relu` 时发生了什么）：

```
1. UserFunctionVariable.call_function(tx, [TensorVariable], {})
2. -> 检查 target 是否 PyTorch 函数
3. -> tx.output.create_proxy("call_function", target, args)
4. -> 在 FX Graph 创建: Node(name="relu", op="call_function", target=relu)
5. -> 返回新 TensorVariable，指向这个 Node
```

这就是 Dynamo 的核心魔法：**用一个 VariableTracker 调用函数，返回一个新的 VariableTracker，同时图上多一个 Node。forward 跑完，图也就建好了。**

#### Guards（守卫条件）

编译后附带的一组检查条件。每次调用 `compiled_fn(x)` 时：
1. 跑 guards check
2. 通过 -> 直接执行编译后的 kernel（不再编译）
3. 不通过 -> 重新编译（recompile）

五种 Guard 类型：

| 类型 | 检查内容 | 示例 |
|------|----------|------|
| `TENSOR_MATCH` | shape/dtype/device | `x.shape == (4, 8)` |
| `TYPE_MATCH` | isinstance 检查 | `type(x) == Tensor` |
| `ID_MATCH` | 对象 id 没变 | `id(torch.relu) == 0x7f...` |
| `GLOBAL_STATE` | grad_mode / default_device | `torch.is_grad_enabled()` |
| `MODULE_MATCH` | 模块类引用没变 | `type(model.fc) == Linear` |

关键源码位置：
- `torch/_dynamo/symbolic_convert.py` - `InstructionTranslator` 核心类
- `torch/_dynamo/variables/base.py` - `VariableTracker` 基类（L320），`call_function()`（L677）
- `torch/_dynamo/variables/tensor.py` - `TensorVariable`（L180）
- `torch/_dynamo/variables/builder.py` - `wrap_fx_proxy()`（L3593），在 Graph 创建 Node 并返回 VT
- `torch/_dynamo/guards.py` - `GuardBuilder`（L1219），`compile_check_fn()`（L4827）

---

### 阶段 ② AOTAutograd：提前追踪 autograd 反向

Dynamo 输出的 FX Graph 只有前向计算。训练时需要反向传播，AOTAutograd 负责**提前（Ahead-Of-Time）**追踪出来。

三个子步骤：

**1. Functionalization（in-place -> 纯函数）**
```
x.relu_()   ->  y = torch.relu(x)
x.add_(1)   ->  y = x + 1
```
原因：纯函数图更容易分析、融合、优化。编译器不喜欢有副作用的操作。

**2. 构建 Joint Graph（前向 + 反向合一）**
```
前向: y = sin(cos(x))
反向: grad_x = d(sin)/d(cos) * d(cos)/dx = cos(cos(x)) * (-sin(x))
```
用 `torch.autograd.grad` 或 `functorch.vjp` 追踪反向计算，和前向拼成一张完整的 Joint Graph。

**3. Partitioner（min-cut 切分）**

把 Joint Graph 切分成两张独立图：
- **forward graph**：input -> output + 反向需要的中间结果（存下来叫 saved tensors）
- **backward graph**：grad_output + saved tensors -> grad_input

目标：**最小化需要保存给反向的 tensor 总显存**——这是 min-cut 算法的核心。一个大模型的中间激活可能比参数还大，不省这一步显存会炸。

关键源码位置：
- `torch/_functorch/aot_autograd.py` - `aot_module_simplified()`（L1132）入口
- `torch/_subclasses/functional_tensor.py` - `FunctionalTensor`（L120）函数化包装
- `torch/_functorch/partitioners.py` - `min_cut_rematerialization_partition()`（L3725）min-cut 算法

**推理时**（`with torch.no_grad()`）跳过此阶段，直接进入 Inductor。

---

### 阶段 ③ Inductor：FX Graph -> 编译后的 kernel

三个子步骤：

**1. Lowering（aten ops -> Inductor IR）**

对 FX Graph 中每个 aten 节点做映射：
```
aten.linear   -> ExternKernel(addmm)   调用 cuBLAS
aten.relu     -> Pointwise             逐元素操作
aten.sigmoid  -> Pointwise             逐元素操作
aten.add      -> Pointwise             逐元素操作
```

**2. Scheduler + Fusion（算子融合）**

BFS 遍历 IR 依赖图，判断哪些算子可以合并：
- **连续 pointwise** -> 融合成一个 kernel（relu + sigmoid + add 合三为一）
- **matmul + pointwise** -> epilogue fusion（Triton 支持）
- **matmul + matmul** -> 不融合（两个 cuBLAS 调用各自跑）

本例的结果：`relu + sigmoid + add` 融合成一个 kernel，`linear(matmul)` 单独一个 kernel。

**3. Codegen（Inductor IR -> Triton/C++ 源码）**

GPU 端（Triton）生成的代码大致如下：
```python
@triton.jit
def fused_add_relu_sigmoid_kernel(in_ptr, out_ptr, ...):
    x = tl.load(in_ptr + offsets)
    x = tl.where(x > 0, x, 0)       # relu
    x = 1.0 / (1.0 + tl.exp(-x))    # sigmoid
    x = x + 1.0                     # add
    tl.store(out_ptr + offsets, x)
```

CPU 端（C++）生成向量化代码，原理类似。

关键源码位置：
- `torch/_inductor/lowering.py` - `register_lowering()`（L535）注册 aten -> IR 映射
- `torch/_inductor/ir.py` - `Pointwise`（L1173）, `Reduction`（L1337）, `Buffer`（L5087）, `ExternKernel`（L6878）
- `torch/_inductor/scheduler.py` - `Scheduler`（L4129）, `fuse()`（L2674）
- `torch/_inductor/codegen/triton.py` - `TritonKernel`（L3131）, `codegen_body()`（L5903）
- `torch/_inductor/codegen/cpp.py` - `CppKernel`（L2081）

---

### 阶段 ④⑤ Triton 编译 + 执行

**阶段 ④ Triton 编译管线：**

```
@triton.jit Python 代码
  -> Triton IR (TTIR)        通用 MLIR-like IR
  -> Triton GPU IR (TTGIR)   GPU 特定优化（swizzling, pipelining）
  -> LLVM IR
  -> PTX (*.ptx)             NVIDIA 虚拟指令集
  -> .cubin                   GPU 可执行二进制

缓存目录: ~/.triton/cache/
```

**阶段 ⑤ 执行 `compiled_fn(x)`：**

```python
def compiled_fn(x):
    # 1) guard check
    if not self.guards.check(x.shape, x.dtype, x.device, ...):
        return self.recompile_and_call(x)

    # 2) (可选) CUDA Graph 包裹（mode="reduce-overhead"）
    if self.use_cuda_graph:
        return cuda_graph_exec(x)

    # 3) 直接启动 kernel
    kernel_1.launch(grid, block, stream, x, buf0, buf1)
    return buf1
```

- guard 通过 -> 直接执行 -> 后续调用都不会再编译
- guard 不通过 -> recompile -> 新 shape/dtype 产生新的编译结果
- `mode="reduce-overhead"`：把整个执行序列 capture 成 CUDA Graph，每步只 launch 1 次

## 真实模型实战手册（来自 `07_practice.py`）

### 训练场景：compile 的策略选择

训练时决定 **compile 谁** 有三种策略：

```python
# 策略 1: 只编译 forward（推荐，最稳定）
model.forward = torch.compile(model.forward, mode="default")

# 策略 2: compile 整个 model
model = torch.compile(model, mode="default")

# 策略 3: compile 整个训练步骤（最激进）
@torch.compile
def train_step(model, x, y):
    logits = model(x)
    loss = F.cross_entropy(logits, y)
    loss.backward()
    optimizer.step()
```

**推荐**：策略 1 或 2。因为：
- forward 是纯张量计算，graph break 最少
- optimizer.step() 里有 `.item()` 和 Python 标量操作，compile 了也会 graph break
- 编译范围越大，图越复杂，编译越慢，调试越难

策略 3 理论上可做到 forward + backward + optimizer 全编译（TorchTune 就是这么做的），但需要模型代码非常干净，实测 graph break 多的话反而不如策略 1。

### 与分布式训练（DDP/FSDP）的交互

```python
# 标准模式: FSDP 在外面，compile 在里面
model = FSDP(MyModel())           # FSDP 包装模型
model.forward = torch.compile(model.forward)  # compile 只包 forward

for x, y in dataloader:
    loss = model(x, y)            # forward 被 compile 加速
    loss.backward()               # 通信在 backward 中自动触发
    optimizer.step()
```

**关键原则**：compile 只包 `forward`，分布式通信（all-reduce、all-gather）由 FSDP 的 backward hook 自动管理，两者互不干扰。

### 动态 Shape 深入

#### 问题场景

```python
# 不做任何处理，每个不同 batch size 都会触发一次重编译
for batch in [4, 8, 16, 32]:
    x = torch.randn(batch, 128, device="cuda")
    compiled_model(x)  # B=4: 编译, B=8: recompile, B=16: recompile...
```

#### 解决方案对比

| 方法 | 写法 | 适用场景 | 代价 |
|------|------|----------|------|
| `dynamic=True` | `torch.compile(m, dynamic=True)` | 多个维度可能变化 | 编译产物略慢（无法做 hard-coded shape 优化） |
| `mark_dynamic` | `torch._dynamo.mark_dynamic(x, 0)` | 仅 batch 维度变 | 精度更高，其他维度仍可优化 |
| padding + 固定 shape | `x = pad_to_256(x)` | 推理服务，可接受 padding | 零代价但浪费少量显存 |
| 每个 shape 各编译一次 | 默认行为 | shape 种类少且固定 | 缓存命中时零开销，但缓存多了占内存 |

#### mark_dynamic 的精细控制

```python
# 第 0 维(batch)动态，其他维度固定
torch._dynamo.mark_dynamic(x, 0)

# 序列长度也动态（可变长输入）
torch._dynamo.mark_dynamic(x, 0)  # B
torch._dynamo.mark_dynamic(x, 1)  # T

# 同时标记多个 tensor
torch._dynamo.mark_dynamic(x, 0)
torch._dynamo.mark_dynamic(loss, 0)
```

### 精度验证

```python
# 上线前必做: 对比 eager 和 compile 的数值精度
model = MyModel().cuda().eval()
x = torch.randn(4, 128, device="cuda")

with torch.no_grad():
    out_eager = model(x)
    out_compiled = torch.compile(model)(x)

diff = (out_eager - out_compiled).abs().max().item()
print(f"max abs diff: {diff}")  # 期望 < 1e-3

# 如果 diff 过大:
#   → backend="aot_eager" 先排除 Inductor 融合的问题
#   → 用 TORCH_LOGS="output_code" 看具体哪个 kernel 的数值异常
#   → 常见原因: 融合改变了计算顺序 (a+(b+c) vs (a+b)+c 浮点精度不同)
```

### 性能 Benchmark 的标准流程

```python
import time

def benchmark(fn, args=(), warmup=5, repeat=30):
    for _ in range(warmup):
        fn(*args)
    torch.cuda.synchronize()

    t0 = time.perf_counter()
    for _ in range(repeat):
        fn(*args)
    torch.cuda.synchronize()
    return (time.perf_counter() - t0) / repeat * 1000  # ms

# 使用
model = MyModel().cuda()
x = torch.randn(32, 128, device="cuda")

eager_ms = benchmark(lambda: model(x))                 # baseline
compiled_ms = benchmark(lambda: torch.compile(model)(x))  # compile
print(f"speedup: {eager_ms / compiled_ms:.1f}x")
```

**注意**：warmup 轮数要足够，第一次调用 compile 会触发编译（可能几秒到几分钟），warmup 后的 repeat 才是真实推理/训练速度。
