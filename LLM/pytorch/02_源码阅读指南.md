# 源码阅读指南

> 追一次真实调用链胜过通读。以下 19 节按「从 Python 到 kernel」组织。

随着我越来越多地使用 torchtitan，有时调用的内核并非我预期的那样。我意识到我需要学习性能分析，并至少对如何端到端追踪一个运算有中等程度的理解。（这也是你是否能深入理解 PyTorch 的一个重要信号）

PyTorch 是一个庞大的库，所以直接克隆然后逐行阅读代码基本行不通。更靠谱的方式是：先建立地图，再选择一个足够复杂但不至于爆炸的算子，沿着调用链走完一遍。

本文使用的源码目录：

```bash
/home/ghr/code/pytorch
```

读 PyTorch 源码时，请始终牢记这几层：

- **Python 前端**：`torch`、`torch.nn`、`torch.nn.functional`、`torch.Tensor` 这些用户直接接触的 API。
- **Python/C++ 绑定层**：`torch/csrc/`，负责把 Python 对象、`Tensor`、`Storage`、autograd 对象接到 C++。
- **Dispatcher**：根据 operator schema、dispatch key、tensor device/layout/dtype/autograd 等信息，决定实际调用哪个 kernel。
- **ATen / c10 后端**：`aten/` 和 `c10/`。ATen 放张量运算、native kernels、BLAS/cuDNN/cuBLAS 调用；c10 放基础设施，比如 `TensorImpl`、`StorageImpl`、`DispatchKey`、`Device`、`ScalarType`。
- **Autograd**：自动微分公式、生成代码和手写 backward。
- **Compiler stack**：`torch.compile` 相关的 Dynamo、FX、AOTAutograd、Inductor、Triton codegen。

不要试图把这几层一次性读完。PyTorch 的源码阅读更像调试一个真实请求：从一个 Python 调用开始，问它“下一跳是谁”。

### 一个实用的源码定位 playbook

当你看到一个 profiler 里的 op，例如 `aten::addmm`、`aten::_scaled_dot_product_flash_attention`、`triton_poi_fused_*`，不要急着搜整仓库。按这个顺序定位会快很多：

1. **确认 Python API 名和 ATen op 名是否一致。**

   ```python
   import torch
   print(torch.ops.aten.mm.default)
   print(torch.ops.aten.addmm.default)
   print(torch.ops.aten.linear.default)
   ```

   很多 Python API 会绕到不同的 ATen op：`nn.Linear` 常常落到 `aten::linear`，`linear` 内部又可能走 `addmm` 或 `matmul`。

2. **在 `native_functions.yaml` 里找 schema。**

   ```bash
   rg -n "func: addmm|func: linear|func: scaled_dot_product_attention" aten/src/ATen/native/native_functions.yaml
   ```

   这里能看到它是 `CompositeImplicitAutograd`，还是直接有 `CPU` / `CUDA` kernel。

3. **找 C++ 实现函数。**

   如果 YAML 写的是 `CUDA: mm_out_cuda`，就搜：

   ```bash
   rg -n "mm_out_cuda|addmm_out_cuda|_scaled_grouped_mm_cuda" aten/src/ATen
   ```

4. **如果搜不到，去 build/generated 里找。**

   常见生成文件位置：

   ```text
   build/aten/src/ATen/RegisterCPU.cpp
   build/aten/src/ATen/RegisterCUDA.cpp
   build/aten/src/ATen/RegisterCompositeImplicitAutograd.cpp
   torch/csrc/autograd/generated/
   ```

5. **最后用 runtime 验证。**

   ```python
   import torch
   print(torch._C._dispatch_dump_table("aten::addmm"))
   ```

   静态源码告诉你“可能走哪里”，runtime table 告诉你“当前 build 里注册了什么”。

## 1. Python 前端：从 `nn.Module` 读起

如果你关心模型执行，建议从 `Module.__call__` 开始，而不是从某个 kernel 开始。

入口文件：

```text
torch/nn/modules/module.py
```

关键点：

- `Module.__call__` 实际绑定到 `_wrapped_call_impl`。
- `_wrapped_call_impl` 如果模块已经 compile，则走 `_compiled_call_impl`。
- 否则进入 `_call_impl`。
- `_call_impl` 处理 hook、tracing state、forward pre/post hook、backward hook，最后调用 `forward`。

源码位置：

```text
torch/nn/modules/module.py
  class Module
  _wrapped_call_impl
  _call_impl
```

读 `nn.Linear` 是很好的第一站：

```text
torch/nn/modules/linear.py
  class Linear(Module)
  def forward(self, input):
      return F.linear(input, self.weight, self.bias)
```

然后继续看：

```text
torch/nn/functional.py
  linear = torch._C._nn.linear
```

这里会让你看到一个很重要的事实：很多 Python API 只是薄薄的一层，真正的 operator 已经注册到了 C++ dispatcher 里。

## 2. Operator 定义：`native_functions.yaml`

绝大部分 ATen operator 都从这个文件开始：

```text
aten/src/ATen/native/native_functions.yaml
```

它定义：

- operator schema：名字、参数、返回值、alias/mutation 信息。
- Python 暴露形式：function / method / module。
- dispatch key 到具体实现函数的映射。
- structured kernel、out variant、autogen 等 codegen 信息。

例如 `linear`：

```yaml
- func: linear(Tensor input, Tensor weight, Tensor? bias=None) -> Tensor
  python_module: nn
  dispatch:
    CompositeImplicitAutograd: linear
    NestedTensorCPU, NestedTensorHPU, NestedTensorCUDA, NestedTensorXPU: nested_linear
    MPS: _mps_linear
```

这说明普通 `linear` 不是直接指定 `CPU: xxx` / `CUDA: xxx`，而是一个 composite op。你需要继续在 ATen 里找 `linear` 的 C++ 实现，它会再调用 `matmul` / `addmm` 等更基础的 op。

再看 `mm`：

```yaml
- func: mm(Tensor self, Tensor mat2) -> Tensor
  structured_delegate: mm.out
  variants: function, method
  dispatch:
    SparseCPU, SparseCUDA, SparseMPS, SparseXPU: _sparse_mm
    SparseCsrCPU, SparseCsrCUDA, SparseCsrMeta, SparseCsrXPU: _sparse_csr_mm
  tags: core

- func: mm.out(Tensor self, Tensor mat2, *, Tensor(a!) out) -> Tensor(a!)
  structured: True
  dispatch:
    CPU: mm_out_cpu
    CUDA: mm_out_cuda
    MPS: mm_out_mps
```

这里更接近“真实 kernel”：dense CPU/CUDA 路径会落到 `mm_out_cpu` / `mm_out_cuda`。

读 YAML 时尤其注意这些字段：

- `func`：operator schema，是 dispatcher、Python binding、autograd 都要对齐的契约。
- `variants`：是否生成 `torch.foo(x)` 和 `x.foo()` 两种形式。
- `dispatch`：dispatch key 到 kernel function 的映射。
- `CompositeImplicitAutograd`：由其他 ATen ops 组合出来，autograd 可以通过内部 op 自动得到。
- `CompositeExplicitAutograd`：也由其他 ops 组合，但需要显式 autograd 处理。
- `structured` / `structured_delegate`：structured kernel 体系，常见于带 `out=` 的算子。
- `autogen`：自动生成 out variant 或 backward variant。

### schema 名字和后缀怎么看

PyTorch operator 名经常带后缀，不理解这些后缀会很容易读串：

```text
add.Tensor        overload name，不同参数签名的同名 op
add.Scalar        另一个 overload
add.out           out= variant，结果写入用户传入的 Tensor
add_              inplace variant，会修改 self
mm.dtype          带 dtype 参数的 overload
```

YAML 里的 alias 标注也很重要：

```yaml
Tensor(a!) self
Tensor(a!) out -> Tensor(a!)
```

可以粗略理解为：

- `Tensor(a)`：这个 tensor 属于 alias set `a`，可能和同一 set 的 tensor 共享 storage。
- `Tensor(a!)`：会写入 alias set `a`，也就是有 mutation。
- `out` 参数通常带 `Tensor(a!)`，因为它会被写入。

这些标注不是注释，而是 codegen、functionalization、autograd correctness 都依赖的契约。读 view / inplace / out 相关 bug 时，先看 alias annotation。

### structured kernel 怎么读

看到：

```yaml
structured: True
structured_delegate: mm.out
```

通常表示 PyTorch 把 shape/dtype/device 检查、输出 tensor resize、真正 kernel 执行拆开了。读这类 op 时要找：

- `meta` 函数：推导输出 shape、stride、dtype。
- `impl` 函数：真正执行计算。
- `out` variant：structured kernel 的主实现常常在这里。

这也是为什么有时 `mm` 的实现不在 `mm`，而在 `mm.out` 对应的 `mm_out_cpu` / `mm_out_cuda`。

## 3. Codegen：为什么你搜不到某些函数

PyTorch 很多 C++ 文件不是手写的，而是由 `torchgen` 和 autograd codegen 生成的。所以你经常会遇到：

- YAML 里有 `func: xxx`，但源码里没有直观的 Python binding。
- 调用栈里出现 `VariableType`、`RegisterCPU.cpp`、`RegisterCUDA.cpp`、`Functions.cpp`，但仓库源码里找不到同名文件。
- gdb 看到的函数来自 `build/aten/src/ATen/...` 或 `torch/csrc/autograd/generated/...`。

ATen codegen 主入口：

```text
torchgen/gen.py
```

这个文件会解析：

```text
aten/src/ATen/native/native_functions.yaml
aten/src/ATen/native/tags.yaml
```

然后生成 dispatcher 注册、C++ API、Python binding 需要的一批文件。

Autograd codegen 主入口：

```text
tools/autograd/gen_autograd.py
tools/autograd/derivatives.yaml
```

如果你要真正调试 C++ 调用栈，建议编译 debug 版本，并保留 `build/` 目录。否则很多生成文件很难跳转。

## 4. Dispatcher：一次调用如何找到 kernel

Dispatcher 的核心问题是：同一个 operator，例如 `aten::mm`，根据输入 tensor 的状态，应该调用哪个实现？

影响 dispatch 的信息包括：

- device：CPU / CUDA / MPS / XPU
- layout：dense / sparse / mkldnn / nested tensor
- dtype：float / half / bfloat16 / quantized
- autograd：是否需要梯度
- tensor subclass / Python mode / functionalization / autocast 等 wrapper key

核心概念：

```text
c10/core/DispatchKey.h
c10/core/DispatchKeySet.h
aten/src/ATen/core/dispatch/
```

阅读顺序建议：

1. 先读 `native_functions.yaml` 中目标 op 的 dispatch 表。
2. 再找 `torchgen` 生成的注册文件，通常在 build 目录里，例如 `RegisterCPU.cpp`、`RegisterCUDA.cpp`、`RegisterCompositeImplicitAutograd.cpp`。
3. 再看手写 kernel，例如 `aten/src/ATen/native/LinearAlgebra.cpp` 或 `aten/src/ATen/native/cuda/Blas.cpp`。

如果你只读源码仓库，不看 build 生成文件，会少一大块拼图。

### wrapper key：为什么你以为会走 CUDA，实际先走了别的层

Dispatcher 不只是 `CPU` / `CUDA` 二选一。很多 key 是 wrapper key，会先截获调用，再 redispatch 到后面的 key：

```text
Python / PythonDispatcher     Tensor subclass、FakeTensor、Python mode 等
Functionalize                 把 mutation / view 转成更函数式的形式
AutogradCUDA / AutogradCPU    autograd wrapper
AutocastCUDA / AutocastCPU    AMP autocast wrapper
BackendSelect                 某些没有 tensor 参数或需要按 device 选择的 factory op
CUDA / CPU                    真正后端 kernel
CompositeImplicitAutograd     composite fallback
```

所以一个 CUDA tensor 的调用链可能是：

```text
aten::mm
  -> AutocastCUDA wrapper
  -> AutogradCUDA wrapper
  -> CUDA kernel
```

也可能在 `torch.compile` / FakeTensor 场景里先经过：

```text
PythonDispatcher / Python / Functionalize
```

相关源码：

```text
c10/core/DispatchKey.h
c10/core/DispatchKeySet.h
aten/src/ATen/core/dispatch/
```

如果 profiler 或栈里出现 `AutocastCUDA`、`Functionalize`、`PythonDispatcher`，不要把它们当成真正数学 kernel。它们通常是在改 dtype、处理 subclass、记录 autograd、去 mutation，最后还会 redispatch。

## 5. ATen：数学运算真正发生的地方

ATen 的核心目录：

```text
aten/src/ATen/native/
aten/src/ATen/native/cuda/
aten/src/ATen/native/cpu/
```

以 `matmul` 为例：

```text
aten/src/ATen/native/native_functions.yaml
  func: matmul
  dispatch:
    CompositeImplicitAutograd: matmul

aten/src/ATen/native/LinearAlgebra.cpp
  static Tensor _matmul_impl(...)
  Tensor matmul(...)
  Tensor& matmul_out(...)
```

`matmul` 本身是 composite，它会根据维度选择更基础的 op：

- 1D @ 1D -> `dot`
- 2D @ 1D -> `mv`
- 1D @ 2D -> `mm` 后 squeeze
- 2D @ 2D -> `mm`
- batch matmul -> `bmm`
- 某些高维情况会 fold 成 `mm`，减少 `bmm` 的开销

所以你以为自己调用的是 `matmul`，最后可能实际走的是 `mm_out_cuda`、`bmm_out_cuda` 或其他路径。

这也是性能分析里最常见的困惑来源：Python API 名称和最终 kernel 名称不一定一样。

## 6. CUDA kernel：从 ATen 到 cuBLAS / 自定义 kernel

以 GEMM 为例，继续往下追：

```text
aten/src/ATen/native/native_functions.yaml
  mm.out -> CUDA: mm_out_cuda

aten/src/ATen/native/cuda/Blas.cpp
  mm_out_cuda
  addmm_out_cuda
  bmm_out_cuda
```

这些函数通常不会自己手写完整矩阵乘法，而是调用：

```text
at::cuda::blas::gemm
at::cuda::blas::bgemm
cublas / cublasLt
```

对于新一点的低精度或 fused 路径，还会看到更专门的文件，例如：

```text
aten/src/ATen/native/cuda/ScaledBlas.cpp
aten/src/ATen/native/cuda/GroupedBlas.cpp
aten/src/ATen/native/cuda/ScaledGroupMM.cu
aten/src/ATen/native/cuda/GroupMM.cu
```

比如 `_scaled_grouped_mm`：

```yaml
- func: _scaled_grouped_mm(...) -> Tensor
  dispatch:
    CUDA: _scaled_grouped_mm_cuda
```

对应实现：

```text
aten/src/ATen/native/cuda/GroupedBlas.cpp
  _scaled_grouped_mm_cuda
  _scaled_grouped_mm_cuda_v2
```

如果你在 torchtitan / MoE / FP8 路径里看到 grouped GEMM 或 scaled GEMM，优先查这些文件。

### AMP / autocast：为什么 dtype 和你传入的不一样

AMP 的 Python 入口在：

```text
torch/amp/autocast_mode.py
torch/cuda/amp/autocast_mode.py
```

C++ dispatcher 注册在：

```text
aten/src/ATen/autocast_mode.cpp
```

这里会注册 `AutocastCUDA` / `AutocastCPU` 等 wrapper kernel。autocast 的工作不是“全局把模型变成 half”，而是按 op policy 选择输入 cast 规则。例如 GEMM 类 op 通常适合低精度，某些 loss / reduction / numerically sensitive op 会保留 fp32 或提升到更宽类型。

如果你发现：

- 输入是 fp32，但 profiler 里 cuBLAS 走了 fp16/bf16。
- 某个 op 在 AMP 下没有用你预期的 dtype。
- weight cast 好像被缓存了。

优先读：

```text
aten/src/ATen/autocast_mode.cpp
  cached_cast
  TORCH_LIBRARY_IMPL(aten, Autocast, ...)
  TORCH_LIBRARY_IMPL(aten, AutocastCUDA, ...)
```

然后再看你关心的 op 是否有 autocast policy。

## 7. Autograd：反向公式在哪里

Autograd 的公式主要在：

```text
tools/autograd/derivatives.yaml
```

例如：

```yaml
- name: matmul(Tensor self, Tensor other) -> Tensor
  self, other: matmul_backward(grad, self, other, grad_input_mask)

- name: mm(Tensor self, Tensor mat2) -> Tensor
  self: mm_mat1_backward(grad, mat2, self.sym_sizes(), self.sym_strides(), self.layout(), 1)
  mat2: mm_mat2_backward(grad, self, mat2.sym_sizes(), mat2.sym_strides(), mat2.layout(), 1)

- name: linear(Tensor input, Tensor weight, Tensor? bias=None) -> Tensor
  input, weight, bias: "grad.defined() ? linear_backward(input, grad, weight, grad_input_mask) : std::tuple<Tensor, Tensor, Tensor>()"
```

手写的 backward helper 常见于：

```text
torch/csrc/autograd/FunctionsManual.cpp
torch/csrc/autograd/FunctionsManual.h
aten/src/ATen/native/*Backward*.cpp
```

读 backward 时要分清三类东西：

- `derivatives.yaml`：声明反向公式。
- generated autograd C++：真正接入 autograd engine 的 wrapper。
- 手写 helper：复杂公式放这里，YAML 里只引用函数名。

Autograd engine 本身在：

```text
torch/csrc/autograd/engine.cpp
torch/csrc/autograd/function.h
torch/csrc/autograd/variable.h
torch/csrc/autograd/python_engine.cpp
```

如果你只是想知道某个 op 的梯度怎么写，先读 `derivatives.yaml`。如果你想知道 backward graph 如何调度执行，再读 `engine.cpp`。

### forward-mode / double backward 不要一开始就追

`derivatives.yaml` 里除了普通 backward，还可能出现：

```text
result:
self_t / self_p
auto_linear
```

这里的 `_t` / `_p` 和 forward-mode AD、双反相关，第一次读可以先跳过。先搞清楚 `grad -> input grad` 的主公式，再回来读 JVP / double backward。否则很容易在 autograd 的生成代码里迷路。

## 8. Tensor / Storage / TensorImpl：张量到底是什么

Python 里看到的 `torch.Tensor` 只是壳。底层重点是：

```text
c10/core/TensorImpl.h
c10/core/StorageImpl.h
aten/src/ATen/core/Tensor.h
aten/src/ATen/core/TensorBody.h
```

可以先建立这个心智模型：

```text
Python torch.Tensor
  -> at::Tensor
      -> c10::intrusive_ptr<TensorImpl>
          -> StorageImpl
          -> sizes / strides / storage_offset
          -> dtype / device / layout
          -> DispatchKeySet
```

很多性能问题都和这里有关：

- view 是否复制
- contiguous 为什么触发拷贝
- stride 是否适合 kernel
- `expand` 为什么可能是 0 stride
- tensor 的 dispatch key 为什么多了 AutogradCUDA / Functionalize / Python

## 9. `torch.compile`：Dynamo -> FX -> AOTAutograd -> Inductor

`torch.compile` 的主线可以理解为：

```text
Python function / nn.Module
  -> TorchDynamo 捕获 Python bytecode
  -> FX Graph
  -> AOTAutograd 切分 forward/backward
  -> decomposition / functionalization
  -> Inductor scheduler
  -> Triton / C++ codegen
  -> 编译运行
```

主要目录：

```text
torch/_dynamo/
  eval_frame.py               compile 入口附近
  symbolic_convert.py         Python bytecode 到 FX graph
  guards.py                   guard 生成
  variables/                  Dynamo 对 Python 对象的抽象

torch/fx/
  graph.py
  graph_module.py
  proxy.py

torch/_functorch/
  aot_autograd.py             AOTAutograd 主线

torch/_inductor/
  compile_fx.py               FX graph 进入 Inductor
  graph.py                    Inductor IR
  scheduler.py                调度
  codegen/triton.py           Triton codegen
  codegen/cpp.py              C++ codegen

torch/_decomp/
  decompositions.py           op decomposition
```

调试建议：

```bash
TORCH_LOGS="+dynamo,+inductor" python your_model.py
TORCHDYNAMO_VERBOSE=1 python your_model.py
TORCH_COMPILE_DEBUG=1 python your_model.py
```

常见问题入口：

- 为什么 graph break：看 `torch/_dynamo/` 和 `TORCH_LOGS="+dynamo"`。
- 为什么没融合：看 `torch/_inductor/scheduler.py`、生成的 debug dump。
- 为什么某个 op 被分解：看 `torch/_decomp/decompositions.py`。
- 为什么动态 shape 变复杂：看 `torch/fx/experimental/symbolic_shapes.py`。

## 10. 推荐的第一条完整路线：追 `nn.Linear`

这是最适合作为第一条端到端路线的 op：

```text
model(x)
  -> torch/nn/modules/module.py
     Module.__call__ -> _wrapped_call_impl -> _call_impl -> forward

  -> torch/nn/modules/linear.py
     Linear.forward -> F.linear(input, weight, bias)

  -> torch/nn/functional.py
     F.linear -> torch._C._nn.linear

  -> aten/src/ATen/native/native_functions.yaml
     func: linear
     CompositeImplicitAutograd: linear

  -> aten/src/ATen/native/Linear.cpp
     linear / linear_out / linear_backward

  -> aten/src/ATen/native/native_functions.yaml
     addmm / matmul / mm

  -> aten/src/ATen/native/LinearAlgebra.cpp
     matmul / addmm CPU composite logic

  -> aten/src/ATen/native/cuda/Blas.cpp
     mm_out_cuda / addmm_out_cuda

  -> tools/autograd/derivatives.yaml
     linear backward formula
```

读完这条线，你会同时接触 Python 前端、dispatcher、ATen、CUDA BLAS、autograd，是性价比最高的一条路线。

## 11. 第二条路线：追 `scaled_dot_product_attention`

如果你关心 LLM 性能，下一条建议追 attention：

```text
torch/nn/functional.py
  scaled_dot_product_attention = torch._C._nn.scaled_dot_product_attention

aten/src/ATen/native/native_functions.yaml
  func: scaled_dot_product_attention

aten/src/ATen/native/transformers/
aten/src/ATen/native/cuda/
```

这条线会涉及：

- math attention
- flash attention
- memory efficient attention
- cuDNN attention
- mask / causal / dropout / GQA 的 dispatch 条件

这条线比 `linear` 难，因为不是简单“一个 op 到一个 kernel”，而是根据设备、dtype、shape、mask、dropout、backend flags 选择不同实现。读它之前先把 `linear -> mm` 路线走熟。

## 12. 第三条路线：追 `torch.compile`

### compile 后怎么找生成代码

打开：

```bash

```


2. `ir_pre_fusion.txt`：Inductor fusion 前的 IR。
3. `ir_post_fusion.txt`：fusion 后的 IR。
4. `output_code.py`：最终调用的 Triton kernel / C++ wrapper。

## 14. 训练源码路线：从 step 到通信和 optimizer

如果目标偏训练，不要只盯 forward kernel。一个训练 step 至少包含：

```text
data -> forward -> loss -> backward -> gradient sync -> optimizer step -> checkpoint/save
```

推荐按这个顺序读源码。

### 14.1 单卡训练 step

先从最普通的 eager training loop 建立主线：

```python
with torch.autocast("cuda", dtype=torch.bfloat16):
    loss = model(x).loss

scaler.scale(loss).backward()
scaler.step(optimizer)
scaler.update()
optimizer.zero_grad(set_to_none=True)
```

对应源码入口：

```text
torch/nn/modules/module.py
  Module.__call__ / _call_impl

torch/csrc/autograd/engine.cpp
  autograd engine 如何执行 backward graph

torch/amp/autocast_mode.py
aten/src/ATen/autocast_mode.cpp
  autocast context、dtype policy、cached_cast

torch/amp/grad_scaler.py
  GradScaler、scale / unscale / step / update

torch/optim/optimizer.py
torch/optim/adam.py
torch/optim/adamw.py
  optimizer.step 的 Python 入口

aten/src/ATen/native/cuda/
  fused / foreach / capturable optimizer kernel 可能落到这里
```

读 optimizer 时要注意三条路径：

- plain Python loop：最容易读，但性能最差。
- `foreach` path：把一组 tensor 操作合并成批量调用。
- fused path：更接近单个或少数 CUDA kernel，常见于 Adam/AdamW。

如果你在 profiler 里看到很多小的 optimizer op，优先检查 optimizer 是否走了 `foreach` / fused。

### 14.2 Activation checkpoint

训练大模型时 checkpointing 很常见。入口：

```text
torch/utils/checkpoint.py
  checkpoint

torch/distributed/algorithms/_checkpoint/checkpoint_wrapper.py
torch/distributed/_composable/checkpoint_activation.py
```

核心思想是 forward 时少存激活，backward 时重算一部分 forward。读源码时重点看：

- RNG state 如何保存/恢复。
- reentrant 和 non-reentrant checkpoint 的差异。
- backward 中如何触发 recompute。
- autocast / no_grad / grad mode 如何被重新设置。

checkpoint 相关 bug 经常不是 kernel 算错，而是随机数、autocast 状态、requires_grad、graph capture 交互出了问题。

### 14.3 DDP：梯度 bucket 和通信重叠

DDP Python 入口：

```text
torch/nn/parallel/distributed.py
  class DistributedDataParallel

torch/distributed/distributed_c10d.py
  process group、collective API 的 Python 层

torch/csrc/distributed/c10d/
  ProcessGroup、Work、Reducer、NCCL/Gloo 后端

torch/csrc/distributed/c10d/reducer.cpp
torch/csrc/distributed/c10d/reducer.hpp
  DDP gradient bucket、autograd hook、allreduce 调度
```

DDP 的关键不是“backward 后统一 allreduce”这么简单。真实路径大概是：

```text
forward
  -> DDP 记录参数使用情况
backward
  -> autograd hook 在每个 param grad ready 时触发
  -> Reducer 把 grad 放入 bucket
  -> bucket ready 后启动 allreduce
  -> allreduce 和后续 backward 计算重叠
optimizer.step
```

如果你在 profiler 里看到通信没有 overlap，优先看：

- bucket size 是否太大或太小。
- 是否有 unused parameters。
- backward graph 顺序是否导致某些 bucket 很晚 ready。
- 是否使用了 comm hook。

通信 hook 入口：

```text
torch/distributed/algorithms/ddp_comm_hooks/
```

这里能看到 PowerSGD、fp16/bf16 compression、debug hook、optimizer overlap hook 等。

### 14.4 FSDP / DTensor / Tensor Parallel

FSDP 入口：

```text
torch/distributed/fsdp/fully_sharded_data_parallel.py
  class FullyShardedDataParallel

torch/distributed/fsdp/
  flatten params、shard/unshard、state dict、mixed precision、wrap policy
```

新一点的 composable FSDP / parallel API 入口：

```text
torch/distributed/_composable/fsdp/fully_shard.py
torch/distributed/tensor/
torch/distributed/tensor/parallel/
```

FSDP 的阅读重点：

- 参数何时从 shard all-gather 成 full param。
- forward/backward 后何时 reshard。
- gradient reduce-scatter 何时发生。
- mixed precision 是参数、grad、buffer 哪一类被 cast。
- state dict 是 full、sharded 还是 local。

Tensor Parallel / DTensor 的重点则是 sharding propagation：

```text
torch/distributed/tensor/_dispatch.py
torch/distributed/tensor/_sharding_prop.py
torch/distributed/tensor/_op_schema.py
torch/distributed/tensor/_ops/
```

如果你在 torchtitan 里看到 `DeviceMesh`、`DTensor`、`parallelize_module`，这部分比传统 DDP 更重要。

### 14.5 训练 checkpoint / distributed checkpoint

普通 `torch.save` 不是大模型训练 checkpoint 的全部。分布式训练常用：

```text
torch/distributed/checkpoint/
torch/distributed/_shard/checkpoint/
```

读这部分重点看：

- state_dict 如何从 FSDP/DTensor 转成可保存格式。
- rank-local shard 如何映射到 storage。
- planner 如何决定每个 rank 写什么。
- load 时如何 reshard 到当前 world size / mesh。

部署侧也会遇到 checkpoint 问题：训练保存的是 sharded state dict，而推理通常想要 consolidated 权重或某种 engine-specific 格式。

## 15. 部署源码路线：export、compile、AOTInductor、量化

部署和训练的阅读路线不同。训练关心 backward、optimizer、通信；部署更关心：

```text
capture graph -> normalize/export -> lower/compile -> package/runtime -> quantize/specialize
```

### 15.1 `torch.export`

入口：

```text
torch/export/__init__.py
torch/export/_trace.py
torch/export/exported_program.py
torch/_export/
torch/csrc/export/
```

`torch.export` 的目标是把 Python 模型捕获成更稳定、可序列化、带 shape 约束的 `ExportedProgram`。读它时重点看：

- graph capture 和 `torch.compile` / Dynamo 的关系。
- `ExportedProgram` 里保存了什么：graph、graph signature、range constraints、state dict。
- dynamic shapes 如何表示。
- mutation、view、alias 如何被 functionalization 处理。

如果部署时遇到“模型 export 不出去”，大概率是 Python control flow、data-dependent shape、unsupported op、mutation/alias 或 dynamic shape constraint 的问题。

### 15.2 Inductor 和 AOTInductor

`torch.compile` 的训练/推理即时编译入口已经在前面讲过。部署更常见的是 AOTInductor，也就是提前生成可加载的 runtime artifact。

Python 侧：

```text
torch/_inductor/
torch/_inductor/compile_fx.py
torch/_inductor/graph.py
torch/_inductor/codegen/
```

C++ runtime / package 侧：

```text
torch/csrc/inductor/aoti_runtime/
torch/csrc/inductor/aoti_runner/
torch/csrc/inductor/aoti_package/
torch/csrc/inductor/aoti_torch/
torch/csrc/inductor/cpp_wrapper/
```

读 AOTInductor 时可以按这条线：

```text
ExportedProgram / FX graph
  -> Inductor IR
  -> scheduler + fusion
  -> generated C++ / Triton / wrapper
  -> AOTI runtime interface
  -> model package loader / runner
```

如果 profiler 里看到部署后的 kernel 已经不是 `aten::xxx`，而是生成的 C++ wrapper 或 Triton kernel，就要去 AOTI 生成物和 `torch/csrc/inductor` 看。

### 15.3 Quantization / PTQ / QAT

PyTorch 量化相关代码有几代 API，读的时候先区分你用的是哪条路径：

```text
torch/ao/quantization/
torch/ao/quantization/quantize.py
torch/ao/quantization/quantize_fx.py
torch/ao/quantization/fake_quantize.py
torch/ao/quantization/observer.py

torch/_inductor/fx_passes/quantization.py
torch/_inductor/quantized_lowerings.py

aten/src/ATen/native/quantized/
```

常见部署量化路线：

```text
PTQ:
  prepare -> calibration -> convert

QAT:
  prepare_qat -> train with fake quant -> convert

compile/inductor quant:
  graph rewrite -> quantized lowering -> backend-specific kernel
```

读量化时要抓住这几个对象：

- observer：统计 min/max/histogram，决定 scale / zero_point。
- fake quant：训练时模拟量化误差，但 tensor 仍多半是 float。
- quant/dequant node：图里显式的量化边界。
- packed weight：部署时 weight 常常会预打包到后端喜欢的 layout。
- quantized op：例如 `quantized::linear`、`quantized::conv2d`。

LLM 里还会遇到 weight-only、int8、int4、FP8、group-wise scaling，这些不一定都走传统 `torch.ao.quantization` API，可能落在 Inductor lowering、自定义 op、Triton kernel、CUTLASS/cuBLASLt 或项目自己的 extension 里。

### 15.4 部署问题的定位顺序

部署 bug 或性能问题建议按这个顺序定位：

1. **模型是否成功 capture/export。**
   看 `torch.export` / Dynamo graph break / dynamic shape constraint。

2. **图是否被正确 normalize。**
   看 decomposition、functionalization、fake tensor/meta kernel。

3. **关键 op 是否被 lower 到目标 backend。**
   看 Inductor lowering、quantized lowering、AOTI generated code。

4. **runtime 是否有 fallback。**
   如果部署后仍看到大量 `aten::` eager op，说明没有完全 lowering 或发生 graph break/fallback。

5. **shape 是否稳定。**
   动态 shape 会影响 specialization、kernel cache、fusion 和 memory planning。

6. **权重格式是否部署友好。**
   比如 packed weight、channels-last、int4/int8 group size、scale layout。

### 15.5 推理 runtime：`inference_mode`、CUDA Graph、动态 shape

部署推理时，性能瓶颈不一定在单个 op，也可能在 runtime overhead：

```text
Python dispatch overhead
autograd metadata overhead
allocator overhead
dynamic shape recompilation
CUDA launch overhead
KV cache layout / update overhead
fallback 到 eager
```

相关入口：

```text
torch/autograd/grad_mode.py
c10/core/InferenceMode.h
c10/core/InferenceMode.cpp
  no_grad / inference_mode 相关状态

torch/cuda/graphs.py
aten/src/ATen/cuda/CUDAGraph.h
c10/cuda/CUDAGraphsC10Utils.h
  CUDA Graph capture / replay

torch/_inductor/cudagraph_trees.py
torch/_inductor/cudagraph_utils.py
torch/_inductor/memory.py
  Inductor 侧 cudagraph 和 memory planning

torch/nested/
torch/nested/_internal/sdpa.py
  nested tensor / variable length attention / KV-cache 相关表示
```

推理部署里几个常见判断：

- `torch.no_grad()` 只是关 autograd 记录；`torch.inference_mode()` 还会进一步减少 autograd/view metadata 开销，但对需要 mutation/view tracking 的代码更严格。
- CUDA Graph 适合 shape 和 memory 地址比较稳定的场景；动态 batch/seq length 会让 capture/replay 变复杂。
- LLM decode 的 batch 和 sequence length 经常变化，KV cache layout、paged attention、varlen attention 会比单个 GEMM 更影响端到端吞吐。
- Inductor 生成代码如果频繁 recompile，优先查 dynamic shape guard 和 cache key。

## 18. 常见误区

- **误区 1：`torch.matmul` 一定对应一个 matmul kernel。**  
  不一定。它可能分解到 `dot`、`mv`、`mm`、`bmm`，高维情况下还可能 fold。

- **误区 2：YAML 里写 `CompositeImplicitAutograd` 就没有后端 kernel。**  
  composite op 本身没有直接后端 kernel，但它调用的内部 op 可能有 CPU/CUDA kernel。

- **误区 3：搜不到函数就是没有源码。**  
  很可能在 build 目录的 generated files 里。

- **误区 4：Python profiler 看到的 op 名就是 CUDA kernel 名。**  
  PyTorch op、cuBLAS 调用、Triton kernel、CUDA kernel name 是不同层次的名字。

- **误区 5：`torch.compile` 后还能按 eager 的路径理解所有执行。**  
  compile 后可能发生 decomposition、fusion、layout planning、Triton codegen，最终 kernel 不再对应单个 eager op。

- **误区 6：CUDA tensor 就一定直接 dispatch 到 CUDA key。**  
  不一定。Autograd、Autocast、Functionalize、PythonDispatcher 都可能先截获，再 redispatch。

- **误区 7：AMP 只是把所有东西 cast 到 fp16/bf16。**  
  不对。autocast 是按 op policy 选择 dtype，有缓存、有黑白名单/策略，也有 device-specific 行为。

- **误区 8：训练性能只看 forward kernel。**  
  大模型训练经常瓶颈在 backward、通信 overlap、optimizer、checkpoint recompute、memory allocator，而不是单个 forward GEMM。

- **误区 9：部署就是 `torch.compile` 一下。**  
  真正部署还要考虑 export 稳定性、shape 约束、AOT runtime、fallback、量化、权重格式和目标平台 runtime。
