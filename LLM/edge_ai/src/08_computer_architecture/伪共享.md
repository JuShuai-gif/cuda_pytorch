# 伪共享（False Sharing）详解

# 1. 什么是伪共享

伪共享（False Sharing）是多线程并发编程中的经典性能问题。

它的特点：

* 代码逻辑完全正确
* 没有 data race（数据竞争）
* 线程修改的是不同变量
* 但程序性能会严重下降

本质原因：

```txt
多个线程虽然访问不同变量，
但这些变量位于同一个 cache line 中。
```

CPU 会频繁进行 cache line invalidation（缓存失效），导致缓存同步风暴。

---

# 2. Cache Line（缓存行）

CPU 不按“变量”读取内存。

CPU 按：

```txt
Cache Line
```

读取内存。

现代 CPU：

```txt
一个 cache line 通常是 64 bytes
```

例如：

```cpp
struct Data {
    int x;
    int y;
};
```

内存布局：

```txt
x -> 0x1000
y -> 0x1004
```

CPU 会把：

```txt
0x1000 ~ 0x103F
```

整体作为一个 cache line 缓存。

因此：

```txt
x 和 y 实际共享同一个 cache line
```

---

# 3. 经典伪共享示例

## 错误写法

```cpp
#include <atomic>
#include <thread>

struct Counter {
    std::atomic<int> x;
    std::atomic<int> y;
};

Counter counter;

void thread1() {
    for (int i = 0; i < 100000000; ++i) {
        counter.x++;
    }
}

void thread2() {
    for (int i = 0; i < 100000000; ++i) {
        counter.y++;
    }
}

int main() {
    std::thread t1(thread1);
    std::thread t2(thread2);

    t1.join();
    t2.join();
}
```

虽然：

```txt
thread1 修改 x
thread2 修改 y
```

但：

```txt
x 和 y 位于同一个 cache line
```

会导致严重的 cache line ping-pong。

---

# 4. MESI 协议

伪共享本质来自：

```txt
CPU Cache Coherence（缓存一致性）
```

现代 CPU 使用：

```txt
MESI 协议
```

维护多核缓存一致性。

MESI 四种状态：

| 状态 | 含义        |
| -- | --------- |
| M  | Modified  |
| E  | Exclusive |
| S  | Shared    |
| I  | Invalid   |

---

# 5. 为什么线程 B 修改 y 会让 A 的 cache line invalid

假设：

```txt
x 和 y 位于同一个 cache line
```

## 初始状态

CoreA：

```txt
[x y] -> Shared
```

CoreB：

```txt
[x y] -> Shared
```

---

## 线程 A 修改 x

CPU 要求：

```txt
写操作必须独占 cache line
```

于是：

```txt
CoreB 的 cache line 被 invalid
```

结果：

CoreA：

```txt
[x y] -> Modified
```

CoreB：

```txt
[x y] -> Invalid
```

---

## 线程 B 修改 y

虽然：

```txt
只修改 y
```

但：

```txt
y 所在 cache line 已被 CoreA 独占
```

因此：

CPU 必须：

```txt
让 CoreA 的 cache line invalid
```

然后：

CoreB 获得 ownership。

结果：

```txt
CoreA <-> CoreB
不断争夺 cache line ownership
```

这就是：

```txt
cache line ping-pong
```

---

# 6. 为什么 atomic 更容易触发伪共享

atomic 操作必须保证：

```txt
严格缓存一致性
```

因此：

* 必须立即同步 cache
* 必须发送 invalidation
* 必须更新 ownership

相比普通变量：

```txt
atomic 会更频繁触发 cache line invalidation
```

因此：

```txt
atomic 是伪共享高发区
```

---

# 7. 无锁队列中的伪共享

lock-free queue 常见结构：

```cpp
std::atomic<size_t> head;
std::atomic<size_t> tail;
```

问题：

```txt
head 和 tail 可能位于同一个 cache line
```

多个线程：

* 修改 head
* 修改 tail

会不断互相 invalid cache。

---

# 8. Ring Buffer 如何避免伪共享

## 错误写法

```cpp
struct RingBuffer {
    std::atomic<size_t> head;
    std::atomic<size_t> tail;
};
```

---

## 正确写法

```cpp
struct alignas(64) PaddedAtomic {
    std::atomic<size_t> value;
};

struct RingBuffer {
    PaddedAtomic head;
    PaddedAtomic tail;
};
```

目的：

```txt
让 head 和 tail 不在同一个 cache line
```

# 9. 工业界解决方案

工业级高性能框架：

* PyTorch
* TensorRT
* folly
* boost lockfree
* DPDK

都会：

```txt
对高频原子变量进行 cache line padding
```

典型写法：

```cpp
struct alignas(64) Counter {
    std::atomic<uint64_t> value;
};
```

或者：

```cpp
char padding[64];
```

# 10. NUMA 与伪共享

NUMA：

```txt
Non-Uniform Memory Access
```

多 CPU Socket 系统中：

* 每个 CPU 有本地内存
* 跨 socket 访问更慢

如果：

```txt
伪共享发生在不同 NUMA 节点
```

则：

* cache invalidation
* ownership transfer
* memory synchronization

都需要跨 socket。

性能会进一步恶化。

---

# 11. 多生产者多消费者队列中的伪共享

MPMC Queue：

```txt
Multiple Producer Multiple Consumer
```

常见问题：

```txt
多个线程同时修改：
head
tail
slot state
```

如果：

```txt
这些变量共享 cache line
```

会导致：

```txt
严重 cache contention
```

工业实现通常：

* head padding
* tail padding
* slot padding
* thread local cache

# 12. Benchmark 实验

## 无 padding

```cpp
struct Counter {
    std::atomic<uint64_t> value;
};
```

多个线程：

```cpp
counter[i].value++;
```

性能：

```txt
极差
```

原因：

```txt
多个 Counter 位于同一个 cache line
```

---

## 有 padding

```cpp
struct alignas(64) Counter {
    std::atomic<uint64_t> value;
};
```

性能：

```txt
接近线性加速
```


示例：

```cpp
struct alignas(std::hardware_destructive_interference_size)
PaddedCounter {
    std::atomic<int> value;

```

作用：

```txt
自动按 cache line 对齐
```

# 14. 伪共享的本质

伪共享真正争夺的不是变量。

而是：

```txt
cache line ownership
```

本质：

```txt
多个核心竞争同一个 cache line 的写权限
```

虽然：

```txt
逻辑上没有共享变量
```

但：

```txt
物理上共享 cache line
```

---

# 15. 伪共享的典型特征

## 表现

* CPU 占用很高
* 多线程比单线程更慢
* 没有锁竞争
* 没有 data race
* perf 显示 cache miss 很高

# 17. 工业级优化建议

## 高频共享变量必须：

* alignas(64)
* padding
* thread-local
* 分离读写热点

---

## 不要：

```txt
多个 atomic 连续存储
```

---

## lock-free queue：

必须：

* 分离 head/tail
* slot padding
* per-thread buffer

---

# 18. 总结

伪共享本质：

```txt
多个线程竞争同一个 cache line 的写权限
```

核心问题：

```txt
cache coherence traffic
```

根本原因：

```txt
CPU 按 cache line 管理缓存
而不是按变量管理
```

解决方案：

```txt
padding
alignas(64)
thread-local
cache line isolation
```

这是高性能并发系统中最重要的优化之一。
