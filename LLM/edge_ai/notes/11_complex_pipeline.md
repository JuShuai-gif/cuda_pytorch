# 复杂流水线与运行时系统优化

## 1. 引言：何谓"复杂流水线"

简单流水线（如上一章的三阶段感知→规划→控制）是理想化的模型。真实的机器人/自动驾驶系统中，流水线远比这复杂：

- **分支与融合**：多个传感器输入融合后再分流处理
- **异构计算**：CPU 做逻辑、GPU 做推理、DSP 做信号处理、FPGA 做预处理
- **多速率**：Camera 30Hz、LiDAR 10Hz、IMU 200Hz，各传感器数据需要时间对齐
- **有状态节点**：跟踪器、预测器等需要维护历史状态
- **反馈回路**：控制输出影响传感器数据（如转向改变摄像头视角）

理解这些复杂流水线的结构和优化方法，是机器人系统性能工程师的核心能力。

## 2. 自动驾驶流水线架构详解

### 2.1 全栈架构

一个 L4 级自动驾驶系统的完整数据流：

```
传感器层 ────────────────────────────────────────────────────
  Camera(6-12路)  LiDAR(1-3台)  Radar(4-6台)  IMU  GPS/RTK
      │                │             │          │      │
      ▼                ▼             ▼          ▼      ▼
预处理层 ────────────────────────────────────────────────────
  ISP(去畸变/白平衡) 点云滤波/下采样  FFT/Range-Doppler  标定/时间同步
      │                │             │          │      │
      └────────────────┴──────┬──────┴──────────┘      │
                              ▼                         │
感知层 ──────────────────────────────────────────────────
  2D检测(NN)  3D检测(LiDAR+Cam融合)  可行驶区域  Lane检测
      │                │                    │          │
      └────────────────┴────────────────────┘          │
                              ▼                         │
融合与跟踪层 ─────────────────────────────────────────────
  多传感器目标融合  Kalman/Extended Kalman追踪  匈牙利匹配
                              │
                              ▼
预测层 ──────────────────────────────────────────────────
  轨迹预测(VectorNet/TNT)  意图预测  交互预测
                              │
                              ▼
规划层 ──────────────────────────────────────────────────
  行为决策(FSM/RL)  路径规划(A*/Lattice)  速度规划(ST图DP)
                              │
                              ▼
控制层 ──────────────────────────────────────────────────
  MPC/LQR横向控制  PID纵向控制  底盘CAN总线通信
```

### 2.2 关键指标

| 指标 | 定义 | L4 目标 |
|------|------|---------|
| 端到端延迟 | 传感器曝光到执行器响应 | < 100ms |
| 感知帧率 | 检测/分割的更新频率 | ≥ 10Hz |
| 跟踪延迟 | 目标状态更新的时效性 | < 30ms |
| 规划周期 | 新轨迹的计算频率 | 10-20Hz |
| 控制频率 | 执行器指令更新率 | 100-200Hz |
| 感知召回率 | 漏检率 | > 99% |
| CPU 利用率 | 合理使用防止热节流 | < 80% |
| GPU 利用率 | Tensor 核心使用效率 | > 70% |

## 3. 机器人系统流水线

### 3.1 典型机器人软件栈

```
SLAM (Simultaneous Localization And Mapping)
├── 前端：视觉/LiDAR 里程计 (Visual Odometry, LOAM)
├── 后端：位姿图优化 (g2o, GTSAM, Ceres)
├── 回环检测：Bag-of-Words (DBoW), Scan Context
└── 全局优化：Pose Graph + Bundle Adjustment

感知 (Perception)
├── 语义 SLAM：静态/动态物体分离
├── 3D 重建：TSDF, Occupancy Grid
└── 场景理解：物体识别、语义分割

规划 (Planning)
├── 全局规划：A*, RRT*, PRM
├── 局部规划：DWA (Dynamic Window Approach), TEB (Timed Elastic Band)
└── 运动基元：采样+优化混合

控制 (Control)
├── 全身控制 (Whole-Body Control, WBC)
├── 模型预测控制 (MPC)
└── 阻抗/导纳控制
```

### 3.2 传感器融合策略

- **前融合 (Early Fusion)**：原始数据层面合并。延迟低，标定精度要求高。
- **中融合 (Middle Fusion)**：特征层面合并。灵活性好，需要同步。
- **后融合 (Late Fusion)**：各自检测后再合并。容错性好，但可能有冲突。

### 3.3 ROS2 实时执行器设计

ROS2 针对实时系统改进了执行器模型：
- **回调组 (Callback Groups)**：互斥回调组保证串行，可重入回调组允许并行
- **优先级调度**：基于 Linux 实时调度策略分配线程优先级
- **零拷贝传输**：Loan Message API 实现节点间零拷贝共享内存
- **确定性执行**：EventsExecutor 提供可预测的执行顺序

## 4. 实时渲染流水线

### 4.1 游戏引擎主循环

```
while (running) {
    poll_events();         // 输入采样 (1-2ms)
    update_physics();      // 物理模拟 (1-5ms)
    update_scene();        // 场景更新 (0.5-2ms)
    culling();             // 视锥剔除 + 遮挡剔除 (0.5-1ms)
    submit_draw_calls();   // GPU 指令提交 (0.5-2ms)
    wait_for_gpu();        // 等待 GPU 完成或双缓冲交换
    present();             // 显示输出
}
```

### 4.2 GPU 指令提交流水线

```
CPU 端：
  State Setup → Draw Call → Command Buffer → Submit Queue

GPU 端（Vulkan / DX12）：
  Command Buffer → Geometry Processing → Rasterization
  → Fragment Shading → ROP → Framebuffer

Async Compute (并行)：
  Physics → Cloth → Particles (异步计算队列与图形队列并行)
```

### 4.3 VR/AR 的特殊要求

- **Motion-to-Photon 延迟**：头动到画面更新 < 20ms（否则晕动症）
- **异步时间扭曲 (ATW)**：在 GPU 合成阶段用最新头部姿态修正画面
- **固定帧率**：90Hz / 120Hz 强制要求，掉帧不可接受

## 5. 高性能 ML 推理流水线

### 5.1 Serving 架构

```
请求到达 → Tokenizer → Embedding → 模型前向
                                    │
                    ┌───────────────┼───────────────┐
                    ▼               ▼               ▼
              Prefill Batch  Decode Batch 0  Decode Batch 1
                    │               │               │
                    └───────────────┴───────────────┘
                                    ▼
                              Detokenizer → 响应返回
```

### 5.2 批处理策略

- **静态批处理**：固定 batch size，延迟可预测但 GPU 利用率可能低
- **动态批处理 (Dynamic Batching)**：在一个时间窗口内收集请求后合并批处理
- **连续批处理 (Continuous Batching / In-flight Batching)**：不等整个 batch 完成就插入新请求
- **分块预填充 (Chunked Prefill)**：将长 prompt 拆分为多个 chunk 交替处理

### 5.3 LLM 推理中的 KV Cache

KV Cache 是 Transformer 解码阶段的核心优化：

- **原理**：已生成的 token 的 Key 和 Value 不需要每步重新计算
- **内存占用**：`2 × num_layers × num_heads × head_dim × seq_len × dtype_size`
- **优化技术**：
  - **PagedAttention (vLLM)**：将 KV Cache 分页管理，类似 OS 虚拟内存
  - **Prefix Caching**：共享公共前缀的请求复用 KV Cache
  - **KV 量化**：将 Key/Value 压缩到 FP8/INT8 存储

### 5.4 模型流水线并行

当模型太大无法放入单 GPU：

- **张量并行 (TP)**：单层内的矩阵乘按行/列拆分到多 GPU
- **流水线并行 (PP)**：不同层在不同 GPU 上，micro-batch 流水
- **数据并行 (DP)**：每 GPU 持有完整模型副本，处理不同数据
- **序列并行**：长序列按维度切分
- **3D 并行**：TP + PP + DP 联合使用

## 6. 吞吐量 vs 延迟的权衡

### 6.1 经典权衡

| 优化方向 | 提高吞吐 | 降低延迟 |
|----------|----------|----------|
| 批处理大小 | 增大 batch | 减小 batch |
| 流水线深度 | 增加并发帧 | 减少 in-flight 数据 |
| 缓冲区 | 增大缓冲 | 减小或去除缓冲 |
| 精度 | FP16/INT8 | FP32（避免量化开销）|
| 调度 | 批调度 (batching scheduler) | 优先级调度 (priority-driven) |

### 6.2 实际案例：Apollo 自动驾驶

百度 Apollo 的优化经验：
- 将高精度地图加载和匹配从关键路径移到后台线程
- 感知模型从 FP32→INT8 量化，延迟减半，召回率下降 < 0.5%
- 规划模块从单线程 A* 改为多线程并行 RRT，搜索时间从 50ms→15ms
- 使用共享内存替代 ROS 网络通信，节点间延迟从 ms 级→μs 级

### 6.3 实际案例：Tesla FSD

Tesla FSD 芯片的设计哲学：
- 片上 SRAM 尽可能大（32MB），减少 DRAM 访问
- NPU（神经网络处理器）与 ISP（图像信号处理器）直连，零拷贝
- 双芯片冗余运行，取更保守的结果（安全设计，非性能设计）
- 取消后融合，所有传感器在 BEV（鸟瞰视角）空间统一表达

## 7. 理解数据依赖关系

在复杂流水线中，数据依赖决定了并行化的上限。

- **真依赖 (RAW - Read After Write)**：B 需要 A 的输出，必须串行。优化方法：让 A 更快，或用近似值启动 B。
- **反依赖 (WAR)**：A 写之前 B 不能读。优化方法：缓冲区双缓冲。
- **输出依赖 (WAW)**：写顺序冲突。优化方法：独立的输出缓冲区。

**系统瓶颈识别法则**：
- 瓶颈 = 流水线中最慢的阶段
- 优化非瓶颈阶段对吞吐量无帮助（Goldratt 约束理论）
- 瓶颈可能随负载变化而转移，需要持续监测

**第一性原理**：流水线的吞吐量由最慢阶段决定，端到端延迟受所有阶段累积影响。你的优化资源应集中在瓶颈阶段。
