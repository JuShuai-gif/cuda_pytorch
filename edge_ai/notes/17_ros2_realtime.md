# ROS2 实时控制与通信模式

## 1. 实时执行器架构

### 1.1 ROS2 控制框架的线程模型

ros2_control 框架将机器人系统划分为两个独立线程域：

- **非实时线程 (Non-RT)**：承担感知（图像处理、目标检测）、规划（路径规划、行为决策）、日志记录、参数更新等任务。运行在 `SCHED_OTHER` 调度策略下，允许被抢占。
- **实时线程 (RT)**：执行控制循环（电机控制、力控、姿态控制）。运行在 `SCHED_FIFO`（优先级 99）下，必须以确定性周期完成，不允许动态内存分配、锁争用、或系统调用。

分离的核心原因：如果控制循环和感知推理共用一线程，当目标检测耗时从 30ms 抖动到 80ms 时，1kHz 控制循环将错过多个周期，导致机器人不稳定。

### 1.2 优先级反转的预防

优先级反转（Priority Inversion）在 ros2_control 中的典型场景：

```
RT 控制线程 (prio=99):  等待共享数据锁
Non-RT 感知线程 (prio=0): 持有锁，被日志线程抢占
Non-RT 日志线程 (prio=0):  正在执行磁盘 I/O
→ RT 线程被无限期阻塞
```

解决方案：
- **RT 路径禁止 mutex**。任何互斥锁都可能触发优先级反转。
- 使用 lock-free 数据结构（SPSC 环形缓冲区）在 RT/Non-RT 之间传递数据。
- 如果需要共享资源，使用优先级继承 mutex（`rt_mutex` on PREEMPT_RT），但最好避免。

### 1.3 rclcpp Executor vs 自定义实时执行器

| 特性 | rclcpp Executor | 自定义 RT Executor |
|------|----------------|-------------------|
| 调度模型 | 协作式（回调不抢占） | 抢占式（SCHED_FIFO） |
| 定时精度 | `std::chrono` + 条件变量 | `clock_nanosleep(TIMER_ABSTIME)` |
| 抖动 | 100μs ~ 1ms | < 50μs (PREEMPT_RT) |
| 适用场景 | 非实时节点 | 硬件控制循环 |

## 2. 无锁通信：SPSC 环形缓冲区

### 2.1 为什么需要无锁

实时线程中调用 `std::mutex::lock()` 会带来两个致命问题：

1. **优先级反转**：如果低优先级的 Non-RT 线程持有锁，RT 线程将被阻塞，等待时间不可预测。
2. **非确定性延迟**：即使没有争用，mutex 内部的 futex 操作也可能触发系统调用（当锁已被持有时），导致延迟抖动。

### 2.2 SPSC 环形缓冲区的正确实现

单生产者单消费者 (SPSC) 环形缓冲区是最简单的无锁数据结构：

```
producer (Non-RT, 30Hz)        consumer (RT, 1kHz)
      |                              |
   write_idx --atomic-->        read_idx
      |                              |
   [slot0] [slot1] [slot2] ... [slotN-1]
```

关键设计要点：

- **独立 head/tail 指针**：生产者和消费者各自拥有独立的写/读索引，通过原子变量同步。
- **内存序**：
  - `push` 使用 `memory_order_release`：确保写入的数据对消费者可见。
  - `pop` 使用 `memory_order_acquire`：确保读取的数据与生产者的写入同步。
- **伪共享防护**：head 和 tail 分配在不同缓存行上（64 字节对齐），避免一个核心写入 tail 时导致另一个核心的 head 缓存行失效。
- **2 的幂容量**：通过位掩码替代取模运算，减少指令开销。

### 2.3 传感器数据的 latest-is-best 语义

对于摄像头图像数据，如果消费者（感知线程）来不及处理，最新的帧比旧的帧更有价值。`push_overwrite()` 在缓冲区满时覆盖最旧的数据，保证消费者总能读到最新数据。

## 3. 实时安全模式

### 3.1 预分配内存池

RT 路径中禁止 `malloc`/`new` 的原因：
- 可能触发 `sbrk`/`mmap` 系统调用扩展堆。
- 可能触发内存压缩/碎片整理。
- 执行时间不可预测（从纳秒到毫秒级别）。

解决：在非实时阶段预分配所有需要的内存（环形缓冲区、对象池），RT 阶段只使用 `placement new` 或栈分配。

### 3.2 无锁计时器

三种计时方案对比：

| 方案 | 精度 | CPU 开销 | 适用场景 |
|------|------|----------|----------|
| `clock_nanosleep(TIMER_ABSTIME)` | < 50μs | 低（睡眠） | 周期性的 RT 任务 |
| 忙等 (`while(now < target)`) | < 1μs | 极高 | 硬实时、极短周期 |
| 条件变量 (`cond.wait_for`) | ~100μs | 低 | 非实时任务 |

`clock_nanosleep(TIMER_ABSTIME)` 使用绝对时间而非相对时间，可以避免累积漂移。

### 3.3 信号驱动的唤醒

对于非周期性但需要快速响应的 RT 任务，使用 `signalfd` 或 `eventfd` 结合 `poll`/`epoll` 等待，比忙等更省电，比条件变量延迟更低。

## 4. 生命周期管理

### 4.1 ros2_control 生命周期状态机

```
UNCONFIGURED → INACTIVE → ACTIVE → FINALIZED
     ↑            ↓  ↑       ↓         ↑
     |←———————————|  |———————|         |
              on_cleanup  on_deactivate  on_shutdown
```

- **UNCONFIGURED**：节点刚创建，尚未分配资源。
- **INACTIVE**：已配置（预分配内存、创建线程），但未启动 RT 循环。
- **ACTIVE**：RT 控制循环正在运行，提供数据输出。
- **FINALIZED**：已销毁资源，不可恢复。

### 4.2 安全的状态转换

状态转换必须在非实时上下文（Non-RT 线程）中执行：

1. 激活前完成所有内存分配和线程创建。
2. 状态变量使用原子操作（`std::atomic`），避免 RT 线程读取时加锁。
3. 如果激活失败（硬件不可用），必须回退到 INACTIVE 状态并报告错误，不能部分处于 ACTIVE。

## 5. QoS 策略与延迟预算

### 5.1 ROS2 QoS 策略

| 策略 | 选项 | 适用场景 |
|------|------|----------|
| Reliability | RELIABLE | 控制指令（每条都要送达） |
| Reliability | BEST_EFFORT | 传感器数据（丢失几帧可接受） |
| Durability | TRANSIENT_LOCAL | 参数、配置（新订阅者也能收到最后值）|
| Deadline | 500μs (for 1kHz) | 检测控制循环是否超时 |
| Liveliness | AUTOMATIC | 检测节点是否存活 |
| Depth | 1 (for latest-only) | 传感器数据走 latest-is-best |
| Depth | 10 | 有重传需求的控制指令 |

### 5.2 不同数据类型的 QoS 配置

- **传感器数据（200Hz IMU）**：BEST_EFFORT + Depth=1 + Deadline=5ms。丢一帧不影响系统，但要检测传感器断连。
- **控制指令（1kHz 电机指令）**：RELIABLE + Depth=10 + Deadline=1ms。每条指令都必须送达，但超时的指令应丢弃。
- **感知结果（30Hz 检测框）**：BEST_EFFORT + Depth=1 + Deadline=50ms。新的检测结果到达时，旧结果立即作废。

## 6. 多速率管线

### 6.1 速率匹配模式

```
传感器 200Hz ──→ 感知 30Hz ──→ 控制 1kHz
  (IMU)        (目标检测)     (电机控制)
```

三个不同速率的节点需要通过适当的匹配策略协同工作：

- **200Hz → 30Hz (下采样)**："latest-is-best" 语义。30Hz 消费者每次只读取最新的传感器数据。200Hz 传感器产生的 6-7 帧中只有 1 帧被感知处理，其余帧自然丢弃。
- **30Hz → 1kHz (上采样)**："hold-last" 语义。1kHz 控制循环在感知结果更新前一直使用上次的检测结果。这种方式保证了控制的连续性，但引入了 0-33ms 的感知延迟。

### 6.2 时间戳对齐

不同速率的传感器需要时间戳对齐才能正确融合。通常以最慢传感器的频率为基准，使用最接近的时间戳进行数据关联。

关键原则：**RT 线程永远不要阻塞等待 Non-RT 线程的数据**。如果感知结果尚未就绪，控制循环使用上一次的有效结果继续运行。
