# NPU 推理优化实践：从 13fps 到 29fps 的完整复盘

> 参考案例：RK3588 (3 核 NPU, 6 TOPS) 边缘端 YOLO 推理优化

## 一、Pipeline 架构与典型瓶颈分布

```
Camera(1080p MJPEG) → MPP Decode → RGA CSC+Resize → NPU Inference → Output
```

优化前的耗时分布：

| 阶段 | 耗时(ms) | 占比 | 说明 |
|------|----------|------|------|
| 输入处理 (rknn_input_set) | 27 | 29% | DMA-BUF 分配 + 映射 |
| 预处理 (letterbox) | 22 | 24% | 双 letterbox 浪费 |
| 输出转换 (FP16→FP32) | 36-55 | 39% | 逐元素 C 转换 |
| NPU 推理 | 11 | 12% | 模型实际推理 |
| **合计** | **~100** | **100%** | 仅 ~13fps |

核心发现：**外围开销 (82ms) 远大于核心推理 (11ms)**，"外围比核心慢" 是边缘推理的典型陷阱。

## 二、优化一：IO 持久化

### 问题
`rknn_input_set()` 每次推理调用时都会：
1. 分配 DMA-BUF 内存
2. 建立内存映射
3. 设置输入 tensor 描述符

单次耗时 27ms，远超推理本身的 11ms。

### 原理
- DMA-BUF 是 NPU 与 CPU 共享内存的零拷贝机制
- 每次重新分配需要内核态系统调用 (`dma_buf_alloc` + `mmap`)
- 频繁分配/释放导致页表刷新和 TLB 失效

### 解决方案
使用 `rknn_set_io_mem()` 预先注册 IO 缓冲区，运行时仅：
1. `rknn_run()` — 执行推理
2. 同步 fence — 等待 DMA 完成

将 IO 内存分配从"每次分配"变为"一次注册，持续复用"。

### 效果
| 指标 | 优化前 | 优化后 | 改善 |
|------|--------|--------|------|
| IO 分配耗时 | 27ms | 0.1ms | -99.6% |
| FPS | 13 | ~25 | +92% |

## 三、优化二：双 Letterbox 问题

### 问题
预处理代码硬编码 `model_input_width=640`，但实际模型输入为 `512×512`。SDK 内部检测到尺寸不匹配后，自动执行 CPU 双线性插值缩放 (640→512)，每帧额外消耗 22ms。

### 根因
```
Camera Frame (1920×1080)
    ↓ RGA resize → 640×640 (硬编码，22ms)       ← 第一次 letterbox
    ↓ SDK 检测 640≠512 → CPU resize (22ms)       ← 第二次 letterbox（浪费！）
    ↓ 512×512 → NPU 推理
```

### 解决方案
通过 `--model-input-width` / `--model-input-height` CLI 参数指定正确的模型输入尺寸，让 RGA 直接缩放至 512×512。

### 效果
| 指标 | 优化前 | 优化后 | 改善 |
|------|--------|--------|------|
| Letterbox 耗时 | ~22ms | ~0.3ms | -98.6% |
| FPS | 25 | 29 | 达到相机上限 |
| NPU 利用率 | 27% | 85% | +215% |

## 四、优化三：NEON 查表法加速 FP16 转换

### 问题
模型输出格式为 FP16 (half float)，需转换为 FP32 供后处理使用。原始逐元素 C 转换耗时 36-55ms。

### 原理
利用 NEON SIMD 的查表法：
1. 预计算 256 个 half-float 值的查找表 (LUT)
2. 使用 `vld1q_u8` 一次加载 8 个 uint8 索引
3. 使用 `vst1q_f16` 一次写入 8 个 FP16 值

```
// 伪代码
uint8_t input[8] → vld1q_u8  加载 8 字节
                 → tbl 查表   8 路并行查表
                 → vst1q_f16 存储 8 个 FP16 值
```

### 效果
| 指标 | 优化前 | 优化后 | 改善 |
|------|--------|--------|------|
| FP16→FP32 转换 | 36-55ms | 0.3-3.6ms | -90~99% |
| 吞吐量 | 0.8 GB/s | 15+ GB/s | ~20x |

## 五、Perf 数据逐层下钻方法

1. **全 pipeline 打点** → 获得各阶段总耗时，定位最大瓶颈
2. **热点函数采样** (`perf top -p <pid>`) → 找到 CPU 热点
3. **追踪点分析** (`perf record -e syscalls:sys_enter_dma_buf_alloc`) → 发现 DMA 分配频率异常
4. **NPU 利用率** (`cat /sys/kernel/debug/rknpu/load`) → 发现利用率仅 27%，远低于预期
5. **日志插桩** → 确认 SDK 内部触发了 CPU resize

逐层下钻的核心逻辑：从宏观到微观，从不正常的数据点反向追溯根因。

## 六、NPU 利用率诊断

利用率的计算公式：

$$
\text{利用率} = \frac{\text{NPU 执行时间}}{\text{总帧时间}}
$$

- 优化前：11ms / 40ms ≈ 27%
- 优化后：11ms / 13ms ≈ 85%

提升路径：
1. IO 持久化消除 27ms DMA 开销 → 核间等待减少
2. 双 Letterbox 消除 22ms CPU resize → NPU 不再等待 CPU
3. NEON 转换消除 36-55ms → 帧间间隔大幅缩短

每一步都让 NPU 的"空闲等待"时间减少，从而利用率自然上升。

## 七、关键教训

1. **外围比核心慢是常态**：默认的 SDK 行为 ≠ 最优行为。输入/输出管线开销往往被严重低估。
2. **先测在做**：不要凭直觉优化 NPU 模型本身；先用 perf 数据定位真正瓶颈。
3. **配置匹配是性价比最高的优化**：一行 CLI 参数纠正，换来 2x 吞吐提升。
4. **IO 持久化是 ZOC (Zero Overhead Communication) 的基础**：一次分配、重复使用。
5. **NEON/SIMD 对数据转换有数量级提升**：简单的查表法就能将纯 C 转换提升 20 倍。
6. **利用率是逆向指标**：低利用率 = 有东西在阻塞 NPU，排查管线而非模型。
