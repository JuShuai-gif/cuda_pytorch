# 36 工程落地·同步与内存序（深度版）

> 本类问题的共性：GPU 代码的执行顺序与 CPU 不同——warp 内并行、block 内共享内存、block 间无同步。难点在于"**在正确的位置插入同步**"。

## 机制 1：Membar——内存屏障插入

### 约束
- 共享内存写后读需要屏障。
- 手工插易漏（竞态）也易多（性能损失）。

### 实现（`lib/Analysis/Membar.cpp`）
- 分析内存操作，决定在何处插入 `gpu.barrier`（`__syncthreads`）。
- 与 layout 转换配合：`ConvertLayoutOpSwizzlingConversion`（走 shared 时插 barrier，`nvidia/ConvertLayoutOpToLLVM.cpp:160-168`）。

> **不变量 S1**：任何共享内存的跨线程写后读，之间必有一个屏障。

### 工程判断
- **同步自动化**：插入点由分析决定，比人工可靠。
- **布局转换的隐式同步**：跨 warp 的 convert_layout 自动带 barrier——用户不知道但正确。

## 机制 2：TMA 的 mbarrier 同步

### 约束
- Hopper 的 TMA（异步拷贝）用 `mbarrier` 同步。
- 消费方必须等 barrier arrive。

### 实现（`LowerLoops.cpp:321-405` createTMABarrierAndWait）
```cpp
// BarrierExpectOp + WaitBarrierOp
// 相同 stageDiff 的连续 TMA load 共享 barrier 组
// barrier arrive 值按 load 字节数算
```

> **不变量 S2**：TMA 数据可读前，对应 mbarrier 必须已 arrive 到期待值。

### 工程判断
- **同步值由数据量推导**：`arrive` 值按字节数算，不是随意值。
- **共享 barrier 组**：同 stageDiff 的 load 合并同步点——减少 barrier 数量。

## 机制 3：跨线程归约

### 约束
- `tl.max/sum` 需要跨线程协作。
- 结果对所有参与线程一致。

### 实现（`ReduceOpToLLVM.cpp`）
- 归约降级为 warp shuffle + 跨 warp 归约序列。

> **不变量 S3**：归约执行后，参与线程持有的结果语义一致。

### 工程判断
- **归约同步内建**：用户写 `tl.max` 不必关心 shuffle/shared，编译器保证。
- 与 TileLang 的 LowerThreadAllreduce 同构。

## 机制 4：无锁读 vs 写时加锁

### 类比（对应面试题 CanEvict）
- 布局推断：`layout_map` 写者串行（pass 单线程），读者（后续 pass）无锁读——**读路径无锁，写路径串行**。
- 这与 `atomic<lease_timeout>` 无锁读同构。

> **不变量 S4**：无锁读路径读到的状态要么完整旧值要么完整新值，绝不中间态。

### 工程判断
- **把共享状态设计成无锁可读**：单次读即可判定，并发窗口集中写路径。
- pass 的不可变性（TIR immutable）天然保证——**不可变即无锁安全**。

## 本类工程判断总结

1. **同步自动化 + 正确性依据**（分析决定插入点）。
2. **同步值由数据量推导**（TMA arrive 按字节）。
3. **布局转换隐式同步**（用户无感知）。
4. **无锁读模式**（不可变即无锁安全）。
5. **归约同步内建**。
