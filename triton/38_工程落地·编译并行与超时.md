# 38 工程落地·编译并行与超时（深度版）

> 本类问题的共性：编译是慢操作（LLVM→PTX→ptxas 秒级到分钟级），需要并行加速，且可能卡死。难点在于"**并行度控制、结果收集、超时保护**"。

## 机制 1：异步编译（AsyncCompileMode）

### 约束
- 首次编译慢，不应阻塞主线程（尤其 warmup/autotune）。

### 实现（`jit.py:887-902` + `_async_compile.py`）
```python
async_mode = _async_compile.active_mode.get()
if async_mode is not None:
    def async_compile(): return self.compile(src, target=target, options=options.__dict__)
    def finalize_compile(kernel): kernel_cache[key] = kernel
    kernel = async_mode.submit(cache_key, async_compile, finalize_compile)
    kernel_cache[key] = kernel   // 先放占位
```

> **不变量 PA1**：异步编译结果最终必须写回正确的 cache key，且调用方能拿到（占位或最终）。

### 工程判断
- **提交时携带 key + 回调**：完成时回调写回，避免"谁写回"竞态。
- **占位先行**：`kernel_cache[key]` 先放 FutureKernel，后续等待——**用 Future 抽象隐藏异步**。

## 机制 2：ptxas 子进程与超时

### 约束
- `make_cubin` 调 ptxas 子进程，可能挂起。

### 实现（`nvidia/backend/compiler.py:550-553`）
```python
ptxas_cmd = [...]   # -lineinfo, --regAllocOptLevel=2, --gpu-name=sm_<cap>
subprocess.run(ptxas_cmd, capture_output=True)
```

### 工程判断
- **子进程是天然超时边界**：`subprocess.run(timeout=...)` 可干净杀掉——**比线程超时可靠**（对应 TileLang 的 SIGALRM 局限讨论）。
- ptxas 是外部依赖，必须隔离失败（PTXASError，见 `35`）。

## 机制 3：autotuner 的 benchmark 并行

### 约束
- 多个 config 需并行测速。
- 结果按 config 归位。

### 实现（`autotuner.py`）
- `_bench` 逐 config 测速。
- 通过 `key` 参数决定哪些 config 需要重测（避免无关参数触发）。

> **不变量 PA2**：benchmark 结果必须携带其 config 身份，不能错位。

### 工程判断
- **按 key 分组避免重复测速**：只有影响性能的参数变了才重测——**减少不必要的编译/测速**。

## 机制 4：编译器自身的并行（MLIR 并行 pass）

### 约束
- 大模块的 pass 执行可并行（多线程）。

### 实现
- MLIR `PassManager` 支持并行（`mlir::parallel`）。
- Triton 的 `make_ttgir` 用单 pass manager 串行跑 pass（pass 内可能并行）。

### 工程判断
- **pass 级并行 vs 模块级**：MLIR 允许 pass 内部并行（分析独立区域），但依赖链 pass 必须串行。
- **并行只在安全的粒度**：跨 pass 的并行会破坏顺序依赖（见 `40`）。

## 本类工程判断总结

1. **Future 抽象隐藏异步**：占位先行 + 回调写回。
2. **子进程是可靠超时边界**（可杀）。
3. **按 key 分组避免重复编译/测速**。
4. **并行只在安全粒度**：pass 内部并行，依赖链串行。
