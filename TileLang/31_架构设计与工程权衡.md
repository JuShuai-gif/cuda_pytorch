# 31 架构设计与工程权衡（深度版）

> 本文目标：从"它是什么"升级为"为什么这么设计"——分析 TileLang 架构决策背后的工程考量、设计模型、好处与代价，以及可复用的编译器设计模式。

## 1. 核心架构决策：为什么基于 TVM 而不是自研/用 MLIR

### 1.1 三个候选方案的工程权衡

| 方案 | 优势 | 代价 | 风险 |
| --- | --- | --- | --- |
| **自研编译器** | 完全可控、无依赖 | IR/pass/FFI/codegen 全要写 | 工程量巨大，易出 bug |
| **基于 MLIR** | 生态成熟、工具链好 | 需学 MLIR，绑定 LLVM | 学习成本高，编译慢 |
| **基于 TVM（选了它）** | 复用 IR/pass/FFI/分析器 | 绑定 TVM 分叉 | TVM 演进需跟进 |

### 1.2 TileLang 选 TVM 的工程理由

**复用（不重复造轮子）**：
1. **IR 体系**：`PrimExpr/Buffer/Stmt/PrimFunc`——不必重写表达式表示。
2. **Pass 框架**：`CreatePrimFuncPass`、`PassContext`、`PassManager`——不必重写 pass 执行。
3. **算术分析**：`arith::Analyzer/DetectIterMap/InverseAffineIterMap`——布局 inverse 直接调用（`layout.cc:790-844`），这是**最难手写**的部分。
4. **FFI**：`tvm_ffi`——Python↔C++ 绑定 + dlpack 零拷贝，不用写绑定代码。
5. **codegen 基类**：`CodeGenC`——CUDA codegen 只覆写 visit 方法。

**工程收益**：TileLang 团队把精力集中在"tile 优化的增量价值"（布局推断、流水线、tileop 降级），而非编译器基础设施。

### 1.3 代价

- 必须 fork TVM（`3rdparty/tvm` 是定制分叉，带 TIRX 扩展），与上游 TVM 分叉。
- 依赖 TVM 的 C++ 编译（首次 10-30 分钟）。
- IR 表达力受限（TIR 是"有副作用的命令式 IR"，与 MLIR 的 SSA/affine 不同）。

## 2. 为什么 DSL 用 eager builder 而不是 AST 遍历

### 2.1 两种前端策略对比

| 策略 | 机制 | 代表 | 好处 | 代价 |
| --- | --- | --- | --- | --- |
| **AST 遍历** | 整体解析 AST，逐节点翻译 | Triton `ast.NodeVisitor` | 编译期控制流清晰 | 难处理 Python 复杂语法 |
| **eager builder** | 逐语句执行 Python，每步构造 IR | TileLang | 直接复用 Python 语义 | 需维护 builder 状态 |

### 2.2 TileLang 选 eager 的工程理由

1. **Python 语义直接可用**：`if`/`for`/算术在 Python 里算好，再 embed 进 IR（常量折叠天然支持）。
2. **无需自己写 AST 解析器**：Python 解释器已解析，`tilelang/language/ast/` 只定义 IR 节点。
3. **调试友好**：逐语句可断点。
4. **`T.const` 符号直接融入表达式**：`n` 既可以是编译期常量也可以是运行时 Var。

**工程收益**：DSL 的"语法糖"成本低——加一个 `T.xxx` 只需定义语义函数，无需改 parser。

## 3. 为什么 C++/Python 分工如此（工程核心）

### 3.1 分工原则

```
Python 层：DSL 语义、tileop 算法、pass 编排、缓存、调优、JIT 驱动
C++ 层：IR 基础设施、pass 执行、布局数学、codegen、FFI
```

**关键决策**：GEMM 的**指令级 IR 生成在 Python**（`tilelang/cuda/intrinsics/gemm/gemm_mma.py`），C++ 只做参数载体和 pass 驱动（`src/op/gemm.cc` 的 `GemmNode::Lower` → `tl.gemm.lower`）。

### 3.2 为什么这样分（工程理由）

| 好处 | 解释 |
| --- | --- |
| **免重编迭代** | 改 gemm 算法只改 Python，不用重编 `libtilelang.so` |
| **表达力** | Python 写循环/分支生成 IR 比 C++ 模板更灵活 |
| **可调试** | Python 层可断点、可打印 |
| **降低贡献门槛** | 社区贡献者改 Python 即可 |

**代价**：Python 层生成 IR 有性能开销（编译期，非运行期，可接受）；需维护 Python↔C++ 的 FFI 契约（`tileop/gemm/__init__.py` 的全局函数）。

### 3.3 对比 Triton

Triton 的 mma 降级全在 C++（`MMAv2.cpp`），改算法需重编。**这是"编译器算法用 Python 开发"vs"用 C++ 开发"的工程哲学差异**。

## 4. 设计模型：注册表（Registry）模式

### 4.1 为什么用注册表

TileLang 有大量"目标→实现"映射，用注册表解耦：

| 注册表 | 作用 | 好处 |
| --- | --- | --- |
| `register_pipeline` | target → pass 序列 | 加新后端只需注册，不改主流程 |
| `register_device_codegen` | target → codegen | 后端解耦 |
| `register_execution_backend` | tvm_ffi/cython/nvrtc | 运行时切换 |
| `TIR_REGISTER_TL_TILE_OP` | 算子 → 实现 | 算子可插拔 |

### 4.2 工程收益

1. **开闭原则**：对扩展开放、对修改封闭——加后端/算子不改既有代码。
2. **可测试**：每个实现可独立测试。
3. **可配置**：运行时通过 `execution_backend` 切换实现。

### 4.3 这是编译器领域的通用模式

- TVM 本身用 `GlobalDef().def` 注册。
- Triton 用 entry points（`_discover_backends`）。
- LLVM 用 pass 注册表。

## 5. 设计模型：分层 IR + 逐步 Lowering

### 5.1 为什么分层

```
高层 IR (tileop) → 中低层 (展开后) → 低层 (向量化/原子) → CUDA
```

**好处**：
1. 每层只做"该层的事"，降低 pass 复杂度。
2. 高层保留语义（`T.gemm`），低层贴近硬件（`mma`）。
3. 可跨后端复用高层（HIP 复用 layout，只换 codegen）。

### 5.2 与 Triton/MLIR 的类比

- Triton：ttir → ttgir → llir（也是分层）。
- **通用编译器设计模式**：HIR/MIR/LIR 分层是所有编译器的共识（GCC/LLVM/TVM 皆如此）。

## 6. 设计模型：JIT + 两级缓存

### 6.1 为什么 JIT

- 目标 GPU 运行时才知道（`target=auto` 探测）。
- 不同参数需要不同 kernel（`n=1024` vs `n=2048`）。
- 避免 AOT 生成所有组合的爆炸。

### 6.2 为什么两级缓存

| 缓存 | 作用 | 键 | 好处 |
| --- | --- | --- | --- |
| `KernelCache` | 整 kernel（源码+.so+参数） | IR脚本+args+target+configs+版本 | 跳过整个编译 |
| `CUDABinaryCache` | 设备二进制 | 源码hash+target+options | 跳过 nvcc |

**工程收益**：命中 KernelCache 全跳过；miss 时先命中 CUDABinaryCache 可跳过 nvcc——**分层缓存把"编译成本"按粒度拆解，最大化复用**。

### 6.3 为什么键含 libtilelang.so 指纹

`_get_base_key()` 在 `env.should_use_kernel_cache_lib_stamp()` 时对 `.so` 内容 sha256——**保证 C++ 改动时缓存失效**，这是正确性优先的工程决策。

## 7. 设计模型：pass_configs 可配置编译器

### 7.1 为什么需要配置

不同场景需要不同编译行为（性能 vs 正确性 vs 调试）：
- `tl.enable_fast_math`：性能 vs 精度。
- `tl.disable_safe_memory_legalize`：性能 vs 安全。
- `tl.disable_wgmma`：架构降级。
- `TL_ENABLE_DUMP_IR`：调试。

### 7.2 实现（`PassConfigKey` + `PassContext`）

```python
with tvm.transform.PassContext(config={"tl.enable_fast_math": True}):
    mod = transform.Simplify()(mod)
```
- pass 用 `PassContext::Current()` 读配置。
- **工程收益**：编译行为参数化，无需改代码即可切换；这是"可配置编译器"的通用模式（LLVM 的 `-mllvm`、Triton 的 knobs 类似）。

## 8. 常见编译器设计方法汇总

| 方法 | 用处 | TileLang 实例 | Triton 类比 |
| --- | --- | --- | --- |
| 分层 IR | 降低复杂度 | TIRX 多层 | ttir/ttgir/llir |
| 注册表 | 解耦后端 | register_pipeline | _discover_backends |
| JIT | 适配目标/参数 | KernelCache | JITFunction |
| 两级缓存 | 粒度化复用 | KernelCache+CUDABinaryCache | 单层 |
| pass_configs | 可配置编译 | PassConfigKey | CUDAOptions/knobs |
| Python 生成 IR | 免重编迭代 | tileop/gemm | C++ |
| 分析驱动优化 | 数据驱动决策 | AxisInfo 类似物(布局) | AxisInfo/Coalesce |

## 9. 架构演进与设计启示

### 9.1 TileLang 的演进路线
1. 早期：基于 TVM 做 tile 优化。
2. 现在：自研 pass 链 + tileop + 多后端。
3. 趋势：更多算法下沉 Python（降低贡献门槛）。

### 9.2 给学习者的启示
1. **先复用再自研**：TileLang 复用 TVM 证明"站在巨人肩膀上"是正确工程策略。
2. **把难的部分交给成熟库**：布局 inverse 用 `arith`，mma 用 CUTLASS 模板。
3. **Python 做算法、C++ 做基础设施**：平衡开发效率与性能。
4. **可配置编译器**：pass_configs 让编译器适应多场景。
