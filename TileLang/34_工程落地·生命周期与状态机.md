# 34 工程落地·生命周期与状态机（深度版）

> 本类问题的共性：编译器里的对象有明确的**创建→使用→销毁**生命周期，且生命周期跨度可能跨模块、跨线程、甚至跨进程。难点在于"**谁拥有、何时释放、引用是否悬垂**"。

## 机制 1：JIT 产物的加载/卸载

### 约束
- `libtilelang.so`（module）被加载后，kernel 才能执行。
- module 必须比所有 kernel 调用活得久（否则悬垂调用）。

### 状态机
```python
module.load_module(lib_path)   # 创建
kernel = ...                   # 使用（依赖 module 存活）
module.unload / GC             # 销毁
```

> **不变量 L1**：kernel 的执行期必须严格包含在 module 的存活期内。

### 工程判断
- Python 用引用计数管理：`CompiledKernel` 持有 module 引用，module 被 GC 时 kernel 也失效——**由持有者决定生命周期**。
- 对比 Triton：`CompiledKernel.__del__`（compiler.py:445）显式 `unloadModule`（driver.c:354），因为 CUfunction 句柄不随 Python GC 自动释放——**显式析构 C 资源**。

## 机制 2：输出张量的分配与释放（out_idx）

### 约束
- `out_idx` 标记的输出参数，运行时由 adapter 用 `torch.empty` 分配。
- 分配的生命周期 = kernel 调用方的持有。

### 实现（`tvm_ffi.py:270`）
```python
tensor = torch.empty(*shape, dtype=dtype, device=out_device)
executable(*tensor_list)   # 张量在此使用
return tensor_list[result_idx]   # 返回值把所有权转给调用方
```

> **不变量 L2**：输出张量在 kernel 执行期间必须存活，且其生命周期由调用方管理。

### 工程判断
- torch 张量有 GC，无需显式释放——**交给语言的资源管理**。
- 但 device 的选择（`out_device` 取第一个输入张量的 device）是一个状态决定：无输入时退化到当前 device（`current_device_functor`）。

## 机制 3：流水线 buffer 的版本窗口

### 约束
- `InjectSoftwarePipeline` 的多缓冲：producer 写版本 i，consumer 读版本 i-k。
- buffer 版本必须存活足够久。

### 状态机（对应 lease 的窗口）
```cpp
num_versions = use_stage - def_stage + 1   // 版本存活窗口
// 索引: floormod(ko, num_versions)
```

> **不变量 L3**：任一 buffer 版本，从 producer 写入到 consumer 读取完成之间，不允许被覆写。

### 工程判断（与 lease 同构）
- 版本窗口 = "对象存活期"；`use-def+1` = "TTL"；epilogue 排水 = "最后持有者离场"。
- **生命周期管理在编译器里的通用形态**：谁写、谁读、写后读前不许动。

## 机制 4：时钟（时间）与缓存失效

### 约束（对应面试题条件 6）
- 缓存目录按 `TILELANG_CACHE_DIR/<version>/...` 组织。
- 版本号可能不变但代码变了。

### 工程判断
- **不依赖系统时钟做正确性判定**：缓存失效靠内容哈希（IR 脚本、lib 指纹），不靠 mtime。因为 mtime 可被工具修改、跨机器不一致。
- 时钟只用于**性能性**判断（如 `_cleanup_stale_staging_dirs` 按 mtime 清理残留），出错方向是保守的（多留一个 staging 无害）。
- 这直接呼应面试题：**正确性不依赖时钟，时钟只用于非关键路径**。

## 机制 5：host/device IR 分离

### 约束
- 编译产物分 host（launcher 逻辑）和 device（kernel 本体）。
- 两者生命周期必须一致（都随 module）。

### 工程判断
- `lower_to_host_device_ir`（lower.py:259）分离后，二者打包进同一个 `.so`——**用一个载体管理两个生命周期**，避免分离管理的悬垂风险。

## 本类工程判断总结

1. **由持有者决定生命周期**：谁创建谁负责（Python 引用计数 / C++ 显式析构）。
2. **借用语言资源管理**（torch GC），只对 C 资源显式析构。
3. **生命周期窗口 = 版本窗口**：写读之间不许动，是编译器和 lease 的共性。
4. **正确性不依赖时钟**：失效靠内容哈希，时钟只用于保守方向的非关键清理。
5. **合并载体管理多个生命周期**（host+device 一个 .so）。
