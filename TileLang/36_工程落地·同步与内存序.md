# 36 工程落地·同步与内存序（深度版）

> 本类问题的共性：GPU 代码的执行顺序与 CPU 不同——warp 内并行、block 内共享内存、block 间无同步。难点在于"**在正确的位置插入同步，且不错插、不漏插**"。

## 机制 1：ThreadSync——自动插入 `__syncthreads()`

### 约束
- shared memory 的写后读需要 block 内同步。
- 手工插易漏（数据竞争）也易多（性能损失）。

### 实现（`src/transform/thread_storage_sync.cc`）
- `ThreadSync` pass 分析 shared 内存的写读关系，在需要处插入 `__syncthreads()`。

> **不变量 S1**：任何共享内存的跨线程写后读，之间必有一个 `__syncthreads()`。

### 工程判断
- **同步自动化的正确性依据**：分析 buffer 的 def/use 关系，比人工插可靠。
- 这解决了两难：不漏插（防竞态）不滥插（保性能）。
- `TL_DISABLE_THREAD_STORAGE_SYNC` 可关闭（高级用户手动管理）。

## 机制 2：跨线程归约——LowerThreadAllreduce

### 约束
- `T.reduce_max/sum` 需要跨线程协作（warp shuffle / shared）。
- 归约结果必须对所有线程可见且一致。

### 实现（`src/transform/lower_thread_allreduce.cc`）
- 把 tile 级归约展开为 warp shuffle + 跨 warp 归约序列。

> **不变量 S2**：归约执行后，参与线程持有的结果语义一致。

### 工程判断
- **归约的同步语义内建在降级中**：用户写 `T.reduce_max` 不必关心 shuffle 还是 shared，编译器保证正确性。
- 与 Triton 的 `tl.max/sum` 自动降级（ReduceOpToLLVM）同构。

## 机制 3：cp.async 的 commit/wait（流水线同步）

### 约束
- `async_copy_global_to_local` 发出后不立即完成。
- consumer 读 shared 前必须确保拷贝完成。

### 实现（`inject_pipeline.cc:348-387`）
```cpp
// commit: async_commit_queue_scope → ptx_commit_group
// wait:   async_wait_queue_scope + inflight_count → ptx_wait_group(n)
```

> **不变量 S3**：consumer 读某 shared buffer 前，对应的 cp.async 必须已 commit 且 wait。

### 工程判断
- 稳态 wait = `num_stages - 1`（测试 :407）——**wait 数量与流水线深度绑定**，不是随意值。
- epilogue 排水 `[N-1, ..., 1, 0]` 递减——**离开循环前必须清空在飞拷贝**（对应 lease 的"最后持有者离场"）。

## 机制 4：无锁读 vs 写时加锁（回收器模式）

### 约束（对应面试题 CanEvict）
- 回收器需要无锁判断对象可否回收。
- 写者（grant/release）与读者（can_evict）并发。

### 类比
- TileLang 编译期：`LayoutInference` 的 `layout_map` 写者在锁内（BFS 队列串行），`ParallelLoopLayoutValidator` 只读——**读路径无锁，写路径串行**。
- 这与面试题的 `atomic<lease_timeout>` 无锁读完全同构。

> **不变量 S4**：无锁读路径读到的状态，要么是完整的旧值要么是完整的新值，绝不中间态。

### 工程判断
- **把共享状态设计成"无锁可读"**（单次原子 load 即可判定），把并发窗口集中到写路径。

## 本类工程判断总结

1. **同步自动化 + 正确性依据**：插入点由数据流分析决定，不是经验。
2. **wait 数量与深度绑定**：`num_stages-1` 是推导值，不是拍脑袋。
3. **无锁读模式**：把共享状态设计成单次原子 load 可判定。
4. **同步与归约语义内建**：用户不关心底层指令。
5. **正确插 vs 保守插**：`disable_thread_sync` 暴露给高级用户，默认自动。
