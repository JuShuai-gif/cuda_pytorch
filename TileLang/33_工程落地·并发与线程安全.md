# 33 工程落地·并发与线程安全（深度版）

> 本类问题的共性：编译器是**多线程 + 多进程**系统——多线程编译、多进程共享缓存、注册表被并发访问。难点在于"**并发读写的正确性**"：锁的粒度、原子性、竞态窗口。

## 机制 1：KernelCache 单例——双检锁

### 约束
- 全局唯一缓存实例，多线程可能同时请求。
- 构造是昂贵操作（初始化目录等），不能每次都建。

### 状态与不变量
```python
class KernelCache:
    _instance = None
    _lock = threading.Lock()

    def __new__(cls):
        if cls._instance is None:          # 快路径：无锁读
            with cls._lock:                 # 慢路径：加锁
                if cls._instance is None:   # 双检：防止两个线程都进快路径
                    cls._instance = super().__new__(cls)
        return cls._instance
```

> **不变量 C1**：任意时刻最多存在一个 `KernelCache` 实例。

### 为什么双检锁（工程判断）
- 单检锁（只加锁不先查）：每次访问都要锁，热点路径慢。
- 双检：快路径无锁读（绝大多数情况命中），只在首次构造时加锁。
- **代价**：Python 的 `__new__` 本身在 GIL 下安全，但 C++ 场景需要 `std::atomic` + `memory_order` 保证——**锁外读共享状态必须保证内存可见性**。

## 机制 2：CUDABinaryCache 多进程写——原子替换

### 约束
- 多进程可能同时编译同一个 kernel（不同 Python 进程，无共享锁）。
- 写缓存不能留下半写文件。

### 实现（`cuda_binary_cache.py`）
```python
# staging + os.replace（原子）
with open(tmp_path, "wb") as f:
    f.write(data)
os.replace(tmp_path, final_path)   # POSIX 原子替换
```

> **不变量 C2**：任何进程读到的缓存文件要么是完整的旧版本，要么是完整的新版本，绝不可能是半写。

### 边界
- 多进程同时 `os.replace`：last-write-wins，且每次都是完整文件。
- 崩溃残留：`.staging/` 目录由 `_cleanup_stale_staging_dirs` 按 mtime 清理。

### 工程判断
- **用文件系统原子性代替进程间锁**——比跨进程 mutex 简单可靠得多。
- 与 Triton 的 `uuid 临时目录 + os.replace`（cache.py:103）同构。

## 机制 3：autotuner 的编译并行

### 约束
- 多个 config 需要并行编译（性能）。
- 每个编译 worker 必须绑定正确 GPU（多 GPU 时）。

### 实现（`autotuner/tuner.py`）
```python
pool = concurrent.futures.ThreadPoolExecutor(max_workers=num_workers)
def cuda_device_wrapper(func, device):
    def inner(**config_arg):
        torch.cuda.set_device(device)   # 每个 worker 绑定 GPU
        return func(**config_arg)
    return inner
```
- benchmark worker 各自绑定 GPU（`_benchmark_worker_loop` :660）。

> **不变量 C3**：任一时刻，每个 worker 使用的 CUDA device 是它被分配的那个。

### 边界
- worker 数来自 `TILELANG_AUTO_TUNING_CPU_UTILITES`（CPU 利用率百分比）——**资源上限显式化**。
- 线程间通过 queue 通信，避免共享可变状态。

## 机制 4：注册表并发访问

### 约束
- `register_pipeline`/`register_device_codegen` 可能在 import 时被多个模块调用。

### 工程判断
- 注册发生在 import 期（单线程初始化阶段），运行期只读——**把并发窗口限制在初始化期**，是简化并发的最强手段。
- 这解释了大量注册表为何"看似不加锁也没事"：不是碰巧安全，而是设计上把可变期放在单线程阶段。

## 本类工程判断总结

1. **快路径无锁、慢路径加锁**（双检锁）：把锁的成本推向不频繁路径。
2. **用原子替换代替进程间锁**：文件系统原子性比 mutex 可靠。
3. **并发窗口最小化**：注册/初始化放单线程阶段，运行期只读。
4. **worker 资源显式化**：并行度由配置控制，而非无限。
5. **线程间用 queue 通信**：避免共享可变状态。
