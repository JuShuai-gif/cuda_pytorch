# 38 工程落地·编译并行与超时（深度版）

> 本类问题的共性：编译是慢操作（nvcc 秒级到分钟级），需要并行加速，且可能卡死。难点在于"**并行度控制、结果收集、超时保护、避免资源耗尽**"。

## 机制 1：autotuner 并行编译

### 约束
- 多个 config 需并行编译，但 GPU 上下文不能并发混用。
- 并行度有硬件上限（CPU 核数）。

### 实现（`autotuner/tuner.py:576`）
```python
num_workers = int(available_cpu_count * cpu_utilizations)  # CPU 利用率
pool = concurrent.futures.ThreadPoolExecutor(max_workers=num_workers)
def cuda_device_wrapper(func, device):
    def inner(**config_arg):
        torch.cuda.set_device(device)   # 绑定 GPU
        return func(**config_arg)
    return inner
```

> **不变量 PA1**：并行 worker 数 ≤ 可用资源，且每个 worker 绑定固定 GPU。

### 工程判断
- **并行度显式化**：`TILELANG_AUTO_TUNING_CPU_UTILITES/CPU_COUNTS/MAX_CPU_COUNT` 三档控制。
- **GPU 绑定**：避免多线程混用 CUDA context 导致错误。

## 机制 2：超时保护——SIGALRM 与看门狗

### 约束
- 单个 config 的编译/benchmark 可能卡死（stuck CUDA kernel）。
- 必须能强制终止。

### 实现（`autotuner/tuner.py:165-178`）
```python
def run_with_timeout(func, timeout, *args, **kwargs):
    if hasattr(signal, "SIGALRM") and current_thread() is main_thread():
        return _run_with_sigalrm(func, timeout, ...)   # POSIX 主线程：真正中断
    return _run_with_thread(func, timeout, ...)          # 其他：看门狗线程
```
- `_run_with_sigalrm`：`signal.alarm(timeout)` 真正打断。
- `_run_with_thread`：看门狗线程 + `PyThreadState_SetAsyncExc`（只在 Python 字节码边界生效）。

> **不变量 PA2**：任何 config 的执行必须在 timeout 内要么完成、要么被终止。

### 工程判断（深度）
- **SIGALRM 的局限**：线程卡在 C 调用（`cudaStreamSynchronize`）时不会响应——信号只在 Python 字节码边界生效。注释明确承认这一局限。
- **看门狗的选择**：为何不用 `TerminateThread`？因为会破坏 CRT 锁、CUDA 驱动状态（注释明确说明）——**终止策略要避免破坏进程不变量**。

## 机制 3：benchmark worker 的结果收集

### 约束
- 编译完成与 benchmark 完成不同步（pipeline 模式）。
- 结果需按 config 索引正确归位。

### 实现（`_benchmark_worker_loop` :660）
```python
# 结果通过 queue 收集
result_queue.put((idx, config, jit_kernel, latency, worker_ref_latency, status, error))
```
- 每项带 `idx`，主线程按 idx 归位。

> **不变量 PA3**：每个结果必须携带其来源 config 的索引，不能错位。

### 工程判断
- **结果携带身份**：并发收集时，索引是唯一归位依据。
- 错误/超时也走同一队列（带 status 字段），统一处理。

## 机制 4：nvcc 编译超时

### 约束
- nvcc 子进程可能挂起。

### 实现（`lower.py:101-175`）
```python
timeout = env.get_compile_timeout_seconds()
# subprocess.Popen + communicate(timeout=...)
```

### 工程判断
- **子进程超时**：`communicate(timeout)` 超时抛 TimeoutExpired，需杀子进程。
- 与 autotune 的线程超时不同：子进程可被干净杀掉，线程不能——**超时策略取决于被超时对象的性质**。

## 本类工程判断总结

1. **并行度显式化 + 资源上限**：避免资源耗尽。
2. **GPU 上下文绑定**：并发不混用。
3. **超时终止要分对象**：子进程可杀，线程只能"在字节码边界中断"。
4. **结果携带身份**：并发收集靠索引归位。
5. **终止策略避免破坏不变量**：不用 TerminateThread（会破坏 CUDA 状态）。
