# 32 工程落地设计·总纲与方法论（深度版）

> 本文是"工程落地设计"系列的总纲。它定义一套分析编译器工程问题的统一方法论，并给出该系列覆盖的知识点地图。后续各篇（33-40）逐一深入。

## 1. 为什么编译器工程需要专门分析

编译器的难点不在"写出能跑的 pass"，而在三类工程判断（与并发/生命周期/时钟这些"脏活"同构）：

1. **哪些状态组合不该存在**——应在设计时排除，而非运行时兜底；
2. **哪些不变量必须守住**——守住则正确，破坏则静默出错（最危险）；
3. **哪些边界必须显式处理**——否则以莫名其妙的 crash 浮出水面。

## 2. 统一方法论（五步）

分析任何工程机制都按这五步，缺一不可：

```mermaid
flowchart LR
    A["① 约束"（不能做什么/必须做什么）] --> B["② 状态定义"（精确的数据结构）]
    B --> C["③ 不变量"（设计的灵魂，一句话）]
    C --> D["④ 关键实现"（伪代码，照不变量抄）]
    D --> E["⑤ 边界情况"（每个分支的存在理由）]
    E --> C
```

**核心信条**：每个 `if` 分支都必须被不变量或约束**逼出来**，而不是先写分支再找理由。

## 4. 每篇的统一结构

每篇（33-40）固定采用：
1. **本类问题的共性**——这类工程难点为什么难。
2. **N 个具体机制**——每个机制用五步法分析，实例取自本项目真实源码（带行号）。
3. **本类工程判断总结**——几条可迁移的原则。
4. **自测题**——验证是否真的理解。

## 5. 贯穿全部系列的三大原则

1. **不该存在的组合，设计时排除**（如布局冲突 fail-fast、多 driver 报错）。
2. **每个分支都被不变量逼出来**（缓存键字段、stageDiff 修正、水位线）。
3. **不可证明正确就当场拒绝或强失效**，绝不静默处理留隐患。
