## 1. 本章解决什么问题

- 如何**估算**算法的效率（大 O 记号）？
- 什么是最坏/平均/均摊复杂度？`vector::push_back` 为什么是均摊 O(1)？
- 优化代码前应测量什么、遵循什么流程？
- latency / throughput / CPU-bound / memory-bound 各指什么？
- 如何用 profiler 找到真正的热点？
- 性能测试有哪些最佳实践（真实数据、尽早测、绘图、回归）？

一句话：**先测量，再优化；优化流程的目标是避免把时间花在没有收益的地方。**

## 4. 核心概念

| 术语 | 含义 |
|---|---|
| **大 O 记号 O(f(n))** | 运行时间/内存随输入规模增长的**上界**增长率 |
| **增长速率** | O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ) |
| **最坏/平均/最好情况** | 同一算法不同输入下的资源用量 |
| **均摊复杂度** | 对**操作序列**整体分析，总时间 ÷ 操作数（如 push_back O(1) 均摊） |
| **延迟（latency）** | 一次请求到响应的耗时 |
| **吞吐量（throughput）** | 单位时间处理的操作数 |
| **CPU-bound / I/O-bound / memory-bound** | 瓶颈在 CPU 计算 / I/O / 内存带宽 |
| **插桩 profiler** | 在函数出入口插入代码，精确但影响被测程序 |
| **采样 profiler** | 按固定间隔采样调用栈，几乎无干扰但统计性 |
| **帕累托法则（80/20）** | 约 20% 代码消耗 80% 资源 |

## 5. 工作原理

### 5.1 大 O：衡量增长率而非绝对时间

> 来源：PDF 第 86～90 页
> 原始小节：Asymptotic complexity and big O notation

求大 O 的实用步骤（书中 p.90）：删掉除最大增长率外的所有项，再删除常数系数。
如 `f(n) = 4n² + 30n + 100` → `O(n²)`。

关键洞察（书中 p.89）：**输入规模足够大时，增长率决定胜负**。
本实验 `complexity_growth` 实测：n 从 1000→100000（×100），线性搜索耗时
×~100，二分搜索仅 ×~2.2。

### 5.2 均摊复杂度与 vector 扩容

> 来源：PDF 第 92～94 页
> 原始小节：Amortized time complexity

`push_back` 每次扩容 O(n)，但**指数扩容**（翻倍）使扩容仅发生 log₂(n) 次。
等比数列求和后，n 次 push_back 总成本 O(n)，均摊每次 O(1)。
本实验 `vector_growth` 实测：1024 次 push_back 发生 11 次扩容
（= log₂(1024)），总移动 1023 ≈ size，均摊 ~1。

### 5.3 优化工作流（书中 7 步）

> 来源：PDF 第 94～95 页
> 原始小节：What to measure?

1. **定义目标**：可量化的性能目标（交互 100ms、60fps=16ms/帧等）；
2. **测量**：用可靠工具测当前基线；
3. **找瓶颈**：profiler 定位热点，不凭直觉；
4. **有依据的猜想**：提出优化假设（查表？缓存？向量化？减少分配？）；
5. **实现**：快速实现假设，随时准备放弃；
6. **评估**：重新测量，无收益就回退；有收益再评估复杂度/可维护性；
7. **重构**：把有效的优化整理干净、加注释。

### 5.4 性能属性

> 来源：PDF 第 96 页
> 原始小节：Performance properties

- **延迟 vs 吞吐**：低延迟关注依赖链；高吞吐关注并行度/流水线；
- **CPU/I/O/memory-bound**：识别瓶颈类型决定优化方向；
- **功耗**：移动设备上避免高频轮询（阻止 CPU 睡眠）；
- **数据聚合**：中位数比均值更稳健，min/max 反映极端情况。

### 5.5 profiler 的两种范式

> 来源：PDF 第 98～102 页
> 原始小节：Profilers / Instrumentation / Sampling

- 插桩 profiler：精确、可给出调用次数，但改变行为、可能被优化掉
  （书中 ScopedTimer 即手工插桩，本实验 `scoped_timer` 复刻）；
- 采样 profiler：每 ~10ms 采样调用栈，统计 Total（在栈中出现比例）与
  Self（在栈顶比例）；不干扰优化，但漏掉短暂/低频函数；
- gprof：插桩 + 采样混合。

## 8. 未优化版本

- 无 reserve 的 `push_back` 循环（`vector_growth/benchmark.cpp`）：频繁扩容；
- 手写插桩（`scoped_timer`）：需要逐函数插入代码；
- 纯函数微基准（`cpu_vs_memory_bound` 早期版本）：被编译器常量折叠 → 假 0ms。

## 9. 优化版本

- `reserve` 预先分配（约 3.5 倍，本环境实测）；
- 采样 profiler（perf）替代手工插桩：对优化代码准确；
- 微基准用 checksum 种子防折叠。

## 10. 为什么可能更快（逐维度分析）

| 维度 | 分析 |
|---|---|
| 时间复杂度 | 算法选择是最大杠杆：线性 O(n) vs 二分 O(log n)（跨数量级） |
| 空间复杂度 | reserve 多占内存换性能（避免多次扩容） |
| 动态内存分配 | 扩容搬移 = 分配 + 复制；reserve 消除 |
| Cache Locality | 连续访问 vs 随机（见 Chapter 4） |
| 函数调用和内联 | 内联消除调用（Chapter 2） |
| 编译期计算 | 微基准陷阱：过度编译期计算让测量失真 |
| SIMD / 并行 | 吞吐优化方向 |

## 11. 该优化什么时候可能无效

- **数据量小**：n=10 时二分比线性没优势（实测 1.7 vs 2.2 ns，接近）；
- **编译器已优化**：插入排序对小输入可能被库函数替代；
- **增加复杂度**：reserve 需知道规模；提前分配可能浪费内存；
- **可维护性**：手写插桩污染源码；
- **依赖平台**：perf 需要内核权限；带宽数字因机器而异；
- **测量本身失真**：Debug 构建、单轮、纯函数折叠都会误导。

## 13. 汇编观察点

本章主要靠计时与 profiler，汇编辅助：
- 纯函数是否被常量折叠（微基准失真根源）；
- `-O2` 下 `compute_heavy` 是否被内联进 main（gprof 失真根源）。

## 14. 常见错误

- **用 Debug 性能下结论**（`release_vs_debug` 实测差 12 倍）；
- **用单次运行 / 无预热数据**（`warmup_effect`：首轮慢 3.5%）；
- **优化未经测量**：凭直觉猜热点；
- **忽略输入规模**：小数据上大 O 无意义；
- **微基准被编译器折叠**：纯函数 + 恒定输入 + 结果未使用 → 0ms 假象
  （本实验 `cpu_vs_memory_bound` 修复过程即实证）；
- **把均值当唯一指标**：忽略中位数/最小值/异常值；
- **未标注构建类型与数据规模**：结果无法复现。

## 15. 实践练习

1. **简单**：把 `complexity_growth` 的规模改为 1M/10M 各跑一次，验证二分
   搜索仍接近常数、线性搜索线性增长；
2. **简单**：在 `vector_growth` 中把扩容因子策略改为每次 +固定量，观察
   均摊成本如何退化为 O(n)（思维实验或改代码）；
3. **中等**：用 `-O0` 和 `-O3` 分别编译 `hotspot_profiling` 并跑 gprof，
   对比热点识别结果（体验插桩 profiler 的失真）；
4. **中等**：给 `chp::benchmark` 写一个封装，输出 min/median/max 三列，
   重新跑 `complexity_growth` 观察三者的差异；
5. **困难**：为 `complexity_growth` 实现一个"性能回归检查"：设定
   binary/linear 时间比的阈值，若超出则断言失败（守护 CI）。

## 17. 本章总结

- **先选对算法和数据结构，再谈调优**：复杂度差异可跨数量级；
- **大 O 看增长率**：输入规模大时增长速率决定胜负；
- **push_back 均摊 O(1)** 靠指数扩容；`reserve` 消除扩容是低风险优化；
- **优化 7 步流程**：目标 → 测量 → 找瓶颈 → 假设 → 实现 → 评估 → 重构；
- **profiler 优先采样式**（perf），理解插桩式（gprof）的失真来源；
- **性能结论必须标注**：构建类型、数据规模、机器、多轮统计；
- **微基准陷阱**：防编译器折叠是测量正确性的前提。
