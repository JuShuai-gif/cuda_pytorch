## 1. 本章解决什么问题

- C++ 在今天为什么仍然值得使用？
- "零成本抽象"（zero-cost abstraction）到底指什么？
- C++ 相比基于垃圾回收（GC）的语言，在性能和健壮性上有哪些结构性差异？
- 值语义、const 正确性、严格类接口、RAII 这些"与性能无直接关系"的特性，
  为什么反而决定了你能写出健壮的高性能代码？
- 异常在现代 C++ 编译器中还有性能代价吗？

一句话：**本章回答"为什么用 C++"，并为全书奠定心智模型——抽象可以廉价，资源必须可控。**

## 4. 核心概念

| 术语 | 含义 |
|---|---|
| **零成本抽象** | 抽象（类、模板、算法）在运行时基本不付出额外代价；编译器把它"编译掉" |
| **值语义** | 对象按值传递/存储，赋值即复制；实例之间互不影响（默认行为） |
| **引用语义** | 对象通过指针/引用共享，修改互相可见（需显式声明） |
| **const 正确性** | 用 const 表达"该函数/该参数不会被修改"，违反则编译失败 |
| **确定性析构** | 对象离开作用域立即析构，资源释放时机完全可控（相对 GC） |
| **RAII** | 资源在构造时获取、析构时释放，任何退出路径都释放 |
| **copy-and-swap** | 先做可能抛异常的工作，再用不抛异常的 swap 提交状态，保证异常安全 |
| **严格类接口** | 复制语义是接口的一部分；不可复制的类应 `= delete` 而非放任 |
| **引用** | 内部是指针，但不可为空、不可重定向；签名可表达"不许传 null" |

## 5. 工作原理

### 5.1 零成本抽象在机器码层面意味着什么

> 来源：PDF 第 24～26 页
> 原始小节：Zero-cost abstractions / Programming languages and machine code abstractions

作者用"一本书里有多少本《Hamlet》"的例子对比 C 与 C++：

```c
// C：手写链表 + 循环 + strcmp
struct string_elem_t { const char* str_; string_elem_t* next_; };
int num_hamlet(string_elem_t* books) {
  int n = 0;
  for (string_elem_t* b = books; b != 0; b = b->next_)
    if (strcmp(b->str_, "Hamlet") == 0) ++n;
  return n;
}
```

```cpp
// C++：容器 + 算法
int num_hamlet(const std::list<std::string>& books) {
  return std::count(books.begin(), books.end(), "Hamlet");
}
```

要点：两者"大致翻译成相同的机器码"。C++ 版本隐藏了指针、循环、比较，
但 `std::list`/`std::count`/`std::string` 作为模板/内联函数会被编译器直接展开，
**没有额外的间接层**。这正是"零成本"的含义——不是所有抽象都零成本
（如虚函数、类型擦除，见 Chapter 2 的 `std::function`），而是 C++ 提供了
足够多的可内联、可优化的抽象，让你在热点处仍有零成本的替代方案。

> 原理补充：零成本抽象依赖三个机制：
> 1. **模板在编译期实例化**——`std::count<T>` 为每个 T 生成专用代码，无运行时派发；
> 2. **内联（inline）**——函数体在调用点展开，消除调用指令与栈帧；
> 3. **自动向量化与常量折叠**——编译器在获得明确语义后做更深优化。
> 这三者在本项目 `zero_cost_asm` 实验中有汇编验证。

### 5.2 C++ 与 Java 的内存布局差异

> 来源：PDF 第 29～32 页
> 原始小节：Competing languages and performance

三个结构性差异：

1. **编译方式**：C++ 直接编译为机器码；Java 先编译为字节码再 JIT；
2. **内存释放**：C++ 自己管理，GC 语言自动回收（防泄漏但牺牲可预测性）；
3. **对象放置**：Java 所有对象单独堆分配；C++ 可放栈上，也可在一个堆分配里
   放多个对象（`std::vector<Car>` 一次分配 7 个对象，Java 的 `ArrayList<Car>`
   只分配 7 个引用，对象本体各自散落在堆上）。

第 3 点的性能后果（PDF 第 32 页）：C++ 只需一次分配；迭代时访问相邻内存
比访问随机地址快。这就是 Chapter 1 中 `contiguous_vs_pointer` 实验验证的核心。

### 5.3 值语义与所有权

> 来源：PDF 第 32～33 页
> 原始小节：Value semantics

Bagel 例子：C++ 的 `Bagel` 把 `std::set<std::string>` **按值复制**进自己的成员，
后续修改原集合不影响任何已构造的 bagel。若想共享，必须显式用
`std::shared_ptr`/`std::weak_ptr`。Java 默认共享引用，两个 bagel 可能"悄悄"
共享调料集合，改动透过所有引用可见——这是隐蔽 bug 的来源。

### 5.4 const 正确性

> 来源：PDF 第 34～35 页
> 原始小节：Const correctness

```cpp
class Person {
 public:
  auto age() const { return age_; }        // 只读
  auto set_age(int age) { age_ = age; }    // 可写
 private:
  int age_ = 0;
};
class Team {
 public:
  auto& leader() const { return leader_; } // const 重载 -> 返回 const Person&
  auto& leader() { return leader_; }       // 可变重载 -> 返回 Person&
};
```

编译器在 const 对象上调用非 const 成员会直接报错（`discards qualifiers`），
把"误改对象"从运行时 bug 变成编译期错误。

### 5.5 异常与资源：从"无效状态"到 copy-and-swap

> 来源：PDF 第 40～42 页
> 原始小节：Preserving the valid state / Resource acquisition

`OakTree::operator=` 若逐个成员复制，中途抛异常会让对象处于"一半新一半旧"的
无效状态。修复用 **copy-and-swap**：先本地复制（可能抛异常，但原对象完好），
再从不抛异常的 `std::swap` 提交。

资源获取章节用 `std::lock_guard` 说明 RAII：无论正常返回、提前 return 还是
抛异常，锁都在作用域退出时自动释放。

### 5.6 异常 vs 错误码的历史与现状

> 来源：PDF 第 42 页
> 原始小节：Exceptions versus error codes

历史上异常有常态成本，性能代码被迫用错误码（代码膨胀、易漏检查）。
现代编译器异常**只在抛出时产生成本**。这是 Chapter 1 `exceptions_vs_error_codes`
实验验证的观点。

## 7. 简单示例

最小的"值语义 + 引用"对比（完整版见 `value_semantics/example.cpp`）：

```cpp
void change_value(std::set<std::string> s) { s.insert("local"); }          // 传值：不影响调用方
void change_ref(std::set<std::string>& s)  { s.insert("local"); }          // 传引用：修改调用方
```

RAII 最小形式：

```cpp
class Guard {
 public:
  Guard() : p_(new Resource()) {}
  ~Guard() { delete p_; }                 // 任何退出路径都执行
  Guard(const Guard&) = delete;           // 不可复制
 private:
  Resource* p_;
};
```

## 8. 未优化版本

- C 风格手写链表 + 手工循环（`linked_list_search/baseline.cpp`）：要写循环、
  比较、指针步进，且抽象度低；
- `vector<unique_ptr<Particle>>`（`contiguous_vs_pointer/baseline.cpp`）：
  对象被指针间接引用，访问要解引用，迭代时缓存不友好；
- 手工 `new`/`delete`（`raii_resource/baseline.cpp`）：异常路径下泄漏资源，
  释放责任全在调用方。

## 9. 优化版本

- `std::vector`/`std::list` + `std::count`（`linked_list_search/optimized.cpp`）：
  语义更清晰，且内联展开；
- `vector<Particle>` 连续存储（`contiguous_vs_pointer/optimized.cpp`）；
- `ResourceGuard`（`raii_resource/optimized.cpp`）：RAII 封装，异常安全。

## 10. 为什么可能更快（逐维度分析）

对本章核心实验：

| 维度 | 分析 |
|---|---|
| 时间复杂度 | C 链表与 `std::count` 都是 O(n)，无差异；差异在常量因子 |
| 空间复杂度 | 链表每节点多一个指针；连续存储无指针开销 |
| 动态内存分配 | 指针存储每对象一次 `new`；连续存储一次分配 |
| 对象复制和移动 | 值语义拷贝有成本；共享语义零拷贝但有别名代价 |
| Cache Locality | **核心因素**：连续内存顺序遍历缓存命中率极高；指针跳转每步 cache miss |
| 分支 | `count` 的分支（命中与否）在现代 CPU 上高度可预测 |
| 函数调用和内联 | `std::count` 内联后无调用开销 |
| 类型擦除 / 虚函数 | 本章未涉及（`std::function` 见 Chapter 2） |
| 锁竞争 / 原子操作 | 本章未涉及 |
| 编译期计算 | 模板实例化让每个类型都有专用代码 |
| SIMD / 并行 | 连续存储允许编译器向量化（`zero_cost_asm` 中 `pcmpeqd` 4 路并行） |
| 编译器优化空间 | 连续数组更容易被自动向量化、循环展开 |

## 11. 该优化什么时候可能无效

- **数据量不够大**：几万个对象、单次遍历时，cache 差异可能小于测量噪声；
- **编译器已自动优化**：如果指针没有被取出（如整段连续分配 + 编译器知道
  无别名），差异会缩小；
- **增加代码复杂度**：为"连续存储"重构数据结构可能破坏接口抽象；
- **影响可维护性**：SoA/指针切换增加心智负担（见 Chapter 4 权衡）；
- **依赖平台**：cache 行大小、预取器行为因 CPU 而异；
- **额外内存开销**：`vector<Particle>` 扩容需要整体搬移，大对象频繁扩容
  可能抵消局部性收益；
- **异常安全**：RAII 无成本，但 `new`/`delete` 手工管理若漏释放仍是 bug。

## 13. 汇编观察点

以 `zero_cost_asm` 为例（`-O3`）：

- **是否内联**：`std::count` 无 `call` 指令；
- **是否存在间接调用**：无 `call *reg`；
- **是否出现 new/delete**：`count` 路径无；
- **是否出现 memcpy**：`std::string` 路径可能内联 SSO 拷贝，可观察到；
- **是否展开循环**：可观察到 `.L39`/`.L20` 主循环 + 收尾标量循环；
- **是否消除分支**：命中率固定时编译器可能转 CMOV；
- **是否常量折叠**：字面量参数下 count 结果可能被预计算（noinline 阻止了这点，
  这正是实验里加 noinline 的原因）；
- **是否自动向量化**：`pcmpeqd` + `paddq` + `movdqu`（SSE2，4 路 int）。

## 14. 常见错误

- **认为 STL 一定更慢**：恰恰相反，内联模板通常与手写循环等价或更优；
- **认为 STL 一定更快**：也不对——容器选择、存储布局才是主导因素；
- **把对象到处按值传**：大对象复制昂贵，除非是移动语义（Chapter 2）；
- **忽略 const**：const 能开启编译器优化（如缓存、更激进的别名分析）；
- **手工资源管理漏掉异常路径**：这是泄漏的常见来源，用 RAII；
- **复制一个含 `shared_ptr` 成员的类就认为"复制了对象"**：共享被复制了，
  对象本体没复制（PDF 第 38-39 页 Boat 例子，应 `= delete` 复制或深度复制）；
- **用异常做循环内高频控制流**：未抛出的异常无成本，但抛出的异常有成本。

## 15. 实践练习

1. **简单**：把 `loop_vs_count` 的数据规模从 4M 改成 10 万、1000 万各跑一次，
   记录手写循环与 `std::count` 的差距是否随规模变化；
2. **简单**：给 `const_correctness` 加一个 `std::vector<Team>` 的
   `sort` 版本（用 `std::sort`），验证 const 对象上能否调用 sort；
3. **中等**：把 `contiguous_vs_pointer` 的对象从 16 字节的 Particle 改成
   64 字节、256 字节的结构，观察 cache 收益如何随对象大小衰减；
4. **中等**：为 `raii_resource` 的 `ResourceGuard` 增加 move 语义
   （`ResourceGuard(ResourceGuard&&)`），思考为什么拷贝要 `= delete`；
5. **困难**：实现一个简单的 `StackArray<T,N>`（固定容量、栈存储、支持
   迭代器），用 `-O3 -S` 对比它与 `std::vector` 在已知上限场景下的汇编，
   说明何时"容器抽象零成本"、何时需要显式栈缓冲。

## 17. 本章总结

- **零成本抽象是 C++ 的核心卖点**：模板 + 内联让 `std::count` 与手写循环
  生成相同汇编（本项目已实测）；
- **性能主导因素是数据布局，不是语言抽象**：连续存储约快 2 倍（本环境），
  与"STL vs 手写"无关；
- **值语义 + const 正确性 + 严格接口**：把错误从运行时移到编译期；
- **RAII 是资源管理的默认解**：零运行时成本，异常安全；
- **现代编译器异常在未抛出时无成本**：成功路径与错误码相当（实测 1.2 vs 1.2 ns）；
- 方法论预告：性能结论必须 **测量**，且声明数据规模与工具链（Chapter 3）。
