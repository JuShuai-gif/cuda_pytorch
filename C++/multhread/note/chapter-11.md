# 第 11 章：测试和调试多线程应用

## 章节概述

多线程程序出 bug 是公认的噩梦。单线程程序至少是可重现的——一样的输入一定得到一样的输出和一样的崩溃点。多线程程序呢？时序稍微一变，bug 出现条件就变了。

第 11 章是全书最后一章，不教新概念，而是教你**如何让前面 10 章学到的知识在真实项目中不出事**。内容分三块：认识敌人（并发 bug 类型）、找到敌人（定位技巧）、构建防线（测试体系）。

---

## 11.1 并发相关的 Bug 类型

### 11.1.1 非预期的阻塞

**死锁（Deadlock）**

最经典的并发 bug。两个线程互相等对方的资源，谁也动不了。

**生活类比**：两个人在狭窄走廊迎面相遇，两人都很有礼貌地说"您先过"，但谁也不先动，结果堵死在那。

```cpp
std::mutex m1, m2;

void thread_a() {
    std::lock_guard g1(m1);
    std::lock_guard g2(m2);  // 等 m2
}

void thread_b() {
    std::lock_guard g2(m2);
    std::lock_guard g1(m1);  // 等 m1 → 死锁
}
// 解法：std::lock(m1, m2) 同时获取，或用 std::scoped_lock（C++17）
```

**活锁（Livelock）**

线程没有堵死，但一直在做"无效工作"——不停尝试一个操作，因为冲突反复失败，重新尝试，还是失败……

**生活类比**：两个人同时过门，都往左让，撞了；都往右让，又撞了。虽然一直在动，但永远过不去。

**饥饿（Starvation）**

某个线程长期得不到它需要的资源（锁、CPU 时间、队列位置），因为总有其他线程抢在前面。

**生活类比**：食堂排队打饭，总有人从你前面插队。你虽然理论上能排到，但实际永远吃不上。

### 11.1.2 竞争条件（Race Condition）

**数据竞争（Data Race）**

这是最底层的并发错误：两个线程同时访问同一内存位置，至少一个是写，且没有同步机制保护。

```cpp
int counter = 0;

void increment() {
    for (int i = 0; i < 1000000; ++i) {
        cntr += 1;  // 读+修改+写，不是原子操作 → 数据竞争！
    }
}
```

后果：count 最终值不确定，UB，编译器可以假定这不会发生然后做出各种吓人的优化。

**破坏不变量（Broken Invariant）**

即使没有数据竞争，逻辑上照样可能出错。比如链表——你拿锁保护了每个节点的插入操作，但插入位置的判定（在锁外面做的）和实际插入（在锁里面做的）之间有时间差，中间别的线程可能改了结构。

**生活类比**：你查了天气预报说今天不下雨（锁外判断），于是没带伞出门（锁内操作）。但判断和出门之间有 30 分钟，天气可能突然变了。你依赖的"外部信息"在你做决策和行动之间已经失效了。

**操作顺序问题**

即使每个独立操作都是线程安全的，操作之间的**组合**不一定正确。典型场景：先检查 `if (!queue.empty())`，再取 `queue.front()`——在检查之后、取之前，另一个线程把最后一个元素 pop 走了。

### 11.1.3 Heisenbug（海森堡 bug）

以海森堡测不准原理命名：**你一调试它，它就消失**。这类 bug 大多由时序敏感导致——加 print 语句引入了 I/O 延迟改变了执行时序，或者 debugger 断点暂停了某个线程，让竞态条件变得刚好不成立。

**生活类比**：家里的水龙头只有深夜 3 点才漏水，白天水管工来检查时一切正常。因为白天用水量大，水压被分散了，只有夜深人静水压足够高时才会漏。

## 11.2 定位并发 Bug 的技巧

### 11.2.1 代码审查——第一道防线

与其等 bug 跑出来再找，不如在代码阶段就拦下来。审查并发代码时可以准备一个清单：

**审查清单**：

1. **所有共享数据都受保护了吗？** —— 用 `grep` 全局搜裸的全局/静态/成员变量，确认每个都有对应的 mutex 或 atomic
2. **锁的获取顺序一致吗？** —— 如果线程 A 先锁 m1 再锁 m2，那整个项目中所有线程都必须遵循 m1→m2 的顺序
3. **锁的粒度合适吗？** —— 持锁时间太长影响吞吐，太短可能破坏不变量。持锁期间调用了外部函数（callback、虚函数）吗？这最容易出问题
4. **条件变量的谓词正确吗？** —— 用不带谓词的 `wait` 是大忌。虚假唤醒是真实存在的
5. **异常安全吗？** —— 如果持锁的代码抛异常，锁会被释放吗？（用 `lock_guard` 而不是手动 unlock 来保证）
6. **有 ABA 问题吗？** —— 使用无锁数据结构时，一个指针先被改成 B 又改回 A，另一个线程以为没变过，实际中间发生过变化
7. **atomic 操作的 memory_order 用对了吗？** —— 如果不是可证明的场景，默认用 `memory_order_seq_cst`

### 11.2.2 通过测试定位

**暴力测试（Brute-Force Testing）**

思路：给并发代码大量压力，把竞态条件的概率窗口尽量撑大，让 bug 浮出水面。

```cpp
// 暴力测试：起 100 个线程，每个操作 10000 次
void brute_force_test() {
    std::vector<std::thread> threads;
    for (int i = 0; i < 100; ++i) {
        threads.emplace_back([]() {
            for (int j = 0; j < 10000; ++j) {
                shared_data_operation();
            }
        });
    }
    for (auto& t : threads) t.join();
    assert(invariant_holds());  // 跑完检查不变量
}
```

**组合测试（Combinatorial Testing）**

改变线程数、改变操作顺序、改变数据大小——把所有已知变量排列组合来测。比如 1/2/4/8/16 个线程 × 小/中/大数据集 × 操作 A 先/操作 B 先/AB 同时。

**压力测试（Stress Testing）**

长时间跑（几小时甚至几天），模拟生产负载。通常与组合测试配合：跑 100 种组合，每种不间断跑 10 分钟。

### 11.2.3 设计可测试性

最容易被忽视的一点：**并发代码本身必须设计得可被测试**。

**内部状态检查**：

暴露一些"测试专用"的方法来检查内部不变量。比如 `is_consistent()` 方法，加在私有成员里，用 `#ifdef` 或 friend 测试类来访问。

```cpp
class thread_safe_queue {
    // ...
#ifdef TESTING
public:
    bool is_internal_state_consistent() const {
        std::lock_guard g(mutex_);
        return head_ <= tail_ && tail_ < capacity_;
    }
#endif
};
```

**日志记录**：

在关键路径上打日志。但注意——`printf`/`cout` 本身不是线程安全的（尽管大多数实现会做一定的锁保护），而且日志 I/O 会显著改变执行时序。用无锁的环形缓冲区存储日志事件，测试结束后再 dump。

### 11.2.4 多线程测试技术

**Thread Sanitizer（TSan）**

这是目前检测数据竞争最有效的工具，没有之一。GCC 和 Clang 都内置支持。

```bash
# 编译时加 -fsanitize=thread
g++ -fsanitize=thread -g -O1 -o test test.cpp
./test  # 运行时 TSan 会检测数据竞争并报告
```

TSan 的工作原理：它在每个内存访问点插入影子状态（shadow state），记录哪个线程在什么时候访问过这块内存。如果检测到两个线程对一个地址的访问至少有一个写且没有 happens-before 关系，它就报警。

**TSan 有什么限制？**
- 性能开销约 5～15 倍（测试用，生产别开）
- 内存开销约 5～10 倍
- 不能检测高层逻辑错误（不变量破坏但不涉及数据竞争）
- 不要同时用 TSan 和 ASan（Address Sanitizer），它们冲突

**LLVM/Clang 下的用法**：

```bash
clang++ -fsanitize=thread -fno-omit-frame-pointer -g -O1 test.cpp -o test
```

### 11.2.5 测试结构

**测试框架**：任何支持多线程的测试框架都可以（Google Test、Catch2、doctest 等）。关键不是框架，而是你写测试的方法。

**线程数测试**：

一个数据结构的测试至少要覆盖：
```cpp
// 不同线程数的组合
for (int thread_count : {1, 2, 4, 8, 16, 32}) {
    run_test_with_thread_count(thread_count);
}
```

因为很多 bug 只在特定线程数下才出现。单线程测试通过 ≠ 并发正确。

**并发测试的典型模式**：

```cpp
TEST(ThreadSafeQueue, ConcurrentPushPop) {
    thread_safe_queue<int> q;
    std::atomic<long long> sum{0};

    std::vector<std::thread> producers;
    for (int i = 0; i < 4; ++i) {
        producers.emplace_back([&q]() {
            for (int j = 0; j < 100000; ++j) q.push(j);
        });
    }

    std::vector<std::thread> consumers;
    for (int i = 0; i < 4; ++i) {
        consumers.emplace_back([&q, &sum]() {
            int val;
            for (int j = 0; j < 100000; ++j) {
                while (!q.try_pop(val));  // 忙等
                sum += val;
            }
        });
    }

    for (auto& t : producers) t.join();
    for (auto& t : consumers) t.join();

    // 验证总数正确
    ASSERT_EQ(sum.load(), expected_value);
}
```

### 11.2.6 测试多线程代码的性能

找出 bug 只是第一步，性能也必须是可测试的。

**Profiling 工具**：
- **perf**（Linux）：`perf record -g ./your_app && perf report` —— 看热点函数
- **VTune**（Intel）：图形化，可以看到每个线程的时间线和锁等待
- **gperftools**（Google）：`CPUProfilerStart/Stop` 插桩

**性能测试的要点**：
1. 测试不同线程数下的吞吐量，找到**扩展性拐点**（线程再多吞吐也不再增加的点）
2. 关注锁竞争率——如果某个 mutex 的竞争时间占总时间超过 10%，说明这里需要优化
3. 比较单线程版本和多线程版本在小数据量下的性能。如果 8 线程处理 100 个元素比单线程还慢，说明并行化的固定开销（线程创建、调度、同步）超过了收益

## 工业场景

| 场景 | 对应技术 |
|------|----------|
| **CI/CD 中的并发测试** | 每次 PR 提交自动跑 TSan 编译 + 全量并发测试套件。关键路径上跑 100 次重复确保 Heisenbug 能被抓住 |
| **压力测试** | 上线前用 10 倍预估负载跑 24 小时，监控线程健康度、内存使用、锁等待时间 |
| **性能回归测试** | 每次发布前对比基线——吞吐量不能下降超过 5%、锁竞争率不能升高超过 10% |

## 常见坑点

1. **`printf` 调试掩盖 bug**
   - 打印日志 → I/O → 锁 → 时序变化 → bug 消失。你喜滋滋以为修好了，其实只是藏起来了
   - 替代方案：用无锁环形缓冲区记录事件，测试结束再输出

2. **单线程测试通过就放心了**
   - 单线程正确是多线程正确的**必要但不充分**条件。一定要在不同线程数、不同时序下测

3. **TSan 没报 ≠ 没有数据竞争**
   - TSan 只能检测**实际执行路径上发生**的竞争。如果你测试用的线程 interleaving 没触发竞争，TSan 也看不出来。覆盖率是关键

4. **Assert 在并发环境下可能不可靠**
   - 传统的 `assert(condition)` 在多线程下有双重问题：条件读取本身可能涉及数据竞争、assert 失败后的 `abort` 可能导致其他线程持有锁死掉

5. **忽视虚假共享（False Sharing）**
   - 两个线程分别写两个独立的变量，但它们在同一个缓存行（cache line，通常 64 字节）。CPU 缓存一致性协议会让两个核频繁互相同步，性能暴跌但看起来没有任何共享数据冲突。`alignas(64)` 是解决办法

## 面试常问

**Q：TSan 是什么？原理是什么？**
- Thread Sanitizer，编译器内置的数据竞争检测工具
- 在每个内存访问处插入影子状态，记录访问线程和时序信息
- 检测违背 happens-before 关系的冲突访问
- 编译选项：`-fsanitize=thread`（GCC/Clang）

**Q：如何测试多线程代码？**
- 先说测试金字塔：单元测试（数据结构正确性）→ 组合测试（不同线程数 × 数据规模）→ 压力测试（长时间、高负载）
- 工具链：TSan 做数据竞争检测、perf/VTune 做性能 profiling
- 代码设计层面：暴露内部不变量检查接口、使用无锁日志

**Q：死锁的四个必要条件是什么？**
- 互斥：资源不能共享，同一时间只能一个线程用
- 持有并等待：线程持有一个资源同时在等另一个
- 不可剥夺：不能强行抢走线程已持有的资源
- 循环等待：线程间形成资源等待环
- 打破其中任何一个条件即可防止死锁。最常见是打破"循环等待"——规定全局统一的加锁顺序

## 小结：全书学习路径回顾

你已读完了《C++ Concurrency in Action》第二版的全部核心章节。回顾这 11 章的旅程：

| 第 2 章 | 线程管理入门 | `std::thread` 的创建、join/detach、线程传参、转移所有权 |
| 第 3 章 | 线程间共享数据 | 用 `std::mutex` 保护共享数据、`lock_guard`、死锁防治 |

| 第 5 章 | C++ 内存模型与原子操作 | `std::atomic`、memory order、fence、无锁编程基础 |
| 第 6 章 | 无锁数据结构设计 | 无锁队列、无锁栈、hazard pointer、RCU |
| 第 7 章 | 并发数据结构设计 | 线程安全的 hash map、链表、队列的工程实现 |

你的能力进阶线：
1. **能用**：会创建线程、加锁、用条件变量（第 2～4 章）
2. **能用好**：理解内存模型，会选正确的 memory_order，能写无锁代码（第 5～6 章）
3. **能设计**：能设计线程安全的数据结构和并发架构（第 7～8 章）
4. **能工业化**：能建线程池、用并行算法、做系统性的并发测试（第 9～11 章）

并发编程不是看一遍书就能精通的领域。建议的学习节奏：
- **第一遍**：通读全书，能理解每个概念的生活类比，知道什么场景用什么工具
- **第二遍**：手写代码，把每章的关键设计（线程池、无锁栈、并行 sort）自己实现一遍
- **第三遍**：带着项目中的真实问题回来查阅，把书当工具手册

**并发编程的核心心法，记住三句话：**
1. **能不共享就不共享**（message passing > shared memory）
2. **共享就必须同步**（mutex 或 atomic，不要裸奔）
3. **同步了就验证它**（TSan + 压力测试，不要相信直觉）
