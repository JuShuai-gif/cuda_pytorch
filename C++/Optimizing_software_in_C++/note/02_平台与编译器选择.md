# 02 平台与编译器选择

> 本笔记对应 PDF 第 2 章 Choosing the optimal platform（第 5～14 页）。
> 本主题还覆盖 PDF 第 3.6 节 Dynamic linking and position-independent code（第 19 页）和第 14.11 / 14.12 节（静态/动态库、PIC，第 158～162 页），将在后续轮次补充。

## 1. 本章解决什么问题

"优化"不只发生在代码层面。**在写第一行代码之前，平台、微处理器、操作系统、编程语言、编译器、函数库、UI 框架的选择就已经决定了性能的上限和下限。** 本章逐个分析这些"事前决策"对最终性能的影响，并说明如何用 C++ 达到"既有高级语言的生产力、又有接近底层的性能"。

一句话结论：**C++ 是性能优先时最值得选的语言；GNU（GCC）和 Clang 是目前优化能力最好的 C++ 编译器；能用 64 位就用 64 位；性能敏感时优先静态链接。**（来源：PDF 第 9、11、158 页）

## 2. 核心概念

| 术语 | 含义 | 出处 |
|------|------|------|
| CISC | 复杂指令集（x86），代码紧凑，利于代码缓存 | PDF 第 5 页 |
| 寄存器 | CPU 内部的临时存储，比内存快得多；数量稀缺 | PDF 第 7 页 |
| 解释型语言 | 逐行解释执行，循环体被反复解释，非常低效 | PDF 第 8 页 |
| 中间代码/JIT | 先编译成字节码，运行时再解释/即时编译 | PDF 第 8 页 |
| 编译器 | 把 C++ 源码翻译成机器码的工具；不同编译器优化能力差异大 | PDF 第 10 页 |
| 函数库 | 标准库不一定最优；关键库值得厂商投入大量优化 | PDF 第 11 页 |
| PIC（位置无关代码） | 共享库使用的相对寻址机制，效率较低 | PDF 第 19 页 |
| 静态链接 vs 动态链接 | 前者把代码并入可执行文件，后者运行时加载共享库 | PDF 第 158 页 |

## 3. 工作原理

**平台选择为什么重要？**

性能优化是"在既定硬件和工具链上榨取性能"。如果语言选了 JIT/解释型、编译器选了优化能力弱的产品、库选了一个不针对 CPU 分派的实现，那么之后的所有微优化都只能弥补"先天差距"的一部分。作者在 2.4 节给出一个判断链（PDF 第 8～10 页）：

1. **语言的实现方式决定性能上限**：编译成机器码 > JIT 字节码 > 解释执行。循环体在解释型语言里每轮都被重新解释，在 JIT 语言里首次运行还要先编译。
2. **运行时框架是隐藏成本**：Java/.NET 这类中间代码框架需要加载庞大的运行时，这个加载/编译时间往往超过程序本身的执行时间。
3. **编译器的选择决定代码质量**：同一个 C++ 源码，好的编译器生成的机器码在指令数、向量化、寄存器分配上明显更优（PDF 第 11 页给出：Clang/GNU 在多数测试中优化最好）。

**64 位 vs 32 位为什么有性能差异？**

x86-64 把通用寄存器从 8 个增加到 16 个，并把函数参数改为寄存器传递（PDF 第 7 页）。寄存器多 → 中间结果可以留在寄存器里而不是反复读写内存；参数走寄存器 → 函数调用开销下降。代价是指针从 4 字节变 8 字节，缓存效率略降。净收益取决于程序特征：函数调用多、内存块大、用 64 位整数计算的应用收益明显（5-10%）；瓶颈不在此处的程序没有差别（PDF 第 7～8 页）。

**为什么要关注静态 vs 动态链接？**

动态链接（共享库 .so / .dll）运行时才解析符号，调用要经过 PLT/GOT 查表；共享库按页对齐加载导致不同库争抢相同的缓存行（PDF 第 158 页）。Linux 共享库默认用 PIC，64 位下相对寻址尚可，32 位下访问静态数据要经过多达四步的地址计算（PDF 第 160 页）。

## 4. PDF 核心观点

### 4.1 硬件平台（2.1，第 5～6 页）

- 硬件平台的选择已不像从前重要；PC、RISC/CISC、主机的界线在模糊化。决定因素多为价格、兼容性、二次供货、开发工具，而非计算能力（PDF 第 5 页）。
- CISC（x86）被批评指令集不优雅，但代码紧凑使其在缓存有限时反而有优势；x86 的寄存器稀缺问题已被 64 位扩展（寄存器翻倍）和 AVX512（向量寄存器翻四倍）缓解（PDF 第 5 页）。
- 图形加速器/FPGA 是可选方案：FPGA 用硬件描述语言表达并行电路，特定任务可更快；但移植性差（PDF 第 5～6 页）。

### 4.2 微处理器（2.2，第 6 页）

- 竞争品牌间的基准性能相近；多核有利于可并行的应用；低功耗小处理器对轻负载足够。

### 4.3 操作系统（2.3，第 7～8 页）

- 64 位系统相对 32 位：寄存器翻倍、参数寄存器传递、64 位整数、大内存分配更高效、SSE2 全支持、支持数据相对寻址（PDF 第 7 页）。
- 64 位的劣势：指针/引用/栈项占 8 字节使缓存效率下降；静态/全局数组寻址多几条指令；部分指令长 1 字节（PDF 第 7～8 页）。
- 32 位 Windows 与 Linux 性能几乎相同（调用约定相同）；64 位下 Linux/BSD/Mac 支持 6 整数 + 8 浮点共 14 个寄存器参数，64 位 Windows 只有 4 个，因此调用多的应用在 64 位 Linux 上可能更快（PDF 第 7～8 页）。
- 需要超过 2 GB 数据时只能用 64 位（PDF 第 8 页）。

### 4.4 编程语言（2.4，第 8～10 页）

- 解释型（JavaScript、PHP、shell）非常低效；JIT（Perl、部分 Java、.NET）可接受但运行时框架开销大（PDF 第 8 页）。
- **编译为原生机器码的语言最快**：C、C++、D、Pascal、Fortran（PDF 第 8～9 页）。
- 选 C++ 的理由：出色的编译器与优化函数库；含 C 子集可做底层优化；能输出汇编便于检查；支持 intrinsics/内联汇编；可移植（PDF 第 9 页）。
- C++ 的缺点：无数组越界/整数溢出/非法指针检查——这是它快的原因，也是安全责任在程序员的原因（PDF 第 9 页）。
- 混合方案：核心热代码用编译 C++ 做成 DLL/.so，外围用高级框架；可行但有边界开销（PDF 第 9～10 页）。

### 4.5 编译器（2.5，第 10～11 页）

- MSVC：功能友好、调试器好，但代码优化不是最好，可用作开发阶段（PDF 第 10 页）。
- GCC（Gnu）：最好的优化编译器之一，免费开源，命令行不友好（PDF 第 10 页）。
- Clang：非常好的优化编译器，很多情况下是最好的；GCC 的同类工具（PDF 第 10 页）。
- Intel icx：基于 LLVM，与 Clang 性能相近；经典版 icc 已于 2024 停止维护，在 AMD 上性能差（PDF 第 10～11 页）。
- **作者结论：开源编译器 Clang 和 Gnu 在优化上表现最好**（PDF 第 11 页）。

### 4.6 函数库（2.6，第 11～13 页）

- 标准库"并不总是完全优化"；库函数面向所有用户、值得深度优化（PDF 第 11 页）。
- 若 profile 显示时间大量花在库函数，换一个更高效的库可能是最大的收益（PDF 第 11 页）。
- 各家库对比（表 2.1，PDF 第 12 页）：memcpy/strlen 每字节周期数差异巨大（如 strlen 128 字节在 Intel Core 2 上，Gnu 32 位默认是 Asmlib 的十余倍）。测试用的库版本较老，仅供示意。
- GNU 的 `-fno-builtin` 可用库版本替代编译器内建内存/字符串函数（PDF 第 12 页）。

### 4.7 UI 框架（2.7，第 13～14 页）

- 大型软件大部分代码在 UI；UI 框架体积可能超过应用本身，加载更耗时（PDF 第 13 页）。
- 轻量替代（如 WTL）比重型框架（如 MFC）更快更小；Qt/wxWidgets 利于跨平台（PDF 第 13 页）。
- 控制台程序最快、最紧凑、最易移植，但可用性差（PDF 第 13～14 页）。

### 4.8 克服 C++ 的缺点（2.8，第 14～15 页）

- 可移植性：把系统相关代码与任务相关代码分模块（PDF 第 14 页）。
- 安全性三问题：非法指针、数组越界、整数溢出（PDF 第 14～15 页）。
- 指针安全：多用引用、指针初始化为 0、避免指针运算与类型转换、避免 `scanf`（PDF 第 14 页）。
- 数组安全：用容器类替代裸数组；字符串用 string 类但注意频繁分配开销，或用内存池（PDF 第 15 页）。
- 整数溢出：C 标准规定有符号溢出是"未定义"，GCC 可能基于"不发生溢出"优化掉检查。对策：溢出前检查、用无符号、`-ftrapv`（极低效）、`-Wstrict-overflow=2` 告警、`-fwrapv`/`-fno-strict-overflow` 使行为良定义（PDF 第 15 页）。

## 5. 简单示例

2.8 节的核心是"让 C++ 快且安全"。下面是整数溢出处理的对策示例（PDF 第 15 页）：

```cpp
// Integer overflow is undefined behavior for signed int.
// Solutions listed on PDF p15 (section 2.8):
//   (1) check before overflow happens
//   (2) use unsigned (guaranteed to wrap around)
//   (3) -ftrapv (extremely slow, only for debugging)
//   (4) -Wstrict-overflow=2  -> compiler warning
//   (5) -fwrapv or -fno-strict-overflow -> define the behavior

#include <iostream>
#include <climits>

// (2) unsigned wraps around by definition:
unsigned int mul_wrapping(unsigned int a, unsigned int b) {
    return a * b;               // well-defined wrap-around
}

// (1) check BEFORE the operation:
int mul_checked(int a, int b, bool &ok) {
    ok = (b != 0 && a > INT_MAX / b);
    return ok ? a * b : 0;
}

int main() {
    bool ok;
    int r = mul_checked(1000, 1000, ok);
    std::cout << "checked result = " << r << ", ok=" << ok << "\n";
    std::cout << "wrapping  = " << mul_wrapping(0xFFFFFFF0u, 4u) << "\n";
}
```

## 6. 未优化代码

安全的"反面"——裸指针 + 无检查字符串 + 依赖未定义行为的写法（PDF 第 14～15 页）：

```cpp
// Unsafe patterns (PDF p14-15):
//   * raw C strings copied into fixed buffers without length checks
//   * relying on signed overflow "working as expected"
//   * scanf / pointer arithmetic everywhere

#include <cstring>

void unsafe_copy(const char *src, char *dst, size_t cap) {
    // NO length check: if src is longer than dst buffer -> buffer overflow,
    // may overwrite the return address and other variables (PDF p15).
    strcpy(dst, src);
}

int unsafe_normalize(int a) {
    return a * 100;   // assumes overflow never happens; it is UB if it does
}
```

## 7. 优化后代码

同样功能，安全且性能可控（PDF 第 14～15 页）：

```cpp
#include <cstring>
#include <string>

// Use std::string instead of raw C arrays. Safe and convenient.
// Note: PDF p15 points out that std::string allocates a new block per
// modification; for extreme throughput use a memory pool (see section 9.8).
void safe_copy(const std::string &src, std::string &dst) {
    dst = src;
}

// Guarded by design: check bounds explicitly where they cannot be ruled
// out by program logic (PDF p15).
bool safe_bounded_copy(const char *src, char *dst, size_t cap) {
    size_t n = strlen(src);
    if (n >= cap) return false;      // explicit bounds check
    memcpy(dst, src, n + 1);
    return true;
}

int safe_normalize(int a) {
    // signed overflow is UB; do it in a well-defined way, or check first
    if (a > 21474836) return 2147483647;   // clamp
    return a * 100;
}
```

## 8. 为什么会更快

本章是"选型"，不是"改代码"。但选型本身就是最大的性能杠杆：

- **语言实现**：原生编译比解释快一个到几个数量级（循环体解释开销，PDF 第 8 页）；比 JIT 快在"省去运行时框架加载与首次编译"（PDF 第 8 页）。
- **编译器**：GNU/Clang 的优化能力（内联、向量化、循环优化、代数化简）直接转化为更少的指令和更好的调度（PDF 第 11 页，详细在第 8 章）。
- **64 位模式**：寄存器翻倍 + 参数寄存器传递 → 更少的访存和调用开销；对调用密集应用可快 5-10%（PDF 第 7～8 页）。
- **静态链接**：避免 PLT/GOT 查表与共享库的缓存行争抢（PDF 第 158 页，后续轮次详述）。
- **函数库选择**：库里 memcpy/strlen 等每字节周期数在不同实现间相差数倍到十余倍（表 2.1，PDF 第 12 页）。

## 9. 如何验证

平台/编译器选择的效果，最直接的验证是"同一段代码、不同工具链跑出不同结果"：

```bash
# 对比不同优化等级（-O0 vs -O2 vs -O3）
g++ -O0 -std=c++17 bench.cpp -o bench_O0
g++ -O2 -std=c++17 bench.cpp -o bench_O2
g++ -O3 -std=c++17 bench.cpp -o bench_O3
time ./bench_O0
time ./bench_O2
time ./bench_O3

# 查看 64 位与 32 位差异（需要 32 位运行库；可选）
# g++ -m32 -O2 -std=c++17 bench.cpp -o bench32

# 查看编译器生成代码，判断是否充分利用寄存器/指令集
g++ -O3 -std=c++17 -S -masm=intel bench.cpp -o /tmp/bench.s

# 换编译器对比（若机器上安装了 clang）
# clang++ -O3 -std=c++17 bench.cpp -o bench_clang
```

- 编译命令：`g++ -O3 -std=c++17`（当前环境 g++ 13.3.0）
- 运行命令：`time ./bench_*`
- Benchmark 方法：正式对比应多轮取中位数，见 `note/14_性能测试与Benchmark.md`
- perf 命令：`sudo perf stat ./bench_O3`（本机 `perf_event_paranoid=4`，需 root，见 README）
- 查看汇编：`g++ -O3 -S -masm=intel ...`

## 10. 常见误区

- **误区一：32 位和 64 位性能一定一样/一定不同。** 作者明确说：只有函数调用多、大内存分配多、用 64 位整数时才有可测差异（PDF 第 8 页）。
- **误区二：MSVC 的代码质量等于 GCC/Clang。** 作者测试表明 MSVC 生成的指令更多（PDF 第 11、80 页）。
- **误区三：标准库是充分优化的。** "标准库并不总是完全优化"（PDF 第 11 页），关键库函数值得换库或替换实现。
- **误区四：C++ 不安全，所以选托管语言更稳。** C++ 不做检查是性能优势；用容器、引用、检查即可可控地规避风险（PDF 第 14～15 页）。
- **误区五：`-O3` 一定比 `-O2` 快。** 编译器优化不是单调递增；某些情况下代码缓存/微指令缓存成为瓶颈时，`-Os` 反而更快（PDF 第 85 页，第 8 章展开）。

## 11. 实践任务

1. 用 `lscpu`、`g++ --version` 记录你机器的 CPU 指令集、编译器版本、`perf_event_paranoid`，判断哪些优化手段可用。
2. 写一个 100 万次函数调用的小程序，分别以 `-O0`/`-O2`/`-O3` 编译并 `time` 对比，验证"编译选项就是性能杠杆"。
3. 用 `-S -masm=intel` 查看 `-O0` 与 `-O3` 的汇编差异，数一数指令条数。
4. 如果系统里同时有 `g++` 和 `clang++`，对同一源码比较两者生成的汇编与运行时间。
5. 读 2.8 节（PDF 第 14～15 页），检查你项目里是否存在依赖有符号整数溢出的代码，用 `-fwrapv` 或显式检查修复。

## 12. 本章总结

- 性能优化的胜负在"写代码之前"就已部分注定：平台、语言、编译器、库、UI 框架的选型。
- C++ + 64 位 + GNU/Clang + 合适的库，是性能优先项目的主流组合。
- C++ 的快来自"不做自动检查"，因此安全责任在程序员——用容器、引用、显式检查来守住边界。
- 静态链接优先于动态链接（细节在 14.11/14.12 轮次补充）。
