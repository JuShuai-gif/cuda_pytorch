# 08 乱序执行与指令级并行

> 本笔记对应 PDF 第 11 章 Out of order execution（第 113～114 页），并衔接第 3.15 节（依赖链，第 21 页）与 3.16 节（执行单元吞吐，第 21～22 页）。

## 1. 本章解决什么问题

现代 x86 CPU（除少量低功耗型号外）都能**乱序执行**：指令不按程序顺序执行，只要结果正确。本章回答：

1. 乱序执行能带来什么收益？（单线程内的指令级并行）
2. 什么会**阻止**乱序执行？（长依赖链）
3. 程序员怎么写能帮助 CPU？（括号分组、多累加器、避免循环携带依赖）

核心结论：**乱序执行是自动的，但前提是没有长依赖链。打破循环携带依赖链（多累加器）是单线程提速最有效的手段之一。**

## 2. 核心概念

| 术语 | 含义 | 出处 |
|------|------|------|
| 乱序执行（OoO） | CPU 按可用性而非程序顺序执行指令 | PDF 第 113 页 |
| 依赖链（dependency chain） | 一串每步依赖上一步的计算 | PDF 第 21 页 |
| 循环携带依赖链 | 每轮迭代依赖上一轮结果 | PDF 第 114 页 |
| 累加器（accumulator） | 并行累加的多路部分和 | PDF 第 114 页 |
| 寄存器重命名（register renaming） | 同一逻辑寄存器映射到多个物理寄存器，实现并行 | PDF 第 114 页 |
| 延迟（latency） | 单条指令从开始到出结果 | PDF 第 21 页 |
| 吞吐（throughput） | 每周期能开始的指令数 | PDF 第 21 页 |

## 3. 工作原理

### 3.1 延迟 vs 吞吐（PDF 第 21 页）

浮点加法延迟可能 3 周期，但执行单元是**流水线**的：第一个加法 T 开始 T+3 结束，只要结果独立，第二个加法 T+1 就能开始、T+4 结束。因此：

- 一串**互相依赖**的加法：每 3 周期才出一个结果（受延迟限制）；
- 一串**相互独立**的加法：每周期都能开始新加法（受吞吐限制）。

### 3.2 寄存器重命名（PDF 第 114 页）

`temp = a[i] + b[i]; c[i] = temp*temp;` 循环中，编译器把 `temp` 放寄存器。CPU 发现本轮的 `temp` 与上轮无关，就给同一个逻辑寄存器分配**新的物理寄存器**，从而同时执行多轮迭代。现代 CPU 可维护上百个待定操作（PDF 第 114 页）。

### 3.3 依赖链如何形成

`y = a+b+c+d` 按 `((a+b)+c)+d` 计算：每步都要等前一步。而 `(a+b)+(c+d)` 两组括号可同时算。循环里的 `sum += list[i]` 更是把整个循环串成一条链。

## 4. PDF 核心观点

### 第 3.15 / 3.16 节（第 21～22 页）

- 乱序执行使 CPU 能同时做多件事，最先进的 CPU 可在结果互不依赖时同时执行 4/6/8 条指令（PDF 第 21 页）。
- 为利用乱序执行，**必须避免长依赖链**；循环携带依赖链尤其致命（PDF 第 21 页）。
- 延迟与吞吐必须区分：加法延迟 3 周期但吞吐可为每周期 1 个（PDF 第 21 页）。
- 性能最优：无瓶颈、无长依赖链时，性能受执行单元**吞吐**限制而非延迟（PDF 第 21 页）。
- 浮点代码最好加乘平衡；除法慢；整数计数操作通常不占总时间（PDF 第 21～22 页）。

### 第 11 章 Out of order execution（第 113～114 页）

- 所有现代 x86 CPU 都能乱序执行，除少量低功耗型号（如 Intel Atom）（PDF 第 113 页）。
- `y = a+b+c+d` 是依赖链；写成 `y = (a+b)+(c+d)` 两括号可独立计算，省几个周期（PDF 第 113 页，Example 11.1）。
- **不要指望编译器自动改写浮点表达式**——可能损失精度（PDF 第 113 页），括号必须手写。
- 循环累加 `sum += list[i]` 是长依赖链：若加法延迟 3 周期，100 个数约 300 周期（PDF 第 113 页，Example 11.2a）。
- **拆成两个累加器**（`sum1`、`sum2`）：两条独立链，约 154 周期；顶级 CPU 有 2 个浮点加法单元且流水线化（PDF 第 114 页，Example 11.2b）。
- **最优累加器数约 3-4 个甚至更多**，视 CPU 而定（PDF 第 114 页）。
- 迭代数不能被展开因子整除时，把余数放循环外或补零元（PDF 第 114 页）。
- 若**没有**循环携带依赖链，无需展开循环：寄存器重命名让 CPU 自动重叠多轮迭代（PDF 第 114 页，Example 11.3）。
- 乱序执行自动工作的条件（PDF 第 114 页）：
  1. 无循环携带依赖链（除整数计数器外）；
  2. 中间结果在寄存器而非内存（重命名只对寄存器生效）；
  3. 循环分支可预测（大/常数循环次数即可）；
  4. 循环体避免预测差的分支。
- 程序员可做两件事最大化收益：**避免长依赖链**；**混合不同类型操作**（整数+浮点、加法+乘法、计算+访存）以平均分配执行单元（PDF 第 114 页）。
- 超长依赖链即使不跨迭代也会耗尽乱序资源；可拆成多个小循环存中间结果（PDF 第 114 页）。

## 5. 简单示例

括号打破依赖链（PDF 第 113 页，Example 11.1）：

```cpp
// (a+b+c+d) evaluates as ((a+b)+c)+d : one serial dependency chain.
// ((a+b)+(c+d)) lets the CPU compute (c+d) while (a+b) is still running.
float y1(float a, float b, float c, float d) {
    return a + b + c + d;          // serial chain (compiler may keep this order)
}

float y2(float a, float b, float c, float d) {
    return (a + b) + (c + d);      // two independent chains
}
```

## 6. 未优化代码

循环携带依赖链：每次加法都要等上一次（PDF 第 113 页，Example 11.2a）：

```cpp
double sum_serial(const double *list, size_t size) {
    double sum = 0.0;
    for (size_t i = 0; i < size; ++i) {
        sum += list[i];     // sum depends on the previous sum -> serial chain
    }
    return sum;
}
```

## 7. 优化后代码

多累加器打破依赖链（PDF 第 114 页，Example 11.2b）：

```cpp
double sum_parallel(const double *list, size_t size) {
    double s0 = 0.0, s1 = 0.0, s2 = 0.0, s3 = 0.0;   // 4 accumulators
    size_t i = 0;
    for (; i + 3 < size; i += 4) {
        s0 += list[i];
        s1 += list[i + 1];
        s2 += list[i + 2];
        s3 += list[i + 3];
    }
    for (; i < size; ++i) s0 += list[i];             // tail
    return (s0 + s1) + (s2 + s3);
}
```

## 8. 为什么会更快

- **指令依赖**：4 条独立累加链，加法延迟被隐藏——只要还有独立的加法可发，执行单元就不断流（PDF 第 21 页的 T/T+1 例子）。
- **执行单元吞吐**：每个加法单元流水线化且通常有 2 个以上（PDF 第 21～22、114 页）；4 累加器喂满它们。
- **编译器优化能力**：`-O3 -ffast-math` 下 GCC 通常会把 `sum_serial` 自动改写为多累加器并向量化（PDF 第 114、129 页），所以可能实测无差别；但依赖编译器和选项，手写版本在任何情况下都成立。
- **循环控制开销**：4 路展开使循环分支每 4 次迭代才执行一次（次要收益）。

## 9. 如何验证

```bash
# 编译两个版本
g++ -O2 -std=c++17 -DUSE_SERIAL demo.cpp -o demo_serial
g++ -O2 -std=c++17 demo.cpp -o demo_parallel

# 多轮计时（程序内置预热与多轮测量）
./demo_serial
./demo_parallel

# 不启用 fast-math 时手动版本优势最明显；启用后编译器可能已自动改写
g++ -O3 -ffast-math -std=c++17 demo.cpp -o demo_fast
./demo_fast

# 看汇编：serial 版本是一条 add 链；parallel 版本有 4 个独立累加寄存器
g++ -O2 -std=c++17 -S -masm=intel demo.cpp -o /tmp/demo.s

# 用 perf 看指令吞吐（instructions / cycles）
sudo perf stat ./demo_serial
sudo perf stat ./demo_parallel
```

- 编译命令：`g++ -O2 -std=c++17`（本机 g++ 13.3.0）
- 运行命令：`./demo_serial` / `./demo_parallel`
- Benchmark 方法：预热 + 多轮取中位数（`note/14_性能测试与Benchmark.md`）
- perf 命令：`sudo perf stat`（本机需 root）；关注 `instructions` 与 `cycles` 比值
- 查看汇编：`g++ -O2 -S -masm=intel`

## 10. 常见误区

- **误区一：指令顺序 = 执行顺序。** 现代 CPU 乱序执行（PDF 第 113 页）。
- **误区二：编译器会替我把浮点表达式改成并行。** 不会，因精度原因（PDF 第 113 页）。
- **误区三：展开循环一定快。** 没有依赖链时寄存器重命名已足够，展开多余（PDF 第 114 页）。
- **误区四：多累加器越多越好。** 最优约 3-4 个，取决于 CPU 的加法单元数量（PDF 第 114 页）。
- **误区五：只要计算独立就自动并行。** 中间结果必须放寄存器；放内存则重命名失效（PDF 第 114 页）。
- **误区六：乱序执行是万能的。** 长依赖链会耗尽乱序资源，需手动拆链（PDF 第 114 页）。

## 12. 本章总结

- 乱序执行 + 寄存器重命名让单线程指令级并行成为可能。
- 最大敌人是依赖链，尤其是循环携带依赖链。
- 手动括号、多累加器、混合操作类型，是喂满执行单元的手段。
- 先确认编译器是否已自动做，再做手写优化（PDF 第 114 页的精神）。
