# 06 内存与缓存优化

> 本笔记对应 PDF 第 9 章 Optimizing memory access（第 92～110 页），覆盖 9.1～9.11，并衔接 7.1（变量存储）与 3.13（内存访问成本）。

## 1. 本章解决什么问题

**内存是最大的性能黑洞之一。** 缓存命中只需 2-4 个周期，而缓存未命中访问 RAM 要**几百个周期**（PDF 第 21、93 页）。当数据量超过缓存、访问又分散时，内存访问就是程序最大的时间消耗者。

本章解决三个问题：

1. **Cache 是怎么组织的？**（9.1、9.2）理解组/路/关键步长，才能解释"为什么 512×512 矩阵转置突然慢了 6 倍"这类现象。
2. **怎么让数据待在缓存里？**（9.3-9.9）函数/变量放在一起、对齐、容器选择、顺序访问、避免 2 的幂竞争。
3. **能主动控制缓存吗？**（9.11）预取与非时间性存储（MOVNT）。

核心结论：**一起用的数据放一起、顺序访问、别用链表、别用 2 的幂的大结构。**

## 2. 核心概念

| 术语 | 含义 | 出处 |
|------|------|------|
| 缓存行（cache line） | 缓存与内存交换的最小单位，通常 64 字节 | PDF 第 92 页 |
| 组（set）/路（way） | 缓存按组组织，每组若干路；地址只能进固定组 | PDF 第 92 页 |
| 关键步长（critical stride） | 相距该倍数的地址争抢同一组缓存行 | PDF 第 92 页 |
| 命中/未命中（hit/miss） | 数据是否已在缓存中 | PDF 第 93 页 |
| AoS / SoA | 结构体数组 vs 数组结构体（数据布局） | PDF 第 93 页 |
| 内存池（memory pool） | 用一大块内存装多个对象 | PDF 第 98 页 |
| 非时间性存储（non-temporal store） | 写内存但不加载缓存行（MOVNT） | PDF 第 109 页 |
| 预取（prefetch） | 提前把未来要用的数据读入缓存 | PDF 第 109 页 |
| 分块（tiling/blocking） | 把大矩阵切成小块处理以利用缓存 | PDF 第 107 页 |

## 3. 工作原理

### 3.1 缓存如何组织（9.2，第 92～93 页）

以 8 KB 缓存、64 字节行、32 组 × 4 路为例：

- 行数 = 8×1024/64 = 128 行；
- 内存地址 `a` 只能进入某个固定组：`set = (a / 行大小) % 组数`；
- 例：地址 `0x2710`，`set = (0x2710/0x40) % 0x20 = 0x1C`，可放入该组的 4 条缓存行之一（LRU 淘汰）。

**关键步长** = 组数 × 行大小 = 总缓存大小 / 路数。地址相距关键步长整数倍的变量会争抢同一组，互相驱逐，造成"缓存竞争"。

### 3.2 未命中为什么这么贵

- L1 命中：2-4 周期；未命中要从 L2/L3/RAM 逐级找。
- RAM 未命中：数百周期（PDF 第 21、93 页）。
- 一个缓存行 64 字节：读一个 `int` 会带进整行，所以**连续访问相邻数据几乎免费**，随机访问则每次都付出未命中代价。

### 3.3 为什么链表慢

链表的每个对象单独 `new`，内存不连续、指向分散；且遍历时必须等上一个节点指针加载完才能算下一个地址——这是**依赖链**，阻塞乱序执行（PDF 第 96～97 页）。连续数组则能被硬件预取器自动预取（PDF 第 109 页）。

## 4. PDF 核心观点

### 9.1 代码与数据的缓存（第 92 页）

- 缓存是主内存的"代理"，更小、离 CPU 更近、访问快得多；常有二到三级（PDF 第 92 页）。

### 9.2 缓存组织（第 92～93 页）

- 组/路/行结构、set 计算公式（见上文）（PDF 第 92 页）。
- **关键步长 = 组数 × 行大小 = 总缓存大小 / 路数**；相距该步长倍数的变量争抢同一组缓存行（PDF 第 92 页）。
- 代码缓存同理：函数相距关键步长也会互相驱逐（PDF 第 92 页）。

### 9.3 一起用的函数应存在一起（第 93 页）

- 函数按源码顺序存放；把关键路径上一起用的函数放同一个源文件、彼此相邻；冷分支（错误处理）放函数末尾或独立函数（PDF 第 93 页）。
- 控制链接顺序可让父/子类成员函数相邻；用链接 map 文件检查（PDF 第 93 页）。

### 9.4 一起用的变量应存在一起（第 93～95 页）

- 变量尽量在函数内声明（栈）、避免全局/静态、避免 new/delete（PDF 第 93 页）。
- 交替访问两个数组 `a[0],b[0],a[1],b[1]...` 时，改成**结构体数组（AoS）**使数据连续（PDF 第 93 页，Example 9.1）。
- 活跃范围不重叠的数组可用 `union` 共享内存省缓存（PDF 第 94 页，Example 9.2）。

### 9.5 数据对齐（第 95 页）

- 变量地址可被其大小整除时访问最有效；对象大于 16 字节按 16 对齐（PDF 第 95 页）。
- 大对象/数组可按缓存行对齐：`alignas(64) int BigArray[1024];`（PDF 第 95 页）。

### 9.6 动态内存分配（第 95～97 页）

- 四种合理用途：大小编译期未知、对象数量未知、变长字符串、栈放不下的大数组（PDF 第 95 页）。
- 优点：结构清晰、不过度分配、支持无上限场景（PDF 第 95 页）。
- 缺点：分配/释放慢、**堆碎片化破坏缓存**、扩容要复制、垃圾回收时机不可控、易泄漏/悬垂、对齐不保证、别名阻碍优化（PDF 第 95～96 页）。
- 数量有限时动态分配成本可忽略；**预估最终大小一次分配**优于逐步扩容（PDF 第 96 页）。
- 链表比线性数组慢的四个原因：逐对象分配、内存不连续、链接指针占空间、指针依赖链（PDF 第 96～97 页）。
- **内存池**：一大块装多个对象，避免逐对象分配（PDF 第 97 页）。
- `alloca`：栈上分配变长数组，分配几乎零开销、不碎片化、返回即释放；但函数不能返回指向它的指针（PDF 第 97 页，Example 9.3）。

### 9.7 数据结构与容器类（第 97～105 页）

- 动态内存应封装进带析构的容器类，防泄漏（PDF 第 97 页）。
- 标准容器"为通用性和灵活性设计，**牺牲了效率**"；内存分配尤其浪费（PDF 第 98 页）。
- `std::vector`：连续块，填满后按约 50% 增长重分配；实验插入 10 个元素发生 7 次分配（1,2,3,4,6,9,13）（PDF 第 98 页）。**用 `reserve()` 预估容量**可避免（PDF 第 98 页）。
- 链表式容器逐对象分配，缓存极差；`vector of vector` 做矩阵是"非常低效"（PDF 第 98 页）。
- 迭代器不是必需；连续数组 + 下标即可，编译器未必能剥掉迭代器开销（PDF 第 98 页）。
- **选择容器的决策清单**（PDF 第 98～99 页）：单元素用局部/智能指针；编译期知最大数用定长数组；数量已知先 `reserve`；FIFO 用环形缓冲队列、LIFO 用带栈顶下标的数组；按键查找用数组/二叉搜索/哈希表（按规模选）；搜索只在全部加入后进行则排序后二分。
- 标准容器一览（PDF 第 100～101 页）：`std::array`（定长无检查）、`vector`（连续、最快）、`deque`（双端队列，折中）、`forward_list`/`list`（链表，逐对象分配）、`stack`、`set`（红黑树）、`map`（键值红黑树）、`unordered_set`/`unordered_map`（哈希表）。
- 自制容器示例：带边界检查的 `SafeArray`（PDF 第 101 页 Example 9.4）、`LIFOStack`（无动态分配，PDF 第 102 页 Example 9.5）、`FIFOQueue` 环形缓冲（PDF 第 103 页 Example 9.6）、`Matrix` 单块连续内存（PDF 第 104 页 Example 9.7）。

### 9.8 字符串（第 105～106 页）

- `string`/`wstring` 每次创建或修改都 new 内存块，频繁操作很浪费（PDF 第 105 页）。
- 最快是 C 风格 `char` 数组 + `strcpy`/`strcat`/`strlen`/`sprintf`（注意溢出检查责任在程序员）（PDF 第 105 页）。
- 兼顾安全与速度：所有字符串放进内存池（PDF 第 106 页）。

### 9.9 顺序访问数据（第 106 页）

- 顺序访问最有效、倒序稍差、**随机访问最差**；读写都一样（PDF 第 106 页）。
- 多维数组最后一个下标在内层循环变化（行主序）；不要交换循环顺序（Fortran 相反）（PDF 第 106 页，Example 9.8）。

### 9.10 大数据结构中的缓存竞争（第 106～108 页）

- 非顺序访问时，行距 = 2 的幂会触发关键步长竞争（PDF 第 106 页）。
- **转置实验**（Example 9.9a，PDF 第 106～107 页）：64×64 矩阵转置每元素 16.4 周期，65×65 反而只有 11.8——因为 64 行的行距命中 L1 关键步长；512×512 时 L2 竞争让每元素从 ~38 周期暴涨到 **230.7**（表 9.1，PDF 第 107 页）。
- 解法一：行距加填充列（512×520，留 8 列不用），时间降到 36（PDF 第 107 页）。
- 解法二：**分块/平铺**（square blocking），小块内转置以利用缓存（Example 9.9b，PDF 第 108 页）。
- L2 竞争极昂贵，务必处理；L1 竞争相对便宜，不必过度工程化（PDF 第 108 页）。

### 9.11 显式缓存控制（第 109～110 页）

- 表 9.2：预取 `_mm_prefetch`（SSE）、非时间性存储 `_mm_stream_*`（MOVNT，SSE/SSE2）（PDF 第 109 页）。
- **预取**：作者测试中显式预取没有提速——现代 CPU 靠乱序执行与预测机制**自动预取**常规访问模式；只要访问是固定步长的规则模式就不用手动预取（PDF 第 109 页）。
- **非时间性存储**：写未缓存内存时，普通写会把整个缓存行读进缓存再写回；MOVNT 直接写内存不污染缓存。适合"写入后近期不再读该区域"的场合（PDF 第 109 页）。
- 实验（表 9.3，PDF 第 110 页）：512×512 转置拷贝，普通写 378.7 周期/元素，MOVNT 168.5；但 64×64（L1 竞争，无 L2 竞争）MOVNT 反而更慢（80.8 vs 14.0）。**只在预期 L2 未命中时才用 MOVNT**（PDF 第 110 页）。
- 不要对同一区域混用普通写与非时间性写（PDF 第 109 页）。

## 5. 简单示例

模拟缓存组织计算（PDF 第 92 页的 8 KB / 64 行 / 32 组 × 4 路例子）：

```cpp
// Simulate the set-associative mapping described on PDF p92.
// 8 KB cache, 64-byte lines, 32 sets x 4 ways.
//   lines = 8*1024/64 = 128,  sets = 32
//   set = (address / line_size) % num_sets

#include <cstdint>
#include <cstdio>

int main() {
    const int line_size = 64;
    const int num_sets  = 32;             // 8 KB / 64 B / 4 ways
    const int critical_stride = num_sets * line_size;   // 2048 bytes

    std::uint64_t a = 0x2710;             // example address from PDF
    int set = (int)((a / line_size) % num_sets);
    std::printf("address 0x%llX -> set %d (PDF says 0x1C = %d)\n",
                (unsigned long long)a, set, 0x1C);

    std::printf("critical stride = %d bytes\n", critical_stride);
    // Addresses 0x2710, 0x2F10, 0x3710, ... are a multiple of 2048 apart
    // and therefore all map to set 0x1C -> they evict each other (PDF p92).
    return 0;
}
```

## 6. 未优化代码

交替访问两个数组，导致数据分散（PDF 第 93 页，Example 9.1a 的思想）：

```cpp
// Two parallel arrays accessed alternately: a[0],b[0],a[1],b[1],...
// Data for one "item" is spread across two distant memory regions.
int Func(int);
void process(int *a, int *b, int size) {
    for (int i = 0; i < size; ++i) {
        b[i] = Func(a[i]);   // jumps between two arrays every iteration
    }
}
```

## 7. 优化后代码

合并为结构体数组（AoS），让一项的数据连续（PDF 第 93 页，Example 9.1b）：

```cpp
int Func(int);
struct Sab { int a; int b; };   // one "item" lives in one struct

void process(Sab *ab, int size) {
    for (int i = 0; i < size; ++i) {
        ab[i].b = Func(ab[i].a);   // both a and b in the same cache line
    }
}
```

## 8. 为什么会更快

- **Cache 命中率**：AoS 中每项的 `a`、`b` 相邻（同一缓存行），读 `a` 时 `b` 已被带入缓存；两个平行数组则 `a`、`b` 各占不同缓存行，访问体积翻倍。
- **内存访问次数**：每个缓存行（64 字节）能服务更多有效数据，未命中次数下降。
- **指令数量**：AoS 只需一个基址+步进（归纳变量），不用维护两个数组指针（PDF 第 93 页）。
- **预取**：AoS 是规则顺序访问，硬件预取器（PDF 第 109 页）能无缝预取；两个平行数组同样规则，但总带宽需求更大。
- **适用范围**：只有当 `a[i]`、`b[i]` 按相同下标一起用时 AoS 才有利；如果各数组独立遍历，SoA 更利于向量化（见 `note/09_SIMD与自动向量化.md` 与 `src/08_memory_cache` 的 AoS/SoA 实验）。

## 10. 常见误区

- **误区一：缓存越大越好，不用管数据布局。** 未命中几百个周期，布局影响巨大（PDF 第 93 页）。
- **误区二：`std::list` 插入快所以更快。** 遍历链表缓存极差、还有指针依赖链；数组+下标通常更优（PDF 第 96～98 页）。
- **误区三：`std::vector` 直接插入没问题。** 会反复重分配（10 元素 7 次分配）；要 `reserve`（PDF 第 98 页）。
- **误区四：行数是 2 的幂更好。** 大矩阵非顺序访问时 2 的幂会触发缓存竞争，512×512 慢了 6 倍（PDF 第 107 页）。
- **误区五：手动预取能提速。** 现代 CPU 自动预取规则模式，显式预取通常无收益（PDF 第 109 页）。
- **误区六：MOVNT 总是更快。** 只在预期 L2 未命中时有利；小数据反而更慢（PDF 第 110 页）。

## 12. 本章总结

- Cache 命中 2-4 周期，未命中数百周期——**内存布局就是性能**。
- 一起用的数据放一起：栈优先、AoS、顺序访问、对齐、避免碎片化。
- 容器：`vector + reserve` 优先，远离链表；自制容器常更高效。
- 大结构非顺序访问避免 2 的幂；用填充列或分块解决缓存竞争。
- 显式缓存控制（预取、MOVNT）在现代 CPU 上收益有限，需按场景实测。
