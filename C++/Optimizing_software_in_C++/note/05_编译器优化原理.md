# 05 编译器优化原理

> 本笔记对应 PDF 第 8 章 Optimizations in the compiler（第 68～91 页），覆盖 8.1～8.7。

## 1. 本章解决什么问题

程序员花大量精力手写"聪明代码"，但**编译器早已学会做大部分基础优化**，而且比人快、比人全。本章解决三个问题：

1. **编译器到底能做哪些优化？**（8.1）了解之后，很多手工优化是白费的。
2. **什么阻碍了编译器优化？**（8.3、8.4）知道障碍，才能写出"编译器看得懂"的代码。
3. **怎么检查编译器实际做了什么？**（8.7）看汇编，是验证一切优化结论的最终手段。

核心结论：**先让编译器干活，再决定要不要自己干。** 但也要知道编译器不是万能的——跨模块、指针别名、纯函数、代数化简等场景它会"认怂"。

## 2. 核心概念

| 术语 | 含义 | 出处 |
|------|------|------|
| 内联（inlining） | 用函数体替换函数调用 | PDF 第 68 页 |
| 常量折叠/传播 | 编译期算出常量表达式并把常量代入后续计算 | PDF 第 68～69 页 |
| 公共子表达式消除（CSE） | 相同的子表达式只算一次 | PDF 第 69 页 |
| 活跃范围分析 | 变量存活范围不重叠则共享寄存器 | PDF 第 70 页 |
| 归纳变量（induction variable） | 用加法递推替代"计数器×常数" | PDF 第 73 页 |
| 调度（scheduling） | 重排指令以利用并行执行单元 | PDF 第 74 页 |
| 代数化简 | 用代数定律改写表达式（整数安全、浮点危险） | PDF 第 75 页 |
| 去虚化（devirtualization） | 编译期确定虚调用目标，绕开虚表 | PDF 第 76 页 |
| 指针别名（aliasing） | 两个指针可能指向同一内存，编译器无法假设独立 | PDF 第 81 页 |
| 纯函数 | 无副作用、结果仅取决于参数 | PDF 第 82 页 |
| 全程序优化（WPO） | 跨多个 .cpp 做内联/寄存器分配/常量传播 | PDF 第 86 页 |
| 剖面引导优化（PGO） | 先用采样数据指导编译器优化分支/布局 | PDF 第 85 页 |

## 3. 工作原理

### 3.1 编译器优化是"一次编译、全盘分析"

编译器把整个函数（或整个程序）读进来后做多趟变换：先内联展开，再做常量传播，再公共子表达式消除，再寄存器分配，再指令调度……一次成功的优化（如内联）往往为后面的优化"打开大门"（PDF 第 68 页）。比如 `parabola(square(x)+1)`，内联后常量传播才能把 `parabola(2.0f)` 变成 `5.0f`。

### 3.2 编译器为什么"不敢"优化？

C++ 的语义把许多自由度交给编译器判断。当编译器**无法证明某个假设成立**时，它宁可保守（生成更慢但正确）的代码，也不冒风险。典型：

- 指针别名：`a[i] = p[0]+2` 的循环里，编译器无法排除 `p[0]` 与 `a` 的某个元素重合，所以不能把 `p[0]+2` 提成循环不变量（PDF 第 81 页）。
- 浮点代数：`(a+b)+c = a+(b+c)` 在浮点上不严格成立（可能丢精度），默认不允许（PDF 第 75 页）。

### 3.3 检查汇编是唯一可信的验证

编译器优化是黑盒。作者建议用 `-S`（或反汇编器 objconv）查看实际生成的机器码（PDF 第 89 页），这也正是本项目所有实验的验证手段。

## 4. PDF 核心观点

### 8.1 编译器如何优化（第 68～76 页）

- **函数内联**：优点——消除调用/返回/传参开销、代码连续利于缓存、只调用一次时代码变小、为后续优化开路；缺点——大函数多处调用时代码膨胀（PDF 第 68 页）。
- **常量折叠**：`2.0/3.0` 编译期算好；用括号标出子表达式以确保被识别（PDF 第 68～69 页）。
- **常量传播**：`parabola(2.0f)` 可能直接折叠成常量（PDF 第 69 页，Example 8.3）。
- **指针消除**：`Plus2(&a)` 内联后变成 `a += 2`（PDF 第 69 页，Example 8.5）。
- **CSE**：`(a+1)*(a+1)` 只算一次 `a+1`（PDF 第 69 页，Example 8.6）。
- **寄存器变量**：编译器自动把最常用的变量放寄存器；32 位约 6 个整数寄存器、64 位约 14 个；浮点 8/16/32 个（PDF 第 70 页）。
- **活跃范围分析**：不重叠的变量共享同一寄存器（PDF 第 70 页，Example 8.7）。
- **合并相同分支**、**消除跳转**、**消除恒真/恒假分支**（PDF 第 70～72 页，Example 8.8-8.11）。
- **循环展开**：小循环完全展开；但**过度展开不优**，会压满代码缓存/微操作缓存/循环缓冲（PDF 第 72 页）。
- **循环不变量外提**：`b*b+1` 与循环无关就移到循环外（PDF 第 72 页，Example 8.13）。
- **向量化**：SSE2 128 位一次 4 个 float；AVX2 一次 8 个；AVX-512 一次 16 个（PDF 第 73 页，Example 8.14）。
- **归纳变量**：`i*9+3` 改为递推 `temp += 9`；数组地址用归纳变量算（PDF 第 73 页，Example 8.15/8.16）。
- **调度**：把两条独立公式交错执行以填满执行单元（PDF 第 74 页，Example 8.17）。
- **代数化简**：整数表达式安全（溢出回绕可抵消）；**浮点表达式默认不做结合律/交换律化简**，除非开选项（PDF 第 75 页，Example 8.18/8.19）。
- **去虚化**：确定 `p` 指向 `C1` 时，虚调用直接调 `C1::f`，不查虚表（PDF 第 76 页，Example 8.20）。

### 8.2 编译器对比（第 76～81 页）

- 表 8.1 列了约 70 项优化在各编译器上的支持情况（PDF 第 77～80 页）。
- **GCC 与 Clang 在多数情况下优化最好；MSVC 用更多指令完成同样任务**（PDF 第 80 页）。
- LLVM 版 Intel 编译器（icx）与 Clang 相似，某些情况下更好或更差（PDF 第 80 页）。
- **Clang 倾向过度展开循环**，代码缓存压力大，可用 `-Os` 限制（PDF 第 80～81 页）。

> 补充说明：表 8.1 测试的是 GCC 12.1、Clang 12.0、MSVC 2022 17.2.5、Intel icc 2021.6 / icx 2022.1（PDF 第 80 页）。本机 g++ 13.3 比表内版本更新，能力只增不减。

### 8.3 编译器优化的障碍（第 81～85 页）

- **跨模块**：编译器看不到其他 .cpp 的函数，无法跨调用内联/常量传播；解决：合并模块、WPO（PDF 第 81 页，Example 8.21）。
- **指针别名**：`a[i]=p[0]+2` 无法外提；用 `__restrict__` 或 `-fno-alias` 或手动存临时变量（PDF 第 81～82 页，Example 8.22）。
- **动态内存分配**：编译器不知道指针是否重叠、是否对齐（PDF 第 82 页）。
- **纯函数**：跨模块无法知道函数无副作用；GCC 用 `__attribute__((const))` 声明（PDF 第 82～83 页，Example 8.23）。
- **虚函数/函数指针**：无法确定目标就无法跨调用优化（PDF 第 83 页）。
- **代数化简受限**：整数化简较多可行，涉及除法/关系运算符的化简可能不合法；浮点几乎都要选项放行（PDF 第 83 页）。
- **浮点归纳变量**：编译器很少做（精度与依赖链问题）；手写需注意累积舍入误差（PDF 第 84 页，Example 8.24）。
- **内联函数的非内联副本**：函数可能被其他模块调用，编译器须留一份非内联副本（死代码），使缓存碎片化；加 `static` 可避免（PDF 第 84 页）。

### 8.4 CPU 优化的障碍（第 85 页）

- 长依赖链（尤其循环携带依赖链）阻止 CPU 乱序执行。见 `note/08_乱序执行与指令级并行.md`。

### 8.5 编译器优化选项（第 85～87 页）

- **调试与优化不兼容**：分别维护 debug 版（带调试支持）与 release 版（全优化）（PDF 第 85 页）。
- **优化大小 vs 速度**：当代码缓存/微操作缓存/循环缓冲是瓶颈时，`-Os` 可能比 `-O3` 更快（PDF 第 85 页）。
- **PGO**：先采样程序流，再针对热点优化与布局分支（PDF 第 85～86 页）。
- **WPO**：把多个源文件编成中间格式再整体链接，第二步完成寄存器分配与内联；中间格式不可分发（PDF 第 86 页）。
- 推荐：关闭异常处理、关闭 RTTI、启用快速浮点、函数级链接、假设无别名（需确认）、省略帧指针（PDF 第 86 页）。
- **浮点选项**（PDF 第 86～87 页）：
  - `-ffp-model=fast` / `-funsafe-math-optimizations`：允许重排操作数（`a+b+c` 与 `c+b+a` 结果可能不同）、融合乘加（FMA）；
  - `-ffinite-math-only`：允许 `a*0=0`、`a-a=0`（假设无 INF/NaN，可能检测不到 NaN）；
  - `-fno-trapping-math`：允许向量化含分支的循环；
  - `-fno-math-errno`：数学函数不设 errno，是向量化含数学函数循环的前提；
  - MSVC 对应 `/fp:fast`。

### 8.6 优化指令（第 87～89 页）

- **通用关键字**：`volatile`（禁止优化该变量）、`const`（帮助优化/折叠）、`static`（本模块专属，利于内联与过程间优化）（PDF 第 87～88 页）。
- **编译器特有**：`__fastcall`、纯函数 `__attribute__((const))`、`__restrict`、`alignas(16)`（PDF 第 88 页）。

### 8.7 检查编译器做了什么（第 89～91 页）

- `-S` 生成汇编输出；或对目标文件用 objconv 反汇编（PDF 第 89 页）。
- 调试器反汇编窗口只能看到 debug 版；想在 release 版打断点可用 `int 3`/`__debugbreak()`（PDF 第 89 页）。
- **案例分析**（Example 8.27a/b，PDF 第 89～91 页）：`a[i] = r + i/2` 的汇编暴露出三个可优化点——`i/2` 因符号位处理变慢（改 `unsigned`）、`r` 被循环内反复重载（别名假设）、`r+i/2` 可用归纳变量；手工改写后循环体从 9 条指令降到 6 条（PDF 第 90～91 页）。

## 5. 简单示例

常量折叠与传播：编译器能把整段计算在编译期算完（PDF 第 69 页，Example 8.3 的思想）：

```cpp
// Constant folding + propagation (PDF p69, Example 8.3).
// The compiler sees parabola(2.0f) -> x*x+1.0f with x=2.0f, folds to 5.0f.

float parabola(float x) {
    return x * x + 1.0f;
}

float a, b;
a = parabola(2.0f);   // compiler folds this to 5.0f
b = a + 1.0f;         // then b becomes 6.0f
```

> 用 `g++ -O2 -S` 验证：`a`、`b` 直接是常量，函数体没有浮点运算指令。

## 6. 未优化代码

指针别名阻塞循环不变量外提（PDF 第 81 页，Example 8.22a）：

```cpp
// Pointer aliasing blocks loop-invariant code motion.
// The compiler CANNOT prove that p[0] is not inside a[] and is not changed
// by the writes to a[i], so p[0]+2 must be reloaded every iteration.
void Func1(int a[], int p[]) {
    for (int i = 0; i < 100; i++) {
        a[i] = p[0] + 2;
    }
}
```

## 7. 优化后代码

```cpp
// (a) Tell the compiler the pointers do not alias (GCC/Clang keyword):
void Func1(int *__restrict__ a, int *__restrict__ p) {
    for (int i = 0; i < 100; i++) {
        a[i] = p[0] + 2;      // now allowed to hoist p[0]+2 out of the loop
    }
}

// (b) Or simply do the hoisting by hand (always works, PDF p82 Example 8.22c):
void Func2(int a[], int p[]) {
    int p02 = p[0] + 2;       // hoisted by hand
    for (int i = 0; i < 100; i++) {
        a[i] = p02;
    }
}
```

## 8. 为什么会更快

- **指令数量**：外提后循环体内从"重载 p[0] + 加法 + 存储"变为"只存储"，每轮少 1-2 条指令（PDF 第 81 页）。
- **内存访问次数**：`p[0]` 从每轮读一次变为整个循环读一次。
- **指令依赖**：去掉循环内的 load→add 依赖，流水线更顺畅。
- **编译器优化能力**：`__restrict__` 只是"许可"，编译器**可能**优化；手工外提是**保证**（PDF 第 82 页）。这也是作者反复强调"不能依赖编译器"的原因。

## 9. 如何验证

```bash
# 编译三个版本
g++ -O2 -std=c++17 alias_bad.cpp -o alias_bad
g++ -O2 -std=c++17 alias_restrict.cpp -o alias_restrict
g++ -O2 -std=c++17 alias_hoisted.cpp -o alias_hoisted

# 对比运行时间（多轮取中位数）
./alias_bad
./alias_restrict
./alias_hoisted

# 看汇编：bad 版本循环体内应有 load [p] 指令，restrict/hoisted 没有
g++ -O2 -std=c++17 -S -masm=intel alias_bad.cpp -o /tmp/bad.s
g++ -O2 -std=c++17 -S -masm=intel alias_restrict.cpp -o /tmp/res.s
diff /tmp/bad.s /tmp/res.s

# 查看向量化/内联报告
g++ -O2 -std=c++17 -fopt-info-inline alias.cpp -o /dev/null
```

- 编译命令：`g++ -O2 -std=c++17`（本机 g++ 13.3.0）
- 运行命令：`./alias_*`
- Benchmark 方法：预热 + 多轮 + 中位数（`note/14_性能测试与Benchmark.md`）
- perf 命令：`sudo perf stat ./alias_bad` 等（本机需 root）
- 查看汇编：`g++ -O2 -S -masm=intel`

## 10. 常见误区

- **误区一：我手写的优化编译器都会做。** 不一定。别名、跨模块、浮点代数都可能让它"认怂"（PDF 第 81-85 页）。
- **误区二：`-O3` 永远比 `-O2` 快。** 代码缓存/微操作缓存成为瓶颈时 `-Os` 可能更快（PDF 第 85 页）。
- **误区三：`inline` 关键字一定内联。** 编译器可能忽略请求，也可能在不需要时仍生成副本（PDF 第 68、84 页）。
- **误区四：浮点代数化简是安全的。** 浮点不满足结合律；不开放选项编译器不会做（PDF 第 75 页）。
- **误区五：debug 版的性能可以推断 release。** 两者完全不同（PDF 第 85 页）。
- **误区六：看优化后的 C++ 就能判断性能。** 必须看汇编和测量（PDF 第 89 页）。

## 11. 实践任务

1. 写 `parabola(2.0f)` 并 `-O2 -S`，确认它被折叠成常量；再试 `sin(0.8)`，观察是否折叠（应不会）。
2. 实现 6/7 节的别名例子，用汇编确认 `p[0]+2` 是否被外提。
3. 用 `-O2 -fopt-info-vec` 编译一个 `a[i]=b[i]+2` 循环，看 GCC 的向量化报告；再试 `-mavx2` 的差异。
4. 对同一程序跑 `-O0/-O2/-O3/-Os` 并比较运行时间与汇编大小，找出哪种优化对你这个程序最好。
5. 写一个含 `__attribute__((const))` 纯函数的两处调用，确认编译后只调用一次（对应 PDF 第 82 页 Example 8.23）。

## 12. 本章总结

- 编译器能做大量优化：内联、常量传播、CSE、寄存器分配、循环优化、向量化、代数化简、去虚化。
- 编译器有明确边界：跨模块、指针别名、纯函数、浮点语义都会阻止优化。
- 用好工具：`-O2/-O3`、WPO、PGO、`__restrict__`、`-ffast-math` 系列选项、`-S` 检查。
- 手写优化只在编译器做不到时才有意义；**最终以汇编和测量为准**。
