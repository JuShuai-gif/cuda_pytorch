# 20 工程实践与常见工作中的坑

> 本笔记将前 19 篇笔记的方法论落地到**真实工程项目**：工程流程、可持续基准、性能回归、以及按类别整理的实战坑库。
> PDF 核心观点仍标注页码；凡超出 PDF 范围的工程经验，一律用"补充说明"标注。

## 1. 本章解决什么问题

前面 18 篇解决的是"某段代码怎么写更快"的**单点技术**。但工作中的性能问题往往不是单点技术问题，而是：

1. **流程问题**：没有基准、没有回归门禁，优化一次就失效；
2. **环境问题**：开发机/CI/生产机的差异让结论不可复现；
3. **踩坑问题**：很多性能事故来自"看起来没问题"的常见写法。

本章回答：**在真实工程里，怎么让性能优化可持续、可复现、可回归，并躲开最常见的坑。**

> 补充说明：本章大量内容不属于 PDF 原文，而是作者依据现代工程实践整理的背景知识，全部以引用块标注。PDF 中与之呼应的章节（16.2 单元测试陷阱、13.4 测试维护、8.5 编译选项、3.2 热点分析）保留页码引用。

## 2. 核心概念

| 术语 | 含义 | 出处 |

| 基准仓库（benchmark repo） | 基准代码 + 结果的版本化管理 | 补充说明 |

## 3. 工作原理

### 3.1 性能工程的完整闭环

真实项目的性能工作是一个循环（补充说明）：

```
定义需求(性能预算/SLA)
   ↓
建立基准(可复现、多轮、防消除)
   ↓
定位热点(perf/flamegraph/汇编)
   ↓
实施优化(先给编译器机会，再手写)
   ↓
A/B 验证(同一环境、同一次运行内交替测)
   ↓
回归门禁(CI 阈值 + 结果仓库)
   ↓
上线后监控(线上热点、告警)
```

**关键：任何优化都必须回到"验证"这一步，否则不算完成。** 这与 PDF 第 167 页"必须确认改动真的提速"一致。

### 3.2 为什么单点技术不够

PDF 第 170 页（16.2）已经指出：单测最快的版本在最终程序里可能输给内存足迹更小的版本。工程层面还要叠加环境因素（CPU 频率、核心数、缓存、并发负载），所以**可持续的测量体系**比一次性优化更重要（补充说明）。

## 4. PDF 核心观点（工程相关章节）

- **单测不能代表真实性能**：测试程序内存小于缓存，未命中代价不可见；应测"含内层循环 + 真实数据"的完整场景。来源：PDF 第 170 页，章节 16.2。
- **多版本代码要能强制运行任意分支**做正确性测试；测速则在目标 CPU 上测。来源：PDF 第 139 页，章节 13.4。
- **调试与优化不兼容**：维护 debug/release 两个构建；性能结论必须来自 Release。来源：PDF 第 85 页，章节 8.5。
- **只优化热点**；优化非热点是浪费。来源：PDF 第 16 页，章节 3.2。
- **真实数据、真实规模**：测试数据要含典型随机性以获得真实的 cache miss 与分支误预测。来源：PDF 第 17 页，章节 3.2。
- **最坏情况也要测**（实时/交互应用）。来源：PDF 第 171 页，章节 16.3。

## 5. 简单示例：性能回归对比

工作中最常用的是"优化前 vs 优化后"或"上一版本 vs 当前版本"的对比。本项目提供 `scripts/compare_versions.sh`：

```bash
# 对比两个构建的同一个基准（多次运行，报告 min/median 与相对差异）
./scripts/compare_versions.sh ./build/13_intrinsics/13_benchmark \
    --other /tmp/13_benchmark_old --threshold 0.05
```

思路（补充说明）：同一环境、同一次会话内交替测 A/B 多次，取中位数，按阈值判断是否显著变慢。避免"跨机器/跨时段/单次"带来的假结论。

## 6. 未优化工程实践（工作中常见的反面）

```cpp
// 反模式 1：用 Debug 构建给用户/CI 报性能（PDF p85）
// 反模式 2：单次计时就写进 PR 描述
// 反模式 3：优化后只跑功能测试，不跑基准 → 回归无人察觉
// 反模式 4：基准里结果没用上 → 编译器删掉被测代码（PDF p168）
// 反模式 5：不同机器上的基准直接比较（频率/核心/负载不同）
```

## 7. 优化后工程实践（可持续的做法）

```cpp
// 正例：基准 = 一个可重复的独立目标（本项目 src/*/benchmark.cpp）
//   * Release 构建，-O3 -g -fno-omit-frame-pointer
//   * 预热 + 多轮，输出 min/median/mean
//   * 校验和保证 baseline/optimized 结果一致
//   * 结果落盘到 benchmark_results/<时间戳>/，可回溯
//   * CI 中跑 compare_versions.sh，超过阈值即失败
```

## 8. 为什么工程上更稳

- **可复现**：同一可执行、同一命令、多轮中位数，消除单次噪声（PDF 第 168 页）。
- **可回归**：基准入仓库 + 阈值门禁，任何"偷偷变慢"的改动都会被拦下（补充说明）。
- **可解释**：结果带时间戳 + 元数据（CPU/编译器/paranoid），跨机器也能判断差异来源（补充说明）。
- **可验证**：校验和证明优化没算错（PDF 第 167 页的精神）。

## 9. 如何验证

```bash
# 重新构建后跑全量
./scripts/build.sh && ./scripts/run_all.sh

# 批量基准（落盘带时间戳）
./scripts/benchmark_all.sh

# 性能回归对比（工程核心工具）
./scripts/compare_versions.sh ./build/04_loop/04_benchmark --threshold 0.05

# 对比两个分支/两次构建
./scripts/compare_versions.sh ./build/13_intrinsics/13_benchmark --other /tmp/old
```

## 10. 常见误区

- **误区一：优化完就完了。** 没做 A/B 验证和回归，等于没优化（PDF 第 167 页）。
- **误区二：CI 上跑一次就够。** 共享 CI 机器噪声大，至少多轮取中位数（补充说明）。
- **误区三：优化不改变正确性。** 浮点重排、UB、`-ffast-math` 都可能改变结果；必须校验和（PDF 第 75 页）。
- **误区四：基准结果能跨机器直接比较。** 频率/核心/缓存/负载都不同（补充说明）。

## 11. 常见工作中的坑（工程坑库）

> 以下为补充说明（非 PDF 原文），按类别整理工作中最常踩的坑。每条 = 现象 → 原因 → 对策。与 PDF 呼应的标注页码。

### 11.1 编译器与构建

- **坑：默认构建忘开优化，拿 Debug 数据写性能结论。**
  原因：`-O0` 不优化（PDF 第 85 页）。对策：CI 与发布强制 Release；性能 PR 附带 Release 构建号。
- **坑：`-march=native` 编出的二进制发给用户直接崩/降级。**
  原因：目标 CPU 没有对应指令集。对策：默认不用 `-march=native`，或用 CPU dispatch（PDF 第 135 页）。
- **坑：`inline` 写了但没生效，热循环里还是 call。**
  原因：跨 TU 的内联需要 LTO/WPO，或函数太大被拒。对策：`-fopt-info-inline` 看报告；关键函数放头文件/static。
- **坑：`-ffast-math` 上线后 NaN/精度问题。**
  原因：`-ffast-math` 改变 NaN/INF 语义、允许重排（PDF 第 175 页）。对策：用 `-fno-trapping-math -fno-math-errno -fno-signed-zeros` 替代，保留 isnan。
- **坑：有符号整数溢出是 UB，编译器把"溢出检查"优化掉了。**
  原因：GCC 假设不溢出（PDF 第 15 页）。对策：`-fwrapv`/无符号/溢出前检查。
- **坑：忘开 `-g` 和 `-fno-omit-frame-pointer`，perf 打不出函数名。**
  原因：无符号/无帧指针。对策：Release 也带这两个参数（本项目默认）。
- **坑：警告被忽略。** GCC 的 `-Wmaybe-uninitialized`、`-Wstringop-overflow` 常预告性能/正确性问题。对策：`-Wall -Wextra -Wpedantic` + 零警告门禁。

### 11.2 测量与基准

- **坑：单次计时下结论。** 原因：频率/调度噪声（PDF 第 168 页）。对策：预热 + 多轮 + 中位数。
- **坑：数据规模太小，全在缓存里。** 原因：测不出 cache miss（PDF 第 170 页）。对策：按目标场景扫数据规模（见 `18_size`）。
- **坑：被测代码被编译器优化掉。** 原因：结果没用（PDF 第 168 页）。对策：volatile/校验和/返回结果（本项目 benchmark.h）。
- **坑：基准里包含了初始化/分配。** 对策：初始化放计时外，只测计算段（PDF 第 168 页"区分初始化与计算时间"）。
- **坑：wall-clock 当 CPU 时间。** 多线程/IO 场景两者差异大。对策：需要时用 perf 的 task-clock 或只测计算段。
- **坑：与其他 CI 任务共享 CPU。** 对策：固定 CPU 亲和性、降并发、或接受更大方差。
- **坑：比较跨机器/跨时段的两个数。** 对策：同会话内 A/B 交替测（`compare_versions.sh`）。

### 11.3 缓存与内存

- **坑：结构体/数组大小是 2 的幂且按行访问 → 缓存集冲突。**
  原因：行距命中关键步长（PDF 第 107 页）。对策：填充列或分块；`08_transpose` 实验可见。
- **坑：多线程写相邻变量 → 伪共享。** 对策：`alignas(64)` 分隔（`11_false_sharing` 实验）。
- **坑：遍历顺序错误（列主序 vs 行主序）。** 原因：缓存局部性差（PDF 第 106 页）。对策：最后下标最快变化。
- **坑：`std::vector` 反复 push_back 不 reserve。** 原因：反复重分配 + 拷贝（PDF 第 98 页）。对策：`reserve()` 预分配。
- **坑：`std::endl` 写日志。** 每行 flush，I/O 拖垮性能。对策：用 `'\n'`；日志批量刷。
- **坑：大表随机查表比计算慢。** 原因：表被驱逐出缓存（PDF 第 145 页）。对策：表小且热才查表。

### 11.4 多线程与并发

- **坑：线程数 > 逻辑核数。** 原因：上下文切换（PDF 第 111 页）。对策：线程数 = 核数，或线程池复用。
- **坑：热路径里加锁/原子。** 原因：同步开销大（PDF 第 112 页）。对策：局部累加 + 最后合并（`10_multithreading`）。
- **坑：假共享（伪共享）在隐藏。** 对策：perf 看 cache-misses，或按缓存行对齐。
- **坑：线程安全函数用了静态变量。** 原因：跨线程污染（PDF 第 62 页）。对策：局部变量/thread_local/加锁。
- **坑：短任务也开线程。** 原因：线程启动开销 > 任务（PDF 第 62 页）。对策：小于几百微秒的任务用线程池或直接执行。

### 11.5 SIMD 与向量化

- **坑：以为 -O3 就自动向量化。** 原因：默认只到 SSE2，且别名/分支阻碍（PDF 第 118-119 页）。对策：`-mavx2` + `__restrict__` + 看 `-fopt-info-vec`。
- **坑：假设所有 CPU 都有 AVX-512。** 对策：CPUID 检测 + 多版本（PDF 第 135 页）。
- **坑：忘对齐。** 原因：老 CPU/Atom 上未对齐 load 慢（PDF 第 124 页）。对策：`alignas(64)` 或 `aligned_alloc`。
- **坑：向量化后结果不对。** 原因：累加顺序/浮点重排差异。对策：校验和对比标量版。
- **坑：数据转换/重排比计算还多。** 原因：打包解包成本（PDF 第 134 页）。对策：数据布局配合向量宽度（SoA）。
- **坑：AVX 与非 AVX 代码混调未 `_mm256_zeroupper()`。** 原因：YMM 状态切换惩罚（PDF 第 117 页）。

### 11.6 浮点与数值

- **坑：混合 float/double。** 原因：转换指令（PDF 第 32、153 页）。对策：统一精度。
- **坑：大数组求和累积误差/变慢。** 对策：多累加器（`04_loop`）；需要高精度用 Kahan 求和（补充说明）。
- **坑：次正规数拖慢数量级。** 原因：FPU 处理 subnormal 极慢。对策：开 flush-to-zero（PDF 第 33 页）。
- **坑：`-ffast-math` 后 isnan/isinf 失效。** 对策：用 `-fno-trapping-math` 等替代（PDF 第 119 页）。
- **坑：浮点 == 比较。** 原因：舍入误差。对策：差值容差比较（补充说明）。

### 11.7 链接与发布

- **坑：动态库 vs 静态库调用开销。** 原因：PLT/GOT 查表 + 按页对齐加载（PDF 第 158-160 页）。对策：速度敏感用静态链接。
- **坑：共享库忘 `-fpie`/`-fno-semantic-interposition`。** 原因：内部引用也走 GOT/PLT（PDF 第 161 页）。对策：隐藏符号 + 关语义 interposition。
- **坑：LTO 与第三方库/调试不兼容。** 对策：LTO 只用于 Release 发布构建，保留非 LTO 用于调试（补充说明）。
- **坑：发布忘跑回归。** 对策：CI 性能门禁（`compare_versions.sh`）。

### 11.8 线上与生产

- **坑：只测单机，未测并发/负载。** 对策：压测 + 最坏情况测试（PDF 第 171 页）。
- **坑：线上热点与开发机不一致。** 原因：数据分布/负载/CPU 不同。对策：用生产采样数据（profile-guided data）。
- **坑：优化后没做功能回归。** 对策：优化 PR 必须带功能测试 + 基准 + 校验和。
- **坑：容器/虚拟化下性能不可复现。** 原因：CPU 配额、共享缓存、vCPU 映射。对策：固定资源、明确测量范围（补充说明）。

## 13. 本章总结

- 性能工作的闭环：预算 → 基准 → 热点 → 优化 → A/B → 回归 → 监控。
- 可持续优于一次性：基准入仓库、阈值门禁、结果可回溯。
- 常见坑按类别（编译器/测量/缓存/多线程/SIMD/浮点/链接/生产）逐条排查。
- 一切结论以"同环境、多轮、防消除"的测量为准（PDF 第 167 页）。
