# 03 性能热点分析

> 本笔记对应 PDF 第 3 章 Finding the biggest time consumers（第 15～21 页），本轮完整覆盖 3.1～3.16。

## 1. 本章解决什么问题

优化开始之前必须先回答两个问题：

1. **时间到底花在哪？** 很多程序 99% 的时间花在内层数学循环里，另一些程序 99% 的时间花在读写文件上，只有不到 1% 用于真正处理数据。优化错地方不仅浪费时间，还让代码变乱、变难维护（PDF 第 16 页）。
2. **一段代码到底多快算快？** 作者引入"时钟周期"作为与机器无关的时间尺度，并给出判断"这段代码值不值得优化"的估算方法。

本章是全书"先测量，再优化"方法论的具体操作篇：**先量化，再用 profiler 或手动仪器定位热点，最后只优化热点。**

## 2. 核心概念

| 术语 | 含义 | 出处 |
|------|------|------|
| 时钟周期（clock cycle） | 一个 CPU 时钟脉冲的时间，= 1/主频 | PDF 第 15 页 |
| 热点（hot spot） | 消耗绝大部分时间的代码段 | PDF 第 16 页 |
| 插桩（instrumentation） | 编译器在每次函数调用处插入计数代码 | PDF 第 16 页 |
| 时间采样 | 每隔固定时间产生中断，统计每个代码段的中断次数 | PDF 第 16 页 |
| 事件采样 | 在 cache miss、分支预测失败等事件发生时采样 | PDF 第 16 页 |
| 上下文切换 | 任务/线程切换，需刷新缓存与分支预测器 | PDF 第 21 页 |
| 依赖链（dependency chain） | 一串相互依赖的计算，阻塞乱序执行 | PDF 第 21 页 |
| 延迟（latency） | 单条指令从开始到出结果的时间 | PDF 第 21 页 |
| 吞吐（throughput） | 单位时间内能开始执行的指令数（流水线） | PDF 第 21 页 |

## 3. 工作原理

**为什么用时钟周期而不是秒？**

不同机器速度差异巨大。如果手册写"某事耗时 10 µs"，下一代机器上可能就是 5 µs，内容很快过时；但如果写"10 个时钟周期"，即使主频翻倍，周期数不变。因此本书以时钟周期为单位（PDF 第 15 页）。

**CPU 时间都去哪了？（按频率排序的常见时间消耗者）**

作者在第 3.3～3.16 节系统列出。按是否需要 CPU 计算区分两大类：

- **I/O 与资源等待类**（程序大部分时间在"等"，而不是"算"）：
  - 文件访问：硬盘比 CPU 慢很多，病毒扫描器雪上加霜（PDF 第 19 页）；
  - 网络访问：延迟不可控（PDF 第 20 页）；
  - 图形/设备驱动调用：涉及保护模式切换，单次调用开销大（PDF 第 20 页）；
  - 内存访问：缓存未命中时几百个周期（PDF 第 21 页）；
  - 上下文切换：刷新缓存和分支预测状态（PDF 第 21 页）。
- **纯计算类**：
  - 依赖链阻塞乱序执行（PDF 第 21 页）；
  - 执行单元吞吐达到上限（PDF 第 21 页）。

**profiler 是怎么工作的？**

四种方法（PDF 第 16 页）：

1. 插桩：编译器在每个函数调用处插入计数代码——精确但改动程序；
2. 调试断点：在每个函数/每行代码处设置临时断点；
3. 时间采样：每毫秒中断一次，统计中断落在各代码段的数量——无需改程序，但较不可靠；
4. 事件采样：在"每 1000 次 cache miss"等事件时采样，可定位 cache miss、分支预测失败热点——需要 CPU 相关的 profiler（Intel VTune / AMD CodeAnalyst）。

## 4. PDF 核心观点

### 4.1 时钟周期（3.1，第 15～16 页）

- 1 周期 = 1/主频。例：4 GHz 下 1 周期 = 0.25 ns（PDF 第 15 页）。
- 估算例子：循环 1000 次，每次 100 次浮点运算，每运算 5 周期 → 1000×100×5×0.25 ns = **125 µs**。这不到屏幕刷新的 1%，用户根本看不到，不值得优化；如果外面再套一层 1000 次循环（125 ms），则值得测量确认（PDF 第 15～16 页）。

### 4.2 用 profiler 找热点（3.2，第 16～18 页）

- 先识别关键部分再优化；优化非关键部分浪费开发时间且降低可维护性（PDF 第 16 页）。
- 四种 profiling 方法及特点（见上文"工作原理"）（PDF 第 16 页）。
- **profiler 常见问题**（PDF 第 16～17 页）：
  - 时间粒度粗：毫秒分辨率下关键函数可能测成 0；
  - 执行时间太短/太长：采样数据不足或过多；
  - 等待用户输入：需用测试数据替代；
  - 其他进程干扰：测量结果混入其他进程时间；
  - 优化后函数地址混淆：内联函数的名称在 profiler 中不可见；
  - 要求 debug 版本：debug 代码未优化，测量失真；
  - 线程跨核心跳转：事件计数器绑定核心，跨核导致计数无意义，需设置 CPU 亲和性；
  - 复现性差：随机任务切换、垃圾回收污染测量。
- 替代方案：在调试器里随机中断，热点处中断概率高（90% 的热点 → 90% 概率中断落在热点）；重复几次即可定位，再用调用栈确认上下文（PDF 第 17 页）。
- **手动插桩**：在代码里加计数器 + 时间戳，是更可靠的定位手段；用 `#if` 包裹，正式版本可关闭（PDF 第 17 页）。
- 高分辨率计时：Windows `QueryPerformanceCounter`，或 CPU 时间戳计数器 `_rdtsc()`（按主频计数）；线程跨核会使 TSC 失效，需固定线程到核心（`sched_setaffinity`，Windows `SetThreadAffinityMask`）（PDF 第 17 页）。
- 用真实、含典型随机性的测试数据，以获得真实的 cache miss 和分支预测失败次数（PDF 第 17 页）。

### 4.3 安装 / 更新 / 加载（3.3-3.5，第 18～19 页）

- 安装时间、自动更新、程序加载时间都是用户时间成本；避免程序启动时搜索更新、避免散布过多 DLL/配置文件（PDF 第 18～19 页）。

### 4.4 动态链接与 PIC（3.6，第 19 页）

- 动态库比静态库慢的原因在第 158 页详述；Mac 默认 PIC + 惰性绑定更慢（PDF 第 19 页）。

### 4.5 文件访问（3.7，第 19 页）

- 顺序向前访问快于随机访问；一次读写至少几 KB，不要小口小口读写；刚访问过的文件在磁盘缓存中更快；数值数据存二进制比 ASCII 紧凑高效（PDF 第 19 页）。
- 可在等磁盘时用独立线程做其他计算（PDF 第 19 页）。

### 4.6 数据库 / 图形 / 其他系统资源 / 网络（3.8-3.12，第 20～21 页）

- 系统数据库访问可能花数秒，应用信息宜存独立文件（PDF 第 20 页）。
- 数据库可被索引、集合操作优化；简单场景可直接用普通数据文件（PDF 第 20 页）。
- 图形操作单次调用昂贵：画整块多边形/位图比逐像素调用快得多（PDF 第 20 页）。
- 设备/驱动写入尽量大块进行；访问系统设备可能加载多个驱动与配置（PDF 第 20 页）。
- 网络延迟不可控；远程数据可镜像到本地（PDF 第 20～21 页）。

### 4.7 内存访问（3.13，第 21 页）

- 典型现代机器有 L1（8-64 KB）、L2（256 KB-2 MB）、L3（几 MB）三级缓存。
- 缓存命中的内存访问仅 2-4 周期，未命中要**几百个周期**（PDF 第 21 页）。
- 当数据总量超过 L2 且访问分散/非顺序时，内存访问就是最大时间消耗者。

### 4.8 上下文切换（3.14，第 21 页）

- 切换会刷新数据缓存、代码缓存、分支目标缓冲、分支历史；时间片越短切换越频繁；多核减少上下文切换（PDF 第 21 页）。

### 4.9 依赖链（3.15，第 21 页）

- 现代 CPU 乱序执行：A 慢时可以先算不依赖 A 结果的 B。
- 但"长依赖链"（每步依赖上一步）会阻止并行；应避免循环内携带的依赖链（详见第 11 章，PDF 第 113 页）。

### 4.10 执行单元吞吐（3.16，第 21～22 页）

- **延迟 ≠ 吞吐**：浮点加法延迟可能 3 周期，但只要结果独立，每个周期都能开始新的加法。
- 例：第一个加法 T 开始 T+3 结束；不依赖它的第二个加法 T+1 开始 T+4 结束；若每个加法都依赖前一个，则每 3 周期才一个加法（PDF 第 21 页）。
- 最优情况：无瓶颈、无长依赖链时，性能受执行单元**吞吐**限制而非延迟。
- 执行核心有多个执行单元（两个以上整数单元、两个浮点加法单元、两个浮点乘法单元），整数与浮点可同时执行；浮点代码最好加乘平衡；除法慢；整数循环计数操作通常不增加总时间（PDF 第 21～22 页）。

## 5. 简单示例

### 5.1 用 `std::chrono` 手动计时定位热点（PDF 第 17 页"手动插桩"思想）

```cpp
// Manual instrumentation: measure the hot parts with std::chrono.
// PDF p17 recommends adding counter variables and timing each critical part,
// wrapped in #if so it can be disabled for release builds.

#include <chrono>
#include <iostream>
#include <vector>

// A fake "hot" function whose cost we want to measure.
double compute(const std::vector<double> &v, double scale) {
    double s = 0.0;
    for (size_t i = 0; i < v.size(); ++i) {
        s += v[i] * scale;                 // floating point work
    }
    return s;
}

int main() {
    const size_t N = 4'000'000;
    std::vector<double> v(N, 1.0);

    // warm-up: page-in + clock/turbo stabilize (PDF p168-169)
    volatile double sink = compute(v, 1.0);

    auto t0 = std::chrono::steady_clock::now();
    double r = compute(v, 1.0001);         // measured region
    auto t1 = std::chrono::steady_clock::now();

    auto us = std::chrono::duration_cast<std::chrono::microseconds>(t1 - t0);
    std::cout << "compute() took " << us.count() << " us, result=" << r << "\n";
    (void)sink;
}
```

### 5.2 估算"是否值得优化"（PDF 第 15～16 页）

见 `note/01_性能优化基本原则.md` 第 5 节的估算示例。判断准则：估算结果小于屏幕刷新时间的 1%（约 100-200 µs）时，用户无感知，不值得优化。

## 6. 未优化代码

一个把时间浪费在"错误的地方"的典型：内层循环存在长依赖链，且数据访问模式很差（PDF 第 21 页依赖链 + 第 21 页内存访问）：

```cpp
// Slow version: a loop-carried dependency chain (each iteration depends on
// the previous one) + poor memory locality.
// PDF p21 (section 3.15): long dependency chains block out-of-order execution.
// PDF p21 (section 3.13): uncached memory access costs hundreds of cycles.

double sum_serial(const double *a, size_t n) {
    double sum = 0.0;
    for (size_t i = 0; i < n; ++i) {
        sum += a[i];       // sum depends on previous sum -> serial chain
    }
    return sum;
}
```

## 7. 优化后代码

打破依赖链（多累加器）+ 顺序访问（已经是顺序的）。注意本章只要求"识别"问题，完整解法在 `note/08_乱序执行与指令级并行.md`（PDF 第 113～114 页）：

```cpp
// Two accumulators break the dependency chain; on a CPU with >=2 pipelined
// FP adders this can nearly double throughput for the addition.
// Full treatment: PDF p113-114 (chapter 11).

double sum_parallel(const double *a, size_t n) {
    double s0 = 0.0, s1 = 0.0;
    size_t i = 0;
    for (; i + 1 < n; i += 2) {
        s0 += a[i];
        s1 += a[i + 1];
    }
    for (; i < n; ++i) s0 += a[i];   // odd tail
    return s0 + s1;
}
```

> 说明：PDF 第 21 页只指出依赖链的害处，第 113 页才给出多累加器的完整解法。这里提前展示便于体会"热点分析"与"优化手段"的分工。

## 8. 为什么会更快

- **指令依赖**：`sum_serial` 中每次加法等待上一次结果，延迟连续累加；`sum_parallel` 两条链互不依赖，乱序执行（PDF 第 21 页）让第二条加法在第一条未完成时就开始（PDF 第 21 页 3.16 的 T/T+1 例子）。
- **执行单元吞吐**：现代 CPU 有 2 个以上浮点加法单元（PDF 第 21～22 页），双累加器正好喂满流水线。
- **内存访问次数**：两个版本都顺序读 `a[]`，Cache 行为一致；热点分析的关键是发现"瓶颈是依赖链还是内存"，从而决定优化方向。
- **编译器优化能力**：`-O3 -ffast-math` 下编译器可能自动把 `sum_serial` 改写为多累加器并向量化（PDF 第 114、129 页），但依赖编译器版本与选项，验证方式见下节。

## 9. 如何验证

本章的验证重点是"测量"，完整实验在 `src/01_profiling`（阶段三实现）：

```bash
# 编译两个版本
g++ -O2 -std=c++17 -DUSE_SERIAL demo.cpp -o demo_serial
g++ -O2 -std=c++17 demo.cpp -o demo_parallel

# 手动计时运行（示例代码内已含 chrono 计时）
./demo_serial
./demo_parallel

# perf 统计（本机需要 root，perf_event_paranoid=4）
sudo perf stat ./demo_serial
sudo perf stat ./demo_parallel

# 事件采样定位热点
sudo perf record -g ./demo_serial
sudo perf report

# 查看汇编，确认两条加法链是否并行（S 状态显示调度）
g++ -O2 -std=c++17 -S -masm=intel demo.cpp -o /tmp/demo.s
```

- 编译命令：`g++ -O2 -std=c++17`（当前环境 g++ 13.3.0）
- 运行命令：`./demo_serial && ./demo_parallel`
- Benchmark 方法：多轮取中位数，预热后测量（PDF 第 168 页），见 `note/14_性能测试与Benchmark.md`
- perf 命令：`perf stat` / `perf record -g` / `perf report`；`perf_event_paranoid=4` 时需 `sudo` 或 `sudo sysctl kernel.perf_event_paranoid=1`
- 查看汇编：`g++ -O2 -S -masm=intel`

## 10. 常见误区

- **误区一：优化 = 改代码。** 顺序反了：先测量定位热点，再优化（PDF 第 16 页）。
- **误区二：profiler 的结论绝对可靠。** PDF 第 16 页列出八类常见问题：粒度、干扰、跨核、优化混淆等。要交叉验证。
- **误区三：用 debug 版本测性能。** debug 代码未优化，测量失真（PDF 第 17 页）。
- **误区四：秒/微秒是最佳时间单位。** 用时钟周期，才能跨机器比较（PDF 第 15 页）。
- **误区五：所有"慢"都靠 CPU 优化解决。** 程序可能主要在等文件/网络/数据库，此时优化 CPU 无用（PDF 第 16、19-21 页）。
- **误区六：忽略首次运行（cold cache）。** 首次调用与热缓存后的时间差异巨大，取决于函数在最终程序中调用频率（PDF 第 17 页、第 168 页）。

## 11. 实践任务

1. 用 `std::chrono` 给自己程序中最重的函数计时，重复 10 次记录，观察第一次与后续的差异（冷/热缓存）。
2. 对比 `sum_serial` 与 `sum_parallel` 的运行时间，并尝试把累加器增加到 4 个看是否更快。
3. 用 `perf record -g` 跑一个热点程序，用 `perf report` 找出占 CPU 最多的函数（本机需 root）。
4. 用 `top` 观察你的程序，判断它在"算"还是在"等"（%CPU vs 时间）。
5. 写一个小程序读一个大文件：小口（每次 64 字节）与大块（每次 1 MB）各读一遍，对比时间，验证 PDF 第 19 页的"大块读写"建议。

## 12. 本章总结

- 用**时钟周期**而不是秒来思考性能。
- **先找热点，再优化**：profiler、手动插桩、调试器中断三种手段各有利弊。
- 时间消耗者分两类：**I/O/资源等待**和**纯计算**；先判断属于哪类。
- 计算瓶颈的两个根源：**依赖链**（阻塞乱序执行）与**执行单元吞吐**（喂不满流水线）。
- 优化只针对热点；优化前先估算值不值得。
