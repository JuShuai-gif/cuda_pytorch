# 01 性能优化基本原则

> 本笔记对应 PDF 第 1 章 Introduction（第 3～4 页），并补充覆盖 PDF 第 4 章 Performance and usability（第 22～23 页）、第 5 章 Choosing the optimal algorithm（第 24 页）、第 6 章 Development process（第 25 页）。这三章同属"优化原则与工程方法"主题。

## 1. 本章解决什么问题

本书开篇回答两个问题：

1. **软件为什么经常慢？** 大多数人以为是 CPU 不够快，作者指出主因是软件设计问题，而不是硬件问题。
2. **优化值得吗？** 优化是有代价的，它与现代软件开发倡导的结构化、面向对象、模块化、可复用等理念存在冲突。本章帮助读者理解：优化的收益与成本如何权衡，以及把精力花在哪里最划算。

结论先行：**软件变慢的元凶往往是浪费的开发工具、框架、虚拟机、脚本语言和层层抽象，而不是微处理器设计。** 降低抽象层次、避免功能膨胀，是把软件做快的根本方法（来源：PDF 第 4 页，对应章节 1.1）。

## 2. 核心概念

| 术语 | 含义 | 出处 |
|------|------|------|
| Moore 定律（摩尔定律） | 硬件性能随时间指数增长；作者指出该增长正在放缓 | PDF 第 4 页 |
| Wirth 定律 | 半开玩笑的说法：软件变慢的速度超过硬件变快的速度 | PDF 第 4 页 |
| 结构化/面向对象开发 | 强调模块化、可复用、多层抽象，与速度优化往往冲突 | PDF 第 4 页 |
| 热点（hot spot） | 程序中消耗绝大部分时间的代码段 | PDF 第 4 页（"identify and isolate the most critical part"） |
| 特性膨胀（feature bloat） | 为营销给每个新版本堆加用户用不到的功能，导致软件更慢 | PDF 第 23 页（第 4 章） |
| 内存交换（swapping） | 物理内存不足时把内存页换到磁盘，导致响应时间激增 | PDF 第 22 页（第 4 章） |
| 过度设计（overkill） | 用过于复杂的数据结构/算法解决小问题，反而更慢更贵 | PDF 第 24 页（第 5 章） |
| 重设计（redesign） | 测试揭示瓶颈后，对整个程序结构重新设计 | PDF 第 24 页（第 5 章） |

> 补充说明：Wirth 定律得名于 Pascal 语言作者 Niklaus Wirth，是软件工程界的著名调侃，并非严格定理。

## 3. 工作原理

**为什么 CPU 明明在变快，软件却在变慢？**

微处理器性能在过去几十年呈指数级增长（Moore 定律），但软件产品的响应时间却仍然很长。作者给出的解释链条（来源：PDF 第 4 页，章节 1.1）：

1. 现代软件开发流程优先追求结构化、面向对象、模块化、可复用、多层抽象；
2. 这些追求常常以运行效率为代价：解释型语言、虚拟机、JIT、大型运行时框架把 CPU 时间消耗在"框架本身"而不是"真正的计算"上；
3. 用户被迫购买更强的电脑来抵消软件的低效（来源：PDF 第 5 页，章节 1.2 段首）。

**优化为什么要付出成本？**

优化往往意味着写出"相对原始"的代码：更少的抽象层、更少的小函数、手动管理内存。这带来三方面代价（来源：PDF 第 4 页，章节 1.2）：

- 代码可读性、可维护性下降；
- 更容易引入错误（C++ 不做数组越界、非法指针等自动检查）；
- 开发调试时间变长。

因此作者主张：**不要对全程序做无差别优化，而是识别并隔离程序中最关键的部分，把优化努力集中在那里。** 同时要搞清楚哪些高级语言结构"贵"、哪些"便宜"（来源：PDF 第 4 页，章节 1.2）。

## 4. PDF 核心观点

- **软件慢的主因是软件设计，而非微处理器设计。** 元凶包括：浪费的开发工具、框架、虚拟机、脚本语言、抽象多层设计。来源：PDF 第 4 页，章节 1.1。
- **Wirth 定律**：软件速度下降比硬件速度上升更快。来源：PDF 第 4 页，章节 1.1。
- **建议**：避免最浪费的软件工具和框架；避免功能膨胀；降低软件开发中的抽象层次，这样更容易理解不同代码结构对性能的影响。来源：PDF 第 4 页，章节 1.1。
- **结构化的代价**：大学课程强调结构化/OOP/模块化/可复用/多层抽象，这些要求常与"为速度或体积优化"冲突。来源：PDF 第 4 页，章节 1.2。
- **历史变迁**：几十年前的建议是"只被调用一次的函数不要单独成函数"，如今却建议"函数不要超过几行"。原因是项目变大、更关注开发成本、电脑更强。来源：PDF 第 4 页，章节 1.2。
- **性能应放在可用性的大背景下**：慢、难用、不兼容、易出错的软件都浪费用户时间，都是可用性问题（详见 4.2 小节）。
- **先选算法，再谈优化**：对排序、搜索、数学计算，换一个更好的算法往往比优化现有代码收益大得多。但不要过度设计——小数据用哈希表就是浪费（详见 4.3 小节）。
- **开发流程**：过多的抽象层是性能下降的常见原因；开发中应多次迭代重设计（详见 4.4 小节）。

### 4.2 性能与可用性（PDF 第 4 章，第 22～23 页）

更快的软件是帮用户省时间的软件。作者把性能放进"可用性"这个更广的框架里，列出典型的用户时间杀手：

- **大型运行时框架**：.NET、Java 虚拟机等框架占用的资源常常比它们运行的程序还多，安装、更新、启动、运行全程都在消耗时间；作者认为跨平台兼容本可通过对语言/OS/API 的更好标准化实现（PDF 第 22 页）。
- **内存交换（swapping）**：开发者往往比终端用户拥有更多内存，看不到内存不足导致的换页延迟；资源大户程序在用户机器上表现极差（PDF 第 22 页）。
- **安装与卸载问题**：应标准化、由操作系统统一处理（PDF 第 23 页）。
- **自动更新**：不应打断用户、不应弹窗骚扰；更新应放在程序重启时进行（PDF 第 23 页）。
- **兼容性问题**：软件应在不同平台、分辨率、权限下测试；使用标准 API 而非自制 hack（PDF 第 23 页）。
- **复制保护（防拷贝）**：常违反系统标准、引发兼容与崩溃，收益常远小于可用性代价（PDF 第 23 页）。
- **硬件升级**：换硬盘等硬件常需重装全部软件；软件需要更好的备份特性（PDF 第 23 页）。
- **安全性**：病毒扫描器等安全软件有时比任何东西都耗时间；系统自带安全软件常比第三方更可靠（PDF 第 23 页）。
- **后台服务**：很多后台服务对用户无用；只在需要时启动（PDF 第 23 页）。
- **功能膨胀**：为营销每版加新功能，即使无人使用也会拖慢软件（PDF 第 23 页）。
- **认真对待用户反馈**：用户投诉是 bug、兼容、可用性问题的重要来源；应系统化处理（PDF 第 23 页）。

> 适用范围说明：4.2 节（第 22～23 页）讨论较多 Windows/.NET 时代的具体问题（系统数据库、注册表等），在今天的 Linux 环境里部分场景不同，但"运行时框架与后台服务浪费资源"的原则仍然成立。

### 4.3 选择最优算法（PDF 第 5 章，第 24 页）

- **算法优先**：对排序、搜索、数学计算这类任务，选对算法比优化第一个想到的算法收益大得多；必要时用典型数据测试几种算法（PDF 第 24 页）。
- **反对过度设计（overkill）**：数据列表很小时，线性/二分搜索足够，不要用哈希表。哈希表增大程序与数据体积，当瓶颈是文件访问或缓存时反而更慢，且更贵更易错（PDF 第 24 页）。
- **复用现成库**：标准任务用现成优化库（Boost、Intel MKL、Intel IPP）；用 Intel 库前确认其在非 Intel CPU 上的表现（PDF 第 24 页）。
- **测试带来重设计的洞察**：性能测试与瓶颈分析常常揭示更好的数据组织方式，值得考虑对已工作的程序做重设计；重设计通常还能让程序更结构化、更易维护（PDF 第 24 页）。

### 4.4 开发流程（PDF 第 6 章，第 25 页）

- **规划阶段做足功课**：尽早分析数据结构、数据流与算法，预测哪个资源最紧张（PDF 第 25 页）。
- **接受迭代重设计**：复杂问题的完整理解往往在开发后期才出现；把开发看作学习过程，准备好多轮重设计（PDF 第 25 页）。
- **过多抽象层有性能代价**：某些软件工程模型强调严格的逻辑架构分层，而把软件拆成过多独立抽象层是性能下降的常见原因（PDF 第 25 页）。
- **版本控制**：开发方法多为增量/迭代，应保存每个中间版本的备份；团队项目使用版本控制工具（PDF 第 25 页）。

> 适用范围说明：本书以 x86 家族的 Intel/AMD/VIA 处理器和 Windows/Linux/BSD/Mac 系统为基准（来源：PDF 第 3、5 页），其结论在 2004-2026 年间多次修订，多数观点仍然适用，但涉及具体型号数字时需以当前硬件为准。

## 5. 简单示例

判断一段代码是否值得优化，先做数量级估算，再决定是否动手。下面这个估算思路来自 PDF 第 15～16 页（章节 3.1），是"先测量、先估算"原则的具体体现：

```cpp
// Estimate whether a loop is worth optimizing.
// A loop repeats 1000 times, each iteration does 100 float ops,
// each float op takes ~5 clock cycles. CPU at 4 GHz:
//   1000 * 100 * 5 cycles * 0.25 ns = 125 us
// Source: PDF p15-16 (section 3.1)

#include <iostream>

int main() {
    // The estimate itself, as a back-of-envelope calculation:
    const long iterations   = 1000;   // outer loop count
    const long float_ops    = 100;    // float ops per iteration
    const long cycles_per_op = 5;     // approximate latency, cycles
    const double ns_per_cycle = 1.0 / 4.0; // 4 GHz CPU -> 0.25 ns

    double ns = iterations * float_ops * cycles_per_op * ns_per_cycle;
    double us = ns / 1000.0;
    std::cout << "estimated time = " << us << " us\n";

    // 125 us < 1% of a screen refresh (~16.7 ms). Not worth optimizing.
    return us < 1000 ? 0 : 1;
}
```

> 注意：PDF 原文用"4 GHz 下 1 个时钟周期 = 0.25 ns"并给出 125 µs 的估算（PDF 第 15～16 页）。本示例只是把这个估算过程写成代码，用于体会"优化前先判断值不值得"。

## 6. 未优化代码

把函数拆得过度细小是典型的"为结构牺牲速度"的反模式。作者明确指出：**只为了函数变短而拆分函数，并不会让程序更清晰，反而更慢；关键的内层循环应尽量完整地留在单个函数内**（来源：PDF 第 48 页，章节 7.14；PDF 第 4 页，章节 1.2 也讨论了这一理念的历史变迁）。

```cpp
// Anti-pattern: every tiny step is its own function (excessive decomposition).
// Each call has call/return overhead, register save/restore, and fills the
// branch target buffer. In a hot inner loop this is pure waste.
// See PDF p48 (section 7.14) for why this is slower.

double step_add(double a, double b) { return a + b; }
double step_mul(double a, double b) { return a * b; }

double hot_loop(int n) {
    double s = 0.0;
    for (int i = 0; i < n; i++) {
        s = step_add(s, (double)i);   // call overhead per iteration
        s = step_mul(s, 1.0001);      // call overhead per iteration
    }
    return s;
}
```

## 7. 优化后代码

同样的计算，让热点保持在一个函数内，让编译器自由内联、安排指令：

```cpp
// Keep the hot loop inside ONE function. The compiler can then do
// inlining, register allocation and scheduling across the whole loop.
// See PDF p48 (section 7.14): "A critical innermost loop should preferably
// be kept entirely inside one function".

double hot_loop(int n) {
    double s = 0.0;
    for (int i = 0; i < n; i++) {
        s += (double)i;      // add
        s *= 1.0001;         // multiply
    }
    return s;
}
```

> 说明：PDF 第 1 章本身没有代码示例；上面对比取材于 PDF 第 4 页（1.2 节关于"拆分函数"理念的讨论）与第 48 页（7.14 节"避免不必要的函数"）。在 -O2/-O3 下编译器通常会把两个版本优化成几乎相同的机器码，但代码可读性和维护成本明显不同。

## 8. 为什么会更快

从本章原则层面分析：

- **函数调用**：每个调用有跳转、返回、寄存器保存/恢复、异常信息等开销（PDF 第 48 页）。内层循环里的调用会被反复执行。
- **指令数量**：少一层函数调用 = 少几条 call/ret 指令。在 64 位模式下参数走寄存器，开销较小，但 32 位模式参数走栈，开销显著（PDF 第 48 页）。
- **编译器优化能力**：函数如果跨模块，编译器无法跨调用做内联和常量传播（PDF 第 81 页，章节 8.3，后续轮次展开）。保持热点集中是给编译器"让路"。
- **指令依赖与乱序执行**：本章第 3.15 节（PDF 第 21 页）指出，现代 CPU 能乱序执行，但前提是没有长依赖链；过度的函数调用会打断可并行计算。

> 重要提醒：本章是"原则"，不承诺具体加速倍数。是否真的更快、快多少，必须用 Benchmark 验证（PDF 第 15、167 页）。"先测量，再优化"是本书反复强调的核心方法论。

## 10. 常见误区

- **误区一：软件慢是因为硬件不够好。** PDF 明确指出主因是软件设计（第 4 页）。升级硬件是"头痛医头"。
- **误区二：优化总是值得做。** 优化有成本（可读性、可维护性、出错风险）。125 µs 的循环不值得优化（第 15～16 页）。
- **误区三：全程序无差别优化。** 正确做法是定位热点、集中优化热点（第 4、16 页）。
- **误区四：函数越短越好。** 几十年前的建议相反；过度拆分反而降低性能（第 4、48 页）。
- **误区五：新的抽象越多越好。** 多层抽象是性能下降的常见原因（第 4、25 页）。
- **误区六：用复杂算法一定更好。** 小数据用哈希表、二分搜索就是过度设计，可能因为代码体积/缓存反而更慢（第 24 页）。
- **误区七：性能只等于 CPU 快。** 运行时框架、内存交换、后台服务、安装/更新等"非计算"环节同样在消耗用户时间（第 22～23 页）。

## 11. 实践任务

1. 用 3.1 的估算方法，为你的一个真实程序里的内层循环估算耗时（循环次数 × 每次操作数 × 每操作周期 × 周期时间）。
2. 阅读你项目中最大的几个函数，找出其中被过度拆分的部分，思考是否值得合并。
3. 打开系统任务管理器 / `top`，找出你机器上消耗最多的软件，思考它慢的原因属于 PDF 第 4 页列出的哪一类。
4. 为一个 1000×1000 的浮点矩阵乘法写两个版本：一个按"模块化"拆成大量小函数，一个保持热点集中；用 `time` 比较（为后续 Benchmark 章节热身）。
5. 检查一个你常用的小数据集合：现在用的是线性搜索还是哈希表？按照 PDF 第 24 页的建议，评估是否有必要。
6. 用 `top`/`free` 观察你的系统：是否存在内存交换？找出你的软件里最占内存的模块。

## 12. 本章总结

- 软件慢的主因是软件设计，不是 CPU。
- 优化有成本，只优化真正的热点。
- 降低抽象层次、避免功能膨胀，是让软件变快的基本功。
- 性能是可用性的一部分：运行时框架、内存交换、安装更新、功能膨胀都在浪费用户时间（PDF 第 22～23 页）。
- 算法选择优先于代码微优化，但警惕过度设计（PDF 第 24 页）。
- 开发流程应接受迭代重设计，警惕过多抽象层（PDF 第 25 页）。
- 整个系列的方法论：**先测量，再优化。**
