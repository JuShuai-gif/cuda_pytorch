## 3. 核心概念

- **L1i（Level 1 Instruction Cache）**：一级指令缓存。
- **Trace Cache（痕迹缓存）**：缓存"已解码指令"而非原始字节流（x86 上用于加速译码）。
- **Unified Cache（统一缓存）**：L2 及更高同时缓存代码与数据。
- **SMC（Self Modifying Code，自修改代码）**：程序运行时修改自身代码。
- **Pipeline（流水线）**：指令分阶段执行；流水线停滞（stall）代价大。
- **Branch Prediction（分支预测）**：提前猜测跳转目标，预取指令掩盖延迟。
- **Bubbles（气泡）**：流水线中因等待资源出现的空档。
- **`__builtin_expect` / likely / unlikely**：向编译器声明分支倾向。
- **PGO（Profile Guided Optimization，配置引导优化）**：用真实运行 profile 重新编译布局代码。
- **LSD（Loop Stream Detector）**：Core 2 前端特性，小循环可锁定在指令队列。
- **`-Os`**：gcc 面向代码大小的优化开关。

## 4. 硬件工作流程

### 4.1 指令获取路径

```text
程序计数器 (PC) → 分支预测器预取目标 → L1i（已解码指令）→ 译码 → 执行
                        │                    │
                    指令字节流            L1i miss 时从 L2/主存取字节流
                   （L2 统一缓存存字节流）
```

- L1i 命中可跳过部分译码（trace cache）。
- 指令流在跳转之间是线性的，这段时间预取效率高；跳转打破线性，是 L1i miss 与流水线气泡的来源。

### 4.2 代码布局与块重排（PDFp56）

```text
未重排：      [A][条件跳转→跳过 B?][B(少执行)][C]
重排后：      [A][条件跳转→跳到远处 B][C]  ...  B 被移到不碍事的地方
```

- 若 B 极少执行，未重排时 B 的缓存行被预取进 L1i 造成污染。
- `-freorder-blocks`（默认在 -O2 开启）配合 likely/unlikely 把少执行块移开。

## 5. PDF 核心观点

> 来源：PDF 第 31~32、55~57、85 页；对应章节 3.4、3.4.1、6.2.2、7.4。以下为概括。

### 3.4 指令缓存概览（PDFp31）

1. **指令缓存比数据缓存好搞**（PDFp31）：代码量取决于问题复杂度（固定）；指令由编译器生成（编译器懂规则）；程序流比数据访问可预测；代码天生有很好的空间/时间局部性。
2. **长流水线放大停滞代价**（PDFp31）：Netburst 流水线 >20 级；停滞后再提速要花时间；停滞来自分支误预测或取指太慢。
3. **L2+ 是统一缓存**（PDFp31）：存指令原始字节流而非解码形式。
4. **L1i 两条规则**（PDFp31）：(a) 生成尽可能小的代码（软件流水等例外）；(b) 帮处理器做好预取（代码布局或显式预取）。

### 3.4.1 自修改代码（PDFp31）

5. **SMC 应避免**（PDFp31）：早期因内存稀缺而用，如今多用于性能优化或漏洞利用；修改过的代码无法留在 trace cache，流水线中已被修改的指令会导致大量工作作废，甚至大部分处理器状态要丢弃。
6. **L1i 用简化 SI 协议**（PDFp31）：处理器假设代码页不可变（99.9999999% 成立），L1i 不用 MESI 而用简化的 SI；一旦检测到修改会做大量悲观假设。
7. **Linux 下代码页写保护**（PDFp31~32）：常规工具链构建的程序代码页写保护，SMC 需链接期"魔法"；Intel 有专门计数器可检测 SMC 使用。

### 6.2.2 L1i 优化（PDFp55~57）

8. **L1i 优化与 L1d 类似，但程序员通常间接影响**（PDFp55）：除非写汇编，否则通过引导编译器做更好的代码布局。
9. **降低代码占用**（PDFp56）：与循环展开、内联平衡；`-Os` 关闭以增大代码为主的优化，常带来意外收益。
10. **内联的权衡**（PDFp56，表 6.3）：内联 `inlcand` 到 f1/f2 → 总代码 +1×inlcand；不内联 → 少占 L1i/L2，且代码可能仍在 L1i 不用重新译码，分支预测也已见过。可调 `-finline-limit`。
11. **何时该内联**（PDFp56）：只调用一次的函数应内联（利于值域传播等）；`always_inline` / `noinline` 属性按需使用；多处以小代价换取更激进优化要个案判断。
12. **likely/unlikely**（PDFp56~57）：`__builtin_expect(!!(expr), 1/0)`，`-freorder-blocks` 将少执行块移出主路径，减少 L1i 污染与误预测。
13. **LSD 小循环**（PDFp57）：Core 2 前端对 ≤18 条指令、≤4 次 16B 取指、≤4 条分支、执行 >64 次的小循环可锁定在指令队列，重复进入更快。
14. **代码对齐**（PDFp57）：代码是线性大块、由编译器生成，程序员只能间接控制；在战略位置对齐（非每条指令）。

### 7.4 改善分支预测（PDFp85）

15. **两种方法**（PDFp85）：静态预测（`__builtin_expect`）+ PGO。
16. **PGO 三步**（PDFp85）：所有文件用 `-fprofile-generate` 编译链接 → 跑代表性工作负载生成 `.gcda` → 用 `-fprofile-use` 重编译。
17. **PGO 的坑**（PDFp85）：测试负载必须代表真实用法，否则优化可能有害；库很难用 PGO（场景差异大），通常只靠静态预测；源码不能有产生代码的改动，否则校验失败。

## 6. 通俗解释

**指令缓存**，就像**厨师手上的菜谱**：

> 数据缓存是"食材冰箱"，指令缓存是"菜谱"。菜谱是固定写好的（编译器写的），照着抄就行——
> 所以它比"随机拿食材"好预测得多。问题只剩：菜谱太长（代码大）、或者老要跳来跳去翻页（分支多）。

**为什么内联要小心**？

> 内联像把常用小抄直接抄进每页菜谱。少抄几次（不内联）时菜谱薄、好查；
> 全抄进去菜谱厚了，翻页（取指）慢。但只在一处用的菜谱，直接抄进去最省事（值域传播等优化更好做）。

**likely/unlikely 在做什么**？

> 告诉编译器"这个分支 99% 走这边"。编译器把"99% 不走的代码"挪到不碍事的地方，
> 避免那几行很少用的代码占着 L1i，还让分支预测更准。

**PGO** 是：

> 让程序先在"真实使用"下跑一遍，记录每段代码被走到多少次，然后据此重新排版代码——
> 把热代码摆在一起。前提是：测试负载得像真实使用，否则优化反而帮倒忙。

## 7. 示例分析

### 7.1 内联 vs 不内联（表 6.3，PDFp56）

- 不内联：`f1 + f2 + inlcand`（代码小），`inlcand` 可能仍在 L1i，无需重新译码，分支预测器已见过它。
- 内联两处：`f1 + f2 + 2×inlcand`（代码大），需要更多 L1i/L2，但如果 f1/f2 被顺序调用、`inlcand` 很小，内联的收益（更大优化范围）可能盖过 L1i 压力。
- 结论：没有绝对答案，`-finline-limit`、`always_inline`/`noinline` 提供控制手段。

### 7.2 L1i 污染的典型场景

```cpp
if (likely(status == OK)) {
    do_main_work();      // 热路径
} else {
    handle_error();      // 冷路径，极少执行
}
```

- 未用 likely：编译器按源码顺序布局，`handle_error` 的代码夹在热路径中间，被预取进 L1i，浪费。
- 用了 likely + `-freorder-blocks`：`handle_error` 被移到远处，热路径线性、无污染。

## 8. 未优化代码

对应"指令缓存不友好"的写法：无分支提示、冷热代码混杂、过度内联。

```cpp
// bad.cpp: 无 likely/unlikely，错误处理代码内联在热路径
#include <cstdlib>

int process(int x) {
    if (x < 0) {                 // 开发者知道几乎不会发生，但未告知编译器
        return std::abort();     // 冷路径，占用热路径位置
    }
    long long s = 0;
    for (int i = 0; i < 1000000; ++i) s += (x + i) % 7;
    return (int)s;
}
```

## 9. 优化后代码

对应"指令缓存友好"的写法：用 likely 告知分支倾向。

```cpp
// good.cpp: 使用 likely，冷路径移出主路径
#include <cstdlib>

#define likely(x)   __builtin_expect(!!(x), 1)
#define unlikely(x) __builtin_expect(!!(x), 0)

int process(int x) {
    if (unlikely(x < 0)) {       // 提示编译器：几乎不会走到
        return std::abort();
    }
    long long s = 0;
    for (int i = 0; i < 1000000; ++i) s += (x + i) % 7;
    return (int)s;
}
```

编译时配合：`g++ -O2 -freorder-blocks`（-O2 默认开启）。

> 更完整的指令缓存实验见 src/27_instruction_cache；PGO 与分支统计命令见下文"如何验证"。

## 10. 为什么会更快

| 角度 | 无分支提示 | likely + 重排 |
|---|---|---|
| L1i 污染 | 冷代码占热路径缓存行 | 冷代码移开，热路径纯净 |
| 预取 | 拉入无用代码行 | 全部预取有用代码 |
| 分支预测 | 可能误预测 | 静态提示 + 更好的布局 |
| 代码足迹 | 不变量 | 不变量（但布局更优） |
| 流水线气泡 | 可能更多 | 更少 |

> 注意：对编译器来说，错误地把 `likely`/`unlikely` 用反反而更糟（PDFp85 提及）。本优化必须实测，
> 不保证一律加速；src/27 会给出本机数据。

- src/27：对比"热路径被冷代码打断"与"布局干净"两版代码的 L1i miss 与运行时间。

- 不要只看一次运行；用多轮统计（本项目所有实验默认）。

## 13. 常见误区

- **误区 1：代码越小一定越快**。`-Os` 是候选之一，但若算法本身受益于展开/内联，小代码可能更慢；需平衡（PDFp56 原文）。
- **误区 2：内联总是好的**。内联增加 L1i 压力，多调用点内联会使代码膨胀（表 6.3）。
- **误区 3：`likely`/`unlikely` 用了就快**。用反方向会误导编译器；且需要配合块重排（-freorder-blocks）才有效果。
- **误区 4：SMC 只是为了性能可以随便用**。SMC 会被坏流水线、L1i 用简化协议、还常是漏洞利用手法；应避免。
- **误区 5：PGO 一定更快**。PGO 把代码按"训练负载"优化；训练负载与真实使用不符时可能有害（PDFp85）。
- **误区 6：对齐每一条指令**。只需在战略位置对齐；`-falign-labels` 对齐每个基本块通常反而变慢（PDFp57 原文）。

## 14. 实践练习

2. 写一个 `if/else` 极不均衡的函数，分别用/不用 likely 编译，对比 L1i miss 或运行时间。
3. 完整走一遍 PGO 三步流程，比较最终二进制的运行时间，并说明训练负载为何关键。

5. 用 `gcov` 查看一个函数的 branch 统计，找出热/冷分支。

## 15. 本章总结

- 指令缓存比数据缓存更可预测：代码量固定、编译器生成、流可预测、局部性好。
- L1i 缓存已解码指令（trace cache），L2+ 统一缓存存字节流。
- 三条规则：代码尽量小、执行线性无气泡、战略位置对齐。
- 内联要权衡 L1i 压力与优化收益；单点调用应内联。
- `likely`/`unlikely` + `-freorder-blocks` 减少冷代码对 L1i 的污染。
- PGO 用真实 profile 重排代码，但训练负载必须代表真实使用。
- SMC 应避免；L1i 用简化 SI 协议假设代码不可变。
