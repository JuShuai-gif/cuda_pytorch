# 31 性能优化检查清单

> 综合篇：把全书优化原则整理为可执行的检查清单，供开发与代码审查时逐项核对。
> 来源：综合 PDF 各章节（第 2~8 章）的优化结论。

## 1. 本章要解决的问题

- 代码审查时按什么顺序检查内存性能？
- 每个优化点的"前提"与"验证方法"是什么？
- 哪些是低成本高收益、哪些是高风险需实测？

## 2. 前置知识

- 全书知识：缓存、局部性、数据布局、多线程、NUMA、工具。

## 3. 核心概念

- **Checklist（检查清单）**：按收益/成本排序的可操作步骤。
- **先测量后优化**：用工具定位热点，再动手。
- **基线对照**：优化前后必须对比同一 checksum 的正确性。

## 4. 硬件工作流程（检查顺序）

```text
第 0 步：确认问题在内存（perf：cache-misses、CPI、带宽）
第 1 步：访问模式（顺序 vs 随机、步长、跨缓存行）
第 2 步：数据布局（AoS/SoA、对齐、关键字段前置）
第 3 步：工作集 vs 缓存（分块、大页）
第 4 步：多线程（false sharing、原子、绑核、NUMA）
第 5 步：预取/流式写（软件预取、non-temporal store）
第 6 步：验证（checksum + 多轮 + 工具）
```

## 5. PDF 核心观点（综合）

> 来源：综合 PDF 各节。以下为全书优化结论的概括汇总。

1. **随机访问尽量改顺序**（6.2.1，PDFp49）：随机访问慢 70%。
2. **改善空间/时间局部性 + 对齐**（6.2，PDFp49）：是所有缓存优化的主题。
3. **利用整条缓存行**（6.2.1）：读取 int 会加载整行；顺序用满行内元素。
4. **数据布局**（6.2.1）：关键字段前置、按定义顺序访问、pahole 查布局、必要时 AoS→SoA。
5. **对齐对象到缓存行**（6.2.1）：posix_memalign / aligned 属性；未对齐慢 300%（图 6.4）。
6. **分块让工作集适应缓存**（6.2.1、LLC 部分）：矩阵乘法分块 100%→17.3%。
7. **避免 false sharing**（6.4.1）：常写变量独立缓存行；只读分组；单线程用 TLS。
8. **原子操作选对类型**（6.4.2）：优先原子算术/局部归约，少用 CAS 循环。
9. **绑核与 NUMA**（6.4.3、6.5）：共享数据绑同缓存核；独立数据分开；本地分配。
10. **预取要有条件地加**（6.3）：先找 miss 大户，加后看"有用预取"计数。
11. **流式写只用于不重用数据**（6.1）：大块一次性写入；写后重用不要用。
12. **用大页减 TLB miss 与页错误**（6.2.4、7.5）：2MB 页减 511 页错误/页。
13. **工具验证**（7）：perf 看真实、Cachegrind 看假设、Massif 看分配模式。

## 6. 通俗解释

检查清单就像**体检单 + 维修手册**：

> 先量血压（perf），再决定动哪里。每项优化都有"什么时候该做"和"怎么做才算数"。
> 别一上来就上分块/预取——先确认瓶颈确实在内存、确实该用这招。

## 7. 示例分析

### 7.1 一段代码的检查流程

```cpp
for (auto& p : particles) sum += p.x;   // AoS，只读 x
```

1. 先 perf：cache-misses 高？
2. 访问模式：顺序，OK。
3. 数据布局：AoS 且只读 x → 每行只用 1/8 → 改 SoA。
4. 多线程：若并行且 sum 是共享 → false sharing/原子问题 → 局部归约。
5. 工作集：若大 → 大页/分块。
6. 验证：checksum 一致 + 多轮对比。

### 7.2 收益/成本分级

| 级别 | 手段 | 成本 | 风险 |
|---|---|---|---|
| 低 | 顺序访问、局部变量 | 低 | 低 |
| 低 | 结构体重排、对齐 | 低 | 低 |
| 中 | AoS→SoA | 中（代码重写） | 访问全字段时可能退化 |
| 中 | 分块 | 中 | 块大小需扫描 |
| 中 | 绑核/本地分配 | 中 | 平台依赖 |
| 高 | 软件预取 | 中 | 可能变慢（图 6.7 仅 8%） |
| 高 | 流式写 | 低 | 写后重用更慢 |
| 高 | 大页 | 低（配置） | 需系统支持 |

## 8. 未优化代码

综合示例：随机访问 + AoS 部分字段 + 共享计数。

```cpp
// bad.cpp
#include <vector>
#include <random>
#include <thread>

struct Particle { float x, y, z, velocity, mass; };

int main() {
    constexpr int N = 1 << 20;
    std::vector<Particle> p(N);
    std::mt19937 rng(42);
    long long sum = 0;
    for (int i = 0; i < N; ++i) {
        int idx = static_cast<int>(rng() & (N - 1));
        sum += (long long)p[idx].x;    // 随机 + AoS 部分字段
    }
    return sum == 0;
}
```

## 9. 优化后代码

综合优化：顺序访问 + SoA 布局 + 局部变量。

```cpp
// good.cpp
#include <vector>

int main() {
    constexpr int N = 1 << 20;
    std::vector<float> x(N);
    long long sum = 0;
    for (int i = 0; i < N; ++i) sum += (long long)x[i];  // 顺序 + 连续数组
    return sum == 0;
}
```

## 10. 为什么会更快

| 角度 | bad | good |
|---|---|---|
| 访问模式 | 随机 | 顺序 |
| 缓存行利用 | 低（AoS+随机） | 高（SoA+顺序） |
| 预取 | 失效 | 生效 |
| 可向量化 | 否 | 是 |

## 11. 如何验证（检查清单）

```bash
./scripts/system_info.sh                      # 记录环境
./scripts/perf_stat.sh ./build/...            # 基线：cache-misses/CPI
# 逐项优化，每步：
#   1) 重编译
#   2) 多轮跑（输出 mean/median/min/stddev）
#   3) 核对 checksum 一致
#   4) perf 对比 cache-misses 变化
```

## 12. 实验结果应该怎么看

- 每步优化要有**可量化的改善**（时间/miss 下降），否则回退。
- 若某优化无改善，检查前提是否满足（如预取距离、写后重用场景）。
- 记录 CPU/内核/编译器，保证可复现。

## 13. 常见误区

- **误区 1：先优化后测量**。必须先用工具定位热点。
- **误区 2：一次改多处**。一次一处，便于归因（论文预取方法）。
- **误区 3：只看运行时间**。要看 miss/带宽/TLB 等多维度。
- **误区 4：优化后不验证正确性**。checksum 必须一致。
- **误区 5：所有机器通用**。缓存大小、NUMA、预取行为因平台而异，要在目标机验证。

## 14. 实践练习

1. 选一个函数，按清单第 0~6 步走一遍完整流程。
2. 对每项优化记录"改善百分比"，只保留有实测收益的。
3. 用 Cachegrind 验证数据布局类优化的 miss 变化。
4. 用 perf 验证多线程优化的 cache-misses 与 CPI。
5. 写一份自己的"性能优化检查清单"，标注各项目标平台。

## 15. 本章总结

- 检查顺序：测量 → 访问模式 → 布局 → 工作集 → 多线程 → 预取 → 验证。
- 每项优化有前提与风险；用基线 + checksum + 多轮验证。
- 低成本优先（顺序访问、对齐、布局），高风险项（预取、流式）先确认前提。
