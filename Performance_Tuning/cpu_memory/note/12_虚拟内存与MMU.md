# 12 虚拟内存与 MMU

> 对应 PDF：第 4 章 Virtual Memory（PDFp37~42）、第 4.4 节 Impact Of Virtualization（PDFp41~42）
> 本篇回答：虚拟地址怎么翻译成物理地址？为什么用多级页表？页表访问太慢怎么办（引出 TLB）？虚拟化为何让内存处理更昂贵？

## 1. 本章要解决的问题

- MMU 与页表如何实现"每个进程独占地址空间"？
- 单级页表为何不可行，多级页表如何省内存？
- 页表驻留内存导致每次翻译要多次内存访问，怎么办？
- 虚拟化（Xen/KVM）为什么增加内存处理成本？

## 2. 前置知识

- note/05：缓存地址切分（Tag/Set/Offset）思想，页表翻译与之类似。
- 进程与地址空间：每个进程有独立虚拟地址空间。
- 段（segment）：x86 上逻辑地址加段偏移（论文说可忽略，性能无碍）。

## 3. 核心概念

- **Virtual Memory / Address Space（虚拟内存/地址空间）**：进程看到的独立地址空间。
- **MMU（Memory Management Unit）**：执行虚拟→物理翻译的硬件单元。
- **Page Table（页表）**：记录虚拟页→物理页映射的数据结构，存于主存。
- **Page Directory Entry（目录项）**：页表中指向下一级目录或物理页的条目。
- **Page Tree Walking（页表遍历）**：从顶级目录逐级索引到物理页的完整过程。
- **Sparse Page Table（稀疏页表）**：未使用地址区间不分配目录，多级结构因此紧凑。
- **Page Size（页面大小）**：如 4KB、2MB、4MB、64KB。
- **TLB（Translation Look-Aside Buffer）**：缓存页表遍历结果的快速缓存（note/14 详述）。
- **Context Switch（上下文切换）**：进程/线程切换，可能触发 TLB 刷新。
- **ASID（Address Space ID）**：AMD Pacifica 引入的 TLB 标签扩展，区分地址空间。
- **Shadow Page Tables（影子页表）**：VMM 维护、硬件实际使用的页表。
- **EPT / NPT**：Intel Extended Page Tables / AMD Nested Page Tables，硬件二次翻译避免影子页表。

## 4. 硬件工作流程

### 4.1 单级地址翻译（论文图 4.1，PDFp37）

```text
虚拟地址: |  Page Directory Index  |  Offset  |
                      │                    │
Page Directory (页目录数组，存主存)         │
  目录项 → 物理页基址 ─────────────────────► 拼成物理地址
  (还含访问权限等)
```

- 顶级目录基址存于专用寄存器。
- 4MB 页面：Offset 22 位 + 目录索引 10 位（1024 项）。
- 多个目录项可指向同一物理页。

### 4.2 多级页表（论文图 4.2，PDFp37~38）

```text
虚拟地址: | L4 | L3 | L2 | L1 | Offset |
              │    │    │    │      │
L4 目录(寄存器指向)  │    │    │      │
  └─►L3 目录        │    │    │      │
      └─►L2 目录    │    │    │      │
          └─►L1 目录 │    │    │      │
              └─► 物理页基址 ──► 物理地址
```

- 目录项为空则无下级目录 → 稀疏紧凑。
- x86/x86-64 硬件自动遍历；其他架构需 OS 协助。
- 4 级 × 512 项（x86-64 4KB 页）：2MB 只需 4 个目录；1GB 需 4+512 个目录。
- 栈与堆分处地址空间两端 → 至少两个 L2 目录。
- ASLR 随机化各段位置 → 用更多目录，牺牲少量内存换安全。

### 4.3 页表访问太慢 → TLB（PDFp38）

```text
每次翻译 → 至多 4 次内存访问（4 级页表）→ 串行依赖 → 太慢
优化：缓存"完整翻译结果"（物理页号 + 页内偏移）
       → 这就是 TLB；tag = 虚拟地址（去掉页内偏移）
       → TLB 通常很小、极快；L1TLB 常全相联 + LRU，现在也组相联
```

- 把页表项当普通数据缓存仍不够：4 级 × 串行依赖 ≥ 12 周期，还抢缓存带宽。
- TLB miss → 页表遍历（昂贵）。
- 硬件预取不能预取 TLB 条目（可能触发无效遍历）；需显式预取。
- TLB 也分指令 TLB（ITLB）/数据 TLB（DTLB），L2TLB 通常统一。

### 4.4 TLB 的一致性与上下文切换（4.3.1，PDFp39）

- TLB 是核心全局资源，所有线程/进程共享。
- 页表改变后，两种处理：刷新 TLB，或给 TLB 条目加"地址空间标识"（ASID）。
- 刷新昂贵：Core2 有 128 ITLB + 256 DTLB，一次全刷浪费大量条目；系统调用进出内核就可能触发。
- 单条目失效（按地址范围）比全刷便宜。
- 扩展 tag（ASID）：内核/VMM/各进程有唯一 ID；缺点：ID 位数有限，需复用并部分刷新。
- 好处：同一进程线程切换无需刷 TLB；进出内核/虚拟机的翻译可保留。

### 4.5 虚拟化（4.4，PDFp41~42）

```text
Xen 模型：VMM + Dom0/DomU
  客户 OS 修改页表 → 触发 VMM → 更新影子页表（硬件用的）→ 昂贵

KVM 模型：Linux 内核兼作 VMM，guest 以进程形式运行
  复用内核成熟的内存管理，减少重复实现

硬件加速：Intel EPT / AMD NPT
  客户页表生成"宿主机虚拟地址"，再经 EPT/NPT 翻译到物理地址
  省掉影子页表更新；翻译结果缓存进 TLB
```

- 虚拟化下缓存/TLB miss 代价更高，内存优化收益更大。

## 5. PDF 核心观点

> 来源：PDF 第 37~42 页；对应章节 4、4.1~4.4。以下为概括。

1. **虚拟内存由 MMU 实现，OS 填充页表数据结构**（PDFp37）：CPU 负责大部分翻译工作。
2. **翻译按页进行**（PDFp37）：与缓存寻址类似，虚拟地址切分后索引各级目录。
3. **单级页表不现实**（PDFp37）：4KB 页、20 位索引 → 2^20 项、4MB 表；每进程一份会吞掉大量物理内存。
4. **多级页表稀疏紧凑**（PDFp37）：未用区域不分配目录；现代最多 4 级。
5. **页表树越小越好**（PDFp38）：内存放得越集中越好（物理地址无关）；栈堆分两端、ASLR 随机化都增加目录数。
6. **页表遍历慢**（PDFp38）：最多 4 次内存访问、串行依赖、抢缓存带宽；L1d 缓存目录项远远不够。
7. **TLB 缓存完整翻译**（PDFp38）：tag 用虚拟地址（去页内偏移）；通常很小、全相联/LRU（新近组相联）；分级（ITLB/DTLB/L2TLB）。
8. **硬件预取不能预取 TLB**（PDFp38）：可能触发无效遍历；需显式预取。
9. **TLB 刷新代价**（PDFp39）：系统调用进出内核可能导致整刷；Core2 全刷浪费 >100 条目。
10. **ASID/扩展 tag**（PDFp39）：避免每次进出内核/虚拟机全刷；但 ID 位数有限需复用。
11. **大页减小 TLB 压力**（PDFp40）：更大页 → 更少翻译 → 更少 TLB 项；但需要物理连续、有浪费（平均浪费半页）、碎片化后难分配。
12. **hugetlbfs**（PDFp40）：Linux 用 hugetlbfs 预留大页（系统启动时分配固定池），改池大小常需重启；数据库是典型用户。
13. **大页减少页表层级**（PDFp40）：页内偏移变大，目录位数变少，TLB miss 时遍历更少。
14. **ELF 对齐**（PDFp40，图 4.3）：`eu-readelf -l` 显示 ELF 程序头的 Align=0x200000=2MB，对应处理器支持的最大页。
15. **把同时使用的数据放到更少页面**（PDFp40）：类似缓存优化，但对齐要求更大；TLB 条目少，值得做。
16. **虚拟化增加内存处理成本**（PDFp41~42）：影子页表每次修改页表都触发 VMM；EPT/NPT 用硬件二次翻译接近无虚拟化速度；虚拟化下 miss 代价更高。

## 6. 通俗解释

虚拟内存翻译，像**公司前台的转接电话**：

> 每个进程以为自己是唯一住户，有自己的"分机号"（虚拟地址）。要真正打通，需要查一本
> "分机号→物理线路"的册子（页表）。册子太厚查不快，所以做成"总机→部门→小组→个人"多级目录（多级页表），
> 没人用的分机段就不建目录（稀疏）。

为什么需要 TLB？

> 每打一个电话都要查 4 层目录，太慢。于是前台把查过的结果记在"小纸条"（TLB）上：
> 同一个分机段下次直接拨，不用再查。小纸条很小、但极快；纸条满了（TLB miss）才重新翻册子。

ASID 就像给不同公司（地址空间）的小纸条贴上"公司名"：

> 前台从 A 公司转到 B 公司时，不用把所有纸条全扔掉——A 公司的纸条还留着，切回来还能用。

虚拟化，则是**多了一层"二房东"（VMM）**：

> 房客（客户 OS）以为自己在管房子，其实二房东还要再查一遍自己的账本（影子页表/EPT）。
> 所以虚拟化环境里，每次"查册子"都更贵——这就是为什么虚拟化下内存优化收益更大。

## 7. 示例分析

### 7.1 单级 vs 多级页表

- 4KB 页、32 位地址：Offset 12 位 + 目录 20 位 → 单级表 2^20 项 × 4B = 4MB/进程。
- 4 级：只有用到的目录才分配；2MB 地址空间仅需 4 个目录。
- 栈堆两端、ASLR 分散 → 目录数增加但远小于 2^20。

### 7.2 TLB 刷新场景

- 系统调用：进内核 → 可能刷 TLB；返回同一进程 → 刚刷的条目全没了，要重新填。
- Core2 128 ITLB/256 DTLB：全刷浪费 100+/200+ 条目。
- 有 ASID：进出内核不刷，翻译可保留。

### 7.3 大页的代价

- 4KB→2MB 页：每次映射平均浪费 1MB 物理内存（半页对齐）。
- 2MB 页需 512 个连续 4KB 页，碎片化后难找。
- Linux 用 hugetlbfs 启动时预留池解决；但池固定、改大要重启。

## 8. 未优化代码

对应"高 TLB 压力"的程序：随机访问覆盖大量页面。

```cpp
// bad.cpp: 随机访问，每页只用一点点，TLB 频繁 miss
#include <vector>
#include <random>

int main() {
    constexpr int N = 1 << 24;
    std::vector<int> data(N, 1);
    std::mt19937 rng(42);
    long long sum = 0;
    for (int i = 0; i < N; ++i)
        sum += data[static_cast<int>(rng() & (N - 1))];
    return sum == 0;
}
```

## 9. 优化后代码

对应"低 TLB 压力"的程序：顺序访问，页内连续命中。

```cpp
// good.cpp: 顺序访问，页连续、TLB 友好
#include <vector>

int main() {
    constexpr int N = 1 << 24;
    std::vector<int> data(N, 1);
    long long sum = 0;
    for (int i = 0; i < N; ++i)
        sum += data[i];
    return sum == 0;
}
```

> TLB 专项实验见 src/18_tlb_capacity；大页见 src/19_page_size、src/20_huge_pages。

## 10. 为什么会更快

| 角度 | 随机访问 | 顺序访问 |
|---|---|---|
| TLB Miss | 每页新位置都 miss | 页内连续命中 |
| 页表遍历 | 频繁触发（昂贵） | 极少 |
| DTLB-load-misses | 高 | 低 |
| Cache 命中 | 差 | 好 |
| 预取 | 无效 | 有效 |

TLB miss 的代价不止翻译本身：页表遍历还要访问主存、抢缓存带宽，串行等待无法被流水线隐藏。

## 12. 实验结果应该怎么看

- src/18：随"使用的页数"增加，dTLB-load-misses 与延迟出现台阶——台阶位置对应 TLB 容量。
- src/19/20：大页下 dTLB miss 大幅下降；若系统未配置大页，程序会提示并跳过，属预期。
- 注意：顺序访问会被硬件预取/缓存掩盖 TLB 效果，src/18 采用"每页访问一个元素"的方法（论文图 3.17 思路）。

## 13. 常见误区

- **误区 1：页表项缓存 = TLB**。TLB 缓存的是"完整翻译结果"，不是目录项；把目录项当数据缓存仍太慢（4 级串行）。
- **误区 2：TLB 越大越好**。TLB 要极快，太大反而慢；而且上下文切换常导致刷新，条目多了也未必填满（论文原意）。
- **误区 3：硬件预取能顺带预热 TLB**。不能——硬件预取可能触发无效页表遍历，TLB 需显式预取。
- **误区 4：大页免费**。要物理连续、平均浪费半页、碎片化难分配；Linux 靠 hugetlbfs 预留。
- **误区 5：虚拟化无内存性能代价**。影子页表时代每次改页表都进 VMM；EPT/NPT 大幅改善但 miss 代价仍更高。

## 15. 本章总结

- 虚拟内存由 MMU + OS 填写的页表实现；翻译按页进行。
- 单级页表不现实；多级（现代 4 级）稀疏紧凑。
- 页表遍历每次至多 4 次串行主存访问，太慢 → 用 TLB 缓存完整翻译。
- TLB 是核心全局资源，上下文切换/进出内核的刷新代价高；ASID 扩展 tag 缓解。
- 大页减少翻译次数与页表层级，但需物理连续与 hugetlbfs 预留。
- 虚拟化（影子页表/EPT/NPT）让内存处理更昂贵，虚拟化下内存优化收益更大。
