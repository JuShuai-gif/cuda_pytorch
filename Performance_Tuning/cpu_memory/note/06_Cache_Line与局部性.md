# 06 Cache Line 与局部性

> 对应 PDF：第 3.2 节 Cache Operation at High Level（PDFp15~16）中关于缓存行与地址切分的部分、第 3.3.2 节 Measurements of Cache Effects（PDFp20~21）、图 3.4（PDFp17）、图 3.10~3.12（PDFp21）

## 1. 本章要解决的问题

- 为什么缓存按行管理，而不是按字/字节？
- 什么是空间局部性与时间局部性，它们如何让缓存生效？
- 论文的缓存效应测量程序（链表 + 可变 NPAD）怎么设计？
- 工作集大小如何决定访问延迟的三个台阶（L1d / L2 / 主存）？
- 元素大小（NPAD）如何通过"每行元素数"影响预取与 L2 命中？
- 硬件预取为什么不能跨页面边界？

## 2. 前置知识

- note/05：缓存行、Tag/Set/Offset、局部性、缓存层级延迟。
- note/03：DRAM 突发传输适合一次传多字。
- 链表与指针：`struct l { l* n; long pad[NPAD]; }` 构成的循环链表。
- 2 的幂：工作集大小按 2 的幂变化（2^10 到 2^28 字节）。

## 3. 核心概念

- **Cache Line（缓存行）**：缓存管理的最小单位（现代多为 64B，早期 32B）。
- **Spatial Locality（空间局部性）**：邻近地址的数据往往短时间内一起被访问。
- **Temporal Locality（时间局部性）**：访问过的数据往往很快再次访问。
- **Working Set（工作集）**：程序短期实际用到的内存集合，决定缓存需要多大。
- **NPAD（填充）**：论文测试中结构体里 `long pad[NPAD]` 的填充数量，决定每个元素跨多少缓存行。
- **Prefetching（预取）**：提前把下一个缓存行载入，掩盖延迟。
- **Prefetch Window（预取窗口）**：硬件预取器能提前预取的距离范围。
- **Page Boundary（页边界）**：硬件预取不能越过虚拟页边界（4KB/大页）。

## 4. 硬件工作流程

### 4.1 一次访问的命中路径

```text
CPU 访问地址 A
   │
   ▼
把 A 的低 6 位清零 → 得到缓存行地址（64B 行）
   │
   ▼
在 L1d 中按 Tag 查找 ──命中──► 返回行内偏移字节（~4 周期）
   │ Miss（下一行可能已被硬件预取）
   ▼
L2（若预取已就位，只需 ~9 周期而不是 14）
   │ Miss
   ▼
主存（无预取时 200+ 周期）
```

### 4.2 论文测量程序的数据结构（PDFp20，3.3.2）

```cpp
struct l {
    struct l *n;          // 下一个链表节点（总是用指针前进）
    long int pad[NPAD];   // 有效载荷，可控制元素大小
};
```

- 循环单链表，节点要么顺序排列、要么随机排列（图 3.9）。
- 无论顺序还是随机，**前进都通过指针 n**，因此每次都要先加载 n 所在缓存行。
- 工作集 2^N 字节，元素数 = 2^N / sizeof(struct l)。
- 32 位系统 NPAD=7 → 元素 32B；64 位系统 NPAD=7 → 元素 64B。

## 5. PDF 核心观点

> 来源：PDF 第 17~21 页；对应章节 3.3.1、3.3.2，图 3.4、图 3.10~3.12。以下为概括。

1. **随机写访问的延迟台阶**（PDFp17，图 3.4）：Y 轴为每个元素平均周期数（对数刻度），X 轴为工作集大小（2 的幂）。三个明显平台：<2^13 字节（<10 周期）、2^13~2^20 字节（~28 周期）、>2^20 字节（480+ 周期）。可反推该 CPU 有 2^13 的 L1d 与 2^20 的 L2。
2. **量级差异**（PDFp17）：不是百分之几，而是数量级——这是研究缓存优化的动机。
3. **顺序读访问（NPAD=0）**（PDFp21，图 3.10）：P4 上三个台阶——工作集 ≤2^14（L1d 16kB）约 4 周期；2^15~2^20（L2 1MB）约 9 周期；>2^21 后靠预取维持在 ~9 周期。
4. **为什么 L2 区域只要 9 周期而非 14**（PDFp21）：硬件预取下一行，等用到时已载入一半，等待时间远小于 L2 访问时间。
5. **预取把主存访问压到 9 周期**（PDFp21）：200+ 周期的主存访问靠有效预取得以隐藏，与"200 vs 9"的差距吻合。
6. **NPAD 破坏预取**（PDFp21，图 3.11）：NPAD=7/15/31 时每迭代需要新缓存行，预取逻辑无法每周期加载一行，L2 区域每条元素回到 ~28 周期。
7. **硬件预取不能跨页**（PDFp21）：元素变大后，页内有效预取减半（每增大一级减少 50% 有效性）；若预取跨页而下一页不存在，OS 会被卷入处理页错误，这是不被允许的。
8. **缓存大小 × 关联度 × 集合数**（PDFp19）：`缓存大小 = 缓存行大小 × 关联度 × 集合数`；O=log2(行大小)、S=log2(集合数)。
9. **关联度收益有上限**（PDFp19）：直接映射→2 路对 8MB 缓存省约 44% 缺失；但超过 8 路收益甚微；多核共享 L2 会"实际减半"关联度，因此共享缓存需要更高关联度。
10. **选机器要测工作集**（PDFp20）：缓存买多大，应基于实际工作集测量（图 3.10 类实验）。

## 6. 通俗解释

**缓存行 + 局部性**，就像"顺路捎货"：

> 你去仓库（主存）取货（读数据），路很远。好在一次可以捎回来一整箱（64B 缓存行）。
> 如果你的需求正好是"顺着一排货架一个个拿"（空间局部性），这一箱箱货全用得上，一趟顶十六趟。
> 如果你过一会儿还要再用同一个东西（时间局部性），它还在桌上，不用再跑仓库。

**NPAD 实验**在揭示什么？

> 把每个货（元素）之间的间隔拉大：本来一箱能装 8 个货（NPAD=0），现在一箱只装 1 个货（NPAD≥7）。
> 于是每取一个货都要跑一趟仓库——预取传送带（一次搬一箱）跟不上你"每个都搬新箱子"的速度，于是回到慢速通道。

**为什么预取不能跨页**？

> 预取器像送外卖的，只能在你确认"这条街存在"（页有效）之后才敢送下一单。
> 页面边界之外的"街"（下一页）可能根本不存在（页错误），它不敢贸然过去。

## 7. 示例分析

### 7.1 读取一个 int 会加载整个缓存行

- 读 `data[i]`（4B），64B 行，地址低 6 位清零。
- 整行载入 L1d，`data[i]` 是行内一个偏移。
- 顺序读 `data[i+1..i+15]` 全命中——一条行覆盖 16 个 int。

### 7.2 NPAD 与每行元素数

- 64 位系统，NPAD=0：元素 8B（指针），每 64B 行 = 8 个元素，预取 1 行够 8 次迭代。
- NPAD=7：元素 64B，每 64B 行 = 1 个元素，预取 1 行只够 1 次迭代。
- NPAD=31：元素 256B，跨越 4 行，每次迭代要 4 行——硬件预取根本跟不及。

### 7.3 延迟台阶反推缓存大小

论文图 3.4：平台出现在 <2^13、2^13~2^20、>2^20。
=> L1d = 2^13 字节 = 8kB（另一台机器 16kB），L2 = 2^20 字节 = 1MB。
这与 `lscpu`/`/sys` 报告的缓存大小应互相印证（本机需实测）。

## 8. 未优化代码

对应论文中"每元素跨多条缓存行"的坏布局：结构体字段交错 + 指针追逐。

```cpp
// bad.cpp: 元素大（大量无用填充）+ 随机排列，每迭代多行 miss
#include <vector>
#include <algorithm>
#include <random>

struct BigNode {
    BigNode* n;
    char padding[248];   // 元素 256B，跨 4 条缓存行
};

int main() {
    constexpr int N = 1 << 16;
    std::vector<BigNode> pool(N);
    std::vector<int> order(N);
    std::mt19937 rng(42);
    for (int i = 0; i < N; ++i) order[i] = i;
    std::shuffle(order.begin(), order.end(), rng);
    for (int i = 0; i < N; ++i) pool[i].n = &pool[order[(i + 1) % N]];

    BigNode* cur = &pool[0];
    long long sum = 0;
    for (int i = 0; i < N; ++i) {   // pointer chasing
        sum += (long long)cur->n;
        cur = cur->n;
    }
    return sum == 0;
}
```

## 9. 优化后代码

对应论文"顺序 + 紧凑 + 可利用预取"的好布局：小结构体 + 连续节点池 + 顺序访问。

```cpp
// good.cpp: 紧凑结构体 + 顺序链，预取友好
#include <vector>

struct Node {
    Node* n;
};

int main() {
    constexpr int N = 1 << 16;
    std::vector<Node> pool(N);
    for (int i = 0; i < N; ++i) pool[i].n = &pool[(i + 1) % N];

    Node* cur = &pool[0];
    long long sum = 0;
    for (int i = 0; i < N; ++i) {
        sum += (long long)cur->n;
        cur = cur->n;
    }
    return sum == 0;
}
```

## 10. 为什么会更快

| 角度 | 随机/大元素 | 顺序/紧凑 |
|---|---|---|
| Cache Line 利用率 | 每元素跨多行，大量浪费 | 一行装 8 个元素，全用上 |
| L1d/L2 命中 | miss 高 | 命中 + 预取 |
| 硬件预取效果 | 无效（元素>预取窗口） | 完美匹配（顺序小步长） |
| DRAM 访问次数 | 每元素多次 | 每行一次 |
| TLB/页 | 随机页 miss | 顺序页连续命中 |
| 时间局部性 | 差 | 好（循环反复扫同一段） |

论文实测：同样工作集，顺序+NPAD=0 在 L2 区约 9 周期/元素，而 NPAD=7+ 约 28 周期/元素；超过 L2 后差异更大（图 3.11）。

## 12. 实验结果应该怎么看

- src/05 的曲线应出现多个平台，平台位置对应 L1d/L2/L3 大小；用 `lscpu -C` 核对。
- 观察**台阶之间的差值**：不是"数值变大了"就完，要解释"从哪级缓存掉到哪级缓存"：
  - 台阶 1→2：L1d 容量不足，开始走 L2；
  - 台阶 2→3：L2 容量不足，开始走 L3/主存；
  - 若随机访问，台阶更高、更陡——因为预取帮不上忙。
- 论文图 3.11 的关键：NPAD 大时 L2 区回到 ~28 周期，说明预取失效。对应到 src/04：步长超过一定阈值后延迟跳升。

## 13. 常见误区

- **误区 1：缓存命中率只要高就够**。命中率的收益取决于命中与未命中的代价差；未命中代价越高，同样命中率收益越大。
- **误区 2：顺序访问"快"只是因为缓存**。既有缓存行利用，也有硬件预取、DRAM 行命中、TLB 连续命中等多因素叠加。
- **误区 3：元素小 = 一定快**。小元素 + 随机排列仍会 miss；关键是"小元素 + 连续 + 可预取"。
- **误区 4：硬件预取可以任意跨页**。它不能跨页边界（论文明确说明），大元素/大步长会削弱预取。
- **误区 5：加更多缓存关联度就能一直提速**。超过 8 路收益甚微；多核共享时有效关联度才被摊薄。

## 15. 本章总结

- 缓存按行管理（现代 64B），利用空间局部性一次加载整行，降低 DRAM 访问次数。
- 时间局部性让反复使用的数据留在缓存中。
- 论文实验证明：工作集大小决定延迟台阶（L1d/L2/主存），台阶位置可反推缓存大小。
- 硬件预取把主存访问从 200+ 周期压到 ~9 周期，但前提是访问模式可预测（顺序、小步长、不跨页）。
- 元素变大（NPAD 增大）会削弱预取，是"为什么数据结构要紧凑"的底层原因之一。
