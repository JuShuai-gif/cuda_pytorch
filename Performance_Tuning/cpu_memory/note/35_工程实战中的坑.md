# 35 工程实战中的坑

> 综合篇：把"工程中真实踩过的坑"整理成可复现的实验与应对清单。
> 对应实验：src/29_engineering_pitfalls/（p1~p9）
> 说明：这一篇与全书笔记不同——前 33 篇讲"原理"，本篇讲"工程中原理被误用时会怎样"。

## 1. 本章要解决的问题

- 为什么"懂原理"还是会写出慢/错/测不准的代码？
- 编译器优化、语言语义、工具误用分别设了哪些坑？
- 每个坑：现象 → 根因 → 如何验证 → 如何避免。
- 坑与 PDF 原理的对应关系。

## 2. 前置知识

- 全书原理（缓存、原子、对齐、大页、benchmark 规范）。
- C++ 语言基础（容器、智能指针、atomic、volatile）。

## 3. 核心概念

- **Dead Code Elimination（死代码消除）**：结果未被观察的计算可能被编译器删除。
- **Closed-Form（闭式化简）**：简单求和可被编译器替换为数学公式，隐藏真实工作量。
- **`max_align_t`**：malloc/new 仅保证对齐到该类型（x86-64 为 16B），不保证 64B。
- **Atomic Refcount（原子引用计数）**：shared_ptr 拷贝会操作共享控制块的原子计数。
- **Memory Order（内存序）**：seq_cst 是默认且最严格；relaxed 最宽松。
- **`volatile` 语义**：抑制寄存器缓存/消除，与"线程安全"无关。
- **THP Hint（透明大页提示）**：`madvise(MADV_HUGEPAGE)` 是提示，不保证生效。

## 4. 硬件工作流程（坑的形成机制）

```text
程序员意图 ──► 编译器优化 ──► 实际执行
                │
                ├─ 死代码消除：结果未用 → 循环删除 → 测速"0ms"
                ├─ 闭式化简：求和 → 公式 → 工作量消失
                └─ volatile/atomic 误用 → 正确性或性能错误

benchmark 链路：单次运行 ──► 页错误/频率爬升/噪声 ──► 结论失真
```

## 5. PDF 核心观点（与坑的关联）

> 以下坑均可对应到 PDF 明确警告过的点。PDF 没有逐条列出这些"工程坑"，
> 本篇是将其原理落到实践。

1. **Debug 构建测速**（关联 PDF 未明说，但 6.2 强调"看编译器实际生成的代码"）：-O0 下所有优化关闭，时间毫无意义。实验 p1 显示同一函数 O0 比 O3 慢 10 倍。
2. **基准代码被优化掉**（关联本项目 benchmark 规范 + PDF 7 工具）：结果未使用的循环被整个删除（p2：0ms）；简单求和被闭式化简（p2：0ms）。必须用 checksum / do_not_optimize / 写缓冲区。
3. **`std::vector<bool>`**（关联 PDF 6.2.1 数据布局）：位打包 + proxy，访问慢（p3：6 倍），且无法取 `bool&`。
4. **shared_ptr 原子计数竞争**（关联 PDF 6.4.2）：每线程复制 shared_ptr 触发同一缓存行原子 RMW（p4：3.6 万倍差距）。
5. **对齐假设**（关联 PDF 6.2.1、图 6.4）：`new` 只保证 16B（p5：12/16 未对齐 64B），SIMD 与缓存行放置需显式对齐。
6. **单次运行下结论**（关联本项目多轮统计规则）：冷启动/噪声让单次结果误导（p6：stddev 0.39ms，单次可偏差 ±6%）。
7. **无脑 seq_cst**（关联 PDF 6.4.2）：x86 上 lock 前缀开销主导，seq_cst vs relaxed 差别小（p7）；真正的坑是"不必要的原子操作"，应局部归约。
8. **volatile 当线程安全**（关联 PDF 6.4.2、8.1）：volatile 只抑制寄存器缓存，不提供原子性（p8：结果 534 万 vs 期望 2000 万，丢了 73%）。
9. **以为 madvise 一定生效**（关联 PDF 7.5、note/15）：THP 是提示，需用 /proc/self/smaps 验证（p9：AnonHugePages=0，未生效）。

## 6. 通俗解释

这些坑的共同主题是"**意图与现实的落差**"：

> 你以为编译器会老实执行你写的每一行，实际上它比你聪明——没用的循环直接删掉，
> 简单求和直接套公式。你以为 malloc 会给够对齐，实际上只保证 16 字节。
> 你以为 shared_ptr 是"方便的指针"，实际上每次拷贝都在共享缓存行上抢锁。
> 你以为 volatile 让变量"线程安全"，实际上它连原子都保证不了。

对策只有一条：**不猜，验证**。用 checksum 验证工作量还在，用 smaps 验证大页生效，
用多轮统计验证时间稳定，用结果值验证正确性。

## 7. 示例分析

### 7.1 p2：为什么基准"快得不真实"

- `for i in N: s += i*3`，若调用处不观察 s：
  - 编译器删除整个循环 → 0ms；
  - 即使观察 s，O3 也能用 `N*(N-1)/2*3` 闭式替换 → 0ms。
- 只有写入缓冲区（真实副作用）才保留工作量 → 32ms。
- 教训：测速前先确认"工作真的发生了"。

### 7.2 p4：shared_ptr 的隐藏成本

- `std::shared_ptr<int> local = sp;` 每句都 `fetch_add(control_block.refcount)`。
- 多线程同时拷贝同一 shared_ptr → 所有线程竞争同一缓存行上的原子计数。
- 对比裸指针读取（纯读，无原子）：3.6 万倍差距。
- 教训：每线程只拷贝一次 shared_ptr，循环内传裸指针/借用引用。

### 7.3 p8：volatile 丢了 73% 的更新

- 4 线程各 `++v`（volatile long）：期望 2000 万，实际 534 万。
- 原因：`++v` 是读-改-写三段，volatile 不保证原子，多线程交错丢失。
- `std::atomic` 保证正确（2000 万）。
- 教训：共享写用 atomic/mutex；volatile 只在"单线程内防止寄存器缓存"时用。

## 8. 未优化代码（常见错误写法）

```cpp
// 一系列"一眼对但实际有坑"的写法
#include <atomic>
#include <memory>
#include <thread>
#include <vector>

// 坑A：shared_ptr 在循环里反复拷贝
void worker_bad(std::shared_ptr<int> sp, long n) {
    long long s = 0;
    for (long i = 0; i < n; ++i) {
        std::shared_ptr<int> local = sp;   // 原子计数++
        s += *local;                       // 原子计数--
    }
}

// 坑B：volatile 当线程安全
volatile long g_counter = 0;
void bump_bad() {
    for (long i = 0; i < 1000000; ++i) ++g_counter;   // 丢更新
}

// 坑C：测速用单次 + 不观察结果
long long bench_bad(const int* a, size_t n) {
    long long s = 0;
    for (size_t i = 0; i < n; ++i) s += a[i];   // 调用处不观察 → 可能被删
    return s;
}
```

## 9. 优化后代码（正确写法）

```cpp
#include <atomic>
#include <memory>
#include <thread>
#include <vector>

// 坑A 修复：循环内用裸指针/借用
void worker_good(const int* raw, long n) {
    long long s = 0;
    for (long i = 0; i < n; ++i) s += raw[i];   // 无原子
}

// 坑B 修复：std::atomic（或局部计数 + 最后归约）
std::atomic<long long> g_counter{0};
void bump_good() {
    for (long i = 0; i < 1000000; ++i) g_counter.fetch_add(1, std::memory_order_relaxed);
}

// 坑C 修复：观察结果 + 多轮
long long bench_good(const int* a, size_t n) {
    long long s = 0;
    for (size_t i = 0; i < n; ++i) s += a[i];
    return s;   // 调用处 do_not_optimize(s)
}
```

## 10. 为什么会（在工程上）更稳

| 坑 | 错误写法代价 | 正确写法规避 |
|---|---|---|
| shared_ptr 循环拷贝 | 原子计数竞争（3.6 万倍） | 借用裸指针 |
| volatile 当线程安全 | 结果错误（丢 73%） | std::atomic / 局部归约 |
| 基准被优化 | 测得 0ms，结论全错 | checksum + 副作用 |
| 单次测速 | 噪声±6% | 多轮 + median/stddev |
| 未对齐分配 | SIMD/缓存行跨线 | alignas / posix_memalign |
| 无脑 seq_cst | x86 上差别小，真正成本在原子本身 | 局部归约 |

## 12. 实验结果应该怎么看

- p1：O0/O3 时间差即"用 Debug 测速"的误差量级。
- p2：0ms 的循环就是被优化掉的证据；对照"真实工作"那行确认正确测法。
- p4：差距数量级来自原子计数，不是指针本身。
- p5：`new` 不保证 64B——看到"碰巧对齐"不要当成"保证对齐"。
- p8：volatile 结果 ≠ 期望值，这是**正确性**问题不是性能问题。
- p9：AnonHugePages=0 说明 madvise 未生效（madvise 模式/碎片/大小），要换 always 或显式 HugeTLB。

## 13. 常见误区（这些坑本身的误区）

- **误区 1：Debug 也能测个大概**。O0 下连函数内联、寄存器分配都没有，时间完全失真。
- **误区 2：do_not_optimize 就够了**。对"简单求和"编译器能用闭式公式绕过循环，需要真实副作用。
- **误区 3：vector<bool> 只是"省内存"**。它牺牲了访问速度与引用语义，读热路径要避开。
- **误区 4：shared_ptr 很轻**。拷贝一次 ~一次原子操作，多线程高频拷贝是灾难。
- **误区 5：volatile 是"弱原子"**。它不是原子，只是防寄存器缓存，用于线程共享是错的。
- **误区 6：madvise 调了就有大页**。它是 hint；madvise 模式下未符合条件就不生效，必须验证。
- **误区 7：对齐是性能细节**。对 SIMD 与缓存行放置，未对齐直接决定能否用对齐指令。

## 14. 实践练习

1. 运行 p1，记录本机 O0/O3 倍率，验证"Debug 测速不可信"。
2. 把 p2 的 `loop_closed_form` 改成更复杂（如带分支的求和），看编译器是否还能化简。
3. 运行 p4，用 `valgrind --tool=helgrind`（若安装）确认原子竞争的来源。
4. 运行 p5，统计 `new` 未对齐比例；改用 `alignas(64)` 结构体验证。
5. 运行 p9，尝试 `sysctl vm.force_thp=...` 或换 madvise 模式，观察 AnonHugePages 变化。
6. 用 p6 的数据，说明"单次运行结论"在真实发布中的风险。

## 15. 本章总结

- 工程的坑主要来自"意图 vs 编译器/运行时实际行为"的落差。
- 九类高频坑：Debug 测速、基准被优化、vector<bool>、shared_ptr 计数、对齐、
  单次测速、原子序、volatile 误用、大页不生效。
- 统一对策：**不猜，验证**（checksum、smaps、多轮统计、结果正确性）。
- 每个坑都对应 PDF 的一个原理点；原理正确不等于工程正确，需要测试兜底。
