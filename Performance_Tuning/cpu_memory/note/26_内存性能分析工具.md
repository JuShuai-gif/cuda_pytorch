# 26 内存性能分析工具

> 对应 PDF：第 7 章 Memory Performance Tools（PDFp78）、第 7.1 节 Memory Operation Profiling（PDFp78~80）、第 7.2 节 Simulating CPU Caches（PDFp81~82）、第 7.3 节 Measuring Memory Usage（PDFp82~84）、图 7.1~7.7
> 本篇回答：有哪些工具能看程序的内存/缓存行为？OProfile/perf 怎么读事件？Cachegrind 怎么模拟缓存？Massif/memusage 怎么测内存占用？分配模式如何影响预取？

## 1. 本章要解决的问题

- 性能计数器的正确打开方式：CPI、命中率、事件比例而非绝对值。
- OProfile（论文时代）与 modern perf 的事件采集。
- Cachegrind：模拟 L1i/L1d/L2 缓存，可改参数。
- Massif / memusage：程序内存占用随时间/调用点。
- 从分配图识别"大量小分配"→ 该用 obstack/批量分配。
- malloc 头/填充对预取的伤害（50%）。

## 2. 前置知识

- 全书缓存/内存概念（note/05~22）。
- Linux 工具基础：valgrind、gdb、命令行。

## 3. 核心概念

- **Performance Counter（性能计数器）**：CPU 硬件提供的事件计数。
- **CPI（Cycles Per Instruction，每指令周期）**：`CPU_CLK_UNHALTED / INST_RETIRED`。
- **OProfile**：论文时代 Linux 上系统级统计采样工具（现代被 perf 取代）。
- **Cachegrind**：基于 valgrind 的缓存模拟器（L1i/L1d/L2）。
- **cg_annotate**：按函数/源码行展示 Cachegrind 结果。
- **Massif**：valgrind 工具，堆内存随时间/调用点。
- **memusage**：glibc 自带，轻量内存测量（非模拟，快）。
- **Minor / Major Page Fault**：小页错误（内容在内存中）/大页错误（需读盘）。
- **Obstack**：glibc 提供的连续分配器，批量分配。
- **Heap-admin（堆管理头）**：malloc 块头部与填充。

## 4. 硬件工作流程

### 4.1 从绝对值到比例

```text
计数器绝对值无意义（多高算高？）
正确做法：把事件互相除
  CPI = CPU_CLK_UNHALTED / INST_RETIRED
  命中率 = miss 事件 / (INST_RETIRED 减去非访存指令)
```

论文图 7.1（Follow Random，Core 2）：

- 小工作集（≤L1d）：CPI ≤1.0。
- L1d 不足：CPI 跳到 ~3.0（L2 惩罚被平均到所有指令）。
- L2 不足：CPI >20（主存惩罚）。

### 4.2 Cachegrind 用法（PDFp81~82）

```bash
valgrind --tool=cachegrind command arg            # 用当前 CPU 缓存参数模拟
valgrind --tool=cachegrind --L2=8388608,8,64 cmd  # 自定义 L2：大小,关联度,行大小
cg_annotate cachegrind.out.PID                    # 按函数/行查看
```

- 输出：I refs/I1 misses、D refs/D1 misses/L2 misses、各自 miss rate（图 7.5）。
- cg_annotate 按函数列出 Ir/Dr/Dw（总访问）与 miss（图 7.6）。
- 局限：模拟 LRU 逐出（真实大关联度缓存未必是 LRU）、不考虑上下文切换/系统调用（会刷 L1、破坏 L2）→ 模拟 miss 低于实际。

### 4.3 Massif / memusage（PDFp82~83）

```bash
valgrind --tool=massif command arg                # 堆占用随时间/调用点
memusage -p out.png command arg                   # glibc 轻量版，生成 PNG
```

- massif：识别分配函数，记录调用点 + 时间戳 + 大小（图 7.7）。
- memusage：直接运行于真实程序（非模拟），快；还可给出分配大小直方图；`-n NAME` 指定被观测程序名。

### 4.4 分配模式与预取（PDFp83~84）

```text
链表逐节点分配的问题：
  无保证连续布局（从后往前返回、跨 chunk、多池、多线程交错）
  → 顺序访问链表元素时，物理布局乱 → 预取失效

malloc 块 = Header(2 字) + Data + Padding
  若 4 块中管理开销占 50% → 预取率也降 ~50%（读了用不上的头/填充）
```

- 识别信号：图中"同一位置大量小分配 + 平缓上升"→ 用 obstack/批量分配。
- obstack：从系统申请大块，内部连续分配小对象（除块耗尽外都顺序）。

## 5. PDF 核心观点

> 来源：PDF 第 78~84 页；对应章节 7、7.1、7.2、7.3、图 7.1~7.7。以下为概括。

1. **用比例而非绝对值**（PDFp78）：计数器绝对值无意义；把多个事件相除（如 CPI）得到可比结果。
2. **事件与处理器相关**（PDFp78）：事件名、含义因 CPU 而异；OProfile 简单但低层，需自己查手册。
3. **CPI 三个台阶**（PDFp78，图 7.1）：L1d 内 ≤1；L1d 不足 ~3；L2 不足 >20。
4. **缓存事件解读**（PDFp79，图 7.2/7.3）：随机访问 L2 demand miss 非零（预取不完美）；顺序访问 demand miss ≈0（预取完美）、L1d/L2 同步、DTLB 也基本零；随机访问 DTLB 提前变高。
5. **预取有效性计数**（PDFp79）：useful/late NTA prefetch 比例可评估软件预取；论文例 5.5% 有用、48% 未及时 → 预取指令大多不必要，可调整。
6. **opannotate**（PDFp79~80）：按指令/源码行标注事件位置；随机采样可能漏掉某些行（阈值）。
7. **页错误两类**（PDFp80）：minor（内容已在内存，如 COW、首次匿名页）、major（需读盘）；major 明显更贵，但 minor 也不便宜（进内核、找页、清页、改页表、同步）。
8. **time/getrusage**（PDFp80，图 7.4）：`\time ls /etc` 显示 major/minor pagefaults；/proc/PID/stat 第 10~14 字段也有。
9. **Cachegrind 是模拟**（PDFp81）：与真实硬件实现可能差异大（LRU 假设、忽略上下文切换/系统调用）→ 实际 miss 可能更高。
10. **cg_annotate 按函数/行**（PDFp82，图 7.6）：先看 L2 miss，再 L1i/L1d miss；需调试信息最好。
11. **Massif/memusage**（PDFp82~83）：massif 按调用点 + 时间；memusage 快速、真实运行、可输出分配大小直方图。
12. **分配模式影响预取**（PDFp83~84）：链表逐节点分配不保证顺序布局；malloc 头/填充可吃掉 50% 预取；同一位置大量小分配 → 用 obstack/批量。
13. **heap-admin 区域**（PDFp83，图 7.7）：massif 图里的管理开销；多数 malloc 头与数据同块（64 位每块 ≥16 字节头）。

## 6. 通俗解释

性能工具就像**给程序做体检**：

> OProfile/perf 看"CPU 内部事件"（血压心率）：每指令周期（CPI）是心跳，缓存 miss 是血脂。
> Cachegrind 是**仿真跑团**：不真实跑在硬件上，而是按你给的地图（缓存参数）模拟每一步的缓存行为——
> 好处是可以换地图看假设（比如把 L2 从 2MB 换成 8MB），坏处是仿真器有自己的简化（LRU、忽略切换）。
> Massif/memusage 是**伙食费账单**：记每笔内存"花在哪"（哪个调用点）、随时间怎么涨。

分配模式的信号怎么看？

> 图上"同一个地方反复出现小小的分配、斜率平缓"= 大量小额分配。就像反复拆小信封买邮票，
> 不如直接买一本邮册（obstack 批量分配）。每个信封还有 2 字的封皮（malloc 头），
> 一堆封皮加填充能占 50%，连预取（读信封内容）都被封皮拖累。

## 7. 示例分析

### 7.1 图 7.2/7.3 的对比

- 随机访问：L2 demand miss 非零（硬件预取猜不到随机）；DTLB miss 提前出现（大工作集页多）。
- 顺序访问：L2 demand miss ≈0（预取完美覆盖）；L1d 与 L2 miss 率相同（所有 L1d miss 都由 L2 满足）；DTLB ≈0。
- 解读：顺序访问是"理想情形"，几乎不可能在所有程序上复现。

### 7.2 软件预取评估

- useful NTA = 2.84%、late NTA = 2.65% → 只有 5.5% 预取有用，其中 48% 未及时。
- 结论：多数预取指令不必要；应减少/调整预取距离。

### 7.3 分配模式对预取的影响

- 链表：每节点单独 malloc → 物理布局不可控 → 顺序遍历时预取猜不中。
- malloc 头/填充：4 块 50% 开销 → 预取读进无用字 → 有效预取率降一半。
- 解决：obstack（大块内连续分配）或自建分配器。

## 8. 未优化代码

对应"大量小分配 + 链表"的程序。

```cpp
// bad.cpp: 每节点单独 malloc，布局不可控
#include <cstdlib>

struct Node { int data; Node* next; };

int main() {
    constexpr int N = 1 << 20;
    Node* head = nullptr;
    for (int i = 0; i < N; ++i) {
        Node* n = (Node*)malloc(sizeof(Node));  // 每次独立分配
        n->data = i;
        n->next = head;
        head = n;
    }
    long long sum = 0;
    for (Node* p = head; p; p = p->next) sum += p->data;  // 顺序遍历，布局乱
    return sum == 0;
}
```

## 9. 优化后代码

对应"连续节点池"的程序（预取友好）。

```cpp
// good.cpp: 连续分配节点池
#include <vector>

struct Node { int data; Node* next; };

int main() {
    constexpr int N = 1 << 20;
    std::vector<Node> pool(N);              // 连续布局
    for (int i = 0; i < N; ++i) {
        pool[i].data = i;
        pool[i].next = (i + 1 < N) ? &pool[i + 1] : nullptr;
    }
    long long sum = 0;
    for (const Node* p = &pool[0]; p; p = p->next) sum += p->data;
    return sum == 0;
}
```

> 完整对比见 src/12_pointer_chasing 与 src/22_memory_mapping。

## 10. 为什么会更快

| 角度 | 单独 malloc | 连续节点池 |
|---|---|---|
| 空间局部性 | 无保证（碎片） | 连续 |
| 预取 | 失效 | 完美匹配 |
| 缓存 miss | 高 | 低 |
| malloc 头/填充 | 每节点 16B+ 头 | 无（pool 一次性） |
| TLB | 多页散布 | 少页 |

## 12. 实验结果应该怎么看

- Cachegrind 的 D1 miss 率：连续池远低于单独 malloc；注意模拟值可能低于实际（论文提醒）。
- perf 的 cache-misses：真实硬件验证。
- massif 图：单独 malloc 会看到大量"平缓小分配"斜坡（同一调用点重复分配）。
- 结论要标注"模拟 vs 实际"，不要混为一谈。

## 13. 常见误区

- **误区 1：计数器绝对值就是结论**。要高多少才算高？要算比例（CPI、miss 率）。
- **误区 2：Cachegrind 结果 = 真实硬件**。它模拟 LRU、忽略上下文切换/系统调用，miss 可能偏低。
- **误区 3：memusage 是模拟**。它真实运行，比 massif 快。
- **误区 4：链表慢只因指针跳转**。根因是分配布局乱 + 缓存 miss + 预取失效（本笔记与 note/12 强调）。
- **误区 5：malloc 头开销可忽略**。头+填充可占 50%，直接砍半预取率。

## 14. 实践练习

1. 用 Cachegrind 分别跑"单独 malloc 链表"与"节点池"，对比 D1 miss 率。
2. 用 perf 验证真实硬件上的 cache-misses 差异。
3. 用 massif 观察两者内存占用曲线，识别大量小分配模式。
4. 用 memusage 输出分配大小直方图，分析分配分布。
5. 讨论：为什么 Cachegrind 的 miss 数通常低于实际。

## 15. 本章总结

- 性能计数器要用比例解读（CPI、命中率）。
- OProfile/perf 看真实硬件事件；Cachegrind 可模拟并改参数；两者互补。
- Massif/memusage 看内存占用与分配模式。
- 页错误分 minor/major，time/getrusage/proc 可查。
- 大量小分配、malloc 头/填充会破坏局部性与预取；用连续池/obstack 改善。
