# 09 多核缓存一致性

> 对应 PDF：第 3.3.4 节 Multi-Processor Support（PDFp25~29）、图 3.18~3.23、表 3.3
> 本篇回答：多核系统如何让所有核看到一致的内存？MESI 状态怎么转移？为什么并发访问同一缓存行代价巨大？多线程效率为什么随工作集变化崩塌？

## 3. 核心概念

- **Cache Coherency（缓存一致性）**：所有处理器对内存内容持有统一视图。
- **Snooping（监听）**：处理器监听其他处理器的总线操作，与本缓存行比对。
- **MESI**：Modified / Exclusive / Shared / Invalid 四状态协议。
- **RFO（Request For Ownership）**：写操作前获取缓存行所有权的请求（I→M 或 S→M）。
- **Inclusive Cache（包含缓存）**：Intel 的做法，L1 内容也存在于 L2。
- **Hyper-Threading / SMT**：单核内两个线程共享几乎全部资源、只有独立寄存器。
- **Cache Hit Rate（命中率）**：`Ghit`，命中缓存的比例。

## 4. 硬件工作流程

### 4.1 MESI 状态（图 3.18，PDFp26）

| 状态 | 含义 | 谁拥有 |
|---|---|---|
| M (Modified) | 本处理器已修改，主存过期 | 唯一副本 |
| E (Exclusive) | 未修改，已知无其他副本 | 唯一副本 |
| S (Shared) | 未修改，可能有其他副本 | 多副本 |
| I (Invalid) | 无效 | 无 |

### 4.2 主要转移（PDFp26）

```text
初始：全部 Invalid

读加载：
  若其他处理器也有 → S；否则 → E
写加载：
  → M（唯一副本）

M 状态：
  本地读/写 → 不变
  远程读 → 发送内容给请求者，→ S（主存同步）
  远程写 → 发送内容，本地 → I（RFO）

S 状态：
  本地读 → 不变
  本地写 → 广播 RFO 作废他人，→ M
  远程读 → 不变（无需总线操作）
  远程写 → 本地 → I

E 状态：
  本地读 → 不变
  本地写 → → M（无需总线广播！E→M 快）
  远程写 → → I
```

关键点：

- E→M 无需广播，是 S→M 的廉价版；处理器尽量保持行在 E。
- RFO（I→M 或 S→M）昂贵，是并发写的主要开销。
- 一致性协议要等**所有处理器**都有机会回复，最慢的响应决定协议速度（脚注 22：这也是三路 Opteron 常见的原因——每处理器一跳）。

### 4.3 一致性消息传播

```text
CPU0 写行X（S→M）
   │ RFO
   ▼
总线广播：作废其他核的X副本 ──► 等所有核确认 ──► 完成状态转移
   │
   （NUMA/多跳拓扑下，最远节点决定延迟）
```

## 5. PDF 核心观点

> 来源：PDF 第 25~29 页；对应章节 3.3.4、图 3.18~3.23、表 3.3。以下为概括。

1. **RFO 何时必要**（PDFp27）：两种情形——(a) 线程被迁移到另一处理器，缓存行需一次性搬过去；(b) 缓存行确实被两个不同处理器使用（含同一 CPU 两个核心）。多线程同步本就依赖内存，必然产生一些 RFO，但要尽量少。
2. **一致性协议受最慢响应制约**（PDFp27）：状态转移要等所有处理器回复；总线冲突、NUMA 高延迟、大流量都会拖慢。
3. **FSB 是共享资源**（PDFp27）：单个处理器就可能打满总线，多处理器共享同一总线时各自带宽被进一步压缩；即使各自有到控制器的总线，到内存模块的瓶颈仍在。
4. **多线程顺序读：18%→34% 惩罚**（PDFp27，图 3.19）：即使不修改内存、无 RFO，2 线程最快线程也慢 18%、4 线程慢 34%——纯粹是共享总线与内存带宽瓶颈。
5. **多线程顺序增量写：93% 惩罚**（PDFp27，图 3.20）：4 线程时预取流量 + 写回流量几乎打满总线。
6. **L1d 在多线程下"基本失效"**（PDFp27）：单线程小工作集低于 20 周期；多线程即便最小工作集也立即超过 20 周期。
7. **随机 Addnextlast 高达 ~1500 周期/元素**（PDFp28，图 3.21）：并发 + 随机 + 修改三重打击。
8. **效率表**（PDFp28，表 3.3）：4 线程的 Seq Read 加速仅 2.98、Seq Inc 2.07、Rand Add 1.65（理论上限 4）；超过 2 线程收益甚微。
9. **加速比曲线**（PDFp28，图 3.22）：工作集在 L2/L3 内时接近线性加速（2/4 线程），一旦超出 LLC 加速比崩落到 2 与 4 相同。
10. **为什么少见 >4 路共享内存控制器的机器**（PDFp28）：LLC 之外多线程加速消失，更大机器需 NUMA（section 5）。
11. **超线程逻辑**（PDFp29）：线程共享几乎全部资源（除寄存器），靠复用"当前线程等内存时闲置的 ALU"获益；模型 `Texe = N[(1-Fmem)Tproc + Fmem(Ghit·Tcache + (1-Ghit)·Tmiss)]`。
12. **超线程命中率门槛**（PDFp29，图 3.23）：单线程命中率 <55% 时通常能受益；目标区是"线程慢 <50% 且每个线程负载减半"的组合。

## 6. 通俗解释

多核一致性，像**多人共用的记事本**：

> 几个同事（CPU）各自有小抄（L1/L2）。大家都得保证看到同一版本的"真相"。
> 正常大家一起读同一页（S 状态）没问题，每人一份副本。
> 一旦有人要改（写），就得喊一嗓子"这一页我要独占！"（RFO），所有人把自己的副本划掉（Invalid），
> 然后改完的内容对大家可见。这嗓子喊得越频繁，办公室越乱（总线拥塞）。

为什么多线程读也会慢？

> 即使没人修改，4 个人同时疯狂翻同一本大书（顺序读大工作集），翻书动作本身就把唯一的"取书通道"（FSB/内存总线）占满了。预取 + 读请求撞在一起。

超线程就像：

> 一个同事在等快递（内存）时，另一个同事借用他的电脑键盘（ALUs）继续干活。前提是：等快递的时间足够长（缓存命中率低），才有空档让另一个线程插进来。

## 7. 示例分析

### 7.1 为什么多线程反复写同一计数器那么慢

- 两个核轮流 `cnt++`：每个核都要 RFO 把行从对方拿过来，再写，再让对方拿走……
- 缓存行在核间来回倒手，每个原子操作都是一次完整的所有权转移。
- 这正是 src/13（false sharing）与 src/14（atomic contention）要量化的现象。

### 7.2 线程迁移的 RFO

- OS 把线程从 CPU0 挪到 CPU1，其工作集缓存行需一次性迁移，产生大批 RFO。
- 这是"绑核（affinity）"能提升性能的原因之一（note/15、src/15）。

### 7.3 命中率模型

模型（PDFp29）：

```text
Texe = N[(1-Fmem)·Tproc + Fmem·(Ghit·Tcache + (1-Ghit)·Tmiss)]
```

- 单线程命中率 Ghit 越高，多线程分摊到每个线程的缓存越少（命中率下降），收益越小。
- 图 3.23：单线程命中率低于约 55% 时多线程总能用上——因为 miss 让 CPU 闲着，有空跑第二线程。

## 8. 未优化代码

对应"多线程竞争同一缓存行"的程序（并发递增共享计数器）。

```cpp
// bad.cpp: 共享计数器竞争，RFO 风暴
#include <thread>
#include <vector>

int main() {
    constexpr int N = 1 << 20;
    long long counter = 0;
    std::vector<std::thread> pool;
    for (unsigned t = 0; t < 8; ++t)
        pool.emplace_back([&] {
            for (int i = 0; i < N; ++i) ++counter;  // 每线程都写同一行
        });
    for (auto &th : pool) th.join();
    return counter == 0;
}
```

## 9. 优化后代码

对应"每线程本地计数 + 最后合并"的程序（零 RFO）。

```cpp
// good.cpp: 线程本地计数，最后归约
#include <thread>
#include <vector>

int main() {
    constexpr int N = 1 << 20;
    unsigned n = std::thread::hardware_concurrency();
    std::vector<long long> local(n, 0);
    std::vector<std::thread> pool;
    for (unsigned t = 0; t < n; ++t)
        pool.emplace_back([&, t] {
            long long c = 0;               // 寄存器/栈局部
            for (int i = 0; i < N; ++i) ++c;
            local[t] = c;                  // 每线程独立位置，无竞争
        });
    for (auto &th : pool) th.join();
    long long sum = 0;
    for (auto v : local) sum += v;
    return sum == 0;
}
```

> 注意：local[t] 若 t 相邻线程写同一缓存行仍是 false sharing（note/23）；这里每线程一个 long long
> 可能仍撞行，工程上要用 padding/分离。完整实验见 src/14。

## 10. 为什么会更快

| 角度 | 共享计数器 | 每线程局部 |
|---|---|---|
| RFO 次数 | 每次++都一次所有权转移 | 零 |
| 缓存行倒手 | 每操作一次 | 无 |
| 一致性协议消息 | 大量 | 无 |
| 总线流量 | 预取+写回+协议饱和 | 仅读流量 |
| 可扩展性 | 线程越多越慢 | 近似线性 |

论文数据佐证：多线程增量写 4 线程惩罚高达 93%；随机加 4 线程加速仅 1.65。而分离计数后理论上限接近线性（论文图 3.22 的 LLC 内区间）。

- src/14：共享 `std::atomic` 递增的耗时随线程数暴增（RFO + 原子 RMW）；每线程局部计数几乎不随线程数变化。两者差一个数量级是正常的。

## 13. 常见误区

- **误区 1：多线程一定比单线程快**。LLC 之外工作集、共享总线、一致性协议可能让加速比崩塌（图 3.22）。
- **误区 2：读共享数据没有成本**。图 3.19 证明：纯读 + 大工作集，多线程也会因带宽损失 18%~34%。
- **误区 3：计数器用 atomic 就安全高效**。正确性上对，性能上 RFO 风暴依旧，需局部归约。
- **误区 4：SMT 线程是"真并行"**。它们共享 ALU 等资源，只能复用闲置周期；命中率高时无益。
- **误区 5：一致性开销只在写时出现**。线程迁移、同步原语、甚至共享缓存容量竞争都会产生间接成本。

## 15. 本章总结

- MESI 四状态保证写回缓存的多核一致性；E→M 便宜、S→M（RFO）昂贵。
- RFO 与线程迁移是主要一致性开销源；一致性受最慢响应制约。
- FSB/内存总线共享使多线程即使纯读也损失带宽（18%~34%）。
- 并发写放大效应显著：4 线程增量写惩罚 93%，随机加几乎无加速。
- 工作集超出 LLC 后，多线程加速崩塌，这正是 NUMA/更大机器结构出现的原因。
- 对程序员：少共享同一缓存行、用局部归约、注意绑核，是降低一致性开销的核心手段。
