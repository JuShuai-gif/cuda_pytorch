# 05 CPU Cache 基础

> 对应 PDF：第 3 章 CPU Caches 开头（PDFp13~14）、第 3.1 节 CPU Caches in the Big Picture（PDFp14）、第 3.2 节 Cache Operation at High Level（PDFp15~16）

## 1. 本章要解决的问题

- 为什么 CPU 需要 Cache（而不直接把 SRAM 暴露给程序）？
- Cache 的基本单位为什么是"缓存行"而不是单个字？
- 一个地址怎么被切成 Tag / Set / Offset？
- 多处理器、多核、多线程如何共享各级缓存？
- Cache 命中和未命中的真实代价差多少？

## 2. 前置知识

- note/01：CPU 与内存速度失衡、总线结构。
- note/02：SRAM 快但贵，DRAM 慢但便宜。

## 3. 核心概念

- **CPU Cache（CPU 缓存）**：位于 CPU 与主存之间的高速 SRAM，保存主存数据的副本。
- **Cache Line（缓存行）**：缓存管理的基本单位，通常 32/64 字节连续数据。
- **Tag / Set / Offset（标签 / 集合 / 偏移）**：地址的三个字段，分别用于区分别名、定位集合、找行内字节。
- **Spatial Locality（空间局部性）**：相邻内存地址往往一起被访问。
- **Temporal Locality（时间局部性）**：刚访问过的数据往往很快再次访问。
- **Working Set（工作集）**：程序在短期内实际使用的内存集合。
- **Dirty Cache Line（脏缓存行）**：已被写入、尚未写回主存的缓存行。
- **Eviction（驱逐）**：为腾出空间把缓存行赶出去。
- **Exclusive Cache（独占缓存）**：同一数据只存在一个缓存级别（如现代 AMD）。
- **Inclusive Cache（包含缓存）**：高一级缓存包含低一级的内容（如 Intel 的 L1/L2 包含关系）。
- **Cache Coherency（缓存一致性）**：多核共享同一内存视图，需保证各缓存内容一致。
- **Snooping（监听）**：处理器监听其他处理器的写访问，与本缓存比对。
- **L1d / L1i / L2 / L3**：一级数据缓存、一级指令缓存、二级、三级缓存。

## 4. 硬件工作流程

### 4.1 最小缓存配置（论文图 3.1，PDFp14）

```text
CPU Core ──► Cache ──► Main Memory Bus
                 │
              Main Memory
```

- 所有 load/store 都必须经过缓存。
- 核心与缓存之间是专用高速连接；缓存与主存之间是系统总线（FSB）。

### 4.2 三级缓存与多核多线程拓扑（论文图 3.2、3.3，PDFp14~15）

```text
        Processor 0                          Processor 1
  ┌─────────────────────────┐          ┌─────────────────────────┐
  │ Core0       Core1       │          │ Core0       Core1       │
  │ L1d L1i    L1d L1i      │          │ L1d L1i    L1d L1i      │
  │   └── L2 ──┘  (每核共享)│          │   └── L2 ──┘            │
  │      └──── L3 ──────┘   │          │      └──── L3 ──────┘   │
  └───────────┬─────────────┘          └───────────┬─────────────┘
              └────────────── 互联总线 ─────────────┘
                                    │
                               Main Memory
```

- 线程（thread）共享几乎全部资源（Intel SMT 只给各自寄存器，部分还共享）→ 线程共享 L1。
- 核心（core）各有独立 L1，共享高一级缓存。
- 处理器（processor）之间不共享任何缓存。

> 现代补充：图 3.3 中"线程共享 L1"对应 Intel SMT/超线程的实现细节；现代 CPU 的 L2/L3 归属与共享关系
> 因型号而异（例如 14900HX 的 L2 每核独立、L3 全核共享），需用 lscpu 实测确认。

### 4.3 一次读访问流程

```text
CPU 需要某地址数据
   │
   ▼
在 L1d 按 Tag 查找 ──命中──► 返回（~3 周期）
   │ Miss
   ▼
L2 查找 ──命中──► 返回（~14 周期）
   │ Miss
   ▼
L3 / 主存 ──► 整条 Cache Line 载入 L1d ──► 返回（~240 周期）
```

论文给出的 Pentium M 延迟（PDFp16）：

| 目标 | 周期 |
|---|---|
| 寄存器 | ≤1 |
| L1d | ~3 |
| L2 | ~14 |
| 主存 | ~240 |

## 5. PDF 核心观点

> 来源：PDF 第 13~16 页；对应章节 3（开头）、3.1、3.2。以下为概括。

1. **缓存成立的根基是局部性**（PDFp13）：代码循环体现空间局部性；数据小范围短时间重用体现时间局部性；"认识到局部性存在"是缓存思想的关键。
2. **缓存的威力**（PDFp13，作者计算）：主存 200 周期、缓存 15 周期时，100 个数据各用 100 次：无缓存 2,000,000 周期，全缓存 168,500 周期，节省约 91.5%。
3. **缓存约为主存的 1/1000**（PDFp13）：作者经验值；工作集必然超过缓存，需要替换策略，最好能"提前"替换（预取）。
4. **为什么不用独立 SRAM 内存区**（PDFp13）：把 SRAM 交给 OS/程序员分配管理会带来资源管理、同步、可移植性等问题，收益被开销吃光；所以缓存由处理器透明管理。
5. **缓存条目用行而非字**（PDFp15）：Tag 本身要占空间，字粒度效率低；空间局部性 + DRAM 突发传输都要求整行加载；早期 32 字节，现代多为 64 字节。
6. **地址三字段**（PDFp15）：`Tag(T) | Set(S) | Offset(O)`，Offset 定位行内字节，Set 选缓存集合，Tag 区分同一集合里的别名。
7. **写操作也要先读缓存行**（PDFp16）：没有指令一次改写整行，所以写前必须先把行读进来（例外：写合并，见 note/22）。
8. **驱逐逐级下移**（PDFp16）：L1d 驱逐推入 L2，再 L3，再主存；独占缓存（AMD/VIA）与包含缓存（Intel）的驱逐代价不同。
9. **一致性两条规则**（PDFp16）：脏行不在其他处理器缓存中；同一行的干净副本可存在于任意多个缓存。
10. **实测延迟**（PDFp16）：寄存器 ≤1、L1d ~3、L2 ~14、主存 ~240 周期——量级差距巨大。

## 6. 通俗解释

Cache 就像**你的办公桌 vs 公司档案室**：

> 档案室（主存 DRAM）什么都有，但去一趟要走几分钟（几百周期）。
> 你在桌上放一个小抽屉（L1），抽屉里的东西抬手就拿（3 周期）。
> 桌子旁边再放一个文件柜（L2/L3），比档案室近但比抽屉慢。

缓存为什么按"行"存而不是按"个"存？

> 因为把一叠 64 个文件一起从档案室搬出来，和只搬 1 个文件的成本差不多（DRAM 突发传输 + 一次寻址）。
> 那干脆一搬就搬一整叠——反正相邻的文件大概率你马上也要用（空间局部性）。

为什么不能让程序自己管那叠快内存？

> 因为每个程序都来抢那点快内存，又要分配、又要同步、还要考虑不同 CPU 快内存大小不同——
> 管理开销会把你省下的时间全部吃掉。所以 CPU 自己透明地管。

## 7. 示例分析

### 7.1 读取一个 int 会加载整个缓存行

- 设缓存行 64B，读 `int a[0]`（地址低 6 位清零）。
- 硬件会把 `a[0]` 所在 64B 整行载入 L1d。
- 若接下来顺序读 `a[1]~a[15]`，全部命中（已在行内）。
- 这就是"为什么连续访问快"的最直接原因。

### 7.2 地址切分示例

- 32 位地址，缓存行 2^O（如 O=6，64B），集合数 2^S，Tag = 32-S-O。
- 例：S=10（1024 集合）、O=6 → Tag=16 位。
- `0x12345678` 中：低 6 位是行内偏移，接下来 10 位选集合，高 16 位是 Tag。

### 7.3 缓存为什么只能有部分主存

- 4MB 缓存 vs 4GB 主存 = 1/1000。
- 若工作集 < 缓存，无所谓；但多进程系统工作集 = 所有进程 + 内核之和，必然超过 → 需要替换策略与预取。

## 8. 未优化代码

对应"没有局部性"的程序：随机访问大数组，浪费每条缓存行。

```cpp
// bad.cpp: 随机访问，空间局部性为零
#include <vector>
#include <random>

int main() {
    constexpr int N = 1 << 24;
    std::vector<int> data(N, 1);
    std::mt19937 rng(42);
    long long sum = 0;
    for (int i = 0; i < N; ++i)
        sum += data[static_cast<int>(rng() & (N - 1))];
    return sum == 0;
}
```

## 9. 优化后代码

对应"充分利用缓存行"的程序：顺序访问。

```cpp
// good.cpp: 顺序访问，空间局部性拉满
#include <vector>

int main() {
    constexpr int N = 1 << 24;
    std::vector<int> data(N, 1);
    long long sum = 0;
    for (int i = 0; i < N; ++i)
        sum += data[i];
    return sum == 0;
}
```

## 10. 为什么会更快

| 角度 | 随机访问 | 顺序访问 |
|---|---|---|
| Cache Line 利用率 | 每 4B 就浪费 60B | 64B 全部用上 |
| L1/L2/LLC 命中率 | 低（miss 多） | 高（命中 + 预取） |
| DRAM 访问次数 | 每个元素一次 | 每 16 个元素一次 |
| 硬件预取 | 无法识别 | 完美匹配 |
| TLB Miss | 频繁 | 连续命中 |
| 有效延迟 | 常踩 240 周期主存路径 | 多在 3/14 周期路径 |

91.5% 理论节省（论文计算）虽不能直接搬到现代机器，但量级方向一致：缓存命中与未命中相差两个数量级。

## 12. 实验结果应该怎么看

- src/01 或 src/05 会随着工作集大小变化出现"延迟台阶"：
  - 工作集 ≤ L1：~4 周期级；
  - ≤ L2：~14 周期级；
  - ≤ L3：几十周期级；
  - > L3：回到主存延迟（几百周期）。
- 台阶位置与 `lscpu -C` 的各级缓存大小对应，就验证了缓存层级的存在。
- 注意：普通数组遍历会被硬件预取掩盖，所以延迟实验还要做 pointer chasing（src/01）。

## 13. 常见误区

- **误区 1：缓存只是"大一点的内存"**。缓存是"更小的、按行管理、有 Tag/Set/Offset 结构、有替换策略"的加速层，行为与内存差异巨大。
- **误区 2：所有 CPU 缓存行都是 64 字节**。早期有 32 字节，现代多数 64 但必须实测；不能硬编码假设。
- **误区 3：Intel 一定是包含缓存、AMD 一定是独占缓存**。论文自己加了注释（PDFp16 脚注 19）：部分包含缓存有独占属性，不能一概而论。
- **误区 4：缓存命中就是免费**。L1 命中也要 ~3 周期，只是相对主存的 240 周期可忽略。
- **误区 5：多线程共享缓存一定是坏事**。共享缓存可以减少重复数据（利于共享数据），但会造成资源竞争与一致性开销——需要具体分析。

## 15. 本章总结

- Cache 存在的根基：局部性 + 成本（SRAM 太贵，不能全用）。
- 缓存按行管理（现代 64B），地址切成 Tag/Set/Offset。
- 缓存层级 L1→L2→L3→主存，延迟逐级上升（约 3/14/几十/240 周期量级）。
- 写操作必须先加载缓存行；驱逐逐级下移；包含/独占缓存实现不同。
- 多核一致性靠监听与协议维持，脏行唯一、干净副本可多份。
- 对程序员：顺序访问、利用空间局部性是让缓存生效的第一步。
