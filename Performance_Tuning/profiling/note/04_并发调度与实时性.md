# 并发、锁、调度与机器人实时性

## Lock Contention

Demo：`26_lock_contention_bad_good`。Bad把sqrt计算放入大临界区，Good在线程局部归约后一次更新。

```bash
./src/build/26_lock_contention_bad_good
strace -f -c ./src/build/26_lock_contention_bad_good
perf stat -e cycles,instructions,context-switches,cpu-migrations ./src/build/26_lock_contention_bad_good
```

CPU利用率只有40%但程序很慢，可能是大量线程off-CPU等待futex。CPU低 + futex高 + context switch高支持锁竞争候选；再用VTune Locks、bpftrace或off-CPU stack确认。

## shared_mutex反例

`27_shared_mutex`比较read-mostly下mutex与shared_mutex。本机shared_mutex反而略慢。临界区很短、线程少、读写比例不够极端或实现开销较高时，它不保证更快。

## False Sharing

`05_false_sharing`比较相邻atomic与`alignas(64)`分离计数器。不同核修改同一cache line会触发MESI/coherence ping-pong。

False Sharing != Data Race：即使每个线程只操作独立atomic，仍可能共享cache line。

## Load Imbalance

`28_thread_imbalance`让thread0承担70%任务，再用动态任务分配修复。总CPU利用率可能掩盖单线程拖尾，应看per-thread runtime、pidstat -t或VTune/nsys CPU timeline。

## Context Switch、Migration与NUMA

```bash
pidstat -w -t -p PID 1
perf stat -e context-switches,cpu-migrations ./src/build/12_context_switch
taskset -c 0-7 ./program
numactl --hardware
numastat -p PID
```

迁核可能破坏cache locality并增加realtime jitter；错误绑定也可能造成争核。NUMA遵循first-touch，线程和内存应尽量同node。本机只有一个NUMA node，因此remote/local对照未伪造。

## 50Hz实时循环

Demo：`30_realtime_jitter [--interference]`，记录scheduled wakeup、actual wakeup、execution、period jitter和deadline miss。

```bash
./src/build/30_realtime_jitter
./src/build/30_realtime_jitter --interference
cyclictest -p 80 -t 4 -n -i 1000 -l 100000
trace-cmd record -e sched_switch -e sched_wakeup -e irq_handler_entry -e softirq_entry sleep 10
```

20ms deadline下，Mean好但P99/Max越界仍不合格。把deadline miss时间点与scheduler、IRQ、softirq、锁、GPU同步和page fault对齐。不要未经授权修改实时优先级或系统全局配置。

## On-CPU与Off-CPU

On-CPU分析回答线程执行了什么；Off-CPU分析回答线程为何没有运行。锁、IO、条件变量和等待调度都可能让CPU利用率低但wall time高。

```bash
perf record -g ./src/build/26_lock_contention_bad_good
strace -f -tt -T ./src/build/26_lock_contention_bad_good
bpftrace -e 'tracepoint:sched:sched_switch { @[comm] = count(); }'
```

## 锁竞争的证据链

CPU Util低 + futex时间高 + context switch高只产生候选。进一步需要调用栈、锁实例或timeline证明哪些线程在等哪个临界区。

优化顺序通常是：

1. 减少共享状态；
2. 将计算移出锁；
3. batch update；
4. 分片锁或per-thread state；
5. 读多写少时再评估shared_mutex；
6. 最后才考虑自旋锁或lock-free。

Lock-free并非wait-free，也可能因CAS重试和cache-line争用更慢。

## False Sharing与MESI

两个线程修改不同变量，因此没有数据竞争；但变量位于同一cache line时，写所有权在核心间来回转移。Padding应按实际hardware destructive interference size评估，过度padding会增加工作集。

## 负载均衡策略

静态分区开销小，适合均匀任务；动态调度改善不均衡但增加原子队列开销；work stealing适合不规则任务。应比较每线程active time、最后完成线程和调度开销。

## Scheduler时间线

关键事件：

- sched_wakeup：线程变为runnable；
- sched_switch：CPU切换到线程；
- wake-up latency：两者间隔；
- IRQ/softirq：可能抢占控制线程；
- migration：线程换核并可能丢失热cache。

```bash
trace-cmd record -e sched_wakeup -e sched_switch -e irq_handler_entry -e irq_handler_exit -e softirq_entry -e softirq_exit sleep 10
trace-cmd report
```

## 实时预算分解

50Hz的20ms周期可拆为：

| 阶段 | 示例预算 |
|---|---:|
| Capture/Decode | 3 ms |
| Preprocess | 2 ms |
| Inference | 10 ms |
| Action/ROS | 2 ms |
| Controller | 1 ms |
| Safety margin | 2 ms |

预算不是平均值；每阶段P99不能简单相加，因为阶段可能相关或重叠。最终以端到端deadline miss为准。

## 优先级反转

高优先级线程等待低优先级线程持有的锁，而中优先级线程持续运行，会产生优先级反转。实时系统需要理解priority inheritance mutex，但配置调度策略和实时优先级会影响系统，不能自动修改。
