# 性能诊断决策树、症状表与指标组合

## 决策树

```text
程序慢
├─ /usr/bin/time → top/pidstat
│  ├─ CPU on-CPU → perf stat
│  │  ├─ 热点 → perf record → FlameGraph → VTune
│  │  ├─ cache/branch → perf events → Cachegrind/VTune
│  │  └─ thread imbalance → pidstat -t → timeline
│  ├─ CPU低/off-CPU → strace → ftrace/bpftrace
│  └─ RSS异常 → heaptrack → Massif → ASan/LSan
├─ GPU慢 → nvidia-smi/tegrastats → nsys
│  ├─ GPU空洞 → CPU feeding/sync/copy/IO
│  └─ 慢Kernel → ncu → Roofline
├─ PyTorch慢 → torch.profiler → nsys → ncu
├─ VLA慢 → Stage Timer/P99 → NVTX → nsys → ncu
└─ Realtime尾延迟 → Histogram → cyclictest → ftrace/bpftrace
```

## 指标定义

| 指标 | 定义 | 高/低的候选含义 | 不能单独说明 |
|---|---|---|---|
| IPC/CPI | instructions/cycles及倒数 | 吞吐/stall | bound类型 |
| Cache/LLC miss | cache访问失败 | 局部性候选 | DRAM瓶颈 |
| Branch miss | 预测失败 | pipeline flush | CUDA divergence |
| TLB miss | 地址翻译缓存失败 | page walk | page fault |
| Page fault | 页映射/驻留处理 | first-touch/压力 | cache miss |
| Context switch/migration | 调度切换/迁核 | 锁、线程、亲和性 | 一定有害 |
| RSS/VSZ | 驻留/虚拟地址 | active/retained/mmap | leak |
| Allocation count/peak | 分配次数/峰值 | churn/capacity | latency根因 |
| IOPS/BW/QD/iowait | IO次数/吞吐/队列/等待 | 存储压力 | 应用根因 |
| GPU Util | 窗口内有GPU工作 | 忙/空洞 | kernel效率 |
| SM/DRAM throughput | 算力/带宽利用 | compute/memory候选 | bound，需AI |
| Occupancy | active warp比率 | 延迟隐藏机会 | 性能高低 |
| Eligible Warps/Stall | 可发射warp/阻塞原因 | 依赖、barrier、throttle | 单一优化 |
| Self/Total CPU/CUDA | 自身/含子调用归因 | operator热点 | 可直接相加 |
| Allocated/Reserved/Peak | 活跃/缓存/峰值显存 | tensor/cache/temporary | leak |
| P50/P99/Max | 延迟分位/极值 | 典型/尾部 | 根因 |
| Wake-up/Execution | 调度/任务时间 | scheduler/工作超期 | miss总因 |

## 指标组合推理

1. IPC低 + LLC Miss高 + DRAM高 → CPU Memory Bound候选。
2. IPC低 + Branch Miss高 + DRAM不高 → branch/frontend候选。
3. CPU Util低 + futex高 + switch高 → Lock Contention候选。
4. GPU Util低 + nsys大量空洞 → feeding/sync/launch/IO候选。
5. GPU Memory高 + SM低 + AI低 → GPU Memory Bound候选。
6. SM高 + DRAM低 + AI高 → Compute Bound候选。
7. Occupancy低 + Long Scoreboard高 + Eligible不足 → 延迟隐藏可能不足。
8. Mean好 + P99差 → scheduler、锁、queue、page fault或thermal候选。
9. RSS高 + live heap稳定 → allocator retained/fragmentation候选。
10. Memcpy高 + compute不重叠 → 串行pipeline候选。

## 如何证明Root Cause

写出假设和预测指标；做只改变一个机制的A/B；确认correctness；观察预测指标和runtime是否同向变化；回到E2E/P99；若未改善，检查Amdahl定律和瓶颈转移。

## 单指标为什么危险

同一个指标可能有多种解释：

- GPU Util低：CPU feeding、同步、任务太小或采样窗口不合适；
- Occupancy低：资源限制，也可能是高效ILP kernel；
- RSS高：leak、cache、mmap或fragmentation；
- futex多：严重竞争，也可能只是大量短等待；
- LLC miss高：随机访问，也可能是正常流式带宽工作负载。

因此诊断至少需要“用户症状 + 位置证据 + 机制指标 + A/B响应”。

## 证据强度分层

| 证据 | 强度 |
|---|---|
| 单次runtime变化 | 很弱 |
| 多次稳定分布变化 | 中等 |
| 关键指标按假设变化 | 较强 |
| 针对性A/B且correctness一致 | 强 |
| 真实E2E/P99和资源指标共同改善 | 很强 |

## 常见指标公式

```text
IPC = instructions / cycles
CPI = cycles / instructions
Branch Miss Rate = branch-misses / branches
Cache Miss Rate = cache-misses / cache-references
Bandwidth = transferred bytes / time
Arithmetic Intensity = FLOPs / transferred bytes
Deadline Miss Ratio = missed periods / total periods
Speedup = time_before / time_after
Efficiency = speedup / workers
```

分母事件必须来自可比较PMU和同一观测窗口。

## CPU低但慢的逐步排查

1. pidstat看线程状态和切换；
2. strace -c看futex、poll、read/write；
3. off-CPU stack看等待调用链；
4. ftrace看wakeup到运行的延迟；
5. 检查上游数据、锁和queue。

## GPU高但慢的逐步排查

1. nsys确认是哪些kernel而非持续小kernel；
2. 比较kernel duration与业务占比；
3. ncu看SM、DRAM、stall和occupancy；
4. 计算AI并对照Roofline；
5. 优化后回到nsys验证E2E，防止只改善孤立kernel。

## Mean正常但P99差

保存逐请求时间戳，将尾样本与context switch、page fault、lock wait、memcpy/sync、temperature/clock和queue depth关联。平均值无法揭示这些偶发事件。

## 性能结论的措辞

优先写“证据支持某候选根因”，避免仅凭一个指标写“证明是Memory Bound”。只有针对性修改使预测指标和E2E同时改善，置信度才足够高。
